## Основная часть

### Тема 1. Базы данных как средство структурированного хранения информации

Данные можно хранить по-разному: в текстовых файлах, электронных таблицах, JSON-документах, специализированных файловых форматах и базах данных.

Файловое хранение само по себе не является плохим решением. Для небольшого набора данных одного CSV-файла может быть вполне достаточно.

Проблемы начинают появляться, когда:

- объём данных растёт;
- одни и те же данные используются несколькими приложениями;
- данные необходимо изменять одновременно;
- между разными наборами данных существуют связи;
- необходимо гарантировать выполнение бизнес-правил;
- требуется разграничение доступа;
- необходимо выполнять сложные запросы;
- важно обеспечить надёжность изменений.

Для решения этих задач используются **системы управления базами данных — СУБД**.

Важно различать два понятия.

**База данных** — организованный набор данных.

**СУБД** — программная система, которая управляет этими данными: принимает запросы, выполняет операции чтения и изменения, контролирует транзакции и права доступа, поддерживает ограничения целостности и выполняет множество других задач.

Например, PostgreSQL, Microsoft SQL Server, MySQL и Oracle Database — это СУБД.

---

### Реляционные и нереляционные базы данных

Один из способов классификации систем хранения данных — разделение на **реляционные** и **нереляционные**.

Реляционные СУБД основаны на реляционной модели данных.

К ним относятся:

- PostgreSQL;
- Microsoft SQL Server;
- MySQL;
- Oracle Database.

Нереляционные системы могут использовать другие модели хранения:

- **key-value** — данные представлены как пары «ключ — значение»;
- **document** — данные хранятся как документы, например JSON-подобные структуры;
- **wide-column** — данные организованы по семействам столбцов;
- **graph** — данные представлены вершинами и связями;
- специализированные модели для временных рядов и других задач.

Нереляционные системы часто объединяют термином **NoSQL**.

При этом NoSQL не означает буквально «SQL запрещён» или «у данных нет схемы».

Некоторые NoSQL-системы:

- поддерживают SQL-подобные языки запросов;
- используют строгие типы данных;
- накладывают ограничения на структуру документов.

Поэтому противопоставление «SQL — строгая схема, NoSQL — вообще никакой схемы» является слишком грубым.

Выбор технологии зависит от задачи: структуры данных, характера запросов, требований к согласованности, масштабированию, производительности и эксплуатации системы.

### Тема 2. Реляционная модель и язык SQL

Реляционная модель была предложена Эдгаром Коддом в 1970 году.

Её основное понятие — **отношение** (*relation*).

Именно от слова *relation* происходит термин **relational database**.

Иногда название «реляционная база» ошибочно объясняют тем, что в ней существуют связи между таблицами. Связи действительно важны, но название модели происходит не от них.

На практике отношение обычно представлено таблицей.

Например:

| customer_id | full_name | email |
|---:|---|---|
| 1 | Анна Иванова | anna@example.com |
| 2 | Иван Петров | ivan@example.com |

У таблицы есть:

- **столбцы** — описывают свойства данных;
- **строки** — содержат конкретные значения.

В терминологии реляционной модели столбцы также называют **атрибутами**, а строки — **кортежами**.

При этом физическая таблица конкретной СУБД и математическое отношение — не полностью одно и то же.

Например:

- SQL допускает дублирование строк, если оно не запрещено ограничениями;
- порядок строк результата без `ORDER BY` не определён;
- конкретная СУБД хранит данные физически в страницах, файлах и других внутренних структурах, которых нет в математической модели.

---

### Что такое SQL

**SQL — Structured Query Language** — язык, используемый для работы с реляционными базами данных.

С помощью SQL можно:

- создавать и изменять объекты базы;
- добавлять данные;
- изменять данные;
- удалять данные;
- получать данные;
- объединять несколько таблиц;
- группировать и агрегировать результаты;
- управлять транзакциями;
- назначать права;
- создавать представления и программные объекты СУБД.

SQL — преимущественно **декларативный язык**.

Мы обычно описываем **какой результат хотим получить**, а не перечисляем процессору последовательность физических действий, которые необходимо выполнить.

Например:

```sql
SELECT customer_id, full_name
FROM customers
WHERE customer_id > 100;
```

Мы описываем требуемый результат:

> получить идентификаторы и имена клиентов с идентификатором больше 100.

А конкретный способ поиска строк выбирает СУБД.

Она может:

- прочитать таблицу;
- использовать индекс;
- выбрать один из нескольких способов соединения таблиц;
- изменить порядок выполнения операций.

Эта особенность станет особенно важной, когда мы будем изучать планы выполнения и оптимизацию запросов.

---

### SQL-стандарт и диалекты

SQL стандартизирован, поэтому основные конструкции похожи в разных реляционных СУБД.

Например, такой запрос будет выглядеть практически одинаково на большинстве платформ:

```sql
SELECT customer_id, full_name
FROM customers
WHERE customer_id > 100;
```

Однако на практике каждая СУБД имеет собственный **SQL-диалект**.

Различия существуют в:

- типах данных;
- функциях работы со строками;
- функциях даты и времени;
- JSON;
- геоданных;
- процедурном языке;
- генерации идентификаторов;
- ограничении количества строк;
- работе с индексами;
- диагностике производительности.

Поэтому идея и бизнес-логика запроса часто остаются одинаковыми, а конкретный SQL может различаться.

На курсе рассматриваются четыре платформы:

- PostgreSQL/PostGIS;
- Microsoft SQL Server;
- MySQL/InnoDB;
- Oracle.

---

### Реляционные операции

SQL тесно связан с идеями реляционной алгебры.

Для первого знакомства достаточно нескольких основных операций.

**Выборка** ограничивает строки по условию:

```sql
WHERE total_amount > 1000
```

**Проекция** оставляет необходимые столбцы:

```sql
SELECT order_id, total_amount
```

**Соединение** позволяет сопоставить связанные данные:

```sql
FROM orders
JOIN customers
  ON customers.customer_id = orders.customer_id
```

Также существуют операции:

- объединения;
- пересечения;
- разности наборов данных.

Кроме классических реляционных операций, SQL предоставляет:

- группировку;
- агрегаты;
- сортировку;
- оконные функции;
- подзапросы;
- CTE;
- множество встроенных функций.

Эти возможности будут подробно изучаться дальше.

### Тема 3. Структура базы данных и организация схемы

В СУБД существует несколько уровней организации объектов.

Однако важно сразу учитывать, что структура этих уровней **не одинакова во всех СУБД**.

Нельзя считать универсальной схему:

```text
сервер
└── база данных
    └── схема
        └── таблица
```

Для PostgreSQL и SQL Server такая схема близка к реальности, но другие платформы устроены иначе.

Например:

**PostgreSQL**

```text
кластер PostgreSQL
└── база данных
    └── схема
        └── объекты
```

**Microsoft SQL Server**

```text
экземпляр SQL Server
└── база данных
    └── схема
        └── объекты
```

В MySQL термины `DATABASE` и `SCHEMA` практически эквивалентны.

В Oracle понятие схемы тесно связано с пользователем: схема представляет набор объектов, принадлежащих конкретному владельцу.

Поэтому при переходе между СУБД важно разделять:

- общую идею пространства имён;
- конкретную реализацию этой идеи в выбранной платформе.

---

### Для чего нужна схема

Схемы помогают организовывать объекты базы данных.

Например, условная система доставки может содержать схемы:

```text
sales
delivery
billing
audit
```

В них могут располагаться таблицы и другие объекты, относящиеся к соответствующим областям.

Например:

```text
sales.orders
delivery.couriers
billing.payments
audit.audit_log
```

Это помогает:

- логически группировать объекты;
- избегать конфликтов имён;
- управлять правами доступа;
- облегчать сопровождение большой базы.

Конкретные правила имён и пространств имён зависят от СУБД.

---

### ER-диаграмма

Для проектирования структуры данных часто используют **ER-диаграммы — Entity-Relationship Diagram**.

Они позволяют представить:

- сущности;
- их атрибуты;
- идентификаторы;
- связи между сущностями;
- кратность связей.

Например:

```text
Customer 1 ───── N Order
```

означает:

> один клиент может иметь несколько заказов.

ER-модель помогает сначала описать предметную область, а затем перейти к реализации таблиц, типов данных, ключей и ограничений в конкретной СУБД.

### Тема 4. Ключи, связи и ограничения целостности

Одной из главных задач СУБД является поддержание корректности данных.

Для этого используются ключи и ограничения целостности.

---

### Первичный ключ

**PRIMARY KEY** однозначно идентифицирует строку таблицы.

Например:

```sql
CREATE TABLE customers (
    customer_id INTEGER PRIMARY KEY,
    full_name VARCHAR(200) NOT NULL
);
```

Для `customer_id` нельзя создать две строки с одним и тем же значением.

Кроме того, значение первичного ключа не может быть `NULL`.

Первичный ключ может состоять не только из одного столбца.

Например:

```sql
PRIMARY KEY (store_id, product_id)
```

Такой ключ называется **составным**.

---

### Внешний ключ

**FOREIGN KEY** используется для контроля ссылочной целостности.

Например:

```sql
CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,

    FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);
```

Теперь заказ не может ссылаться на несуществующего клиента, если ограничение внешнего ключа действует для выполняемой операции.

Чаще всего внешний ключ ссылается на первичный ключ другой таблицы.

Однако его задача шире: он должен ссылаться на подходящий уникально идентифицирующий ключ. Конкретные требования к такому ключу немного различаются между СУБД.

---

### Типы связей

В модели данных обычно выделяют:

#### Один к одному — 1:1

Одной строке первой сущности соответствует не более одной строки второй.

#### Один ко многим — 1:N

Одна строка первой сущности может быть связана со многими строками второй.

Например:

```text
Customer 1 ───── N Order
```

#### Многие ко многим — M:N

Один объект может быть связан со многими объектами второго типа, и наоборот.

В реляционной базе такую связь обычно реализуют через отдельную таблицу.

Например:

```text
Order 1 ───── N OrderItem N ───── 1 Product
```

---

### Ограничения целостности

Кроме ключей используются и другие ограничения.

#### NOT NULL

Запрещает отсутствие значения:

```sql
full_name VARCHAR(200) NOT NULL
```

#### UNIQUE

Запрещает повторение значения или комбинации значений:

```sql
email VARCHAR(320) UNIQUE
```

#### CHECK

Проверяет логическое условие:

```sql
CHECK (price >= 0)
```

#### FOREIGN KEY

Контролирует ссылочную целостность.

Преимущество ограничений базы данных заключается в том, что правило проверяет сама СУБД.

Это особенно важно, если данные изменяет не одно приложение, а несколько разных клиентов или сервисов.

### Тема 5. Индексы и производительность доступа к данным

Когда таблица становится большой, поиск нужных строк может требовать значительного объёма работы.

Один из основных инструментов ускорения доступа — **индекс**.

Индекс — дополнительная структура данных, которую СУБД может использовать для поиска строк.

Например:

```sql
CREATE INDEX idx_orders_customer_id
    ON orders(customer_id);
```

Такой индекс может помочь запросам, которые ищут заказы определённого клиента.

Важно: индекс нельзя представлять просто как «отсортированную копию столбца».

Существуют разные структуры и разновидности индексов:

- B-tree;
- hash;
- bitmap;
- полнотекстовые;
- пространственные;
- другие специализированные варианты.

Набор поддерживаемых типов зависит от СУБД.

---

### Индекс не всегда ускоряет запрос

Наличие индекса ещё не означает, что СУБД обязательно его использует.

Например, если запрос должен прочитать значительную часть таблицы, чтение таблицы целиком иногда оказывается дешевле использования индекса.

Кроме того, индекс необходимо поддерживать при изменении таблицы.

При выполнении операций:

```sql
INSERT
UPDATE
DELETE
```

СУБД может потребоваться обновлять не только строки таблицы, но и связанные индексы.

Поэтому индексы:

- занимают дополнительное место;
- ускоряют одни операции;
- могут удорожать другие.

Оптимизация индексов — это поиск баланса под конкретную нагрузку.

Подробнее эту тему мы разберём в модуле производительности.

### Тема 6. Представления и программные объекты СУБД

СУБД хранит не только таблицы.

Она может содержать и другие объекты, например:

- представления;
- функции;
- процедуры;
- триггеры.

При этом представление и исполняемый программный код — не одно и то же, поэтому их полезно разделять.

---

### Представление

**VIEW** — сохранённое определение запроса, к которому можно обращаться как к виртуальной таблице.

Например:

```sql
CREATE VIEW customer_names AS
SELECT customer_id, full_name
FROM customers;
```

Представление может:

- скрывать сложность запроса;
- предоставлять удобный интерфейс доступа к данным;
- ограничивать набор доступных столбцов или строк;
- избавлять от повторения одних и тех же запросов.

Обычное представление обычно не хранит отдельную копию результата.

Есть и другие механизмы, например материализованные представления, но их наличие и возможности зависят от конкретной СУБД.

---

### Функции

Функция принимает аргументы и возвращает некоторый результат.

В зависимости от СУБД это может быть:

- одно значение;
- строка;
- набор строк;
- таблица.

Конкретные возможности функций различаются между платформами.

---

### Хранимые процедуры

Хранимая процедура — программный объект, который вызывается для выполнения некоторой операции.

Например, процедура может:

1. проверить состояние заказа;
2. создать резерв товара;
3. создать платёж;
4. изменить статус заказа.

Особенности процедур сильно зависят от СУБД.

В частности, различаются:

- способы возврата данных;
- возможности управления транзакциями;
- процедурный синтаксис;
- обработка ошибок.

---

### Триггеры

Триггер запускается автоматически при наступлении определённого события.

Часто используются события:

- `INSERT`;
- `UPDATE`;
- `DELETE`.

Например, после изменения заказа триггер может добавить запись в журнал аудита.

Триггеры полезны, но использовать их необходимо осознанно.

Поскольку логика выполняется автоматически, её сложнее заметить при чтении обычного SQL-кода приложения.

---

### Тема 7. Преимущества и ограничения логики на стороне СУБД

Часть бизнес-логики можно размещать непосредственно в базе данных.

Например:

- ограничения целостности;
- триггеры;
- функции;
- процедуры;
- представления как интерфейс доступа к данным.

У такого подхода есть преимущества.

Логика находится рядом с данными и может применяться независимо от того, какое приложение обращается к базе.

Несколько связанных действий иногда можно выполнить одним обращением к СУБД вместо серии сетевых запросов.

Критичные правила можно централизовать.

Но важно не делать ошибочный вывод:

> перенос логики в СУБД автоматически ускоряет приложение.

Это не так.

Сложная серверная логика может, наоборот:

- повышать нагрузку на сервер базы данных;
- усложнять тестирование;
- затруднять сопровождение;
- делать систему сильнее зависимой от конкретной СУБД.

Поэтому вопрос о том, какую часть логики реализовать в приложении, а какую — в СУБД, является архитектурным решением.

Универсального ответа нет.

---

### Тема 8. Роли, пользователи и управление доступом

С базой данных обычно работают разные участники:

- приложения;
- разработчики;
- аналитики;
- администраторы;
- технические сервисы.

Им не должны автоматически предоставляться одинаковые права.

СУБД позволяют разграничивать доступ.

Например, можно разрешить пользователю:

- выполнять `SELECT`;
- изменять определённые таблицы;
- выполнять процедуру;
- использовать конкретную схему;

и запретить остальные операции.

Для этого используются пользователи, роли и привилегии.

Конкретная модель различается между СУБД.

Например:

- PostgreSQL во многом строит модель доступа вокруг ролей;
- SQL Server различает серверные логины и пользователей базы;
- MySQL использует учётные записи и роли;
- Oracle использует пользователей, роли и системные/объектные привилегии.

На этом этапе достаточно запомнить общий принцип:

> приложение или пользователь должны получать только необходимые им права.

К этой теме мы будем возвращаться при работе с конкретными СУБД.

---

### Тема 9. Типы нагрузок OLTP и OLAP

При проектировании базы важно понимать не только структуру данных, но и то, **как с ними будут работать**.

Два распространённых понятия — OLTP и OLAP.

---

### OLTP — Online Transaction Processing

OLTP описывает операционную нагрузку.

Например, в системе доставки постоянно выполняются:

- создание заказа;
- изменение статуса заказа;
- проведение платежа;
- резервирование товара;
- назначение курьера.

Для такой нагрузки характерны:

- большое количество сравнительно небольших операций;
- частое изменение данных;
- конкурентная работа пользователей;
- требования к корректности транзакций;
- необходимость быстро обрабатывать отдельные операции.

---

### OLAP — Online Analytical Processing

OLAP связан преимущественно с аналитическими запросами.

Например:

- выручка за месяц;
- средний чек по городам;
- динамика заказов;
- эффективность магазинов;
- сравнение периодов.

Такие запросы могут:

- читать большие объёмы данных;
- выполнять сложные соединения;
- группировать миллионы строк;
- рассчитывать агрегаты.

---

### OLTP и OLAP — характеристики нагрузки

Не стоит воспринимать OLTP и OLAP как жёсткое разделение:

> эта СУБД — OLTP, а эта — OLAP.

Одна информационная система может обслуживать оба вида задач.

Однако требования у этих нагрузок разные, поэтому в крупных архитектурах операционную и аналитическую обработку нередко разделяют.

---

### Тема 10. Клиент-серверная архитектура и взаимодействие с СУБД

Большинство промышленных реляционных СУБД работает по клиент-серверной модели.

Есть сервер СУБД и есть клиент.

Клиентом может быть:

- SQL-клиент;
- приложение;
- backend-сервис;
- IDE;
- аналитическая система;
- консольная утилита.

Упрощённо взаимодействие выглядит так:

```text
клиент
   │
   │ SQL-запрос
   ▼
СУБД
   │
   │ работа с данными
   ▼
база данных
   │
   │ результат
   ▼
клиент
```

Например, пользователь выполняет:

```sql
SELECT *
FROM orders
WHERE customer_id = 100;
```

Клиент передаёт SQL серверу СУБД.

Упрощённо СУБД должна:

1. разобрать запрос;
2. проверить используемые объекты и выражения;
3. проверить права доступа;
4. определить способ выполнения;
5. выполнить необходимые операции;
6. вернуть результат.

Для запросов к данным оптимизатор выбирает **план выполнения**.

При этом SQL описывает требуемый результат, а конкретную последовательность физических операций выбирает СУБД.

Например, она может решить:

- прочитать таблицу целиком;
- использовать индекс;
- начать соединение с одной или другой таблицы;
- выбрать один из доступных алгоритмов соединения.

Позже мы подробно разберём, как читать планы выполнения и понимать решения оптимизатора.

### Тема 11. Подготовка учебного окружения

Для дальнейшей практики необходимо подготовить локальное окружение.

На курсе можно выбрать одну из четырёх СУБД:

- PostgreSQL/PostGIS;
- Microsoft SQL Server;
- MySQL/InnoDB;
- Oracle.

С выбранной платформой студент работает в практических заданиях курса.

Для запуска СУБД используется Docker Desktop.

---

### Что даёт Docker

Docker позволяет запускать приложение вместе с необходимым окружением в контейнере.

В нашем случае внутри контейнера будет работать сервер СУБД.

Упрощённая схема:

```text
SQL-клиент
     │
     ▼
Docker Desktop
     │
     ▼
контейнер
     │
     ▼
СУБД
```

Такой подход позволяет:

- не устанавливать сервер СУБД непосредственно в операционную систему;
- использовать заранее определённую версию;
- воспроизводить одинаковое учебное окружение;
- при необходимости удалить контейнер и развернуть его заново.

---

### Что будет создано в начале курса

На первом этапе разворачивается **чистая рабочая СУБД**.

В ней пока нет канонических таблиц и данных общей платформы курса.

Это сделано специально: первые задания связаны в том числе с проектированием логической и физической структуры данных.

Начиная с ДЗ-03 студент получает подготовленную единую базу курса с общей предметной областью.

Для установки и запуска окружения предоставляются отдельные инструкции.

## Итоговые выводы

- База данных и СУБД — разные понятия: база содержит данные, а СУБД управляет работой с ними.
- Реляционная модель основана на отношениях; в практических SQL-СУБД основным способом представления данных являются таблицы.
- SQL — преимущественно декларативный язык: пользователь описывает требуемый результат, а способ выполнения выбирает СУБД.
- SQL имеет общий стандарт, но PostgreSQL, SQL Server, MySQL и Oracle используют собственные диалекты и отличаются набором возможностей.
- Первичные ключи, внешние ключи и ограничения помогают поддерживать целостность данных.
- Индекс — дополнительная структура доступа, которая может ускорять запросы, но требует ресурсов и не всегда используется оптимизатором.
- Представления, функции, процедуры и триггеры решают разные задачи и не должны восприниматься как один тип «хранимого кода».
- Размещение логики внутри СУБД имеет преимущества и недостатки и не гарантирует автоматического роста производительности.
- OLTP и OLAP описывают разные типы нагрузки, а не два жёстко разделённых вида баз данных.
- Архитектура баз, схем и пользователей различается между СУБД, поэтому общие SQL-концепции необходимо соотносить с конкретной платформой.
- Практическая работа на курсе выполняется в локальной СУБД, развёрнутой через Docker Desktop.
