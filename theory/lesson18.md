
# Секционирование таблиц в реляционных СУБД

## Превью / аннотация / краткое содержание

Занятие посвящено секционированию (партиционированию) таблиц как способу организации больших объёмов данных в реляционных СУБД.

Секционирование позволяет представить данные как одну логическую таблицу, физически распределённую между несколькими частями — секциями. Это помогает управлять жизненным циклом данных, ускорять определённые запросы и выполнять административные операции над отдельными частями большой таблицы.

Однако секционирование не является универсальным средством оптимизации. Его эффективность зависит от выбора ключа, условий запросов, количества секций, структуры индексов и возможностей конкретной СУБД.

На занятии рассматриваются:

- назначение секционирования;
- логическая и физическая модель секционированной таблицы;
- выбор ключа секционирования;
- исторический механизм наследования PostgreSQL;
- декларативное секционирование;
- стратегии `RANGE`, `LIST`, `HASH`, `INTERVAL` и `KEY`;
- создание секций и управление ими;
- присоединение, отсоединение и удаление секций;
- особенности PostgreSQL, SQL Server, MySQL/InnoDB и Oracle;
- `partition pruning` — исключение ненужных секций;
- ограничения первичных и уникальных ключей;
- индексирование секционированных таблиц;
- преобразование существующей таблицы в секционированную;
- выбор секционирования с учётом производительности и эксплуатации.

Основные практические примеры приведены для PostgreSQL. Особенности остальных СУБД рассматриваются отдельно.

## Основные понятия

**Секционирование (Partitioning)** — разделение данных одной логической таблицы на отдельные физические части по определённому правилу.

**Партиционирование** — синоним секционирования.

**Секция (Partition)** — физическая часть секционированной таблицы, содержащая строки, соответствующие определённому условию распределения.

**Секционированная таблица (Partitioned Table)** — логическая таблица, данные которой размещаются в секциях.

**Ключ секционирования (Partition Key)** — один или несколько столбцов либо поддерживаемых выражений, определяющих распределение строк между секциями.

**RANGE Partitioning** — секционирование по диапазонам значений.

**LIST Partitioning** — секционирование по спискам значений.

**HASH Partitioning** — секционирование на основе хеширования ключа.

**INTERVAL Partitioning** — механизм Oracle, позволяющий автоматически создавать диапазонные секции при поступлении новых значений за пределами заданных диапазонов.

**KEY Partitioning** — разновидность хеш-секционирования MySQL, использующая внутренний механизм хеширования ключей.

**Subpartitioning** — дополнительное секционирование уже существующей секции.

**Partition Pruning** — исключение секций, которые заведомо не могут содержать строки, удовлетворяющие запросу.

**Partition Elimination** — другое название механизма исключения секций, особенно распространённое в SQL Server.

**Declarative Partitioning** — декларативное секционирование, при котором структура и правила распределения задаются специальным синтаксисом СУБД.

**Inheritance Partitioning** — исторический подход PostgreSQL, при котором секционирование реализуется через наследование таблиц.

**Partition Bound** — условие, определяющее диапазон или набор значений секции.

**Default Partition** — секция, принимающая строки, которые не соответствуют ни одной из явно заданных секций.

**ATTACH PARTITION** — операция PostgreSQL для присоединения существующей таблицы к секционированной структуре.

**DETACH PARTITION** — операция PostgreSQL для отсоединения секции от родительской таблицы.

**Partition Function** — объект SQL Server, определяющий распределение значений между секциями.

**Partition Scheme** — объект SQL Server, связывающий секции с файловыми группами.

**Partition Switching** — механизм SQL Server для переключения секций между совместимыми таблицами.

**EXCHANGE PARTITION** — механизм Oracle для обмена секции с обычной таблицей.

**Tablespace** — логическая область размещения объектов базы данных, физическая организация которой зависит от СУБД.

**Filegroup** — механизм SQL Server для организации файлов данных.

**CHECK Constraint** — ограничение, проверяющее условие допустимости данных.

**PRIMARY KEY** — ограничение первичного ключа.

**UNIQUE Constraint** — ограничение уникальности.

**Aligned Index** — индекс SQL Server, секционирование которого согласовано с секционированием базовой таблицы.

**Nonaligned Index** — индекс SQL Server, организация секций которого отличается от организации базовой таблицы либо который не секционирован.

**Local Index** — индекс, связанный с отдельными секциями таблицы; термин особенно распространён в Oracle.

**Global Index** — индекс, охватывающий данные нескольких секций и поддерживаемый некоторыми СУБД.

**Modulus** — параметр PostgreSQL HASH-секционирования, задающий модуль распределения.

**Remainder** — остаток, определяющий соответствующую секцию при HASH-секционировании PostgreSQL.

**Rolling Window** — схема сопровождения данных, при которой регулярно добавляются новые временные секции и удаляются или архивируются старые.

## Основная часть

### Тема 1. Секционирование как механизм организации больших таблиц

В реляционных базах данных отдельные таблицы могут содержать миллионы и миллиарды строк.

Например, в платформе доставки постоянно создаются:

- заказы;
- события изменения статусов;
- координаты курьеров;
- записи аудита;
- результаты расчётов;
- сообщения интеграционных сервисов.

Если данные накапливаются годами, таблицы становятся большими.

Это может усложнять:

- обслуживание индексов;
- очистку устаревших данных;
- архивирование;
- выполнение запросов по отдельным временным периодам;
- административные операции.

Одним из способов организации такой таблицы является секционирование.

#### Основная идея

Предположим, существует таблица:

```text
delivery_events
```

Она содержит события за несколько лет.

Вместо размещения всех строк в одной физической таблице можно использовать секции по месяцам:

```text
delivery_events
    |
    +-- delivery_events_2026_01
    |
    +-- delivery_events_2026_02
    |
    +-- delivery_events_2026_03
    |
    +-- delivery_events_2026_04
```

Приложение продолжает выполнять:

```sql
SELECT *
FROM delivery_events
WHERE event_time >= TIMESTAMP '2026-03-01'
  AND event_time <  TIMESTAMP '2026-04-01';
```

При корректном секционировании СУБД может определить, что данные за март находятся только в соответствующей секции.

Остальные секции не требуется сканировать.

Этот механизм называется `partition pruning`.

#### Секционирование не равно индексированию

Индекс предоставляет альтернативный способ поиска строк.

Секционирование определяет, между какими физическими частями распределены строки.

Эти механизмы дополняют друг друга.

Например:

- секционирование позволяет выбрать один месяц;
- индекс внутри выбранной секции помогает найти события конкретного курьера.

Не следует считать, что после секционирования индексы больше не нужны.

#### Секционирование не равно шардингу

Секционирование одной таблицы внутри СУБД не означает автоматического распределения данных между несколькими независимыми серверами.

Например, HASH-секционирование PostgreSQL само по себе не создаёт распределённую базу данных.

Все секции могут находиться в одном экземпляре PostgreSQL.

Шардинг предполагает распределение данных между отдельными узлами или экземплярами с дополнительной логикой маршрутизации и управления.

Это самостоятельная архитектурная задача.

#### Когда секционирование полезно

Типичные сценарии:

1. Большие таблицы событий.
2. Временные ряды.
3. Журналы аудита.
4. История заказов.
5. Финансовые операции, организованные по периодам.
6. Архивы.
7. Аналитические таблицы с естественными диапазонами данных.

Однако сама по себе большая таблица не означает необходимость секционирования.

Если запросы эффективно используют индексы и работают с небольшим количеством строк, обычная таблица может оставаться оптимальным решением.

### Тема 2. Логическая и физическая модель секционированной таблицы

С точки зрения приложения секционированная таблица может оставаться единым объектом.

Например:

```sql
SELECT COUNT(*)
FROM delivery_events;
```

Запрос обращается к логической таблице, а СУБД обрабатывает данные её секций.

#### Родительская таблица PostgreSQL

При декларативном секционировании PostgreSQL родительская секционированная таблица сама не хранит обычные строки данных.

Строки размещаются в секциях.

Каждая конечная секция является физической таблицей, имеющей собственное хранение и, при необходимости, индексы.

#### Создание таблицы

```sql
CREATE TABLE delivery_events (
    event_id BIGINT NOT NULL,
    event_time TIMESTAMP NOT NULL,
    courier_id BIGINT NOT NULL,
    event_type TEXT NOT NULL,
    payload JSONB
)
PARTITION BY RANGE (event_time);
```

Здесь:

```sql
PARTITION BY RANGE (event_time)
```

означает, что строки распределяются по диапазонам значений `event_time`.

Пока секции не созданы, вставка строки, не имеющей подходящего места размещения, завершится ошибкой.

#### Создание секций

```sql
CREATE TABLE delivery_events_2026_01
PARTITION OF delivery_events
FOR VALUES FROM ('2026-01-01')
             TO ('2026-02-01');
```

```sql
CREATE TABLE delivery_events_2026_02
PARTITION OF delivery_events
FOR VALUES FROM ('2026-02-01')
             TO ('2026-03-01');
```

```sql
CREATE TABLE delivery_events_2026_03
PARTITION OF delivery_events
FOR VALUES FROM ('2026-03-01')
             TO ('2026-04-01');
```

В PostgreSQL нижняя граница диапазона включается, верхняя не включается.

То есть:

```text
[2026-03-01, 2026-04-01)
```

Такой способ предотвращает пересечение соседних временных диапазонов.

#### Вставка данных

```sql
INSERT INTO delivery_events (
    event_id,
    event_time,
    courier_id,
    event_type
)
VALUES (
    1,
    TIMESTAMP '2026-03-15 12:30:00',
    101,
    'location_updated'
);
```

PostgreSQL самостоятельно направит строку в:

```text
delivery_events_2026_03
```

Это можно проверить:

```sql
SELECT
    tableoid::regclass AS physical_table,
    event_id,
    event_time
FROM delivery_events;
```

Системный столбец `tableoid` позволяет увидеть физическую таблицу, которой принадлежит строка.

#### Выбор ключа секционирования

Ключ определяет распределение данных.

Распространённые варианты:

- дата события;
- дата создания заказа;
- идентификатор клиента;
- регион;
- тип операции;
- идентификатор организации.

При выборе ключа необходимо учитывать:

- какие условия чаще используются в запросах;
- какие данные удаляются или архивируются вместе;
- распределение строк;
- число потенциальных секций;
- необходимость уникальных ограничений;
- частоту изменения ключа.

Например, секционирование заказов по статусу может оказаться неудобным.

Статус изменяется:

```text
created → processing → completed
```

При изменении ключа секционирования строка может перемещаться между секциями.

Это создаёт дополнительные расходы и ограничения конкурентной обработки.

Поэтому стабильные признаки часто удобнее для секционирования, чем активно изменяемые.

### Тема 3. Секционирование через наследование в PostgreSQL

До PostgreSQL 10 типовые схемы секционирования часто строились через наследование таблиц.

#### Пример исторического подхода

Создавалась родительская таблица:

```sql
CREATE TABLE old_events (
    event_id BIGINT,
    event_time DATE NOT NULL
);
```

Затем дочерняя таблица:

```sql
CREATE TABLE old_events_2026_01 (
    CHECK (
        event_time >= DATE '2026-01-01'
        AND event_time < DATE '2026-02-01'
    )
)
INHERITS (old_events);
```

Механизм наследования позволял выполнять запрос к родительской таблице и получать строки из дочерних таблиц.

Но это не было полноценным современным декларативным секционированием.

#### Основные ограничения

Разработчик или администратор должен был самостоятельно организовывать:

- маршрутизацию вставок;
- ограничения диапазонов;
- создание новых дочерних таблиц;
- управление индексами;
- проверку целостности;
- исключение лишних таблиц при чтении.

Для автоматической маршрутизации вставок могли использоваться триггеры или правила.

У этого подхода были существенные эксплуатационные сложности.

#### Декларативное секционирование

Начиная с PostgreSQL 10 появился специальный механизм декларативного секционирования.

Он развивается в последующих версиях PostgreSQL.

Сегодня для обычных задач рекомендуется именно:

```sql
PARTITION BY RANGE
```

```sql
PARTITION BY LIST
```

```sql
PARTITION BY HASH
```

Однако наследование таблиц как самостоятельная возможность PostgreSQL продолжает существовать.

Оно не было полностью удалено из СУБД.

Поэтому корректнее говорить, что наследование больше не является предпочтительным способом реализации типового секционирования.

### Тема 4. Декларативное секционирование и управление секциями

Декларативное секционирование позволяет явно описать правила распределения строк.

PostgreSQL самостоятельно:

- выбирает секцию для вставки;
- проверяет допустимые границы;
- учитывает структуру секций при планировании запросов;
- поддерживает связанные объекты и ограничения в рамках реализованных возможностей.

#### Секция по умолчанию

Можно создать:

```sql
CREATE TABLE delivery_events_default
PARTITION OF delivery_events DEFAULT;
```

Эта секция принимает строки, которые не попадают в явно заданные диапазоны.

Например:

```sql
INSERT INTO delivery_events (
    event_id,
    event_time,
    courier_id,
    event_type
)
VALUES (
    2,
    TIMESTAMP '2027-01-10 10:00:00',
    102,
    'location_updated'
);
```

При отсутствии секции за январь 2027 года строка попадёт в `delivery_events_default`.

#### Нужно ли всегда создавать DEFAULT

Нет.

Секция по умолчанию может предотвращать ошибки вставки при отсутствии подходящей секции.

Но она также способна скрывать проблемы управления диапазонами.

Если заранее не создаются новые секции, DEFAULT может постепенно превратиться в большую таблицу, содержащую данные за множество периодов.

Кроме того, наличие строк в DEFAULT может осложнить добавление новой секции.

При создании секции PostgreSQL должен убедиться, что строки, соответствующие новому диапазону, не остаются в DEFAULT.

Это может потребовать дополнительной проверки и блокировок.

Поэтому для регулярных временных секций часто предпочтительнее автоматически создавать новые диапазоны заранее и отдельно контролировать ошибки маршрутизации.

#### Удаление секции

Если данные за январь больше не нужны:

```sql
DROP TABLE delivery_events_2026_01;
```

В результате удаляется вся физическая секция.

Это принципиально отличается от:

```sql
DELETE FROM delivery_events
WHERE event_time >= TIMESTAMP '2026-01-01'
  AND event_time < TIMESTAMP '2026-02-01';
```

Массовый DELETE затрагивает строки и создаёт соответствующую нагрузку на механизмы изменения данных, индексы и журналирование.

Удаление секции позволяет избавиться от целого физического объекта.

Однако `DROP TABLE` также требует соответствующих блокировок.

#### Отсоединение секции

```sql
ALTER TABLE delivery_events
DETACH PARTITION delivery_events_2026_01;
```

После выполнения таблица `delivery_events_2026_01` продолжает существовать, но больше не является секцией `delivery_events`.

Это позволяет:

- сохранить архив;
- отдельно выполнить экспорт;
- переместить данные;
- выполнить административные операции.

В PostgreSQL также существует:

```sql
ALTER TABLE delivery_events
DETACH PARTITION delivery_events_2026_01 CONCURRENTLY;
```

У этого режима есть дополнительные ограничения, в частности он не поддерживается в некоторых случаях с DEFAULT-секцией и не выполняется внутри обычного транзакционного блока.

Поэтому `CONCURRENTLY` не означает полного отсутствия блокировок или возможности применять команду в любом контексте.

### Тема 5. Реализация секционирования в четырёх СУБД

Хотя общая концепция похожа, физическая реализация и синтаксис различаются.

#### PostgreSQL

В PostgreSQL секционированная таблица представляет собой логический родительский объект и отдельные дочерние секции.

Основной синтаксис:

```sql
CREATE TABLE ...
PARTITION BY RANGE (...);
```

```sql
CREATE TABLE ...
PARTITION OF ...
FOR VALUES FROM (...) TO (...);
```

Секции являются отдельными отношениями, которым можно назначать собственные индексы и параметры хранения в пределах поддерживаемых правил.

#### SQL Server

В SQL Server секционирование строится на двух основных объектах:

- partition function;
- partition scheme.

Partition function определяет границы.

Partition scheme связывает секции с файловыми группами.

Пример:

```sql
CREATE PARTITION FUNCTION pf_orders_by_date (DATE)
AS RANGE RIGHT FOR VALUES (
    '2026-02-01',
    '2026-03-01',
    '2026-04-01'
);
```

Создадим схему:

```sql
CREATE PARTITION SCHEME ps_orders_by_date
AS PARTITION pf_orders_by_date
ALL TO ([PRIMARY]);
```

В этом примере все секции размещаются в одной файловой группе `PRIMARY`.

Это показывает, что секционирование не требует отдельной файловой группы для каждой секции.

Создадим таблицу:

```sql
CREATE TABLE dbo.partitioned_orders (
    order_id BIGINT NOT NULL,
    created_date DATE NOT NULL,
    customer_id BIGINT NOT NULL,
    total_amount DECIMAL(12, 2) NOT NULL,
    CONSTRAINT PK_partitioned_orders
        PRIMARY KEY CLUSTERED (
            created_date,
            order_id
        )
)
ON ps_orders_by_date(created_date);
```

В SQL Server секционирование не обязано подразумевать наличие кластерного первичного ключа.

Возможны heap-таблицы, секционированные индексы и различные варианты их размещения.

Однако для уникальных секционированных индексов существуют требования к включению столбца секционирования.

Для изменения границ используется, например:

```sql
ALTER PARTITION FUNCTION pf_orders_by_date()
SPLIT RANGE ('2026-05-01');
```

При добавлении границ необходимо учитывать наличие подготовленной файловой группы `NEXT USED` в соответствующей схеме.

Для схемы `ALL TO` поведение упрощено, но в более сложной конфигурации размещением файлов необходимо управлять явно.

#### Oracle

Oracle поддерживает развитую систему секционирования.

Например:

```sql
CREATE TABLE orders_partitioned (
    order_id NUMBER NOT NULL,
    created_at DATE NOT NULL,
    total_amount NUMBER(12, 2)
)
PARTITION BY RANGE (created_at) (
    PARTITION p_2026_01
        VALUES LESS THAN (DATE '2026-02-01'),
    PARTITION p_2026_02
        VALUES LESS THAN (DATE '2026-03-01'),
    PARTITION p_future
        VALUES LESS THAN (MAXVALUE)
);
```

Oracle позволяет выполнять операции над отдельными секциями, включая:

- добавление;
- удаление;
- разделение;
- объединение;
- перемещение;
- обмен с обычной таблицей.

Пример обмена:

```sql
ALTER TABLE orders_partitioned
EXCHANGE PARTITION p_2026_01
WITH TABLE orders_staging
WITH VALIDATION;
```

Таблица `orders_staging` должна быть заранее подготовлена и соответствовать требованиям операции.

Также необходимо учитывать индексы, ограничения и дополнительные параметры обмена.

`EXCHANGE PARTITION` может быть эффективным способом загрузки и выгрузки данных, но не является универсальной заменой произвольного переноса строк.

#### MySQL/InnoDB

MySQL поддерживает:

- `RANGE`;
- `RANGE COLUMNS`;
- `LIST`;
- `LIST COLUMNS`;
- `HASH`;
- `LINEAR HASH`;
- `KEY`;
- `LINEAR KEY`.

Пример:

```sql
CREATE TABLE partitioned_orders (
    order_id BIGINT NOT NULL,
    created_date DATE NOT NULL,
    customer_id BIGINT NOT NULL,
    PRIMARY KEY (order_id, created_date)
)
ENGINE = InnoDB
PARTITION BY RANGE COLUMNS (created_date) (
    PARTITION p_2026_01
        VALUES LESS THAN ('2026-02-01'),
    PARTITION p_2026_02
        VALUES LESS THAN ('2026-03-01'),
    PARTITION p_future
        VALUES LESS THAN (MAXVALUE)
);
```

Важное ограничение MySQL/InnoDB 8.4:

**Пользовательское секционирование InnoDB несовместимо с внешними ключами.**

Секционированная InnoDB-таблица не может выступать обычной родительской или дочерней таблицей внешнего ключа.

Это существенное отличие от PostgreSQL, SQL Server и Oracle.

Поэтому секционирование в MySQL необходимо оценивать не только с точки зрения производительности, но и с точки зрения модели ссылочной целостности.

### Тема 6. Стратегии секционирования

Существуют разные способы распределения строк.

#### RANGE

Разбиение по диапазонам:

```text
Январь
Февраль
Март
Апрель
```

Подходит для:

- дат;
- временных меток;
- числовых диапазонов;
- последовательных идентификаторов.

#### LIST

Разбиение по наборам значений:

```text
Москва
Санкт-Петербург
Другие регионы
```

Подходит для:

- регионов;
- категорий;
- типов клиентов;
- устойчивых бизнес-признаков.

#### HASH

Распределение на основе хеш-функции.

Например:

```text
customer_id → hash → секция
```

Подходит, когда:

- нет естественных временных диапазонов;
- необходимо распределять строки по нескольким физическим частям;
- запросы часто используют равенство по ключу;
- нет требования удалять данные целыми периодами.

Но HASH не гарантирует идеально равномерного распределения.

Также он не создаёт автоматически независимые вычислительные ресурсы или распределённую систему.

#### INTERVAL

Oracle предоставляет interval partitioning.

Оно позволяет автоматически создавать новые диапазонные секции при появлении значений за пределами заданной области.

Это удобно для регулярно поступающих временных данных.

PostgreSQL не создаёт новые RANGE-секции автоматически только потому, что появились данные за новый месяц.

Для этого обычно используются:

- миграции;
- планировщик;
- административные скрипты;
- специализированные инструменты сопровождения секций.

#### KEY

MySQL предоставляет KEY partitioning.

В отличие от пользовательского HASH-выражения, хеширование ключа в KEY partitioning выполняется механизмом MySQL.

Это не полностью идентично синтаксису HASH-секционирования PostgreSQL.

### Тема 7. RANGE-секционирование на практике

Рассмотрим отдельную таблицу событий доставки.

```sql
CREATE TABLE shipment_events (
    event_id BIGINT NOT NULL,
    event_date DATE NOT NULL,
    shipment_id BIGINT NOT NULL,
    event_type TEXT NOT NULL,
    PRIMARY KEY (event_id, event_date)
)
PARTITION BY RANGE (event_date);
```

Создадим три секции:

```sql
CREATE TABLE shipment_events_2026_01
PARTITION OF shipment_events
FOR VALUES FROM ('2026-01-01')
             TO ('2026-02-01');
```

```sql
CREATE TABLE shipment_events_2026_02
PARTITION OF shipment_events
FOR VALUES FROM ('2026-02-01')
             TO ('2026-03-01');
```

```sql
CREATE TABLE shipment_events_2026_03
PARTITION OF shipment_events
FOR VALUES FROM ('2026-03-01')
             TO ('2026-04-01');
```

Добавим данные:

```sql
INSERT INTO shipment_events (
    event_id,
    event_date,
    shipment_id,
    event_type
)
VALUES
    (1, '2026-01-10', 1001, 'created'),
    (2, '2026-02-15', 1002, 'created'),
    (3, '2026-03-20', 1003, 'delivered');
```

Проверим распределение:

```sql
SELECT
    tableoid::regclass AS partition_name,
    event_id,
    event_date
FROM shipment_events
ORDER BY event_date;
```

Результат:

| partition_name | event_id | event_date |
|---|---:|---|
| shipment_events_2026_01 | 1 | 2026-01-10 |
| shipment_events_2026_02 | 2 | 2026-02-15 |
| shipment_events_2026_03 | 3 | 2026-03-20 |

#### Работа с TIMESTAMPTZ

Для временных меток с часовым поясом необходимо явно определить правила формирования диапазонов.

Например, месячные секции могут соответствовать:

- календарным месяцам UTC;
- календарным месяцам определённого региона;
- отдельным бизнес-периодам.

Это не всегда одно и то же.

Если приложение работает в разных часовых поясах, необходимо согласовать, где именно проходит граница периода.

Иначе событие около полуночи может оказаться в неожиданной секции.

### Тема 8. LIST- и HASH-секционирование

#### LIST

Создадим таблицу:

```sql
CREATE TABLE regional_orders (
    order_id BIGINT NOT NULL,
    region TEXT NOT NULL,
    customer_id BIGINT NOT NULL
)
PARTITION BY LIST (region);
```

Секции:

```sql
CREATE TABLE regional_orders_moscow
PARTITION OF regional_orders
FOR VALUES IN ('Moscow');
```

```sql
CREATE TABLE regional_orders_spb
PARTITION OF regional_orders
FOR VALUES IN ('Saint Petersburg');
```

```sql
CREATE TABLE regional_orders_other
PARTITION OF regional_orders DEFAULT;
```

Добавим данные:

```sql
INSERT INTO regional_orders
VALUES
    (1, 'Moscow', 101),
    (2, 'Saint Petersburg', 102),
    (3, 'Kazan', 103);
```

Строка с регионом `Kazan` попадёт в секцию по умолчанию.

#### HASH

Создадим таблицу:

```sql
CREATE TABLE customer_activity (
    activity_id BIGINT NOT NULL,
    customer_id BIGINT NOT NULL,
    action_type TEXT NOT NULL
)
PARTITION BY HASH (customer_id);
```

Четыре секции:

```sql
CREATE TABLE customer_activity_p0
PARTITION OF customer_activity
FOR VALUES WITH (
    MODULUS 4,
    REMAINDER 0
);
```

```sql
CREATE TABLE customer_activity_p1
PARTITION OF customer_activity
FOR VALUES WITH (
    MODULUS 4,
    REMAINDER 1
);
```

```sql
CREATE TABLE customer_activity_p2
PARTITION OF customer_activity
FOR VALUES WITH (
    MODULUS 4,
    REMAINDER 2
);
```

```sql
CREATE TABLE customer_activity_p3
PARTITION OF customer_activity
FOR VALUES WITH (
    MODULUS 4,
    REMAINDER 3
);
```

Теперь PostgreSQL распределяет строки по хешу `customer_id`.

```sql
INSERT INTO customer_activity
VALUES
    (1, 101, 'login'),
    (2, 102, 'login'),
    (3, 103, 'purchase'),
    (4, 104, 'logout');
```

#### MODULUS и REMAINDER

`MODULUS` определяет модуль распределения.

`REMAINDER` определяет соответствующий остаток.

Однако значение ключа не обязательно распределяется как обычное:

```sql
customer_id % 4
```

PostgreSQL использует собственные хеш-функции для секционирования.

Поэтому нельзя вручную определять секцию только через арифметический остаток исходного значения.

#### Изменение числа HASH-секций

Увеличение числа секций может потребовать перераспределения данных.

Нельзя считать, что достаточно добавить пятую секцию к четырём существующим с произвольными значениями MODULUS и REMAINDER.

PostgreSQL предъявляет требования к совместимости схемы остатков и модулей.

На практике изменение структуры HASH-секционирования требует планирования миграции.

#### Недостаток HASH для архивирования

Если требуется удалить все данные за январь, HASH-секции не подходят для прямого удаления январского диапазона.

Строки января могут находиться во всех секциях.

Поэтому для временных данных, регулярно удаляемых целыми месяцами, RANGE обычно удобнее.

### Тема 9. Partition pruning — исключение секций

Partition pruning — один из основных механизмов оптимизации запросов к секционированным таблицам.

СУБД определяет, какие секции заведомо не могут содержать нужные строки.

#### Пример PostgreSQL

```sql
EXPLAIN
SELECT *
FROM shipment_events
WHERE event_date >= DATE '2026-02-01'
  AND event_date < DATE '2026-03-01';
```

Если секции организованы по месяцам, PostgreSQL может обращаться только к февральской секции.

В плане ожидается операция над:

```text
shipment_events_2026_02
```

Вместо чтения всех секций.

#### Partition pruning не зависит от обязательного наличия индекса

Исключение секций использует условия и границы секционирования.

Для самого факта pruning индекс по ключу секционирования не требуется.

Например, PostgreSQL может выполнить последовательное сканирование одной выбранной секции.

Это может быть оптимально, если запросу нужна большая часть её строк.

#### Pruning на этапе планирования

Если значение фильтра известно при планировании, оптимизатор может исключить ненужные секции заранее.

Пример:

```sql
SELECT *
FROM shipment_events
WHERE event_date = DATE '2026-02-15';
```

#### Pruning во время выполнения

PostgreSQL также поддерживает execution-time partition pruning.

Это важно для параметризованных запросов.

Например:

```sql
PREPARE get_events(DATE) AS
SELECT *
FROM shipment_events
WHERE event_date = $1;
```

Выполнение:

```sql
EXECUTE get_events(DATE '2026-02-15');
```

В зависимости от выбранного плана PostgreSQL может исключить секции с учётом значения параметра.

Во время выполнения pruning также может использовать значения, полученные из подзапросов или параметризованных соединений.

Поэтому утверждение, что PostgreSQL исключает секции только на этапе планирования, неверно.

#### Проверка плана

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM shipment_events
WHERE event_date = DATE '2026-02-15';
```

В плане следует смотреть:

- какие секции реально использовались;
- `Append` и `Merge Append`;
- `Subplans Removed`;
- `loops`;
- секции с отметкой `never executed`;
- фактическое количество строк;
- обращения к буферам.

Секция может присутствовать в плане, но не выполняться из-за pruning во время исполнения.

Поэтому важно анализировать не только текстовый список узлов, но и их фактическую активность.

#### Настройка

В PostgreSQL используется параметр:

```sql
SHOW enable_partition_pruning;
```

Обычно он включён:

```text
on
```

Для учебного сравнения можно временно отключить механизм:

```sql
SET enable_partition_pruning = off;
```

После эксперимента:

```sql
RESET enable_partition_pruning;
```

Отключение pruning в рабочей системе без необходимости может существенно ухудшить производительность.

### Тема 10. Когда partition pruning не срабатывает

Наличие секций не гарантирует их исключения.

Запрос должен содержать условие, позволяющее сопоставить значения с границами секций.

#### Прямое сравнение диапазона

Хороший вариант:

```sql
SELECT *
FROM shipment_events
WHERE event_date >= DATE '2026-03-01'
  AND event_date < DATE '2026-04-01';
```

Условие непосредственно связано с ключом секционирования.

#### Функция над ключом

Для таблицы, секционированной по `event_time`, запрос:

```sql
SELECT *
FROM delivery_events
WHERE event_time::date = DATE '2026-03-15';
```

может затруднить исключение секций, поскольку условие вычисляет выражение над столбцом.

Более предсказуемый вариант:

```sql
SELECT *
FROM delivery_events
WHERE event_time >= TIMESTAMP '2026-03-15 00:00:00'
  AND event_time < TIMESTAMP '2026-03-16 00:00:00';
```

Это не означает, что любые выражения над ключом всегда отключают pruning.

Возможности оптимизатора зависят от выражения, типа данных и реализации СУБД.

Но прямые диапазонные условия обычно проще соотнести с границами секций.

#### Фильтрация не по ключу

Например:

```sql
SELECT *
FROM shipment_events
WHERE shipment_id = 1001;
```

Если таблица секционирована только по `event_date`, PostgreSQL не знает, в каком месяце находится заказ.

Поэтому могут потребоваться обращения ко всем секциям.

Индексы по `shipment_id` внутри секций способны ускорить поиск, но не обязательно исключат сами секции.

Это одна из причин, почему секционирование не всегда улучшает точечные запросы.

#### Чрезмерное число секций

Если таблица содержит тысячи секций, могут увеличиться расходы на:

- планирование;
- управление объектами;
- память;
- открытие отношений;
- блокировки;
- сопровождение индексов;
- изменение схемы.

Даже при эффективном pruning слишком большое количество секций может создавать накладные расходы.

Поэтому секционировать таблицу по каждому отдельному идентификатору обычно неразумно.

### Тема 11. Ограничения секционирования

Ограничения существенно различаются между СУБД.

#### PRIMARY KEY и UNIQUE в PostgreSQL

Для секционированной таблицы PostgreSQL глобальный первичный или уникальный ключ должен включать все столбцы ключа секционирования.

Например:

```sql
CREATE TABLE partitioned_orders (
    order_id BIGINT NOT NULL,
    created_date DATE NOT NULL,
    customer_id BIGINT NOT NULL,
    PRIMARY KEY (order_id, created_date)
)
PARTITION BY RANGE (created_date);
```

Такое определение допустимо.

Но:

```sql
CREATE TABLE invalid_partitioned_orders (
    order_id BIGINT PRIMARY KEY,
    created_date DATE NOT NULL
)
PARTITION BY RANGE (created_date);
```

для PostgreSQL завершится ошибкой.

Причина: первичный ключ не содержит `created_date`.

Однако это не означает, что у каждой секционированной таблицы обязательно должен быть первичный ключ.

Таблицу без `PRIMARY KEY` создать можно.

Ограничение относится к объявлению глобальной уникальности на секционированной таблице.

#### Почему требуется ключ секционирования

Индексы PostgreSQL физически создаются на отдельных секциях.

Если уникальность проверяется только внутри секций, одинаковый `order_id` мог бы существовать в разных месячных секциях.

Включение ключа секционирования в уникальное ограничение обеспечивает необходимое разграничение комбинаций значений.

Но если бизнес-требование звучит как:

> `order_id` должен быть уникален независимо от даты,

составной ключ `(order_id, created_date)` этого требования не обеспечивает.

Нужно изменить модель идентификаторов, организацию данных или использовать отдельный механизм обеспечения глобальной уникальности.

#### Другие ограничения PostgreSQL

Следует учитывать:

- ограничения на выражения в ключах при создании глобальных UNIQUE и PRIMARY KEY;
- требования совместимости структуры секций;
- особенности внешних ключей;
- ограничения операций изменения ключа секционирования;
- ограничения некоторых триггеров;
- особенности `ON CONFLICT`;
- отсутствие обычного глобального B-tree индекса, охватывающего все секции как единое дерево.

#### SQL Server

В SQL Server требования к уникальности зависят от того, является ли индекс выровненным и секционированным.

Для уникального секционированного индекса необходимо учитывать столбец секционирования.

Однако SQL Server поддерживает и невыравненные индексы.

Например, глобальную уникальность по `order_id` иногда можно обеспечивать отдельным непартиционированным уникальным индексом.

Это повышает гибкость, но может ограничивать административные операции, включая быстрое переключение секций.

Поэтому нельзя распространять ограничение PostgreSQL на любой индекс SQL Server.

#### MySQL/InnoDB

В MySQL каждый уникальный ключ секционированной таблицы должен включать все столбцы, используемые в выражении секционирования.

Это относится и к первичному ключу.

Кроме того, пользовательское секционирование InnoDB 8.4 несовместимо с внешними ключами.

Это может оказаться главным ограничивающим фактором для реляционной модели приложения.

#### Oracle

Oracle поддерживает локальные и глобальные индексы для секционированных таблиц.

Поэтому ограничения глобальной уникальности отличаются от PostgreSQL и MySQL.

Но наличие глобальных индексов может усложнять операции обслуживания секций и увеличивать их стоимость.

### Тема 12. Индексы секционированных таблиц

Секционирование и индексирование необходимо проектировать совместно.

#### Индекс на родительской таблице PostgreSQL

```sql
CREATE INDEX idx_shipment_events_shipment
ON shipment_events (shipment_id);
```

PostgreSQL создаёт соответствующие физические индексы на секциях.

Индекс родительской секционированной таблицы является логическим объектом.

Фактические индексные записи находятся в индексах секций.

#### Составной индекс

```sql
CREATE INDEX idx_shipment_events_date_shipment
ON shipment_events (event_date, shipment_id);
```

Такой индекс может помогать запросам:

```sql
SELECT *
FROM shipment_events
WHERE event_date >= DATE '2026-03-01'
  AND event_date < DATE '2026-04-01'
  AND shipment_id = 1003;
```

Но необходимость включать ключ секционирования в каждый обычный неуникальный индекс отсутствует.

Например, индекс только по `shipment_id` может быть полезен внутри выбранной секции.

#### Индексы отдельных секций

Можно создать индекс на конкретной секции:

```sql
CREATE INDEX idx_shipment_events_2026_03_type
ON shipment_events_2026_03 (event_type);
```

Это позволяет адаптировать индексирование к особенностям отдельных периодов.

Но необходимо учитывать, что при появлении новых секций такие индивидуальные индексы не будут автоматически воспроизводиться, если они не заданы через родительский индекс.

#### CREATE INDEX CONCURRENTLY

Создание индекса на большой таблице может быть дорогим.

PostgreSQL поддерживает:

```sql
CREATE INDEX CONCURRENTLY
```

Но непосредственно создавать индекс `CONCURRENTLY` на секционированной родительской таблице обычным способом нельзя.

Для минимизации блокировок можно:

1. Создать родительский индекс с `ON ONLY`.
2. Создать индексы на отдельных секциях с `CONCURRENTLY`.
3. Присоединить эти индексы к родительскому индексу через `ALTER INDEX ... ATTACH PARTITION`.

Такой подход сложнее, но полезен при эксплуатации больших таблиц.

#### Локальные и глобальные индексы

В Oracle существуют специальные механизмы локальных и глобальных индексов.

В SQL Server — выравненные и невыравненные индексы.

В PostgreSQL обычные индексы секционированной таблицы строятся через индексы отдельных секций.

Поэтому выражение «глобальный индекс» нельзя использовать как полностью одинаковую концепцию для всех четырёх СУБД.

### Тема 13. Присоединение существующей таблицы как секции

PostgreSQL позволяет присоединить подготовленную таблицу к секционированной структуре.

Это используется для:

- миграций;
- загрузки исторических данных;
- предварительной проверки данных;
- архивных операций.

#### Создание отдельной таблицы

```sql
CREATE TABLE shipment_events_2026_04
(
    LIKE shipment_events
    INCLUDING DEFAULTS
    INCLUDING CONSTRAINTS
);
```

В данном примере структура копируется из родительской таблицы.

При этом необходимо учитывать, что `LIKE` не копирует автоматически все свойства исходной таблицы во всех возможных вариантах.

Для миграции нужно отдельно проверять индексы, ограничения, идентификаторы и зависимости.

#### Ограничение диапазона

```sql
ALTER TABLE shipment_events_2026_04
ADD CONSTRAINT shipment_events_2026_04_date_chk
CHECK (
    event_date >= DATE '2026-04-01'
    AND event_date < DATE '2026-05-01'
);
```

Теперь в таблице можно хранить строки будущей секции.

#### Присоединение

```sql
ALTER TABLE shipment_events
ATTACH PARTITION shipment_events_2026_04
FOR VALUES FROM ('2026-04-01')
             TO ('2026-05-01');
```

PostgreSQL проверяет совместимость таблицы и границ секции.

#### Почему CHECK важен

Если подходящего проверенного ограничения нет, PostgreSQL может сканировать присоединяемую таблицу, чтобы убедиться, что все строки соответствуют границам.

Во время этой операции удерживаются блокировки.

Заранее созданное и валидное `CHECK`-ограничение может позволить избежать полного сканирования.

Но `NOT VALID` само по себе не является доказательством корректности данных.

Ограничение необходимо проверить:

```sql
ALTER TABLE shipment_events_2026_04
VALIDATE CONSTRAINT shipment_events_2026_04_date_chk;
```

После этого оно может использоваться как доказательство допустимости диапазона.

В приведённом примере CHECK был создан без `NOT VALID`, поэтому PostgreSQL проверяет его при создании. Отдельный `VALIDATE CONSTRAINT` здесь не требуется.

#### Блокировки ATTACH PARTITION

Присоединение секции не является полностью неблокирующей операцией.

В PostgreSQL `ATTACH PARTITION` использует более мягкий режим блокировки родительской таблицы, чем непосредственное `CREATE TABLE ... PARTITION OF`, но также блокирует присоединяемую таблицу.

При наличии DEFAULT-секции могут потребоваться дополнительные проверки и блокировки.

Поэтому операцию следует планировать с учётом активной нагрузки.

### Тема 14. Преобразование существующей таблицы в секционированную

Одна из сложных задач — преобразование большой обычной таблицы в секционированную.

В PostgreSQL нет универсальной простой команды:

```sql
ALTER TABLE existing_table
PARTITION BY RANGE (...);
```

которая автоматически превратила бы произвольную существующую таблицу в декларативно секционированную без дополнительных действий.

#### Общая стратегия миграции

Обычно необходимо:

1. Проанализировать существующую структуру.
2. Определить ключ и стратегию секционирования.
3. Проверить ограничения уникальности.
4. Создать новую секционированную таблицу.
5. Подготовить секции.
6. Перенести данные или присоединить совместимые таблицы.
7. Воссоздать необходимые индексы и ограничения.
8. Проверить данные.
9. Переключить приложение на новую структуру.
10. Организовать создание и удаление секций.

#### Подход с переносом данных

Например, существует:

```sql
CREATE TABLE old_delivery_events (
    event_id BIGINT NOT NULL,
    event_time TIMESTAMP NOT NULL,
    courier_id BIGINT NOT NULL,
    event_type TEXT NOT NULL
);
```

Создаётся новая таблица:

```sql
CREATE TABLE new_delivery_events (
    event_id BIGINT NOT NULL,
    event_time TIMESTAMP NOT NULL,
    courier_id BIGINT NOT NULL,
    event_type TEXT NOT NULL
)
PARTITION BY RANGE (event_time);
```

Затем секции:

```sql
CREATE TABLE new_delivery_events_2026_01
PARTITION OF new_delivery_events
FOR VALUES FROM ('2026-01-01')
             TO ('2026-02-01');
```

```sql
CREATE TABLE new_delivery_events_2026_02
PARTITION OF new_delivery_events
FOR VALUES FROM ('2026-02-01')
             TO ('2026-03-01');
```

После подготовки всех нужных диапазонов выполняется перенос данных.

```sql
INSERT INTO new_delivery_events (
    event_id,
    event_time,
    courier_id,
    event_type
)
SELECT
    event_id,
    event_time,
    courier_id,
    event_type
FROM old_delivery_events;
```

При этом каждая исходная строка должна соответствовать одной из созданных секций либо DEFAULT-секции.

Иначе перенос завершится ошибкой.

#### Миграция под активной нагрузкой

Если приложение продолжает записывать данные в исходную таблицу, простое копирование не гарантирует согласованности.

Между началом копирования и переключением могут появиться новые или изменённые строки.

Для таких случаев требуется стратегия синхронизации.

Возможные подходы:

- ограниченное окно обслуживания с остановкой записи;
- перенос данных партиями и финальная синхронизация;
- использование CDC;
- временная двойная запись при тщательно спроектированной логике;
- другие схемы миграции с контролем конкурентных изменений.

Конкретный способ зависит от допустимого времени простоя, объёма данных и требований к согласованности.

#### Проверка результата

После переноса полезно проверить:

- количество строк;
- контрольные суммы или агрегаты;
- минимальные и максимальные даты;
- распределение по секциям;
- уникальность идентификаторов;
- ограничения целостности;
- планы ключевых запросов.

Пример:

```sql
SELECT
    tableoid::regclass AS partition_name,
    COUNT(*) AS rows_count
FROM new_delivery_events
GROUP BY tableoid
ORDER BY partition_name;
```

Одного сравнения общего количества строк недостаточно для доказательства полной идентичности данных.

### Тема 15. Секционирование и жизненный цикл данных

Одно из главных преимуществ секционирования — управление устаревающими данными.

Предположим, журнал событий хранится 12 месяцев.

Каждый месяц необходимо:

1. Создать будущую секцию.
2. Убедиться, что маршрутизация работает.
3. Проверить полноту данных.
4. Отсоединить устаревшую секцию.
5. При необходимости сохранить архив.
6. Удалить секцию после выполнения правил хранения.

Такой процесс называется rolling window.

#### Пример

Для событий за январь 2026 года:

```sql
ALTER TABLE delivery_events
DETACH PARTITION delivery_events_2026_01;
```

После этого таблицу можно экспортировать и удалить:

```sql
DROP TABLE delivery_events_2026_01;
```

Но в рабочей системе удалять данные следует только после выполнения требований к хранению и резервному копированию.

#### Секционирование и резервное копирование

Секционирование может облегчить отдельные эксплуатационные сценарии.

Например, можно логически отделять архивные данные.

Но стандартное физическое резервное копирование PostgreSQL не превращается автоматически в независимое резервное копирование каждой секции.

Для физического восстановления экземпляра PostgreSQL по-прежнему необходимо учитывать целостность всего кластера данных и WAL.

Логический экспорт отдельных секций возможен, но он не заменяет полноценную стратегию резервного копирования.

#### Секционирование и VACUUM

В PostgreSQL секции являются отдельными таблицами.

Поэтому можно обслуживать их раздельно.

Например:

```sql
VACUUM (ANALYZE) shipment_events_2026_03;
```

Это позволяет сосредоточиться на конкретной части данных.

Но секционирование не устраняет необходимость autovacuum и сбора статистики.

Также большое число секций может увеличить суммарные эксплуатационные расходы.

### Тема 16. Анализ производительности секционирования

Секционирование следует проверять экспериментально.

#### План выполнения

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM shipment_events
WHERE event_date >= DATE '2026-03-01'
  AND event_date < DATE '2026-04-01';
```

Следует определить:

- какие секции были включены в план;
- какие реально исполнялись;
- сработал ли pruning;
- были ли использованы индексы;
- сколько страниц прочитано;
- сколько строк обработано;
- сколько времени заняло выполнение.

#### Сравнение с таблицей без секций

Для объективной оценки необходимо сравнивать не только два отдельных времени выполнения.

Следует учитывать:

- одинаковые данные;
- одинаковые условия фильтрации;
- наличие соответствующих индексов;
- актуальность статистики;
- состояние кеша;
- порядок тестовых запусков;
- стоимость планирования;
- стоимость выполнения;
- количество возвращаемых строк.

Например, секционированная таблица может показать выигрыш при выборе одного месяца из нескольких лет.

Но точечный поиск по `order_id` без даты может работать хуже, если СУБД вынуждена обращаться к индексам множества секций.

#### Слишком много секций

Необходимо соблюдать баланс.

Недостаточно крупные секции могут увеличивать количество объектов базы данных.

Слишком крупные секции могут снижать преимущества локального обслуживания.

Нет универсального оптимального количества секций.

Для одной системы удобны месячные секции.

Для другой — дневные.

Для третьей — квартальные.

Выбор зависит от объёма строк, запросов и правил хранения.

#### Секционирование и параллелизм

Некоторые СУБД могут выполнять операции над разными секциями параллельно.

Однако сам факт разбиения таблицы не гарантирует ускорения за счёт многопоточности.

Параллельное выполнение зависит от:

- реализации СУБД;
- настроек;
- плана;
- доступных ресурсов;
- стоимости запроса.

Также секционирование внутри одного сервера не означает, что ресурсы CPU, памяти и диска разделяются на независимые узлы.

### Тема 17. Когда секционирование применять не следует

Секционирование имеет смысл только при наличии понятной выгоды.

Оно может быть нецелесообразным, если:

- таблица сравнительно небольшая;
- основные запросы уже эффективно используют индексы;
- запросы не фильтруют по ключу секционирования;
- отсутствуют требования к удалению данных целыми диапазонами;
- количество секций будет чрезмерным;
- структура уникальных ограничений несовместима с выбранным ключом;
- стоимость сопровождения превышает ожидаемый выигрыш.

Особенно важно учитывать проектирование первичных ключей.

Например, если приложение предполагает:

```text
order_id — глобально уникальный идентификатор заказа
```

а таблица секционируется по `created_at`, в PostgreSQL нельзя просто создать глобальный `PRIMARY KEY (order_id)` на родительской таблице.

Это может потребовать изменения схемы и связей.

В MySQL/InnoDB дополнительным критическим ограничением становятся внешние ключи.

#### Как принимать решение

Перед внедрением секционирования необходимо ответить:

1. Каковы основные запросы?
2. Есть ли естественный ключ секционирования?
3. Какая доля секций потребуется типичному запросу?
4. Каковы требования к уникальности?
5. Какие индексы нужны?
6. Как создаются будущие секции?
7. Как удаляются старые данные?
8. Как выполняются миграции?
9. Как проверяется partition pruning?
10. Какие дополнительные эксплуатационные расходы возникнут?

Если ответы неизвестны, сначала необходимо исследовать нагрузку и существующие планы выполнения.

## Итоговые выводы

1. **Секционирование разделяет одну логическую таблицу на физические части.** Это позволяет управлять данными по диапазонам, спискам или результатам хеширования.

2. **Секционирование не является заменой индексам.** Индексы и секции решают разные задачи и часто используются совместно.

3. **Основные преимущества связаны с partition pruning и управлением жизненным циклом данных.** Особенно заметен эффект при работе с большими временными таблицами.

4. **Выбор ключа секционирования определяет эффективность всей структуры.** Важно учитывать не только объём данных, но и запросы, уникальность и правила удаления.

5. **PostgreSQL поддерживает современное декларативное секционирование через RANGE, LIST и HASH.** Историческое наследование таблиц остаётся доступным, но обычно не подходит для новых типовых решений.

6. **Секции PostgreSQL являются отдельными физическими таблицами.** Родительская секционированная таблица обеспечивает общий логический интерфейс.

7. **HASH-секционирование не гарантирует идеального распределения и не является шардингом.** Для архивирования временных данных чаще удобнее RANGE.

8. **Partition pruning может выполняться как при планировании, так и во время исполнения запроса.** Это особенно важно для параметризованных запросов PostgreSQL.

9. **Исключение секций не требует обязательного индекса по ключу секционирования.** Оно использует информацию о границах секций.

10. **Ограничения уникальности зависят от СУБД.** В PostgreSQL PRIMARY KEY и UNIQUE родительской секционированной таблицы должны включать ключ секционирования, а SQL Server и Oracle предоставляют другие варианты индексной организации.

11. **MySQL/InnoDB имеет серьёзные ограничения на секционированные таблицы с внешними ключами.** Это необходимо учитывать ещё на этапе логического проектирования.

12. **Присоединение и отсоединение секций требуют контроля блокировок и ограничений.** Подготовленные CHECK-ограничения помогают оптимизировать некоторые операции ATTACH PARTITION.

13. **Преобразование большой существующей таблицы в секционированную требует миграционного сценария.** Необходимо обеспечить перенос данных, целостность и корректное переключение приложения.

14. **Секционирование может упрощать обслуживание, архивирование и удаление больших объёмов данных.** Но оно не заменяет резервное копирование и не устраняет необходимость сопровождения индексов и статистики.

15. **Слишком большое количество секций может ухудшать производительность и сопровождение.** Число секций и их размер должны определяться реальной нагрузкой.

Главный результат занятия — понимание секционирования как архитектурного решения, которое необходимо проектировать одновременно с индексами, ограничениями целостности, характером запросов и жизненным циклом данных.
