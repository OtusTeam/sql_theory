
# Шаблонный поиск, регулярные выражения и оконные функции в SQL

## Превью / аннотация / краткое содержание

Занятие посвящено двум направлениям обработки данных в реляционных СУБД: работе с текстовыми значениями и аналитическим вычислениям с использованием оконных функций.

Первая часть рассматривает поиск по шаблону, регулярные выражения, проверку формата строк и преобразование неструктурированных текстовых данных в значения с предсказуемой структурой.

Вторая часть посвящена оконным функциям: вычислению итогов и накопительных показателей, нумерации и ранжированию строк, сравнению соседних записей, а также управлению границами оконного вычисления.

Основные темы занятия:

- организация данных и выбор способа их представления;
- поиск строк с помощью `LIKE`, `ILIKE` и `SIMILAR TO`;
- использование регулярных выражений;
- проверка и нормализация текстовых данных;
- построение последовательных преобразований в SQL;
- отличие агрегатных вычислений от оконных;
- работа с `OVER`, `PARTITION BY` и `ORDER BY`;
- функции ранжирования и смещения;
- оконные рамки `ROWS`, `RANGE` и `GROUPS`;
- особенности `FIRST_VALUE`, `LAST_VALUE` и накопительных вычислений;
- производительность текстового поиска и оконной аналитики.

Основные примеры приведены для PostgreSQL. Дополнительно рассматриваются различия Microsoft SQL Server, MySQL/InnoDB и Oracle.

## Основные понятия

**Шаблонный поиск (Pattern Matching)** — сопоставление текстового значения с заданным шаблоном.

**LIKE** — SQL-оператор поиска по шаблону с использованием символов `%` и `_`.

**ILIKE** — оператор PostgreSQL для регистронезависимого поиска по шаблону с учётом правил локали.

**SIMILAR TO** — оператор SQL-сопоставления с шаблоном, объединяющий особенности `LIKE` и регулярных выражений.

**Регулярное выражение (Regular Expression, Regex)** — формальное описание множества строк с помощью специальных символов и конструкций.

**Класс символов** — конструкция, задающая допустимый набор символов в определённой позиции строки.

**Квантификатор** — элемент регулярного выражения, определяющий допустимое количество повторений.

**Экранирование** — способ указать, что специальный символ необходимо интерпретировать буквально.

**Валидация** — проверка соответствия данных установленным требованиям.

**Нормализация текста** — приведение текстовых данных к согласованному представлению.

**ETL (Extract, Transform, Load)** — процесс извлечения, преобразования и загрузки данных.

**Агрегатная функция** — функция, вычисляющая итог по набору строк, например `SUM`, `COUNT` или `AVG`.

**Оконная функция (Window Function)** — функция, которая вычисляет значение для каждой строки с использованием связанного набора строк.

**OVER** — SQL-конструкция, определяющая окно вычисления.

**PARTITION BY** — логическое разделение строк на независимые группы внутри оконного вычисления.

**ORDER BY внутри OVER** — порядок строк, используемый оконной функцией.

**Window Partition** — набор строк, принадлежащих одной логической группе окна.

**Window Frame** — подмножество строк раздела окна, используемое функциями, учитывающими рамку.

**ROWS** — режим определения рамки по количеству строк.

**RANGE** — режим определения рамки по значениям выражения сортировки и группам равных значений.

**GROUPS** — режим определения рамки по группам строк с одинаковыми значениями сортировки.

**Peer Group** — группа строк с одинаковыми значениями всех выражений `ORDER BY` внутри окна.

**ROW_NUMBER** — оконная функция последовательной нумерации строк.

**RANK** — оконная функция ранжирования с пропусками номеров после совпадающих значений.

**DENSE_RANK** — оконная функция ранжирования без пропусков номеров.

**LAG** — функция получения значения из предыдущей строки раздела окна.

**LEAD** — функция получения значения из следующей строки раздела окна.

**FIRST_VALUE** — функция получения первого значения в оконной рамке.

**LAST_VALUE** — функция получения последнего значения в оконной рамке.

**Накопительный итог (Running Total)** — сумма значений от начала последовательности до текущей позиции.

**Скользящее среднее (Moving Average)** — среднее значение по перемещающемуся набору последовательных строк.

## Основная часть

### Тема 1. Организация данных в базе и выбор форм представления

Перед обработкой данных необходимо понимать, каким образом они организованы и какие задачи должна решать база данных.

В реляционных СУБД данные обычно распределяются между схемами, таблицами и столбцами.

Например, в PostgreSQL можно организовать структуру приложения с помощью отдельных схем:

```sql
CREATE SCHEMA IF NOT EXISTS sales;
CREATE SCHEMA IF NOT EXISTS integration;
CREATE SCHEMA IF NOT EXISTS archive;
```

Такая организация может отражать функциональное назначение объектов:

- `sales` — основные данные продаж;
- `integration` — данные внешних интеграций;
- `archive` — архивные данные.

Но схема базы данных сама по себе не обеспечивает физическое разделение нагрузки или автоматическое архивирование.

Схемы прежде всего являются пространствами имён для объектов базы данных и позволяют организовывать права доступа.

Физическая организация данных решается отдельно: с помощью партиционирования, отдельных таблиц, табличных пространств, других баз данных и иных механизмов СУБД.

#### Разграничение доступа

В PostgreSQL права можно выдавать на уровне схем и отдельных объектов:

```sql
GRANT USAGE ON SCHEMA sales TO analyst_role;

GRANT SELECT ON ALL TABLES
IN SCHEMA sales TO analyst_role;
```

Здесь предполагается, что роль `analyst_role` уже существует.

Право `USAGE` позволяет обращаться к объектам схемы при наличии необходимых прав на сами объекты.

Отдельная схема не означает, что все находящиеся в ней таблицы автоматически становятся доступны определённой роли.

#### Архивные и временные данные

Текущие и архивные данные могут храниться в разных таблицах или партициях.

Однако перенос старых строк в другую схему не гарантирует ускорения запросов.

Производительность зависит от:

- количества обрабатываемых строк;
- структуры индексов;
- условий фильтрации;
- физической организации таблиц;
- статистики оптимизатора;
- фактических планов выполнения.

Для больших таблиц с временными данными может использоваться партиционирование по дате.

Временные таблицы применяются для хранения промежуточных результатов и имеют особенности жизненного цикла, зависящие от СУБД.

#### JSON и JSONB как формы хранения данных

Данные не всегда поступают в полностью структурированном виде.

Например, внешняя система может передать документ:

```json
{
  "customer_id": 101,
  "name": "Анна",
  "contacts": {
    "email": "anna@example.com",
    "phone": "+7 (999) 123-45-67"
  }
}
```

В PostgreSQL такой документ может храниться в `json` или `jsonb`.

```sql
CREATE TABLE integration.raw_customers (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload JSONB NOT NULL
);
```

Тип `json` хранит исходное текстовое представление JSON, а `jsonb` — разобранное бинарное представление.

`jsonb` позволяет использовать дополнительные операторы и GIN-индексы для определённых видов поиска.

При этом `jsonb` не гарантирует более высокой производительности во всех сценариях.

Извлечение вложенных значений по-прежнему имеет вычислительную стоимость.

Пример:

```sql
SELECT
    payload ->> 'name' AS customer_name,
    payload #>> '{contacts,email}' AS email
FROM integration.raw_customers;
```

Такая обработка позволяет преобразовывать внешние документы в привычную табличную форму.

В PostgreSQL 17 и новее для этого также доступна `JSON_TABLE`.

Работа с JSON подробно рассматривалась на предыдущем занятии. Далее сосредоточимся на текстовых значениях, которые могут поступать как из обычных столбцов, так и из JSON-документов.

### Тема 2. Шаблонный поиск как базовый механизм работы со строками

Шаблонный поиск позволяет отбирать строки, соответствующие определённой структуре.

Для простых условий используется оператор `LIKE`.

Его стандартный синтаксис:

```sql
expression LIKE pattern
```

В шаблоне используются два основных специальных символа:

| Символ | Значение |
|---|---|
| `%` | Любая последовательность из нуля или более символов |
| `_` | Ровно один символ |

#### Поиск по началу строки

```sql
SELECT *
FROM customers
WHERE customer_name LIKE 'Ан%';
```

Запрос ищет значения, начинающиеся с `Ан`.

Например:

- Анна;
- Антон;
- Анжелика.

#### Поиск по окончанию строки

```sql
SELECT *
FROM customers
WHERE customer_name LIKE '%ова';
```

Запрос ищет строки, заканчивающиеся на `ова`.

#### Поиск подстроки

```sql
SELECT *
FROM customers
WHERE customer_name LIKE '%иван%';
```

Шаблон допускает произвольный текст до и после последовательности `иван`.

#### Поиск с одним произвольным символом

```sql
SELECT *
FROM customers
WHERE customer_code LIKE 'A_15';
```

Подходящие значения:

```text
AB15
AC15
A115
```

Неподходящие:

```text
A15
ABX15
```

#### Чувствительность к регистру

Поведение `LIKE` зависит от СУБД и правил сравнения строк.

В PostgreSQL обычный `LIKE` с распространёнными детерминированными правилами сравнения чувствителен к регистру.

Но нельзя утверждать, что `LIKE` во всех реляционных СУБД всегда чувствителен к регистру.

Например, в SQL Server поведение во многом определяется collation столбца или выражения.

В MySQL результат также зависит от collation.

Поэтому один и тот же запрос с `LIKE` может давать разные результаты в различных СУБД.

#### Экранирование специальных символов

Иногда необходимо найти не шаблон, а буквальный символ `%` или `_`.

Например, строку:

```text
discount_10%
```

В PostgreSQL:

```sql
SELECT *
FROM products
WHERE product_code LIKE '%!_10!%' ESCAPE '!';
```

Здесь `!` используется как символ экранирования.

Последовательности `!_` и `!%` означают буквальные символы `_` и `%`.

Похожий синтаксис поддерживается в ряде других СУБД, но необходимо учитывать их особенности.

Для пользовательского поиска символы шаблона нужно экранировать отдельно от обычной параметризации SQL.

Параметризованный запрос защищает от SQL-инъекции, но не делает символы `%` и `_` буквальными автоматически.

### Тема 3. LIKE, ILIKE и SIMILAR TO

В PostgreSQL существует несколько способов сопоставления строк.

#### LIKE

Подходит для простых шаблонов.

```sql
SELECT
    'PostgreSQL' LIKE 'Post%' AS result;
```

Результат:

```text
true
```

#### ILIKE

`ILIKE` — расширение PostgreSQL для поиска без учёта регистра в соответствии с действующими правилами локали.

```sql
SELECT
    'PostgreSQL' ILIKE 'post%' AS result;
```

Результат:

```text
true
```

`ILIKE` не является переносимым оператором стандартного SQL.

Для кросс-платформенных запросов иногда используют нормализацию регистра:

```sql
SELECT *
FROM customers
WHERE LOWER(customer_name) LIKE 'ан%';
```

Но это не всегда полностью эквивалентно использованию регистронезависимой collation.

Правила преобразования регистра, особенности Unicode и производительность могут различаться.

#### SIMILAR TO

PostgreSQL поддерживает оператор `SIMILAR TO`.

Он использует синтаксис, объединяющий свойства SQL-шаблонов и регулярных выражений.

Пример:

```sql
SELECT
    'AB123' SIMILAR TO '(AB|CD)[0-9]{3}' AS result;
```

Результат:

```text
true
```

Шаблон означает:

- строка начинается с `AB` или `CD`;
- после этого идут ровно три цифры.

`SIMILAR TO`, как и `LIKE`, сопоставляет шаблон со всей строкой.

В отличие от него многие операции регулярных выражений по умолчанию ищут совпадение в любой части строки.

`SIMILAR TO` не следует рассматривать как обязательную промежуточную ступень между `LIKE` и регулярными выражениями.

Это отдельный механизм с собственным синтаксисом и ограничениями.

#### Сравнение

| Возможность | LIKE | ILIKE | SIMILAR TO |
|---|---|---|---|
| `%` и `_` | Да | Да | Да |
| Поиск без учёта регистра | Зависит от collation | Да, в PostgreSQL | Зависит от используемых правил |
| Альтернативы через `|` | Нет | Нет | Да |
| Классы символов | Нет | Нет | Да |
| Квантификаторы | Нет | Нет | Да |
| Стандартный SQL | Да | Нет | Да |
| Переносимость между СУБД | Относительно высокая | Низкая | Требует проверки поддержки |

#### Производительность LIKE

Поиск по префиксу:

```sql
WHERE customer_name LIKE 'Ан%'
```

может использовать B-tree индекс при подходящих условиях.

Но использование индекса зависит от collation, операторного класса и конкретной СУБД.

В PostgreSQL при некоторых правилах сравнения применяют индекс с `text_pattern_ops`.

```sql
CREATE INDEX idx_customers_name_pattern
ON customers (customer_name text_pattern_ops);
```

Для поиска вида:

```sql
WHERE customer_name LIKE '%ан%'
```

обычный B-tree индекс зачастую не помогает, поскольку шаблон начинается с произвольной последовательности символов.

В PostgreSQL для таких запросов можно использовать расширение `pg_trgm`.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

Пример индекса:

```sql
CREATE INDEX idx_customers_name_trgm
ON customers
USING GIN (customer_name gin_trgm_ops);
```

Он способен ускорять многие запросы с `LIKE`, `ILIKE` и регулярными выражениями.

Однако эффективность зависит от структуры шаблона и возможности выделить из него полезные триграммы.

Нельзя утверждать, что `LIKE` всегда быстрее регулярных выражений или что любой `LIKE` автоматически использует индекс.

### Тема 4. Регулярные выражения как инструмент поиска и преобразования данных

Регулярные выражения используются для описания сложных текстовых шаблонов.

Они применяются при:

- поиске строк;
- проверке формата;
- очистке данных;
- извлечении фрагментов;
- замене подстрок;
- разбиении строк;
- предварительной подготовке данных к загрузке.

В PostgreSQL регулярные выражения поддерживаются специальными операторами и функциями.

#### Операторы PostgreSQL

| Оператор | Назначение |
|---|---|
| `~` | Совпадение с регулярным выражением с учётом регистра |
| `~*` | Совпадение без учёта регистра |
| `!~` | Отсутствие совпадения с учётом регистра |
| `!~*` | Отсутствие совпадения без учёта регистра |

Пример:

```sql
SELECT
    'Order-123' ~ '[0-9]+' AS contains_digits;
```

Результат:

```text
true
```

Здесь регулярное выражение ищет цифровую последовательность в любой части строки.

Чтобы проверить всю строку, используются якоря:

```sql
SELECT
    'Order-123' ~ '^Order-[0-9]+$' AS valid_code;
```

Результат:

```text
true
```

#### Основные элементы синтаксиса

| Конструкция | Назначение |
|---|---|
| `.` | Один символ, за исключением особенностей режима обработки переводов строк |
| `*` | Ноль или более повторений |
| `+` | Одно или более повторений |
| `?` | Ноль или одно повторение |
| `{n}` | Ровно n повторений |
| `{n,m}` | От n до m повторений |
| `[abc]` | Один символ из набора |
| `[0-9]` | Одна цифра из диапазона |
| `[^0-9]` | Один символ, не являющийся цифрой из диапазона |
| `^` | Начало строки в обычном режиме |
| `$` | Конец строки в обычном режиме |
| `(abc)` | Группировка |
| `a|b` | Альтернатива |

Различные движки регулярных выражений могут по-разному поддерживать расширенные конструкции, Unicode-классы, обратные ссылки и режимы сопоставления.

Поэтому синтаксис регулярных выражений не является полностью переносимым между СУБД.

#### Пример проверки кода

Пусть идентификатор должен содержать две заглавные латинские буквы и четыре цифры.

```sql
SELECT
    'AB1234' ~ '^[A-Z]{2}[0-9]{4}$' AS valid_code;
```

Результат:

```text
true
```

А строка:

```text
AB12345
```

не соответствует этому шаблону, поскольку содержит пять цифр.

#### Экранирование

Метасимволы регулярных выражений необходимо экранировать, если они должны восприниматься буквально.

Например, точка означает произвольный символ.

```sql
SELECT 'fileXtxt' ~ 'file.txt';
```

Результат:

```text
true
```

Для поиска буквальной точки:

```sql
SELECT 'file.txt' ~ 'file[.]txt';
```

Класс `[.]` содержит именно символ точки.

Такой способ также удобен тем, что не требует учитывать правила интерпретации обратной косой черты в SQL-строках.

Важно различать два уровня экранирования:

1. Экранирование SQL-строкового литерала.
2. Экранирование метасимволов регулярного выражения.

В PostgreSQL обычные строковые литералы при стандартном `standard_conforming_strings = on` не интерпретируют обратную косую черту как специальную SQL-последовательность.

Для литералов `E'...'` правила другие.

#### Проверка формата не равна проверке бизнес-правил

Например:

```sql
SELECT
    '2026-99-99' ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$';
```

Результат:

```text
true
```

Строка соответствует формату `YYYY-MM-DD`, но не является корректной календарной датой.

Регулярное выражение проверяет структуру, а полноценная валидация должна учитывать смысл данных.

### Тема 5. Валидация и нормализация строковых данных

Данные из внешних систем и пользовательского ввода часто имеют неоднородное представление.

Например, телефонный номер может выглядеть следующим образом:

```text
+7 (999) 123-45-67
8 999 123 45 67
79991234567
```

Хотя записи могут относиться к одному номеру, текстовые значения различаются.

Для корректного сравнения, поиска и агрегации данные необходимо нормализовать.

#### REGEXP_REPLACE

В PostgreSQL функция `regexp_replace` заменяет фрагменты, соответствующие регулярному выражению.

```sql
SELECT regexp_replace(
    '+7 (999) 123-45-67',
    '[^0-9]',
    '',
    'g'
);
```

Результат:

```text
79991234567
```

Аргумент `'g'` означает глобальную замену всех найденных совпадений.

Без него в этой форме вызова заменяется только первое совпадение.

#### Нормализация телефонных номеров

Удаление нецифровых символов является только первым этапом.

Для корректной нормализации номера необходимо учитывать:

- код страны;
- национальные правила нумерации;
- допустимую длину;
- добавочные номера;
- международный формат;
- возможную неоднозначность записи.

Поэтому простое удаление символов не следует считать полноценной проверкой телефонного номера.

Для международной нормализации часто используется формат E.164 и специализированные библиотеки.

В SQL можно выполнять предварительную очистку, а более сложную проверку реализовать в приложении или отдельном сервисе.

#### Проверка адреса электронной почты

Пример простой проверки:

```sql
SELECT
    'anna@example.com' ~
    '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+[.][A-Za-z]{2,}$'
    AS email_format_valid;
```

Такой шаблон может использоваться для предварительной проверки наиболее распространённых адресов.

Но он не реализует весь синтаксис допустимых email-адресов и может как отвергать корректные, так и принимать нежелательные значения.

Кроме того, корректный синтаксис адреса не гарантирует:

- существование домена;
- наличие почтового ящика;
- возможность доставки сообщения;
- принадлежность адреса пользователю.

Если требуется подтвердить доступ пользователя к почте, необходимо использовать процедуру подтверждения адреса.

#### Извлечение текстовых фрагментов

В PostgreSQL для получения фрагмента, соответствующего регулярному выражению, можно использовать `substring`.

```sql
SELECT substring(
    'Заказ ORD-12345 оформлен',
    'ORD-[0-9]+'
);
```

Результат:

```text
ORD-12345
```

#### Разбиение строки

Для разбиения текста по регулярному выражению используется `regexp_split_to_table`.

```sql
SELECT value
FROM regexp_split_to_table(
    'SQL, PostgreSQL; MySQL',
    '[,;][[:space:]]*'
) AS t(value);
```

Результат:

```text
SQL
 PostgreSQL
 MySQL
```

Фактически ведущий пробел перед `PostgreSQL` после разделителя удаляется, поскольку шаблон учитывает пробельные символы.

Строковое представление результата зависит от SQL-клиента, но значения будут:

```text
SQL
PostgreSQL
MySQL
```

#### Разбиение ФИО

Фамилию, имя и отчество иногда пытаются выделять с помощью пробелов или регулярных выражений.

Однако такое преобразование не всегда корректно.

Например, существуют:

- составные фамилии;
- двойные имена;
- имена без отчества;
- национальные особенности порядка имён;
- дополнительные части имени.

Поэтому автоматическое разбиение ФИО следует выполнять только тогда, когда формат входных данных строго определён.

Иначе предпочтительнее собирать структурированные компоненты имени отдельно.

### Тема 6. Многоэтапная трансформация данных средствами SQL

Очистку данных удобно выполнять последовательно.

Пусть имеются исходные записи:

```sql
CREATE TEMP TABLE raw_contacts (
    id INTEGER PRIMARY KEY,
    full_name TEXT,
    phone TEXT,
    email TEXT
);
```

Добавим данные:

```sql
INSERT INTO raw_contacts (
    id,
    full_name,
    phone,
    email
)
VALUES
(1, '  Анна Иванова  ', '+7 (999) 123-45-67', 'ANNA@EXAMPLE.COM'),
(2, 'Пётр Сидоров', '8 999 555 66 77', 'petr@example.com'),
(3, 'Мария', 'invalid', 'not-an-email');
```

Необходимо:

1. Удалить лишние пробелы.
2. Привести email к нижнему регистру.
3. Удалить форматирующие символы из телефона.
4. Проверить формат email.
5. Сформировать структурированный результат.

Для этого используем CTE.

```sql
WITH cleaned AS (
    SELECT
        id,
        btrim(full_name) AS full_name,
        regexp_replace(
            phone,
            '[^0-9]',
            '',
            'g'
        ) AS phone_digits,
        lower(btrim(email)) AS email
    FROM raw_contacts
),
validated AS (
    SELECT
        id,
        full_name,
        phone_digits,
        email,
        email ~
            '^[a-z0-9._%+-]+@[a-z0-9.-]+[.][a-z]{2,}$'
            AS email_format_valid,
        phone_digits ~ '^[0-9]{11}$'
            AS phone_length_valid
    FROM cleaned
)
SELECT *
FROM validated
ORDER BY id;
```

В результате мы получаем отдельные признаки проверки.

Это лучше, чем незаметно заменять некорректные данные на произвольные значения.

Важно учитывать, что проверка длины телефона ещё не подтверждает его действительность.

А преобразование email к нижнему регистру не всегда является строго эквивалентным преобразованием адреса по всем стандартным правилам: регистр локальной части адреса теоретически может иметь значение.

В прикладных системах политика нормализации должна быть определена явно.

#### Что делать с невалидными строками

В процессе загрузки данных полезно разделять:

- корректные записи;
- записи, требующие исправления;
- записи, которые нельзя обработать автоматически.

Это позволяет не терять исходную информацию и объяснять причины отклонения записей.

Для больших ETL-процессов можно использовать промежуточные таблицы и отдельные журналы ошибок.

#### Отличия СУБД

| Возможность | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| Простые шаблоны | `LIKE`, `ILIKE` | `LIKE` | `LIKE` | `LIKE` |
| Регулярные выражения | `~`, `~*`, `regexp_*` | `REGEXP_*` с SQL Server 2025 | `REGEXP_LIKE`, `REGEXP_REPLACE` и другие | `REGEXP_LIKE`, `REGEXP_REPLACE` и другие |
| Замена подстроки | `replace` | `REPLACE` | `REPLACE` | `REPLACE` |
| Нормализация регистра | `lower`, `upper` | `LOWER`, `UPPER` | `LOWER`, `UPPER` | `LOWER`, `UPPER` |
| Разбиение строки | `regexp_split_to_table`, `string_to_array` | `STRING_SPLIT`, функции regex в новых версиях | `SUBSTRING_INDEX` и другие способы | `REGEXP_SUBSTR` и другие способы |

В SQL Server 2022 и более ранних версиях нет встроенного набора регулярных функций, сопоставимого с PostgreSQL.

SQL Server 2025 расширил эту функциональность. Доступность отдельных возможностей зависит от версии, совместимости базы и используемого продукта Microsoft. В частности, `REGEXP_LIKE` в SQL Server 2025 требует уровня совместимости 170.

Нельзя автоматически переносить регулярное выражение из PostgreSQL в SQL Server, MySQL или Oracle без проверки поддерживаемого синтаксиса.

### Тема 7. Оконные функции как аналитический механизм без сворачивания строк

Агрегатные функции позволяют получить итог по набору строк.

Например:

```sql
SELECT
    department_id,
    SUM(salary) AS total_salary
FROM employees
GROUP BY department_id;
```

Результат содержит одну строку для каждого отдела.

Исходные сотрудники больше не представлены отдельными строками.

Оконные функции работают иначе.

```sql
SELECT
    employee_id,
    department_id,
    salary,
    SUM(salary) OVER (
        PARTITION BY department_id
    ) AS department_total
FROM employees;
```

Запрос сохраняет отдельные строки сотрудников и добавляет сумму зарплат по каждому отделу.

#### Пример данных

Создадим учебную таблицу:

```sql
CREATE TEMP TABLE employees (
    employee_id INTEGER PRIMARY KEY,
    department_id INTEGER NOT NULL,
    employee_name VARCHAR(100) NOT NULL,
    salary NUMERIC(12, 2) NOT NULL,
    hire_date DATE NOT NULL
);
```

Добавим сотрудников:

```sql
INSERT INTO employees (
    employee_id,
    department_id,
    employee_name,
    salary,
    hire_date
)
VALUES
(1, 10, 'Анна',   100000, '2024-01-10'),
(2, 10, 'Борис',  120000, '2024-02-15'),
(3, 10, 'Вера',   120000, '2024-03-20'),
(4, 20, 'Глеб',    90000, '2024-01-05'),
(5, 20, 'Дарья',  110000, '2024-04-12'),
(6, 20, 'Елена',  130000, '2024-05-17');
```

#### Агрегатная функция

```sql
SELECT
    department_id,
    SUM(salary) AS total_salary
FROM employees
GROUP BY department_id
ORDER BY department_id;
```

Результат:

| department_id | total_salary |
|---|---:|
| 10 | 340000 |
| 20 | 330000 |

#### Оконная функция

```sql
SELECT
    employee_id,
    department_id,
    employee_name,
    salary,
    SUM(salary) OVER (
        PARTITION BY department_id
    ) AS total_salary
FROM employees
ORDER BY department_id, employee_id;
```

Результат:

| employee_id | department_id | employee_name | salary | total_salary |
|---|---|---|---:|---:|
| 1 | 10 | Анна | 100000 | 340000 |
| 2 | 10 | Борис | 120000 | 340000 |
| 3 | 10 | Вера | 120000 | 340000 |
| 4 | 20 | Глеб | 90000 | 330000 |
| 5 | 20 | Дарья | 110000 | 330000 |
| 6 | 20 | Елена | 130000 | 330000 |

Разница принципиальная:

- `GROUP BY` формирует групповой результат;
- `OVER (PARTITION BY ...)` выполняет вычисление по группам, сохраняя детализацию строк.

#### Агрегаты как оконные функции

С `OVER` могут использоваться многие агрегатные функции:

```sql
COUNT(*) OVER (...)
SUM(value) OVER (...)
AVG(value) OVER (...)
MIN(value) OVER (...)
MAX(value) OVER (...)
```

Например:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    AVG(salary) OVER (
        PARTITION BY department_id
    ) AS department_avg
FROM employees
ORDER BY department_id, employee_id;
```

#### Процент от общего итога

```sql
SELECT
    employee_id,
    department_id,
    salary,
    ROUND(
        salary * 100.0 /
        SUM(salary) OVER (
            PARTITION BY department_id
        ),
        2
    ) AS salary_share_percent
FROM employees;
```

Такой запрос показывает долю зарплаты сотрудника в фонде оплаты труда отдела.

Если знаменатель может быть равен нулю, нужно предусмотреть защиту, например через `NULLIF`.

### Тема 8. PARTITION BY, ORDER BY и виды оконных функций

Базовая конструкция оконной функции выглядит следующим образом:

```sql
function_name(...) OVER (
    PARTITION BY ...
    ORDER BY ...
)
```

Не все части обязательны для каждой функции.

Например:

```sql
SELECT
    employee_id,
    salary,
    AVG(salary) OVER () AS company_avg_salary
FROM employees;
```

`OVER ()` означает одно окно, включающее все строки результата, доступные на этапе оконных вычислений.

#### PARTITION BY

`PARTITION BY` разделяет строки на независимые логические группы.

```sql
SELECT
    employee_id,
    department_id,
    salary,
    COUNT(*) OVER (
        PARTITION BY department_id
    ) AS department_employee_count
FROM employees;
```

Каждый сотрудник получает количество сотрудников своего отдела.

Это логическое разделение не следует путать с физическим партиционированием таблиц.

`PARTITION BY` в оконной функции не создаёт физических партиций хранения.

#### ORDER BY внутри окна

`ORDER BY` определяет последовательность строк для оконных вычислений.

Например:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    ROW_NUMBER() OVER (
        PARTITION BY department_id
        ORDER BY salary DESC, employee_id
    ) AS salary_position
FROM employees;
```

Нумерация начинается заново для каждого отдела.

Добавление `employee_id` обеспечивает однозначный порядок среди сотрудников с одинаковой зарплатой.

Важный момент:

**`ORDER BY` внутри `OVER` не гарантирует порядок строк итогового результата.**

Если итоговая сортировка важна, требуется внешний `ORDER BY`.

```sql
SELECT
    employee_id,
    department_id,
    salary,
    ROW_NUMBER() OVER (
        PARTITION BY department_id
        ORDER BY salary DESC, employee_id
    ) AS salary_position
FROM employees
ORDER BY department_id, salary_position;
```

#### Функции ранжирования

Основные функции:

- `ROW_NUMBER`;
- `RANK`;
- `DENSE_RANK`;
- `NTILE`.

Сравним первые три:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    ROW_NUMBER() OVER (
        PARTITION BY department_id
        ORDER BY salary DESC
    ) AS row_num,
    RANK() OVER (
        PARTITION BY department_id
        ORDER BY salary DESC
    ) AS salary_rank,
    DENSE_RANK() OVER (
        PARTITION BY department_id
        ORDER BY salary DESC
    ) AS dense_salary_rank
FROM employees
WHERE department_id = 10
ORDER BY salary DESC, employee_id;
```

Результат:

| employee_id | salary | row_num | salary_rank | dense_salary_rank |
|---|---:|---:|---:|---:|
| 2 | 120000 | 1 | 1 | 1 |
| 3 | 120000 | 2 | 1 | 1 |
| 1 | 100000 | 3 | 3 | 2 |

Различия:

**ROW_NUMBER** присваивает уникальный порядковый номер каждой строке.

**RANK** присваивает одинаковый ранг строкам с равными значениями сортировки, но оставляет пропуски.

**DENSE_RANK** присваивает одинаковый ранг равным значениям без пропусков.

Если `ORDER BY` не определяет уникальный порядок, выбор строки с конкретным `ROW_NUMBER` среди равных значений может быть недетерминированным.

#### Функции смещения

`LAG` получает значение из предыдущей строки.

`LEAD` — из следующей.

Пример:

```sql
SELECT
    employee_id,
    department_id,
    hire_date,
    salary,
    LAG(salary) OVER (
        PARTITION BY department_id
        ORDER BY hire_date, employee_id
    ) AS previous_salary,
    LEAD(salary) OVER (
        PARTITION BY department_id
        ORDER BY hire_date, employee_id
    ) AS next_salary
FROM employees
ORDER BY department_id, hire_date, employee_id;
```

Эти функции позволяют анализировать последовательность без самостоятельного соединения таблицы с самой собой.

При этом `LAG` и `LEAD` работают с предыдущей и следующей строкой в заданном порядке, а не автоматически с предыдущей календарной датой.

Если в данных пропущены даты, функции не создают отсутствующие строки.

#### Изменение относительно предыдущего значения

```sql
WITH ordered_employees AS (
    SELECT
        employee_id,
        department_id,
        hire_date,
        salary,
        LAG(salary) OVER (
            PARTITION BY department_id
            ORDER BY hire_date, employee_id
        ) AS previous_salary
    FROM employees
)
SELECT
    employee_id,
    department_id,
    hire_date,
    salary,
    previous_salary,
    salary - previous_salary AS salary_difference
FROM ordered_employees
ORDER BY department_id, hire_date, employee_id;
```

Для первой строки раздела окна предыдущее значение отсутствует, поэтому `previous_salary` будет `NULL`.

#### Именованные окна

Если несколько функций используют одинаковые параметры окна, можно определить именованное окно.

Пример PostgreSQL:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    ROW_NUMBER() OVER w AS row_num,
    RANK() OVER w AS salary_rank,
    DENSE_RANK() OVER w AS dense_salary_rank
FROM employees
WINDOW w AS (
    PARTITION BY department_id
    ORDER BY salary DESC
);
```

Именованные окна позволяют сократить повторение SQL.

Поддержка и отдельные ограничения синтаксиса `WINDOW` различаются между СУБД.

### Тема 9. Window Frame как механизм ограничения набора строк

`PARTITION BY` определяет раздел окна.

`ORDER BY` определяет порядок внутри раздела.

`FRAME` определяет, какая часть раздела используется конкретной функцией, если эта функция учитывает рамку.

Важно: не каждая оконная функция использует frame.

Например, `ROW_NUMBER`, `RANK` и `LAG` не ограничивают свою логику стандартной рамкой так, как это делают оконные агрегаты и `FIRST_VALUE`/`LAST_VALUE`.

#### ROWS

Режим `ROWS` определяет рамку по количеству строк относительно текущей строки.

Например:

```sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
```

Означает:

- две предыдущие строки;
- текущая строка.

Если предыдущих строк меньше двух, рамка содержит только существующие строки.

#### Накопительная сумма

```sql
SELECT
    employee_id,
    department_id,
    hire_date,
    salary,
    SUM(salary) OVER (
        PARTITION BY department_id
        ORDER BY hire_date, employee_id
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND CURRENT ROW
    ) AS running_total
FROM employees
ORDER BY department_id, hire_date, employee_id;
```

`UNBOUNDED PRECEDING` означает начало раздела окна.

`CURRENT ROW` означает текущую строку.

Таким образом, сумма накапливается по мере продвижения по разделу.

#### Скользящее среднее

```sql
SELECT
    employee_id,
    department_id,
    hire_date,
    salary,
    AVG(salary) OVER (
        PARTITION BY department_id
        ORDER BY hire_date, employee_id
        ROWS BETWEEN 2 PRECEDING
                 AND CURRENT ROW
    ) AS moving_avg
FROM employees
ORDER BY department_id, hire_date, employee_id;
```

Здесь используется текущая строка и не более двух предшествующих.

Для первых строк раздела среднее рассчитывается по меньшему количеству строк.

Такое окно удобно для последовательных наблюдений.

Но если записи относятся к датам с пропусками, это среднее по трём записям, а не обязательно по трём календарным дням.

#### RANGE

`RANGE` использует значения выражения сортировки, а не фиксированное число строк.

Например, в PostgreSQL:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    COUNT(*) OVER (
        PARTITION BY department_id
        ORDER BY salary
        RANGE BETWEEN 10000 PRECEDING
                  AND CURRENT ROW
    ) AS employees_in_salary_range
FROM employees
ORDER BY department_id, salary, employee_id;
```

Для каждого сотрудника подсчитываются строки в разделе, у которых зарплата находится в диапазоне от текущей зарплаты минус 10 000 до текущей зарплаты включительно.

Если несколько сотрудников имеют одинаковую зарплату, все они относятся к одной peer group в данном окне.

Синтаксис смещений `RANGE` поддерживается не всеми СУБД одинаково.

Например, SQL Server не поддерживает произвольное числовое смещение `RANGE n PRECEDING` в таком виде.

В MySQL существуют дополнительные ограничения на типы значений и выражения сортировки.

#### GROUPS

`GROUPS` определяет рамку по группам строк с одинаковыми значениями сортировки.

Например:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    COUNT(*) OVER (
        PARTITION BY department_id
        ORDER BY salary
        GROUPS BETWEEN 1 PRECEDING
                   AND CURRENT ROW
    ) AS employees_in_groups
FROM employees
ORDER BY department_id, salary, employee_id;
```

В PostgreSQL это означает подсчёт строк:

- из текущей группы равных зарплат;
- из непосредственно предыдущей группы отличающихся значений зарплат.

Отличие от `ROWS` заключается в том, что одна группа может содержать несколько строк.

Отличие от `RANGE` заключается в том, что смещение измеряется количеством групп, а не разницей числовых значений.

#### Поддержка рамок в четырёх СУБД

| Режим | PostgreSQL | SQL Server | MySQL 8.4 | Oracle |
|---|---|---|---|---|
| ROWS | Да | Да | Да | Да |
| RANGE | Да | Да, с ограничениями | Да, с ограничениями | Да |
| GROUPS | Да | Нет | Нет | Да |
| Числовые смещения для RANGE | Да, с ограничениями по типу и сортировке | Нет | Да, с ограничениями | Да, с ограничениями |

В MySQL 8.4 конструкция `GROUPS` распознаётся парсером, но её выполнение не поддерживается.

SQL Server поддерживает `ROWS` и ограниченную форму `RANGE`, но не `GROUPS`.

Поэтому перенос сложных оконных рамок между СУБД требует адаптации.

#### Граничные элементы

Для описания frame используются:

| Конструкция | Значение |
|---|---|
| `UNBOUNDED PRECEDING` | Начало раздела |
| `n PRECEDING` | n строк, групп или единиц диапазона перед текущей позицией |
| `CURRENT ROW` | Текущая строка либо группа равных значений в зависимости от режима |
| `n FOLLOWING` | n строк, групп или единиц диапазона после текущей позиции |
| `UNBOUNDED FOLLOWING` | Конец раздела |

Смысл `n PRECEDING` и `n FOLLOWING` зависит от того, используется `ROWS`, `RANGE` или `GROUPS`.

### Тема 10. Поведение оконных рамок по умолчанию и LAST_VALUE

Одна из распространённых ошибок при использовании оконных функций — предположение, что окно автоматически включает весь раздел.

Это не всегда так.

Если для оконной функции не указан `ORDER BY`, рамка для функций, учитывающих её, обычно охватывает весь раздел.

Если `ORDER BY` указан, а рамка не задана, в PostgreSQL и других рассматриваемых СУБД для соответствующих функций типичен стандартный вариант:

```sql
RANGE BETWEEN UNBOUNDED PRECEDING
          AND CURRENT ROW
```

При этом `CURRENT ROW` в режиме `RANGE` включает всю peer group — строки с такими же значениями сортировки.

Из-за этого результаты некоторых оконных функций оказываются неожиданными.

#### LAST_VALUE

`LAST_VALUE` возвращает последнее значение **в текущей оконной рамке**, а не обязательно в полном разделе.

Рассмотрим пример:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    LAST_VALUE(salary) OVER (
        PARTITION BY department_id
        ORDER BY salary
    ) AS last_salary
FROM employees
WHERE department_id = 10
ORDER BY salary, employee_id;
```

При сортировке по возрастанию зарплаты рамка по умолчанию заканчивается текущей peer group.

Поэтому `LAST_VALUE(salary)` в данном случае фактически возвращает зарплату текущей группы равных значений.

Результат:

| employee_id | salary | last_salary |
|---|---:|---:|
| 1 | 100000 | 100000 |
| 2 | 120000 | 120000 |
| 3 | 120000 | 120000 |

Если ожидалось получить максимальную зарплату отдела в каждой строке, такой запрос не решает задачу так, как предполагалось.

#### Явное расширение рамки

Чтобы `LAST_VALUE` использовала весь раздел, укажем границы явно:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    LAST_VALUE(salary) OVER (
        PARTITION BY department_id
        ORDER BY salary, employee_id
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND UNBOUNDED FOLLOWING
    ) AS last_salary
FROM employees
WHERE department_id = 10
ORDER BY salary, employee_id;
```

Результат:

| employee_id | salary | last_salary |
|---|---:|---:|
| 1 | 100000 | 120000 |
| 2 | 120000 | 120000 |
| 3 | 120000 | 120000 |

Теперь рамка включает весь раздел.

Сортировка внутри окна позволяет определить, какая строка считается последней.

Для воспроизводимого результата при равных значениях используется дополнительный критерий `employee_id`.

#### FIRST_VALUE

Аналогично работает `FIRST_VALUE`.

```sql
SELECT
    employee_id,
    department_id,
    salary,
    FIRST_VALUE(salary) OVER (
        PARTITION BY department_id
        ORDER BY salary, employee_id
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND UNBOUNDED FOLLOWING
    ) AS first_salary
FROM employees
WHERE department_id = 10
ORDER BY salary, employee_id;
```

В данном случае функция возвращает минимальную зарплату отдела.

Но важно отличать получение первого значения по сортировке от поиска минимума как агрегатной операции.

Если задача заключается исключительно в поиске минимального значения, проще использовать:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    MIN(salary) OVER (
        PARTITION BY department_id
    ) AS min_department_salary
FROM employees;
```

`FIRST_VALUE` нужна тогда, когда важно значение из первой строки определённого порядка.

Например, можно получить зарплату сотрудника, который был принят в отдел раньше остальных.

```sql
SELECT
    employee_id,
    department_id,
    hire_date,
    salary,
    FIRST_VALUE(salary) OVER (
        PARTITION BY department_id
        ORDER BY hire_date, employee_id
    ) AS first_hired_salary
FROM employees;
```

#### Фильтрация по результату оконной функции

В PostgreSQL нельзя напрямую использовать оконную функцию в `WHERE` того же уровня запроса.

Например, следующая конструкция некорректна:

```sql
SELECT
    employee_id,
    department_id,
    salary
FROM employees
WHERE ROW_NUMBER() OVER (
    PARTITION BY department_id
    ORDER BY salary DESC
) = 1;
```

Для фильтрации используется подзапрос или CTE.

```sql
WITH ranked AS (
    SELECT
        employee_id,
        department_id,
        salary,
        ROW_NUMBER() OVER (
            PARTITION BY department_id
            ORDER BY salary DESC, employee_id
        ) AS rn
    FROM employees
)
SELECT
    employee_id,
    department_id,
    salary
FROM ranked
WHERE rn = 1;
```

Запрос возвращает одного сотрудника с максимальной зарплатой из каждого отдела.

Если необходимо вернуть всех сотрудников, разделяющих максимальную зарплату, можно использовать `RANK()` или `DENSE_RANK()`.

В PostgreSQL, SQL Server и MySQL такой способ фильтрации через CTE или подзапрос является распространённым.

Некоторые другие SQL-системы предоставляют конструкцию `QUALIFY`, но её нельзя считать универсальным синтаксисом всех четырёх СУБД курса.

### Тема 11. Производительность оконных функций и текстовой обработки

Текстовые операции и оконные функции могут становиться значимой частью стоимости SQL-запросов.

Однако их производительность зависит от объёма данных, структуры индексов, селективности фильтров, распределения значений и выбранного плана выполнения.

#### Производительность регулярных выражений

Регулярные выражения могут требовать более сложной обработки, чем простой поиск фиксированного префикса.

Но это не означает, что любое регулярное выражение всегда медленнее любого `LIKE`.

Например, в PostgreSQL некоторые регулярные выражения могут использовать триграммные индексы.

В то же время сложное выражение с большим количеством вариантов и неудачной структурой может потребовать значительных ресурсов CPU.

Регулярные выражения, поступающие от недоверенных пользователей, требуют отдельного внимания.

Сложные или специально подобранные шаблоны могут создавать чрезмерную вычислительную нагрузку.

Для таких запросов необходимо применять ограничения доступа, времени выполнения и другие защитные меры.

#### Производительность оконных функций

Оконные функции часто требуют:

- сортировки;
- разделения строк по ключам;
- хранения промежуточных состояний;
- обработки больших наборов строк;
- повторного использования или выполнения нескольких оконных операций.

Например:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    employee_id,
    department_id,
    salary,
    ROW_NUMBER() OVER (
        PARTITION BY department_id
        ORDER BY salary DESC
    ) AS rn
FROM employees;
```

В PostgreSQL в плане можно увидеть узел `WindowAgg`.

Также может присутствовать `Sort`, если данные необходимо упорядочить для оконного вычисления.

#### Индексы для оконных функций

В некоторых случаях индекс по столбцам разделения и сортировки может позволить избежать отдельной сортировки или уменьшить её стоимость.

Например:

```sql
CREATE INDEX idx_employees_department_salary
ON employees (
    department_id,
    salary DESC
);
```

Он соответствует порядку:

```sql
PARTITION BY department_id
ORDER BY salary DESC
```

Но это не означает, что PostgreSQL обязательно выберет индексный доступ.

Если запрос читает значительную часть таблицы, последовательное сканирование и сортировка могут оказаться дешевле.

Индекс также имеет стоимость хранения и обслуживания.

#### Анализ нескольких оконных функций

Если в запросе несколько оконных функций с разными порядками сортировки, СУБД может потребоваться дополнительная обработка.

Например:

```sql
SELECT
    employee_id,
    department_id,
    salary,
    ROW_NUMBER() OVER (
        PARTITION BY department_id
        ORDER BY salary DESC
    ) AS salary_rn,
    ROW_NUMBER() OVER (
        PARTITION BY department_id
        ORDER BY hire_date
    ) AS hire_rn
FROM employees;
```

Две функции используют разные порядки.

Оптимизатор может применять разные стратегии выполнения, включая дополнительные сортировки.

Для анализа необходимо смотреть фактический план.

#### Особенности четырёх СУБД

| СУБД | Что анализировать |
|---|---|
| PostgreSQL | `EXPLAIN (ANALYZE, BUFFERS)`, `WindowAgg`, `Sort`, индексный доступ |
| SQL Server | Actual Execution Plan, сортировки, Window Aggregate, Segment, Sequence Project и другие операторы |
| MySQL | `EXPLAIN`, `EXPLAIN ANALYZE`, временные структуры и сортировки |
| Oracle | Execution Plan, аналитические операции `WINDOW SORT`, использование индексов |

Нельзя оценивать производительность только по наличию или отсутствию одного конкретного оператора плана.

Необходимо учитывать фактическое время выполнения, количество строк, чтение данных и стоимость возвращения результата клиенту.

## Итоговые выводы

1. **SQL предоставляет разные способы текстового поиска.** `LIKE` подходит для простых шаблонов, а регулярные выражения позволяют описывать более сложные структуры. `ILIKE` и `SIMILAR TO` имеют особенности поддержки и не являются универсальной заменой обычному `LIKE`.

2. **Чувствительность поиска к регистру зависит от СУБД и правил сравнения строк.** При переносе запросов необходимо учитывать collation, локаль и особенности Unicode.

3. **Регулярные выражения подходят для валидации и нормализации текстовых данных.** Однако проверка формата не равна проверке бизнес-смысла: корректный шаблон даты, телефона или email ещё не гарантирует корректности самого значения.

4. **Обработку неструктурированных данных удобно организовывать как последовательность SQL-преобразований.** CTE, строковые функции и регулярные выражения позволяют строить понятные ETL-операции с отдельными этапами очистки и проверки.

5. **Оконные функции выполняют аналитические вычисления без сворачивания строк.** В отличие от `GROUP BY`, они позволяют сохранить детализацию исходных записей и добавить к каждой строке агрегаты, ранги и результаты сравнения.

6. **`PARTITION BY` задаёт логические группы, а `ORDER BY` — порядок внутри них.** При этом оконный `ORDER BY` не гарантирует порядок строк итогового результата.

7. **Функции `ROW_NUMBER`, `RANK` и `DENSE_RANK` решают разные задачи ранжирования.** Для корректной нумерации важно учитывать одинаковые значения сортировки и обеспечивать однозначный порядок, когда он необходим.

8. **`LAG` и `LEAD` позволяют сравнивать соседние строки без самостоятельного соединения таблицы с собой.** Они особенно полезны при анализе последовательностей и временных рядов.

9. **Window Frame определяет набор строк для вычислений, учитывающих рамку.** `ROWS`, `RANGE` и `GROUPS` используют разные принципы определения границ, а поддержка этих режимов различается между СУБД.

10. **Поведение `LAST_VALUE` зависит от рамки окна.** При сортировке рамка по умолчанию часто заканчивается текущей строкой или её peer group, а не концом всего раздела. Поэтому для получения последнего значения полного раздела необходимо явно задавать соответствующие границы.

11. **Производительность необходимо проверять по фактическим планам выполнения.** Ни регулярные выражения, ни оконные функции, ни индексы нельзя оценивать исключительно по общим правилам без учёта данных и характера нагрузки.

Главный результат занятия — умение выбирать подходящие инструменты обработки текстовых данных и строить аналитические SQL-запросы с пониманием того, какие строки участвуют в каждом вычислении.
