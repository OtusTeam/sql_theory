
# Индексы в реляционных базах данных: принципы работы, типы и критерии применения

## Превью / аннотация / краткое содержание

Занятие посвящено индексам в реляционных системах управления базами данных: их назначению, внутренней организации, влиянию на выполнение SQL-запросов и стоимости сопровождения.

Индексы позволяют ускорять поиск и обработку данных, но не являются универсальным способом повышения производительности. Их эффективность зависит от структуры таблиц, количества строк, распределения значений, условий запросов и решений оптимизатора.

На занятии рассматриваются:

- назначение индексов и способы доступа к строкам;
- устройство B-tree и других индексных структур;
- стоимость поддержки индексов при изменении данных;
- кардинальность, селективность и статистика;
- кластерные и некластерные индексы;
- составные индексы и принцип левого префикса;
- покрывающие индексы и чтение только из индекса;
- частичные, уникальные индексы и индексы по выражениям;
- использование индексов при `WHERE`, `JOIN`, `ORDER BY` и `GROUP BY`;
- анализ планов выполнения;
- стратегия проектирования индексов с учётом нагрузки.

Основные практические примеры приведены для PostgreSQL. Дополнительно рассматриваются особенности Microsoft SQL Server, MySQL/InnoDB и Oracle.

## Основные понятия

**Индекс (Index)** — вспомогательная структура данных, позволяющая СУБД ускорять определённые операции поиска, чтения и обработки строк.

**Ключ индекса (Index Key)** — значение одного или нескольких столбцов либо выражений, используемое для организации индексных записей.

**Ссылка на строку (Row Locator)** — информация, позволяющая найти соответствующую строку таблицы или кластерного хранилища.

**Последовательное сканирование (Sequential Scan / Table Scan)** — чтение строк таблицы без использования индексного поиска как основного способа доступа.

**Index Seek** — целенаправленный поиск по индексной структуре. Термин особенно распространён в планах SQL Server.

**Index Scan** — сканирование части или всей индексной структуры. Точная терминология и способ выполнения зависят от СУБД.

**Кардинальность (Cardinality)** — количество элементов или различных значений в рассматриваемом наборе данных. В контексте индексации часто подразумевается количество различных значений индексируемого столбца.

**Селективность (Selectivity)** — характеристика условия фильтрации, отражающая долю строк, удовлетворяющих условию. Необходимо учитывать, как именно СУБД или источник определяет эту величину.

**Статистика оптимизатора** — сведения о размере таблиц, распределении значений, количестве различных значений и других характеристиках данных, используемые для оценки стоимости планов.

**B-tree / B+tree** — семейство сбалансированных древовидных структур, используемых для индексирования упорядоченных значений.

**Hash Index** — индекс, основанный на хешировании ключей.

**GIN (Generalized Inverted Index)** — обобщённый инвертированный индекс PostgreSQL.

**GiST (Generalized Search Tree)** — обобщённая поисковая структура PostgreSQL, применяемая, в частности, для пространственных данных.

**BRIN (Block Range Index)** — индекс PostgreSQL, хранящий сводную информацию о диапазонах страниц таблицы.

**Кластерный индекс (Clustered Index)** — индекс, связанный с организацией хранения строк таблицы по индексному ключу. Конкретная реализация зависит от СУБД.

**Некластерный индекс (Nonclustered Index)** — отдельная индексная структура, содержащая ключи и информацию для доступа к строкам.

**Составной индекс (Composite / Multicolumn Index)** — индекс по нескольким столбцам или выражениям.

**Левый префикс (Leftmost Prefix)** — принцип эффективного использования ведущих столбцов составного B-tree индекса.

**Покрывающий индекс (Covering Index)** — индекс, содержащий все значения столбцов, необходимые для выполнения определённого запроса.

**Included Columns** — дополнительные столбцы, хранящиеся в индексе, но не являющиеся его ключами.

**Частичный индекс (Partial Index)** — индекс, содержащий записи только для строк, соответствующих заданному условию.

**Filtered Index** — название механизма индексации подмножества строк в SQL Server.

**Уникальный индекс (Unique Index)** — индекс, обеспечивающий ограничение уникальности индексируемых значений или их комбинаций.

**Индекс по выражению (Expression / Function-Based Index)** — индекс, ключ которого вычисляется из выражения.

**Index-Only Scan** — способ выполнения запроса, при котором необходимые данные могут извлекаться преимущественно из индекса без обычного чтения соответствующих строк таблицы.

**Key Lookup** — операция SQL Server, извлекающая недостающие столбцы из кластерного индекса после доступа через некластерный индекс.

**Bitmap Scan** — способ обработки найденных индексом ссылок на строки через промежуточное битовое представление или структуру адресов.

**DML (Data Manipulation Language)** — операции изменения данных, включая `INSERT`, `UPDATE` и `DELETE`.

**План выполнения (Execution Plan)** — последовательность операций, выбранная оптимизатором для выполнения SQL-запроса.

## Основная часть

### Тема 1. Назначение индексов в реляционной модели

В реляционной базе данные логически представлены в виде таблиц.

Однако SQL-запрос не обязан физически прочитывать каждую строку таблицы, чтобы найти подходящие записи.

Для ускорения доступа могут использоваться индексы.

Рассмотрим таблицу заказов:

```sql
CREATE TABLE orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    status VARCHAR(30) NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL
);
```

Предположим, таблица содержит несколько миллионов заказов.

Необходимо найти заказы конкретного клиента:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Если подходящего индекса нет, СУБД может выполнить последовательное сканирование таблицы.

В PostgreSQL такая операция обычно отображается в плане как:

```text
Seq Scan on orders
```

При последовательном сканировании СУБД читает страницы таблицы и проверяет строки на соответствие условию.

Если запрос возвращает лишь небольшую часть строк большой таблицы, чтение всей таблицы может оказаться дорогим.

Создадим индекс:

```sql
CREATE INDEX idx_orders_customer
ON orders (customer_id);
```

Теперь оптимизатор получает альтернативный путь доступа к данным.

Он может найти записи по `customer_id` через индекс и обратиться только к соответствующим строкам.

Однако наличие индекса **не означает, что СУБД обязательно будет его использовать**.

Решение зависит от оценки стоимости доступных способов выполнения.

#### Индекс не заменяет таблицу

Индекс обычно представляет собой вспомогательную структуру, содержащую ключи и информацию для поиска строк.

В PostgreSQL B-tree индекс хранится отдельно от основной таблицы и содержит ссылки на версии строк в heap.

В SQL Server некластерный индекс содержит ключи и локаторы строк, а кластерный индекс организует само хранение строк.

В MySQL/InnoDB кластерный индекс содержит полные строки таблицы на уровне листовых страниц.

Поэтому утверждение «индекс всегда содержит ключ и указатель на физический адрес строки» является слишком сильным упрощением.

Механизм поиска зависит от реализации СУБД и типа индекса.

#### Какие операции ускоряют индексы

Индексы могут использоваться для:

- поиска по условиям `WHERE`;
- соединения таблиц через `JOIN`;
- получения строк в нужном порядке;
- выполнения `ORDER BY`;
- некоторых операций `GROUP BY`;
- поиска минимальных и максимальных значений;
- проверки уникальности;
- поиска диапазонов;
- отдельных пространственных, текстовых и JSON-операций.

Например:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001
ORDER BY created_at DESC;
```

Индекс:

```sql
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, created_at DESC);
```

потенциально позволяет не только найти заказы клиента, но и получить их в нужном порядке.

Но эффективность такого решения необходимо проверять по плану выполнения.

#### Индекс и последовательное сканирование

Последовательное сканирование нельзя считать ошибкой оптимизатора.

Оно может быть оптимальным, если:

- таблица небольшая;
- запрос возвращает значительную часть строк;
- большинство страниц таблицы всё равно придётся прочитать;
- индекс не покрывает нужные значения;
- чтение по индексу потребует слишком много случайных обращений к таблице.

Следовательно, цель индексирования — не устранить все последовательные сканирования, а уменьшить стоимость наиболее важных запросов.

### Тема 2. Логика работы индекса и стоимость его поддержки

Индексы могут использовать разные внутренние структуры.

Наиболее распространённым индексом для обычных реляционных запросов является B-tree.

#### Устройство B-tree

B-tree представляет собой сбалансированную древовидную структуру.

В типичных реализациях B-tree индексов используются:

- корневые страницы;
- внутренние страницы;
- листовые страницы.

Упрощённо поиск выглядит следующим образом:

```text
                  [50]
                 /    \
            [20, 35]  [70, 90]
             / |  \     / | \
            ... ...    ...
```

Сначала СУБД обращается к корню дерева.

Затем по значениям ключей выбирает подходящую ветвь.

Так происходит до достижения листового уровня.

В листовых страницах находятся индексные записи, необходимые для поиска соответствующих строк.

Реальные B-tree индексы обычно имеют высокую степень ветвления и небольшую глубину даже при большом количестве строк.

Поэтому поиск по подходящему ключу требует сравнительно небольшого числа переходов между уровнями дерева.

Но это не означает, что стоимость всего запроса всегда логарифмическая.

После нахождения индексных записей могут потребоваться:

- чтение большого числа листовых страниц;
- переходы к строкам таблицы;
- проверка видимости версий;
- применение дополнительных фильтров;
- сортировка;
- передача результатов клиенту.

Если запрос возвращает миллионы строк, стоимость чтения найденных данных может значительно превышать стоимость самого поиска в дереве.

#### Диапазонный поиск

B-tree подходит не только для равенства.

Например:

```sql
SELECT *
FROM orders
WHERE total_amount BETWEEN 1000 AND 5000;
```

Индекс:

```sql
CREATE INDEX idx_orders_amount
ON orders (total_amount);
```

может использоваться для поиска диапазона значений.

После нахождения начала диапазона СУБД может последовательно обрабатывать подходящие индексные записи.

Это одно из преимуществ упорядоченного индексирования.

#### Другие типы индексов

PostgreSQL поддерживает несколько индексных методов.

| Тип | Основное назначение |
|---|---|
| B-tree | Равенство, диапазоны, сортировка |
| Hash | Равенство |
| GIN | Массивы, JSONB, полнотекстовый поиск |
| GiST | Пространственные данные и другие специализированные операторы |
| SP-GiST | Пространственные и разделяющие пространство структуры |
| BRIN | Компактное индексирование диапазонов страниц, особенно для коррелированных данных |

Например, GIN-индекс может ускорять определённые операции поиска по JSONB:

```sql
CREATE INDEX idx_events_payload
ON events
USING GIN (payload);
```

Для геометрических объектов PostGIS часто использует GiST:

```sql
CREATE INDEX idx_locations_geometry
ON locations
USING GIST (geom);
```

Эти примеры предполагают, что соответствующие таблицы и столбцы существуют.

В SQL Server, MySQL и Oracle набор доступных индексных структур отличается.

Поэтому индекс не следует определять исключительно как упорядоченное дерево.

#### Стоимость поддержки индексов

Индексы ускоряют некоторые запросы чтения, но создают дополнительную нагрузку при изменении данных.

Рассмотрим вставку:

```sql
INSERT INTO orders (
    customer_id,
    created_at,
    status,
    total_amount
)
VALUES (
    1001,
    CURRENT_TIMESTAMP,
    'created',
    1500
);
```

Помимо записи строки таблицы, СУБД должна поддержать соответствующие индексные структуры.

Если таблица содержит пять индексов, вставка может потребовать изменений в каждом из них.

Это не означает, что все индексы полностью перестраиваются.

Обычно обновляются затронутые записи и страницы.

При необходимости могут выполняться:

- разделение страниц;
- перераспределение записей;
- выделение новых страниц;
- журналирование изменений;
- дополнительная работа по обслуживанию версий строк.

#### UPDATE и DELETE

При обновлении индексируемых столбцов может потребоваться изменение индексных записей.

```sql
UPDATE orders
SET customer_id = 2002
WHERE order_id = 100;
```

В PostgreSQL из-за MVCC обновление создаёт новую версию строки.

Если соблюдены определённые условия, PostgreSQL может выполнить HOT-update — обновление без добавления новых записей в индексы.

Однако HOT-update невозможен, если изменяются столбцы, на которые ссылаются обычные индексы, включая столбцы в выражениях и предикатах.

При удалении строк также возникает работа по обслуживанию индексов и очистке устаревших данных.

В PostgreSQL важную роль играет `VACUUM`.

В SQL Server, MySQL/InnoDB и Oracle используются другие механизмы организации версий строк и сопровождения индексных структур.

#### Избыточное индексирование

Чем больше индексов, тем выше потенциальные расходы на:

- вставку;
- обновление;
- удаление;
- журналирование;
- хранение;
- резервное копирование;
- обслуживание.

Поэтому нельзя создавать отдельный индекс на каждый столбец просто на случай возможного использования.

Индекс должен решать конкретную задачу.

### Тема 3. Критерии эффективности индекса

Эффективность индекса определяется характеристиками данных и запроса.

Особое значение имеют кардинальность, селективность и распределение значений.

#### Кардинальность

Термин «кардинальность» используется в нескольких контекстах.

Кардинальность таблицы — количество её строк.

Кардинальность набора значений столбца часто означает количество различных значений.

Рассмотрим таблицу:

| order_id | status |
|---|---|
| 1 | created |
| 2 | created |
| 3 | delivered |
| 4 | delivered |
| 5 | cancelled |
| 6 | delivered |

В таблице шесть строк.

Столбец `status` содержит три различных значения.

Для оценки количества различных значений можно использовать:

```sql
SELECT COUNT(DISTINCT status)
FROM orders;
```

Однако количество различных значений само по себе не определяет полезность индекса.

Индекс по столбцу с малым числом уникальных значений может быть эффективным для редкого значения.

Например, если в таблице 10 миллионов заказов, а статус `cancelled` встречается только у 0,1% строк, индекс может оказаться полезным.

#### Селективность

Под селективностью условия часто понимают долю строк, проходящих фильтр.

Для оценки:

\[
s = \frac{\text{Количество подходящих строк}}{\text{Общее количество строк}}
\]

Например, если условию соответствует 100 строк из 1 миллиона:

\[
s = \frac{100}{1\,000\,000} = 0{,}0001
\]

Это 0,01% строк.

Условие очень избирательно: оно возвращает малую долю таблицы.

В отдельных источниках термин «высокая селективность» означает именно высокую избирательность и малую долю совпадений, а не большое числовое значение отношения.

Чтобы избежать путаницы, полезнее прямо указывать ожидаемую долю подходящих строк.

#### Селективность и распределение

Рассмотрим два условия:

```sql
WHERE status = 'delivered'
```

и:

```sql
WHERE status = 'cancelled'
```

Оба используют один столбец.

Но первое условие может возвращать 80% таблицы, а второе — 0,1%.

Для первого условия последовательное сканирование может оказаться дешевле.

Для второго индекс может дать значительный выигрыш.

Таким образом, эффективность индекса зависит от распределения данных, а не только от количества разных значений.

#### Стоимость доступа к строкам

Предположим, индекс позволил найти 500 000 подходящих записей.

Если запрос использует:

```sql
SELECT *
FROM orders
WHERE status = 'delivered';
```

СУБД может потребоваться получить множество строк таблицы.

Если подходящие строки расположены на разных страницах, это приводит к большому количеству обращений к данным.

В такой ситуации последовательное сканирование может быть дешевле.

Для более узкого запроса:

```sql
SELECT order_id, status
FROM orders
WHERE status = 'cancelled';
```

индекс может оказаться значительно эффективнее.

#### Селективность составных условий

Рассмотрим:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001
  AND status = 'created';
```

Результат зависит от распределения комбинаций значений.

Нельзя всегда вычислить селективность сложного условия простым перемножением селективностей отдельных столбцов.

Например, статус заказа может быть связан с датой, типом клиента или регионом.

Поэтому современные СУБД используют статистику распределения и дополнительные механизмы оценки зависимостей.

В PostgreSQL для связанных столбцов могут применяться расширенные статистики.

### Тема 4. Базовые типы индексов и их организация

Различие между кластерными и некластерными индексами особенно важно при сравнении СУБД.

Однако устройство физического хранения различается.

#### PostgreSQL

В PostgreSQL обычные таблицы хранятся в heap.

Индексы являются отдельными структурами.

B-tree индекс содержит ключи и ссылки на версии строк через TID.

Пример:

```sql
CREATE INDEX idx_orders_created
ON orders (created_at);
```

PostgreSQL предоставляет команду:

```sql
CLUSTER orders USING idx_orders_created;
```

Она физически переписывает таблицу в порядке выбранного индекса.

Но результат **не поддерживается автоматически при последующих вставках и обновлениях**.

Поэтому `CLUSTER` в PostgreSQL не является эквивалентом постоянно поддерживаемого кластерного индекса SQL Server или InnoDB.

Таблица со временем может утратить порядок, достигнутый при выполнении `CLUSTER`.

#### SQL Server

В SQL Server широко используются два основных типа rowstore-индексов:

- clustered;
- nonclustered.

**Clustered index** организует хранение строк таблицы в B-tree структуре.

На листовом уровне кластерного индекса находятся сами строки данных.

Одна rowstore-таблица может иметь только один кластерный индекс.

Пример:

```sql
CREATE CLUSTERED INDEX idx_orders_clustered
ON dbo.orders (order_id);
```

Пример предполагает, что таблица не имеет другого кластерного индекса.

Если кластерного индекса нет, rowstore-таблица может храниться как heap.

**Nonclustered index** является отдельной структурой.

```sql
CREATE NONCLUSTERED INDEX idx_orders_customer
ON dbo.orders (customer_id);
```

Если таблица имеет кластерный индекс, некластерный индекс использует ключ кластерного индекса для поиска соответствующей строки.

Если таблица представляет собой heap, используются другие локаторы строк.

При этом физическое размещение страниц на диске не обязано строго соответствовать непрерывному порядку ключей.

Выражение «кластерный индекс физически сортирует всю таблицу» является полезным упрощением, но не полным описанием хранения.

#### MySQL/InnoDB

В InnoDB каждая таблица организована вокруг кластерного индекса.

Если задан `PRIMARY KEY`, InnoDB использует его как кластерный индекс.

```sql
CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    created_at DATETIME NOT NULL,
    status VARCHAR(30) NOT NULL
) ENGINE = InnoDB;
```

Полные строки находятся в листовых страницах кластерного индекса.

Вторичные индексы содержат собственные ключи и значения первичного ключа, используемые для получения полной строки через кластерный индекс.

Если явный первичный ключ отсутствует, InnoDB выбирает подходящий уникальный индекс с не-NULL столбцами либо создаёт внутренний скрытый идентификатор.

Это одна из причин, по которым для InnoDB рекомендуется явно определять компактный и стабильный первичный ключ.

Например, очень длинный составной первичный ключ увеличивает размер вторичных индексов, поскольку его значения используются в их записях.

#### Oracle

В Oracle обычные heap-organized tables хранят данные отдельно от B-tree индексов.

Индексные записи могут содержать `ROWID`, позволяющий получить соответствующую строку таблицы.

Также Oracle поддерживает index-organized tables (IOT).

В IOT строки таблицы хранятся непосредственно в структуре B-tree, организованной по первичному ключу.

Это концептуально ближе к кластерному хранению InnoDB, хотя реализации отличаются.

В Oracle также существует механизм table clusters, который не следует автоматически отождествлять с clustered index SQL Server.

#### Сравнение

| Особенность | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| Обычное хранение строк | Heap | Heap или clustered rowstore | Кластерный индекс | Обычно heap |
| Кластерный индекс как основной способ хранения | Нет | Да | Да | IOT как отдельный вариант |
| Вторичные индексы | Да | Да | Да | Да |
| Локатор строки | TID | RID или ключ clustered index | Первичный ключ | ROWID или другой механизм для IOT |
| Физическая реорганизация по индексу | `CLUSTER`, не поддерживается автоматически | Поддерживается структурой clustered index | Поддерживается кластерным индексом | Зависит от организации таблицы |

### Тема 5. Составные и покрывающие индексы

Составной индекс содержит несколько ключевых столбцов.

Например:

```sql
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, created_at);
```

Порядок ключей имеет значение.

#### Принцип левого префикса

Для B-tree индекса:

```text
(customer_id, created_at)
```

особенно эффективен поиск:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Или:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001
  AND created_at >= TIMESTAMP '2026-01-01 00:00:00';
```

Сначала индекс позволяет ограничить записи по `customer_id`, затем обработать диапазон дат внутри найденной группы.

Однако запрос:

```sql
SELECT *
FROM orders
WHERE created_at >= TIMESTAMP '2026-01-01 00:00:00';
```

не всегда может столь же эффективно использовать тот же индекс.

Причина в том, что значения `created_at` упорядочены внутри групп `customer_id`, а не глобально как первый ключ.

#### Правило левого префикса не абсолютно

Неверно утверждать, что индекс никогда не может использоваться при фильтрации только по правому столбцу.

Некоторые СУБД поддерживают дополнительные способы обработки составных индексов.

В PostgreSQL 18 предусмотрена оптимизация B-tree skip scan.

Она может выполнять повторяющиеся поиски по группам значений пропущенного ведущего столбца.

Например, для индекса:

```text
(status, customer_id)
```

и запроса:

```sql
WHERE customer_id = 1001
```

оптимизатор в определённых условиях может использовать skip scan, если количество различных значений `status` достаточно мало.

Это не означает, что порядок столбцов перестал иметь значение.

Skip scan выгоден только для определённого распределения данных и стоимости альтернативных планов.

В MySQL и Oracle также существуют механизмы skip scan со своими ограничениями.

#### Порядок условий WHERE

Следует отличать порядок столбцов индекса от порядка условий в SQL.

Например:

```sql
WHERE customer_id = 1001
  AND status = 'created'
```

и:

```sql
WHERE status = 'created'
  AND customer_id = 1001
```

логически эквивалентны для обычных детерминированных сравнений.

Оптимизатор не обязан учитывать текстовый порядок условий `AND` как порядок индексного поиска.

Важен порядок ключевых столбцов в определении индекса и фактическая структура запроса.

#### Равенство и диапазон

Предположим, существует индекс:

```sql
CREATE INDEX idx_orders_status_date_amount
ON orders (status, created_at, total_amount);
```

Запрос:

```sql
SELECT *
FROM orders
WHERE status = 'created'
  AND created_at >= TIMESTAMP '2026-01-01 00:00:00'
  AND total_amount > 1000;
```

может эффективно использовать равенство по `status` и диапазон по `created_at`.

Условие по `total_amount` также может проверяться в индексе, но не обязательно позволит существенно сократить просматриваемую часть дерева после диапазонного условия.

Конкретный результат зависит от СУБД, версии и оптимизатора.

#### Покрывающие индексы

Покрывающим называют индекс, содержащий все значения, необходимые определённому запросу.

Например:

```sql
SELECT
    customer_id,
    created_at,
    total_amount
FROM orders
WHERE customer_id = 1001;
```

Для него можно создать индекс:

```sql
CREATE INDEX idx_orders_covering
ON orders (customer_id, created_at)
INCLUDE (total_amount);
```

В PostgreSQL `INCLUDE` позволяет добавить неключевые столбцы.

Они не участвуют в поиске и сортировке по ключу, но хранятся в индексе.

#### Index-Only Scan в PostgreSQL

Покрывающий индекс может позволить выполнить `Index Only Scan`.

Однако это не гарантирует полного отсутствия чтения heap.

PostgreSQL использует MVCC и должен проверять видимость строк.

Для этого применяется visibility map.

Если страница таблицы помечена как полностью видимая, данные можно вернуть без чтения соответствующей строки heap.

Если отметки нет, потребуется дополнительная проверка.

Поэтому фактическую эффективность можно оценить через:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    customer_id,
    created_at,
    total_amount
FROM orders
WHERE customer_id = 1001;
```

В плане `Index Only Scan` важно обращать внимание на `Heap Fetches`.

Большое число `Heap Fetches` означает, что индекс не позволил избежать всех обращений к таблице.

#### Покрывающие индексы в SQL Server

В SQL Server `INCLUDE` также используется для некластерных индексов.

```sql
CREATE NONCLUSTERED INDEX idx_orders_covering
ON dbo.orders (customer_id, created_at)
INCLUDE (total_amount);
```

Если запрос покрывается индексом, SQL Server может избежать дополнительных обращений к кластерному индексу или heap.

Иначе в плане может появиться `Key Lookup` или `RID Lookup`.

Большое число таких операций иногда становится причиной высокой стоимости запроса.

#### MySQL/InnoDB и Oracle

MySQL/InnoDB не использует аналог PostgreSQL/SQL Server `INCLUDE` для обычных B-tree индексов.

Покрытие достигается включением необходимых столбцов в ключ вторичного индекса либо использованием уже присутствующего первичного ключа.

В Oracle покрывающий эффект также может достигаться составными B-tree индексами и некоторыми другими средствами.

Однако синтаксис и стоимость таких решений отличаются.

#### Недостатки широких индексов

Добавление большого количества столбцов увеличивает:

- размер индексных страниц;
- объём хранения;
- расходы на запись;
- нагрузку на кеш;
- затраты на обслуживание.

Следовательно, покрывающий индекс стоит проектировать под конкретный важный запрос, а не пытаться включить в него все столбцы таблицы.

### Тема 6. Частичные, уникальные индексы и индексы по выражению

Не все индексы содержат записи для каждой строки таблицы.

Некоторые позволяют ограничить индексируемый набор или вычислять ключ из выражения.

#### Частичные индексы в PostgreSQL

Частичный индекс создаётся с условием `WHERE`.

Например, большинство заказов уже завершены, а приложение часто ищет только активные.

```sql
CREATE INDEX idx_orders_active_customer
ON orders (customer_id)
WHERE status IN ('created', 'processing');
```

Такой индекс содержит записи только для строк, удовлетворяющих условию.

Запрос:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001
  AND status IN ('created', 'processing');
```

может использовать частичный индекс.

Преимущества:

- меньший размер;
- меньше записей для обслуживания;
- более узкий набор данных для определённых запросов.

Но оптимизатор должен определить, что условие запроса предполагает выполнение предиката индекса.

Например, запрос:

```sql
WHERE customer_id = 1001
```

не гарантирует этого.

Он может возвращать и завершённые заказы, которые в частичном индексе отсутствуют.

Поэтому такой индекс не является универсальной заменой обычному индексу по `customer_id`.

#### Параметризованные запросы

Частичные индексы могут иметь особенности использования в подготовленных запросах.

Например:

```sql
WHERE status = $1
```

При обобщённом плане PostgreSQL оптимизатор может не знать конкретное значение параметра.

В таком случае он не всегда способен доказать, что условие соответствует предикату частичного индекса.

Поэтому эффективность частичных индексов следует проверять с учётом реального способа выполнения запросов приложением.

#### Filtered Index в SQL Server

В SQL Server существует похожий механизм filtered indexes.

```sql
CREATE NONCLUSTERED INDEX idx_orders_active
ON dbo.orders (customer_id)
WHERE status = 'created';
```

Он позволяет индексировать только часть строк.

Однако поддерживаемые выражения фильтра и требования к использованию индекса имеют ограничения.

Например, фильтр SQL Server не поддерживает произвольные сложные условия так же свободно, как предикат частичного индекса PostgreSQL.

#### MySQL/InnoDB и Oracle

В MySQL/InnoDB нет прямого аналога произвольного частичного B-tree индекса PostgreSQL с `WHERE` в `CREATE INDEX`.

Для отдельных сценариев используются вычисляемые столбцы и функциональные индексы.

В Oracle можно реализовать условную индексацию с помощью функциональных выражений, например возвращающих `NULL` для строк, которые не должны участвовать в индексе.

Однако такие решения не полностью эквивалентны частичным индексам PostgreSQL.

#### Уникальные индексы

Уникальный индекс обеспечивает ограничение уникальности.

```sql
CREATE UNIQUE INDEX idx_customers_email_unique
ON customers (email);
```

Однако если уникальность является частью бизнес-модели, обычно предпочтительнее явно объявить ограничение.

```sql
CREATE TABLE customers (
    customer_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email TEXT NOT NULL UNIQUE
);
```

В PostgreSQL уникальное ограничение обычно обеспечивается уникальным B-tree индексом.

#### Уникальность и NULL

Поведение `NULL` в уникальных индексах различается между СУБД.

В PostgreSQL по умолчанию несколько строк с `NULL` в уникальном столбце допускаются.

Начиная с PostgreSQL 15 можно указать:

```sql
CREATE UNIQUE INDEX idx_customers_external_id
ON customers (external_id) NULLS NOT DISTINCT;
```

Такой индекс рассматривает значения `NULL` как равные для проверки уникальности.

В SQL Server, MySQL и Oracle правила уникальности с `NULL` отличаются.

Поэтому перенос уникальных ограничений требует отдельной проверки.

#### Индексы по выражению

В PostgreSQL можно индексировать результат выражения.

Например, пользователи вводят адреса электронной почты в разном регистре.

```sql
CREATE INDEX idx_customers_email_lower
ON customers (lower(email));
```

Запрос:

```sql
SELECT *
FROM customers
WHERE lower(email) = 'anna@example.com';
```

может использовать такой индекс.

Но запрос:

```sql
WHERE email = 'anna@example.com'
```

не обязательно использует индекс по `lower(email)`, поскольку это другое выражение.

#### Функциональные индексы в других СУБД

| СУБД | Подход |
|---|---|
| PostgreSQL | Индексы по выражению |
| SQL Server | Индексы по подходящим вычисляемым столбцам |
| MySQL/InnoDB | Functional key parts и generated columns |
| Oracle | Function-based indexes |

Во всех случаях необходимо учитывать требования к детерминированности или неизменности выражений.

Например, в PostgreSQL функции, используемые непосредственно в индексном выражении, должны удовлетворять требованиям к неизменности (`IMMUTABLE`).

Нельзя бездумно индексировать выражение, результат которого может измениться со временем без изменения самой строки.

### Тема 7. Статистика и оптимизация решений СУБД

Современные реляционные СУБД используют стоимостные оптимизаторы.

Они рассматривают альтернативные способы выполнения SQL-запроса и оценивают их стоимость.

Для этого необходима статистика.

#### Что содержит статистика

В зависимости от СУБД статистика может включать:

- количество строк;
- количество страниц;
- количество различных значений;
- долю `NULL`;
- наиболее частые значения;
- гистограммы распределения;
- корреляцию с физическим порядком;
- сведения о зависимостях между столбцами.

Важно различать статистику распределения данных и статистику фактического использования индексов.

Например, количество обращений к индексу может быть полезно администратору, но оно не является тем же самым, что гистограмма или оценка селективности для оптимизатора.

#### PostgreSQL: ANALYZE

Для обновления статистики используется:

```sql
ANALYZE orders;
```

Команда собирает статистику по данным таблицы.

PostgreSQL также запускает автоматический сбор статистики через autovacuum.

После массовой загрузки данных или существенного изменения распределения значений может потребоваться дополнительный `ANALYZE`.

#### Просмотр статистики

В PostgreSQL доступно представление `pg_stats`.

```sql
SELECT
    schemaname,
    tablename,
    attname,
    null_frac,
    n_distinct,
    correlation
FROM pg_stats
WHERE tablename = 'orders';
```

Здесь:

- `null_frac` — доля значений `NULL`;
- `n_distinct` — оценка количества различных значений;
- `correlation` — оценка корреляции между логическим порядком значений и физическим размещением строк.

Отрицательное значение `n_distinct` в PostgreSQL выражает оценку количества различных значений как долю числа строк, а не просто отрицательное количество значений.

#### Расширенная статистика

Если столбцы связаны, независимые оценки селективности могут давать значительные ошибки.

Например, город может быть связан с регионом.

```sql
CREATE STATISTICS stats_customers_region_city
ON region_id, city_id
FROM customers;
```

После создания:

```sql
ANALYZE customers;
```

PostgreSQL может использовать дополнительные статистические сведения для более точной оценки некоторых комбинаций условий.

Однако расширенная статистика не делает оптимизатор безошибочным и не заменяет корректные индексы.

#### Статистика SQL Server

В SQL Server используются объекты статистики, содержащие в том числе гистограммы и плотности распределения.

Статистика может создаваться и обновляться автоматически в зависимости от настроек базы данных.

При необходимости применяется:

```sql
UPDATE STATISTICS dbo.orders;
```

#### Статистика MySQL/InnoDB

MySQL/InnoDB использует статистику таблиц и индексов, а также поддерживает гистограммы для определённых столбцов.

Для обновления статистики используется:

```sql
ANALYZE TABLE orders;
```

#### Статистика Oracle

В Oracle сбором статистики оптимизатора управляет пакет `DBMS_STATS`.

Например:

```sql
BEGIN
    DBMS_STATS.GATHER_TABLE_STATS(
        ownname => USER,
        tabname => 'ORDERS'
    );
END;
/
```

Oracle также поддерживает автоматический сбор статистики.

#### Устаревшая статистика

Предположим, первоначально таблица содержала 10 тысяч строк.

Затем в неё загрузили 10 миллионов строк.

Если статистика осталась прежней, оптимизатор может неправильно оценить:

- количество возвращаемых строк;
- стоимость индексного поиска;
- объём сортировки;
- способ соединения таблиц.

Однако неверно утверждать, что статистику необходимо вручную обновлять после каждой вставки или каждого изменения.

В современных СУБД существуют автоматические механизмы её сопровождения.

Задача разработчика и администратора — понимать, когда эти механизмы недостаточны.

### Тема 8. Практика применения и стратегия проектирования индексов

Индексирование следует начинать с анализа запросов, а не со списка столбцов таблицы.

Рассмотрим типичный сценарий платформы доставки.

Есть таблица:

```sql
CREATE TABLE delivery_orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    courier_id BIGINT,
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL
);
```

Предположим, приложение выполняет несколько типов запросов.

#### Запрос 1. Получение заказа по идентификатору

```sql
SELECT *
FROM delivery_orders
WHERE order_id = 1001;
```

Первичный ключ уже обеспечивается индексом.

Создавать дополнительный индекс на тот же столбец обычно не требуется.

#### Запрос 2. История заказов клиента

```sql
SELECT
    order_id,
    created_at,
    status,
    total_amount
FROM delivery_orders
WHERE customer_id = 1001
ORDER BY created_at DESC
LIMIT 20;
```

Подходящий кандидат:

```sql
CREATE INDEX idx_delivery_orders_customer_date
ON delivery_orders (customer_id, created_at DESC);
```

Если запрос очень частый, можно рассмотреть включение дополнительных столбцов:

```sql
CREATE INDEX idx_delivery_orders_customer_cover
ON delivery_orders (customer_id, created_at DESC)
INCLUDE (status, total_amount);
```

Это альтернативный вариант, а не индекс, который обязательно следует создавать дополнительно к предыдущему.

Создание двух почти одинаковых индексов может привести к избыточным расходам.

#### Запрос 3. Активные заказы курьера

```sql
SELECT
    order_id,
    created_at,
    status
FROM delivery_orders
WHERE courier_id = 500
  AND status IN ('created', 'processing');
```

Если активных заказов относительно немного, можно рассмотреть частичный индекс:

```sql
CREATE INDEX idx_delivery_orders_active_courier
ON delivery_orders (courier_id)
WHERE status IN ('created', 'processing');
```

Но его эффективность необходимо проверить на реальном распределении статусов и фактических запросах.

#### Запрос 4. Аналитика по датам

```sql
SELECT
    created_at::date AS order_date,
    COUNT(*) AS orders_count
FROM delivery_orders
WHERE created_at >= TIMESTAMP '2026-01-01 00:00:00'
  AND created_at < TIMESTAMP '2026-02-01 00:00:00'
GROUP BY created_at::date;
```

Возможный кандидат:

```sql
CREATE INDEX idx_delivery_orders_created
ON delivery_orders (created_at);
```

Однако если запрос обрабатывает большую часть таблицы, последовательное сканирование может оказаться эффективнее.

Для очень больших таблиц, где `created_at` хорошо коррелирует с физическим порядком строк, можно рассмотреть BRIN-индекс.

```sql
CREATE INDEX idx_delivery_orders_created_brin
ON delivery_orders
USING BRIN (created_at);
```

BRIN обычно значительно компактнее B-tree, но использует другую стратегию поиска и может возвращать дополнительные страницы для последующей проверки.

Он особенно полезен для больших таблиц с коррелированными данными.

#### Индексы на внешние ключи

Внешние ключи часто участвуют в соединениях.

Например:

```sql
SELECT
    o.order_id,
    o.total_amount
FROM delivery_orders AS o
JOIN customers AS c
    ON c.customer_id = o.customer_id
WHERE c.customer_id = 1001;
```

Индекс по `delivery_orders.customer_id` может быть полезен.

Но необходимо различать две задачи:

1. Обеспечение ссылочной целостности.
2. Ускорение поиска и соединений.

В PostgreSQL внешний ключ сам по себе не создаёт индекс на ссылающемся столбце.

Индекс на стороне родительского ключа обычно существует благодаря `PRIMARY KEY` или подходящему `UNIQUE`-ограничению.

В SQL Server индексы на ссылающихся столбцах внешних ключей также не создаются автоматически.

В MySQL/InnoDB для поддержки внешнего ключа требуется подходящий индекс, и InnoDB может создать его автоматически, если необходимого индекса нет.

В Oracle индексы на столбцах внешних ключей не создаются автоматически только из-за объявления ограничения.

Поэтому правило «первичные и внешние ключи индексируются автоматически» не является универсальным.

#### Анализ плана PostgreSQL

Используем:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    order_id,
    created_at,
    status,
    total_amount
FROM delivery_orders
WHERE customer_id = 1001
ORDER BY created_at DESC
LIMIT 20;
```

При анализе следует смотреть:

- выбранный способ доступа;
- фактическое количество строк;
- предполагаемое количество строк;
- число повторений узла;
- сортировки;
- обращения к heap;
- чтение буферов;
- общее время выполнения.

В PostgreSQL возможны следующие операции:

| Оператор | Значение |
|---|---|
| `Seq Scan` | Последовательное чтение таблицы |
| `Index Scan` | Доступ через индекс с получением строк таблицы |
| `Index Only Scan` | Чтение через индекс с возможными проверками видимости |
| `Bitmap Index Scan` | Получение ссылок на подходящие строки через индекс |
| `Bitmap Heap Scan` | Чтение соответствующих страниц таблицы |
| `Sort` | Сортировка |
| `Incremental Sort` | Сортировка с использованием уже упорядоченной части входных данных |

Само наличие `Seq Scan` не доказывает проблему.

Необходимо определить, почему оптимизатор выбрал этот способ доступа.

#### Как правильно сравнивать индексы

Для оценки индекса следует:

1. Зафиксировать SQL-запрос и его параметры.
2. Убедиться, что статистика соответствует данным.
3. Посмотреть исходный план выполнения.
4. Измерить фактическое время выполнения и обращения к данным.
5. Создать проверяемый индекс.
6. Повторить измерения несколько раз.
7. Проверить влияние кеша и порядка запусков.
8. Сравнить не только чтение, но и стоимость изменения данных.
9. Оценить размер индекса.
10. Проверить, не дублирует ли он существующие структуры.

Для PostgreSQL размер индекса можно получить так:

```sql
SELECT pg_size_pretty(
    pg_relation_size('idx_delivery_orders_customer_date')
);
```

Название индекса должно соответствовать реально существующему объекту.

Использование `EXPLAIN ANALYZE` важно, но не всегда достаточно для оценки производительности приложения.

Например, при выполнении обычного `EXPLAIN (ANALYZE, BUFFERS)` PostgreSQL измеряет выполнение запроса на сервере, но не учитывает полную стоимость передачи результата клиенту.

Для полной оценки иногда необходимы дополнительные измерения.

#### Особенности эксплуатации

Индексы требуют сопровождения.

В PostgreSQL важно учитывать:

- autovacuum и `VACUUM`;
- статистику;
- разрастание индексов;
- конкуренцию операций;
- влияние индексов на HOT-update.

Для создания B-tree индекса на рабочей таблице с минимизацией блокирования записей можно использовать:

```sql
CREATE INDEX CONCURRENTLY idx_delivery_orders_amount
ON delivery_orders (total_amount);
```

`CREATE INDEX CONCURRENTLY` имеет ограничения, в том числе не может выполняться внутри обычного блока транзакции.

Также такая операция не является бесплатной: она потребляет ресурсы и может занимать значительное время.

В SQL Server используются собственные средства обслуживания индексов и статистики.

MySQL/InnoDB и Oracle также имеют механизмы мониторинга, изменения и обслуживания индексов.

Универсального правила «регулярно перестраивать все индексы» не существует.

Необходимость обслуживания определяется конкретными показателями и характером нагрузки.

## Итоговые выводы

1. **Индекс — вспомогательный путь доступа к данным, а не обязательная замена последовательному сканированию.** Оптимизатор выбирает способ выполнения на основании стоимости операций.

2. **Индексы имеют разную внутреннюю организацию.** B-tree подходит для равенства, диапазонов и сортировки, а специализированные структуры решают задачи поиска по документам, пространственным данным и другим типам значений.

3. **Индексирование ускоряет определённые операции чтения, но увеличивает стоимость изменения данных.** При вставках, обновлениях и удалениях СУБД должна поддерживать соответствующие индексные структуры.

4. **Кардинальность и селективность необходимо рассматривать отдельно.** Количество различных значений не определяет эффективность индекса без учёта распределения данных и доли строк, удовлетворяющих запросу.

5. **Кластерные индексы различаются между СУБД.** В SQL Server и MySQL/InnoDB они связаны с организацией хранения строк, тогда как в PostgreSQL обычные индексы являются отдельными структурами, а команда `CLUSTER` не обеспечивает постоянной автоматической кластеризации.

6. **Порядок столбцов составного B-tree индекса имеет значение.** Ведущие столбцы обычно обеспечивают наиболее эффективный поиск, хотя механизмы skip scan позволяют в отдельных случаях использовать индекс и без ограничения ведущего ключа.

7. **Покрывающие индексы позволяют уменьшить число обращений к таблице.** Однако в PostgreSQL `Index Only Scan` зависит от проверки видимости строк через MVCC и visibility map.

8. **Частичные и функциональные индексы помогают оптимизировать конкретные сценарии.** Их эффективность зависит от соответствия условий запросов индексным предикатам и выражениям.

9. **Уникальные индексы не только ускоряют поиск, но и обеспечивают ограничения целостности.** Поведение уникальности для `NULL` различается между СУБД.

10. **Статистика оптимизатора влияет на выбор плана выполнения.** Устаревшие или недостаточные сведения о распределении данных могут приводить к ошибочным оценкам количества строк и стоимости операций.

11. **Индексы на внешние ключи не всегда создаются автоматически.** Это зависит от СУБД, поэтому структуру индексов необходимо проверять отдельно.

12. **Проектирование индексов должно опираться на реальные запросы и измерения.** Избыточное индексирование увеличивает нагрузку, а минимально необходимый набор индексов обычно проще сопровождать и оптимизировать.

Главный результат занятия — понимание того, как индекс влияет на физический доступ к данным, почему оптимизатор может выбрать или проигнорировать индекс и как обоснованно проектировать индексные структуры под конкретную нагрузку.
