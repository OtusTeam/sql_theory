
# Мониторинг производительности базы данных

## Превью / аннотация / краткое содержание

Занятие посвящено мониторингу производительности реляционных баз данных: сбору метрик, анализу текущей нагрузки, диагностике медленных запросов, ожиданий, блокировок и потребления серверных ресурсов.

Если предыдущие занятия были посвящены оптимизации отдельных SQL-запросов и операций изменения данных, то заключительное занятие рассматривает производительность на уровне работающей системы.

Мониторинг позволяет не только обнаруживать уже возникшую деградацию, но и наблюдать за её развитием, находить причины проблем, оценивать эффективность изменений и предупреждать исчерпание ресурсов.

На занятии рассматриваются:

- назначение мониторинга СУБД;
- связь доступности, производительности и наблюдаемости;
- основные метрики: latency, throughput, QPS, TPS;
- число и состояние подключений;
- мониторинг CPU, RAM, диска и сети;
- блокировки, ожидания и длительные транзакции;
- буферный кеш и интерпретация cache hit ratio;
- встроенные статистические представления PostgreSQL;
- `pg_stat_activity`, `pg_stat_database`, `pg_stat_io`;
- мониторинг WAL, checkpoint и autovacuum;
- расширение `pg_stat_statements`;
- журналы ошибок и медленных запросов;
- инструменты MySQL, SQL Server и Oracle;
- внешние системы Prometheus, Grafana, Zabbix и Percona Monitoring and Management;
- построение дашбордов и настройка оповещений;
- практическая диагностика деградации базы данных.

Основные SQL-примеры приведены для PostgreSQL. Дополнительно рассматриваются соответствующие возможности Microsoft SQL Server, MySQL/InnoDB и Oracle.

## Основные понятия

**Мониторинг базы данных (Database Monitoring)** — систематический сбор и анализ показателей состояния СУБД, запросов и инфраструктуры.

**Наблюдаемость (Observability)** — способность исследовать внутреннее состояние системы по доступным метрикам, журналам, трассировкам и другим диагностическим данным.

**Доступность (Availability)** — способность системы предоставлять необходимые функции в заданные моменты времени.

**Производительность (Performance)** — способность обрабатывать определённую нагрузку с требуемой задержкой и потреблением ресурсов.

**Latency** — задержка выполнения операции.

**Throughput** — количество обработанных операций за единицу времени.

**QPS (Queries Per Second)** — количество SQL-запросов в секунду.

**TPS (Transactions Per Second)** — количество транзакций в секунду.

**P50 / P95 / P99** — перцентили распределения времени ответа.

**SLA (Service Level Agreement)** — соглашение об уровне предоставления сервиса.

**SLO (Service Level Objective)** — целевое значение показателя качества сервиса.

**SLI (Service Level Indicator)** — измеряемый показатель качества сервиса.

**Connection** — подключение клиента к СУБД.

**Connection Pool** — пул подключений, предназначенный для повторного использования соединений.

**Active Session** — сессия, в которой в данный момент выполняется запрос или происходит ожидание в контексте выполнения.

**Idle Session** — подключение, не выполняющее запрос в данный момент.

**Idle in Transaction** — состояние PostgreSQL, при котором транзакция открыта, но сессия не выполняет запрос.

**CPU Utilization** — загрузка процессорных ресурсов.

**RAM** — оперативная память.

**I/O** — операции ввода и вывода.

**IOPS** — число операций ввода-вывода в секунду.

**I/O Latency** — время выполнения операции ввода-вывода.

**Buffer Cache** — кеш страниц данных СУБД.

**Shared Buffers** — буферный кеш PostgreSQL.

**Cache Hit Ratio** — доля обращений к буферным страницам, обслуженных из соответствующего кеша.

**WAL (Write-Ahead Logging)** — журнал предзаписи PostgreSQL.

**Checkpoint** — процесс создания согласованной точки восстановления посредством записи необходимых изменённых страниц и выполнения сопутствующих действий.

**Autovacuum** — автоматическое обслуживание таблиц PostgreSQL, включая VACUUM и ANALYZE.

**Dead Tuple** — версия строки PostgreSQL, доступная для очистки после завершения необходимых правил видимости.

**Lock** — механизм синхронизации конкурентных операций.

**Lock Wait** — ожидание освобождения конфликтующего ресурса.

**Deadlock** — циклическая взаимная блокировка транзакций.

**Wait Event** — событие, отражающее причину ожидания процесса СУБД.

**Slow Query Log** — журнал запросов, удовлетворяющих настроенным критериям медленного выполнения.

**EXPLAIN ANALYZE** — механизм получения фактического плана выполнения запроса в PostgreSQL.

**pg_stat_activity** — системное представление PostgreSQL со сведениями о процессах и текущей активности подключений.

**pg_stat_database** — представление с накопленной статистикой на уровне баз данных.

**pg_stat_user_tables** — статистика обращений и обслуживания пользовательских таблиц.

**pg_stat_user_indexes** — статистика использования индексов.

**pg_stat_io** — представление PostgreSQL со статистикой ввода-вывода по категориям процессов, объектов и контекстов.

**pg_stat_bgwriter** — статистика фонового процесса записи PostgreSQL.

**pg_stat_checkpointer** — статистика процесса контрольных точек PostgreSQL.

**pg_stat_wal** — статистика активности WAL.

**pg_stat_statements** — расширение PostgreSQL, собирающее агрегированную статистику выполнения SQL-запросов.

**pg_stat_statements.track** — параметр, определяющий глубину учёта запросов расширением.

**log_min_duration_statement** — параметр PostgreSQL, задающий порог длительности запроса для журналирования.

**log_lock_waits** — параметр PostgreSQL для записи определённых длительных ожиданий блокировок.

**deadlock_timeout** — интервал ожидания до проверки возможного deadlock в PostgreSQL, также используемый для некоторых событий логирования ожиданий.

**log_checkpoints** — параметр PostgreSQL для журналирования сведений о контрольных точках.

**track_io_timing** — параметр PostgreSQL для сбора времени операций ввода-вывода.

**Performance Schema** — подсистема MySQL для сбора диагностических данных об активности сервера.

**sys Schema** — набор представлений и вспомогательных объектов MySQL для удобного анализа данных Performance Schema и системных сведений.

**Query Store** — механизм SQL Server для сохранения истории запросов, планов и показателей выполнения.

**Dynamic Management Views (DMV)** — системные представления SQL Server для получения текущих и накопленных диагностических данных.

**DBMS_XPLAN** — пакет Oracle для просмотра планов выполнения.

**AWR (Automatic Workload Repository)** — механизм Oracle для хранения исторической статистики нагрузки, использование которого может требовать соответствующего лицензирования.

**ASH (Active Session History)** — механизм анализа активности сессий Oracle с отдельными требованиями к доступности и лицензированию.

**Prometheus** — система сбора и хранения метрик в виде временных рядов.

**Exporter** — компонент, предоставляющий метрики внешней системе мониторинга.

**PostgreSQL Exporter** — exporter для публикации метрик PostgreSQL.

**Grafana** — платформа визуализации и анализа данных наблюдаемости.

**Zabbix** — система мониторинга инфраструктуры и приложений.

**Percona Monitoring and Management (PMM)** — платформа мониторинга и диагностики баз данных.

**Dashboard** — панель визуализации показателей.

**Alerting** — механизм формирования оповещений при выполнении заданных условий.

**Baseline** — исходный или типичный профиль метрик, относительно которого анализируются изменения.

**Bottleneck** — ресурс или компонент, ограничивающий производительность.

**Cardinality** — количество элементов набора; в планах запросов часто означает оценочное количество строк.

**Sampling** — выборочный сбор данных вместо регистрации каждого события.

**Time Series** — последовательность измерений, привязанных ко времени.

**Retention** — срок и правила хранения диагностических данных.

**Metric Cardinality** — количество уникальных комбинаций меток временных рядов в системе метрик.

## Основная часть

### Тема 1. Мониторинг как основа управляемости базы данных

Работающая база данных постоянно меняет своё состояние.

Изменяются:

- количество подключений;
- число выполняемых запросов;
- объём данных;
- состояние индексов;
- интенсивность чтения и записи;
- количество конкурентных транзакций;
- нагрузка на CPU и память;
- активность WAL;
- состояние репликации.

Без мониторинга разработчик часто узнаёт о проблеме только после жалобы пользователя.

Например:

> Система оформления заказов стала медленно работать.

Само по себе это сообщение не объясняет причину.

Возможные варианты:

1. Изменился план SQL-запроса.
2. Появилась длительная блокировка.
3. Приложение открыло слишком много соединений.
4. Хранилище перестало справляться с записью.
5. Запросы начали использовать временные файлы.
6. Сервер перегружен параллельными вычислениями.
7. Реплика отстаёт и приложение ждёт доступности данных.

Мониторинг позволяет перейти от общего симптома к измеряемым фактам.

#### Мониторинг и наблюдаемость

Мониторинг обычно отвечает на вопросы:

- Работает ли база?
- Не превышены ли заданные пороги?
- Какие показатели изменились?
- Нужно ли отправить оповещение?

Наблюдаемость позволяет исследовать причины:

- Какие запросы создают нагрузку?
- Почему они стали медленнее?
- Какая транзакция удерживает блокировку?
- Какие операции выполнялись перед деградацией?
- Изменился ли план?
- Есть ли связь с нагрузкой приложения?

Для полноценной диагностики нужны не только графики, но и сведения о запросах, блокировках, ожиданиях и событиях.

#### Мониторинг не гарантирует доступность

Мониторинг помогает обнаруживать проблемы и реагировать на них.

Но сам по себе он не обеспечивает высокую доступность.

Для отказоустойчивости дополнительно необходимы:

- резервное копирование;
- репликация;
- механизмы восстановления;
- автоматизация переключений;
- управление ресурсами;
- процедуры реагирования на инциденты.

Мониторинг является необходимой частью эксплуатации, но не заменяет эти механизмы.

### Тема 2. Основные направления мониторинга СУБД

Мониторинг базы данных должен охватывать несколько уровней.

#### Уровень SQL

Необходимо отслеживать:

- частоту выполнения запросов;
- среднее и суммарное время;
- задержки отдельных запросов;
- количество возвращённых и изменённых строк;
- планы выполнения;
- появление дорогих операций.

#### Уровень транзакций

Важны:

- количество активных транзакций;
- их продолжительность;
- ошибки и откаты;
- ожидания блокировок;
- deadlock;
- длительные idle in transaction.

#### Уровень СУБД

Необходимо контролировать:

- число соединений;
- буферный кеш;
- фоновую запись;
- контрольные точки;
- autovacuum;
- WAL;
- состояние репликации;
- свободные ресурсы.

#### Уровень операционной системы

Основные показатели:

- CPU;
- RAM;
- дисковая подсистема;
- сеть;
- ограничения контейнера или виртуальной машины.

#### Уровень приложения

Полезно знать:

- время пользовательских операций;
- количество запросов на одну операцию;
- ожидание соединения из пула;
- ошибки доступа к БД;
- тайм-ауты;
- количество повторных попыток.

Одна и та же проблема может проявляться сразу на нескольких уровнях.

Например, большое количество зависших HTTP-запросов может оказаться следствием одной транзакции, удерживающей блокировку в PostgreSQL.

### Тема 3. Время выполнения запросов

Время выполнения SQL — один из основных показателей производительности.

Но необходимо определить, что именно измеряется.

#### Серверное время

В PostgreSQL `EXPLAIN ANALYZE` измеряет выполнение запроса на стороне сервера.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 1001;
```

В результате можно увидеть:

```text
Planning Time
Execution Time
```

Показатель Execution Time не обязан включать полную стоимость передачи и обработки результата клиентом.

#### Время приложения

Приложение может измерять время от отправки SQL до получения всех строк.

Это время дополнительно включает:

- сетевую передачу;
- обработку протокола;
- ожидание клиента;
- сериализацию результата;
- чтение всех строк из курсора.

Поэтому серверный запрос может выполняться быстро, но приложение долго получать миллион строк.

#### Длительность запроса и частота

Предположим:

- запрос A занимает 2 секунды, выполняется один раз в сутки;
- запрос B занимает 20 мс, выполняется 500 000 раз в сутки.

Запрос B создаёт значительно больше суммарного времени работы.

Поэтому мониторинг должен показывать не только самые медленные отдельные запросы, но и запросы с наибольшим суммарным потреблением ресурсов.

#### Перцентили

Среднее время полезно, но часто недостаточно.

Например:

| Показатель | Время |
|---|---:|
| P50 | 15 мс |
| P95 | 120 мс |
| P99 | 1500 мс |

Большинство операций выполняется быстро, но часть запросов имеет большие задержки.

Причиной могут быть:

- блокировки;
- перегрузка ресурсов;
- неудачные планы для отдельных параметров;
- пики фоновой нагрузки;
- сетевые проблемы.

Для диагностики необходимо изучать распределение задержек и время появления выбросов.

### Тема 4. Throughput, QPS и TPS

Throughput показывает количество успешно обработанной работы за единицу времени.

Для базы данных используются:

```text
QPS — запросы в секунду
TPS — транзакции в секунду
```

Но сравнивать эти показатели без определения нагрузки нельзя.

Например, одна транзакция может содержать один SELECT.

Другая — десять UPDATE, вставку журнала и проверку ограничений.

Поэтому одинаковый TPS не означает одинаковую вычислительную нагрузку.

#### Рост QPS

Если QPS растёт, а время ответа остаётся стабильным, база может успешно справляться с увеличением нагрузки.

Если вместе с QPS растут:

- latency;
- очередь запросов;
- CPU;
- число активных соединений;

возможно приближение к пределу производительности.

Но причины необходимо проверять.

#### Низкий QPS и высокая latency

Такое сочетание может возникать, если запросы:

- ожидают блокировки;
- ожидают свободное подключение;
- используют медленное хранилище;
- выполняют тяжёлую работу;
- ожидают сетевое взаимодействие.

Следовательно, небольшой QPS не гарантирует отсутствия перегрузки.

#### Метрики как временные ряды

Важно анализировать скорость изменения, а не просто текущее значение.

Например, если за одну минуту число подтверждённых транзакций выросло на 12 000, среднее значение за эту минуту составляет 200 TPS.

При использовании накопительных счётчиков необходимо учитывать:

- сброс статистики;
- перезапуск;
- изменение интервала наблюдения;
- пропущенные измерения.

### Тема 5. Подключения к базе данных

Каждое подключение использует ресурсы СУБД.

В PostgreSQL обычное клиентское соединение обслуживается отдельным серверным процессом.

Поэтому большое количество подключений влияет на:

- память;
- переключение процессов;
- число конкурентных запросов;
- управление транзакциями;
- использование ресурсов операционной системы.

#### Проверка количества подключений

```sql
SELECT
    state,
    COUNT(*) AS connections_count
FROM pg_stat_activity
WHERE datname = current_database()
  AND backend_type = 'client backend'
GROUP BY state
ORDER BY connections_count DESC;
```

Возможные состояния:

- `active`;
- `idle`;
- `idle in transaction`;
- `idle in transaction (aborted)`.

#### Active не означает CPU-загрузку

Сессия со статусом `active` может:

- выполнять вычисления;
- читать данные;
- ожидать блокировку;
- ожидать I/O;
- ожидать другой ресурс.

Поэтому количество active-сессий не равно количеству запросов, одновременно использующих CPU.

#### Idle

Обычное состояние `idle` означает, что соединение ожидает следующую команду клиента.

Для пула подключений это может быть нормальным.

Но чрезмерное число простаивающих соединений потребляет ресурсы и может приводить к исчерпанию лимитов.

#### Idle in Transaction

Особенно важно состояние:

```text
idle in transaction
```

Оно означает, что транзакция открыта, но клиент в данный момент не выполняет SQL-команду.

Такая сессия может:

- удерживать блокировки;
- препятствовать обслуживанию старых версий строк;
- задерживать DDL;
- увеличивать расходы на хранение.

Поэтому такие транзакции необходимо отслеживать отдельно.

#### Connection Pool

Для приложений часто используются пулы подключений.

Они уменьшают стоимость постоянного открытия новых соединений.

Но неправильно настроенный пул может создавать проблемы:

- слишком много соединений;
- слишком длинное ожидание свободного соединения;
- удержание соединения во время внешних операций;
- утечки соединений;
- слишком длинные транзакции.

Мониторинг базы необходимо сопоставлять с метриками пула приложений.

### Тема 6. Мониторинг CPU

CPU используется при:

- фильтрации;
- вычислении выражений;
- сортировке;
- построении хеш-таблиц;
- соединении данных;
- агрегации;
- обработке JSON;
- выполнении процедурного кода.

Высокая загрузка CPU может означать:

- большое количество запросов;
- дорогостоящие вычисления;
- чрезмерный параллелизм;
- неудачные планы;
- интенсивную фоновую работу.

Но высокая CPU-загрузка сама по себе не означает проблему.

Если база соблюдает заданные показатели latency и throughput, активное использование CPU может быть ожидаемым.

#### Диагностика

При росте CPU полезно проверить:

1. Какие запросы стали выполняться чаще?
2. Какие запросы имеют наибольшее суммарное время?
3. Изменились ли планы?
4. Увеличилось ли число активных запросов?
5. Не возник ли чрезмерный параллелизм?
6. Какие процессы потребляют CPU?

Для PostgreSQL сведения о текущих запросах предоставляет `pg_stat_activity`, а агрегированную статистику запросов — `pg_stat_statements`.

Для системных метрик необходим мониторинг операционной системы или инфраструктуры.

### Тема 7. Мониторинг памяти

RAM используется для:

- буферного кеша;
- сортировок;
- хеш-соединений;
- хеш-агрегаций;
- служебных структур;
- процессов клиентских подключений.

#### Shared Buffers

В PostgreSQL `shared_buffers` определяет размер буферного кеша СУБД.

Проверка:

```sql
SHOW shared_buffers;
```

Однако PostgreSQL также использует файловый кеш операционной системы.

Поэтому общий объём полезного кеширования не ограничивается только shared_buffers.

#### Work Mem

```sql
SHOW work_mem;
```

Параметр влияет на бюджет памяти отдельных операций запроса.

Важно: `work_mem` не является общим лимитом памяти одного SQL-запроса.

Один запрос может содержать несколько сортировок и хеш-операций, а несколько запросов могут выполняться одновременно.

Поэтому чрезмерное увеличение `work_mem` способно привести к избыточному потреблению RAM.

#### Временные файлы

Если операция не помещается в предоставленный бюджет памяти, PostgreSQL может использовать временные файлы.

В плане можно увидеть:

```text
Sort Method: external merge
```

или соответствующую статистику временного ввода-вывода.

Но увеличение RAM не всегда является правильным решением.

Возможно, запрос обрабатывает слишком много ненужных строк или требует другого индекса.

### Тема 8. Мониторинг диска и I/O

Для базы данных важны не только объём чтения и записи, но и задержки.

Основные показатели:

- IOPS;
- MB/s;
- latency;
- очередь операций;
- свободное место;
- интенсивность записи WAL;
- временные файлы.

#### Источники I/O-нагрузки

- последовательные сканирования;
- случайный индексный доступ;
- массовые INSERT и UPDATE;
- запись WAL;
- checkpoint;
- VACUUM;
- сортировки;
- хеширование с временными файлами;
- резервное копирование.

#### Логические и физические чтения

PostgreSQL может находить страницы в shared buffers.

При отсутствии страницы в этом кеше она читается через файловую подсистему.

Но это не обязательно физическое чтение SSD, поскольку страница может находиться в кеше ОС.

Поэтому:

```text
shared read
```

в EXPLAIN не следует трактовать как точное число физических дисковых операций.

Для диагностики необходимо сопоставлять статистику СУБД и метрики операционной системы.

#### Временное пространство

В PostgreSQL:

```sql
SELECT
    datname,
    temp_files,
    pg_size_pretty(temp_bytes) AS temp_written
FROM pg_stat_database
WHERE datname = current_database();
```

Показатели накопительные.

Они помогают определить масштаб использования временных файлов.

Но один большой объём temp_bytes не указывает автоматически на конкретный запрос.

Для поиска источника необходимо использовать статистику запросов, планы и соответствующее логирование.

### Тема 9. Блокировки и ожидания транзакций

Блокировки обеспечивают корректность конкурентного доступа.

Но длительное ожидание блокировки может замедлить целую цепочку операций.

Например:

1. Транзакция A обновляет заказ.
2. Транзакция A остаётся открытой.
3. Транзакция B пытается изменить тот же заказ.
4. Транзакция B ожидает.
5. Другие операции также начинают накапливать ожидания.

При этом запрос B может почти не использовать CPU.

Его задержка определяется ожиданием.

#### pg_stat_activity

Для просмотра текущих сессий:

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    xact_start,
    query_start,
    query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY query_start NULLS LAST;
```

#### Активный запрос и ожидание

Если:

```text
state = active
wait_event_type = Lock
```

процесс выполняет запрос, но находится в ожидании блокировки.

Если `wait_event_type` равен `IO`, процесс ожидает операцию ввода-вывода в соответствующей категории.

Но отсутствие wait_event_type не означает автоматически, что процесс постоянно использует CPU.

Это моментальный снимок состояния.

#### Поиск блокирующих процессов

```sql
SELECT
    a.pid,
    a.usename,
    a.state,
    a.wait_event_type,
    a.wait_event,
    pg_blocking_pids(a.pid) AS blocking_pids,
    a.query
FROM pg_stat_activity AS a
WHERE a.datname = current_database()
  AND cardinality(pg_blocking_pids(a.pid)) > 0;
```

Функция `pg_blocking_pids` возвращает идентификаторы процессов, блокирующих указанный процесс.

Для диагностики блокировок это часто удобнее, чем самостоятельно пытаться интерпретировать все отношения между записями `pg_locks`.

#### Почему нельзя автоматически завершать блокирующую сессию

Блокирующая транзакция может выполнять важную операцию.

Принудительное завершение способно вызвать:

- откат большого объёма изменений;
- ошибки приложения;
- повторные попытки;
- дополнительную нагрузку;
- потерю прогресса длительной операции.

Поэтому перед вмешательством необходимо определить владельца операции, её назначение и последствия отмены.

### Тема 10. Долгие транзакции

Длительная транзакция может влиять на производительность даже в момент, когда не выполняет SQL.

В PostgreSQL длительные снимки могут препятствовать очистке устаревших версий строк.

Это способствует накоплению физической работы по обслуживанию данных.

#### Поиск долгих транзакций

```sql
SELECT
    pid,
    usename,
    state,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = current_database()
  AND xact_start IS NOT NULL
ORDER BY xact_start;
```

Необходимо учитывать, что продолжительность транзакции не равна времени выполнения текущего запроса.

Транзакция может содержать несколько SQL-команд и периоды ожидания между ними.

#### Контроль idle in transaction

```sql
SELECT
    pid,
    usename,
    now() - xact_start AS transaction_age,
    now() - state_change AS idle_duration,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND datname = current_database()
ORDER BY xact_start;
```

Этот запрос позволяет найти сессии, которые удерживают открытые транзакции без текущего выполнения SQL.

Для защиты PostgreSQL предоставляет:

```sql
SHOW idle_in_transaction_session_timeout;
```

Параметр может ограничивать время простоя внутри транзакции.

Но устанавливать его необходимо с учётом поведения приложений, чтобы не прерывать ожидаемые долгие операции.

### Тема 11. Кеширование и Cache Hit Ratio

Кеширование позволяет уменьшить количество обращений к файловой подсистеме.

PostgreSQL использует shared buffers, а операционная система может дополнительно кешировать страницы файлов.

#### Расчёт Cache Hit Ratio

На уровне базы:

```sql
SELECT
    datname,
    blks_hit,
    blks_read,
    ROUND(
        100.0 * blks_hit /
        NULLIF(blks_hit + blks_read, 0),
        2
    ) AS cache_hit_percent
FROM pg_stat_database
WHERE datname = current_database();
```

Показатель отражает долю обращений к страницам, обслуженных из PostgreSQL shared buffers, в рамках данной статистики.

#### Высокий Cache Hit Ratio

Высокий показатель часто означает, что значительная доля обращений обслуживается из буферного кеша PostgreSQL.

Но это не гарантирует низкую задержку SQL.

Запрос может:

- выполнять дорогие вычисления;
- ожидать блокировку;
- обрабатывать миллионы строк;
- возвращать большой результат.

#### Низкий Cache Hit Ratio

Низкий показатель не обязательно означает нехватку RAM.

Например, большая последовательная аналитическая выгрузка может читать данные, которые редко повторно используются.

Даже при достаточной памяти такое чтение может снижать общий hit ratio.

#### Почему нельзя ориентироваться на универсальный порог

Иногда предлагается считать, что cache hit ratio обязательно должен быть выше фиксированного значения, например 99%.

Это слишком сильное обобщение.

Нормальное значение зависит от:

- размера рабочего набора;
- характера запросов;
- объёма последовательных чтений;
- режима нагрузки;
- размера буферного кеша;
- частоты повторного использования страниц.

Поэтому метрику нужно сравнивать с собственным историческим профилем системы.

### Тема 12. Ключевые метрики в динамике

Для мониторинга полезно одновременно наблюдать несколько показателей.

| Метрика | Что показывает | Возможный сигнал |
|---|---|---|
| Latency P95/P99 | Задержки операций | Деградация пользовательского отклика |
| QPS/TPS | Интенсивность обработки | Изменение нагрузки |
| Active connections | Активные подключения | Рост конкурентной работы или ожиданий |
| Idle in transaction | Простаивающие открытые транзакции | Риск удержания ресурсов |
| Lock waits | Ожидания блокировок | Конкурентные конфликты |
| CPU utilization | Вычислительная нагрузка | Ограничение по CPU |
| I/O latency | Задержки хранения | Ограничение подсистемы I/O |
| Temp bytes | Работа с временными файлами | Дорогие сортировки и хеш-операции |
| WAL rate | Интенсивность журналирования | Высокая нагрузка записи |
| Replication lag | Отставание реплики | Риск устаревших данных на реплике |
| Dead tuples | Оценка мёртвых версий | Необходимость исследовать VACUUM |

Важно: отдельная метрика обычно не доказывает причину проблемы.

Например:

```text
Latency растёт
CPU низкий
Lock waits высокие
```

Это похоже на проблему ожиданий, а не нехватку вычислительных ресурсов.

А:

```text
Latency растёт
CPU высокий
Lock waits низкие
```

может указывать на вычислительную перегрузку.

Но окончательный вывод требует проверки конкретных запросов и процессов.

### Тема 13. Встроенные инструменты PostgreSQL

PostgreSQL предоставляет несколько категорий диагностических средств.

#### Текущая активность

```sql
pg_stat_activity
```

Позволяет наблюдать за процессами и запросами.

#### Накопленная статистика базы

```sql
pg_stat_database
```

Содержит показатели транзакций, буферов, временных файлов и других операций.

#### Таблицы

```sql
pg_stat_user_tables
```

Позволяет анализировать:

- последовательные и индексные сканирования;
- вставки;
- обновления;
- удаления;
- оценки живых и мёртвых строк;
- работу VACUUM и ANALYZE.

#### Индексы

```sql
pg_stat_user_indexes
```

Предоставляет статистику использования индексов.

#### Ввод-вывод

```sql
pg_stat_io
```

Позволяет исследовать активность ввода-вывода по категориям процессов и контекстам.

#### WAL

```sql
pg_stat_wal
```

Предоставляет накопленную статистику операций WAL.

#### Checkpoint

В PostgreSQL 18 для контрольных точек используется:

```sql
pg_stat_checkpointer
```

А:

```sql
pg_stat_bgwriter
```

предоставляет статистику background writer.

Это важно: в старых версиях PostgreSQL часть checkpoint-показателей находилась в `pg_stat_bgwriter`.

Поэтому запросы мониторинга нельзя без проверки переносить между версиями.

#### Статистика обновляется не мгновенно

Накопленные счётчики PostgreSQL могут обновляться с задержкой.

Также полученные статистические данные могут кешироваться до завершения текущей транзакции.

Поэтому несколько чтений статистики внутри одной длительной транзакции могут показывать одинаковые значения.

Для принудительного сброса локального снимка статистики существует:

```sql
SELECT pg_stat_clear_snapshot();
```

Но использование этой функции не делает все показатели абсолютно синхронными с выполняющимися операциями.

Для текущего состояния запросов используется отдельная динамическая статистика.

### Тема 14. pg_stat_database

Представление `pg_stat_database` содержит агрегированные показатели по базам данных.

Пример:

```sql
SELECT
    datname,
    numbackends,
    xact_commit,
    xact_rollback,
    blks_read,
    blks_hit,
    tup_returned,
    tup_fetched,
    tup_inserted,
    tup_updated,
    tup_deleted,
    deadlocks,
    temp_files,
    temp_bytes
FROM pg_stat_database
WHERE datname = current_database();
```

#### numbackends

Текущее количество подключённых backend-процессов к соответствующей базе.

Это текущий показатель, а не накопительный счётчик соединений.

#### xact_commit

Количество подтверждённых транзакций за период накопления статистики.

#### xact_rollback

Количество транзакций, завершённых откатом в учёте PostgreSQL.

Нельзя автоматически считать каждый rollback ошибкой приложения.

Откат может быть нормальной частью бизнес-логики или диагностического эксперимента.

#### blks_read и blks_hit

Показывают обращения к страницам, включая попадания в кеш PostgreSQL.

Но не являются точным измерением физических операций накопителя.

#### deadlocks

Накопленное количество обнаруженных deadlock.

Даже один deadlock может быть важным событием, если он регулярно затрагивает критичную операцию.

Но значение счётчика следует анализировать относительно временного интервала.

#### Накопительные значения

Многие показатели `pg_stat_database` являются накопительными.

Чтобы вычислить скорость, нужны два измерения и интервал между ними.

Например:

```text
TPS ≈ изменение xact_commit за период / секунды периода
```

Также необходимо учитывать `stats_reset`.

### Тема 15. pg_stat_io, pg_stat_bgwriter и pg_stat_checkpointer

#### pg_stat_io

В PostgreSQL 18:

```sql
SELECT
    backend_type,
    object,
    context,
    reads,
    writes,
    extends,
    hits,
    evictions
FROM pg_stat_io
ORDER BY backend_type, object, context;
```

Представление предоставляет статистику по категориям процессов, объектов и контекстов.

Оно позволяет исследовать, кто именно создаёт I/O-нагрузку.

Например:

- клиентские backend-процессы;
- autovacuum;
- фоновые процессы.

Но не все комбинации полей обязательно имеют осмысленные значения для каждого вида операции.

Нужно учитывать `NULL` и специфику статистики.

#### pg_stat_bgwriter

```sql
SELECT *
FROM pg_stat_bgwriter;
```

В современных PostgreSQL здесь находится статистика фоновой записи.

#### pg_stat_checkpointer

```sql
SELECT *
FROM pg_stat_checkpointer;
```

Здесь находятся показатели работы checkpointer.

Разделение позволяет точнее анализировать разные фоновые механизмы.

#### pg_stat_wal

```sql
SELECT *
FROM pg_stat_wal;
```

Важны:

- количество WAL-записей;
- объём WAL;
- полные образы страниц;
- буферные операции WAL;
- статистика записи и синхронизации при соответствующей настройке.

Для диагностики массовых INSERT и UPDATE полезно измерять прирост WAL за определённый период.

### Тема 16. Мониторинг autovacuum

Autovacuum необходим для нормальной работы PostgreSQL.

Он:

- обслуживает устаревшие версии строк;
- обновляет служебную информацию;
- участвует в предотвращении переполнения идентификаторов транзакций;
- запускает ANALYZE.

#### Статистика таблиц

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    last_autoanalyze,
    autovacuum_count,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

`n_dead_tup` — оценка, а не точное число строк, которые можно немедленно очистить.

Большое значение может быть поводом для исследования.

Но оно не является абсолютным доказательством проблемы.

#### Текущий прогресс VACUUM

```sql
SELECT
    pid,
    relid::regclass AS relation_name,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed
FROM pg_stat_progress_vacuum;
```

Этот запрос помогает увидеть текущие операции VACUUM.

Но не каждая операция обслуживания отражается в одном и том же представлении прогресса.

#### Длительные транзакции

Если старая транзакция удерживает снимок данных, VACUUM может не иметь права удалить некоторые старые версии.

Поэтому проблему накопления версий нельзя всегда решить только увеличением количества autovacuum workers.

Нужно также исследовать длительные транзакции и репликационные механизмы.

### Тема 17. pg_stat_statements

`pg_stat_statements` — расширение PostgreSQL для сбора агрегированной статистики SQL-запросов.

Оно помогает найти:

- часто выполняемые запросы;
- запросы с большим суммарным временем;
- запросы с большим средним временем;
- запросы с большим количеством чтений;
- операции, создающие заметную нагрузку.

#### Установка

Проверим настройку:

```sql
SHOW shared_preload_libraries;
```

Для полноценного сбора статистики расширение обычно должно быть включено в `shared_preload_libraries`.

Например:

```text
shared_preload_libraries = 'pg_stat_statements'
```

Если используется несколько модулей, их необходимо учитывать вместе, а не заменять значение параметра без проверки.

Изменение `shared_preload_libraries` требует перезапуска PostgreSQL.

После загрузки модуля в нужной базе:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

Для выполнения этих действий нужны соответствующие права.

#### Основные настройки

```sql
SHOW pg_stat_statements.track;
```

```sql
SHOW pg_stat_statements.max;
```

```sql
SHOW pg_stat_statements.track_planning;
```

`pg_stat_statements.track` определяет глубину сбора вложенных запросов.

`max` ограничивает количество сохраняемых различных записей статистики.

`track_planning` управляет дополнительным учётом планирования при соответствующей настройке.

#### Топ запросов по суммарному времени

```sql
SELECT
    query,
    calls,
    ROUND(total_exec_time::numeric, 2)
        AS total_exec_ms,
    ROUND(mean_exec_time::numeric, 2)
        AS mean_exec_ms,
    rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

Этот запрос показывает кандидатов для оптимизации по суммарному времени выполнения.

#### Топ по среднему времени

```sql
SELECT
    query,
    calls,
    ROUND(mean_exec_time::numeric, 2)
        AS mean_exec_ms,
    ROUND(max_exec_time::numeric, 2)
        AS max_exec_ms
FROM pg_stat_statements
WHERE calls > 0
ORDER BY mean_exec_time DESC
LIMIT 20;
```

#### Частые запросы

```sql
SELECT
    query,
    calls,
    ROUND(total_exec_time::numeric, 2)
        AS total_exec_ms
FROM pg_stat_statements
ORDER BY calls DESC
LIMIT 20;
```

#### Ограничения pg_stat_statements

Необходимо помнить:

- статистика агрегированная;
- текст запросов нормализуется в рамках механизма группировки;
- разные значения параметров часто учитываются совместно;
- статистика не является полной трассировкой каждого вызова;
- история ограничена конфигурацией и состоянием счётчиков;
- отдельные сведения могут быть недоступны без соответствующих прав;
- сброс статистики влияет на интерпретацию результатов.

Поэтому для анализа проблемы с определёнными параметрами запроса могут потребоваться дополнительные логи и прикладная трассировка.

### Тема 18. Логи медленных запросов PostgreSQL

PostgreSQL позволяет записывать в журнал запросы, выполнение которых превысило определённый порог.

Основной параметр:

```sql
SHOW log_min_duration_statement;
```

Значение задаётся в миллисекундах, если не указаны другие единицы.

Например, значение `500ms` означает регистрацию запросов, достигших соответствующего порога длительности.

#### Настройка

В конфигурации PostgreSQL:

```text
log_min_duration_statement = '500ms'
```

Для временного эксперимента администратор может использовать настройки конкретной сессии.

Например:

```sql
SET log_min_duration_statement = '200ms';
```

Это требует соответствующих прав.

Не следует считать, что любой пользователь может произвольно менять настройки журналирования.

#### Перезагрузка конфигурации

После изменения параметров, допускающих применение без перезапуска, можно выполнить:

```sql
SELECT pg_reload_conf();
```

Но эта функция не делает все параметры динамически изменяемыми.

Например, изменение `shared_preload_libraries` требует перезапуска сервера.

#### log_min_duration_statement

Этот параметр помогает находить медленные запросы.

Но лог медленных запросов не объясняет сам по себе причину задержки.

Он показывает факт превышения порога, после чего необходимо исследовать:

- план выполнения;
- блокировки;
- нагрузку;
- параметры;
- объём данных.

#### log_lock_waits

Для диагностики ожиданий блокировок используется:

```sql
SHOW log_lock_waits;
```

При включении журналируются определённые ожидания, продолжительность которых связана с `deadlock_timeout`.

#### deadlock_timeout

```sql
SHOW deadlock_timeout;
```

Этот параметр определяет интервал до проверки на возможный deadlock.

При включённом `log_lock_waits` он также влияет на порог регистрации ожиданий блокировок.

Изменять его без необходимости не следует: слишком маленькое значение может увеличить накладные расходы на проверки.

#### Осторожно с логированием всех запросов

Установка слишком низкого порога может привести к большому объёму журналов.

Это создаёт:

- дополнительную нагрузку на запись;
- расход диска;
- необходимость ротации;
- дополнительные требования к защите логов.

Кроме того, SQL-тексты и сообщения могут содержать чувствительную информацию.

Поэтому настройки логирования должны учитывать безопасность и срок хранения.

### Тема 19. pgAdmin как средство диагностики

pgAdmin — графический клиент для работы с PostgreSQL.

Он позволяет:

- просматривать объекты базы;
- выполнять SQL;
- исследовать планы выполнения;
- просматривать некоторые статистические сведения;
- администрировать доступные объекты.

Но pgAdmin не является полноценной заменой непрерывного внешнего мониторинга.

Для длительной истории метрик, алертов и сопоставления нагрузки нескольких серверов удобнее специализированные системы наблюдаемости.

#### Диагностический запрос

Например, через Query Tool:

```sql
SELECT
    pid,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = current_database();
```

Или:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Графический клиент может визуализировать дерево плана, но смысл показателей не меняется.

Необходимо понимать:

- estimated rows;
- actual rows;
- loops;
- Buffers;
- Execution Time.

### Тема 20. Мониторинг MySQL/InnoDB

MySQL предоставляет собственные инструменты диагностики.

Основные:

- Performance Schema;
- sys Schema;
- Slow Query Log;
- EXPLAIN;
- EXPLAIN ANALYZE;
- MySQL Enterprise Monitor и внешние системы.

#### Performance Schema

Performance Schema собирает данные о выполнении операций внутри сервера.

Она позволяет анализировать:

- SQL-активность;
- ожидания;
- блокировки;
- обращения к таблицам;
- использование ресурсов;
- статистику событий.

Пример:

```sql
SELECT
    DIGEST_TEXT,
    COUNT_STAR,
    SUM_TIMER_WAIT,
    AVG_TIMER_WAIT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;
```

Временные показатели Performance Schema обычно представлены в пикосекундах в соответствующих колонках и требуют корректного преобразования для отображения в миллисекундах или секундах.

Также необходимо учитывать, какие instruments и consumers включены.

#### sys Schema

MySQL предоставляет удобные представления в схеме `sys`.

Например:

```sql
SELECT *
FROM sys.statement_analysis
LIMIT 20;
```

Они помогают анализировать агрегированную статистику без необходимости каждый раз вручную интерпретировать низкоуровневые показатели Performance Schema.

#### Slow Query Log

MySQL поддерживает журнал медленных запросов.

Основные параметры:

```text
slow_query_log
long_query_time
```

Проверка:

```sql
SHOW VARIABLES LIKE 'slow_query_log';
```

```sql
SHOW VARIABLES LIKE 'long_query_time';
```

Включение и способ хранения журнала зависят от конфигурации сервера.

Лог полезен для поиска долгих SQL-операций, но не заменяет профилирование и план выполнения.

#### InnoDB

Для диагностики InnoDB также важны:

- состояние буферного пула;
- redo log;
- блокировки;
- транзакции;
- purge;
- временные структуры;
- статистика индексов.

Необходимо учитывать, что реализация MVCC в InnoDB отличается от PostgreSQL.

Поэтому нельзя напрямую переносить понятия heap dead tuples и visibility map в мониторинг MySQL.

### Тема 21. Мониторинг SQL Server

Microsoft SQL Server предоставляет развитые встроенные средства наблюдаемости.

Основные:

- Dynamic Management Views;
- Query Store;
- Actual Execution Plan;
- Extended Events;
- Wait Statistics;
- `SET STATISTICS IO`;
- `SET STATISTICS TIME`.

#### Активные запросы

Пример:

```sql
SELECT
    r.session_id,
    r.status,
    r.command,
    r.cpu_time,
    r.total_elapsed_time,
    r.wait_type,
    r.wait_time,
    r.blocking_session_id
FROM sys.dm_exec_requests AS r
WHERE r.session_id <> @@SPID;
```

Здесь можно увидеть:

- текущие запросы;
- затраченное CPU-время;
- общее время;
- ожидания;
- блокирующие сессии.

Но соответствующие DMV могут требовать дополнительных разрешений.

#### Статистика ожиданий

SQL Server предоставляет накопленную статистику ожиданий.

Например:

```sql
SELECT TOP (20)
    wait_type,
    waiting_tasks_count,
    wait_time_ms
FROM sys.dm_os_wait_stats
ORDER BY wait_time_ms DESC;
```

Не каждое ожидание является проблемой.

В статистике присутствуют и фоновые ожидания, нормальные для работы СУБД.

Поэтому при анализе необходимо исключать нерелевантные категории и учитывать временной интервал.

#### Query Store

Query Store позволяет изучать:

- историю выполнения запросов;
- изменение планов;
- регрессии производительности;
- распределение времени;
- влияние изменений оптимизатора и статистики.

Это особенно полезно, когда проблема возникла не в момент непосредственного наблюдения администратора.

#### Extended Events

Extended Events используется для сбора событий SQL Server.

Он позволяет создавать диагностические сессии для:

- ошибок;
- deadlock;
- длительных запросов;
- отдельных событий выполнения;
- других задач диагностики.

Собирать всё подряд не следует: детализация мониторинга должна соответствовать задаче и допустимым накладным расходам.

### Тема 22. Мониторинг Oracle

Oracle предоставляет собственные системные представления и инструменты анализа производительности.

Основные:

- `V$SESSION`;
- `V$SQL`;
- `V$SQL_PLAN`;
- `DBMS_XPLAN`;
- SQL Monitor;
- AWR;
- ASH;
- `DBMS_STATS`.

#### Активные сессии

Пример:

```sql
SELECT
    sid,
    serial#,
    username,
    status,
    event,
    wait_class,
    sql_id
FROM v$session
WHERE type = 'USER';
```

Этот запрос позволяет получить сведения о пользовательских сессиях и ожиданиях.

Для доступа необходимы соответствующие права.

#### SQL-статистика

Oracle хранит сведения о выполнении SQL через динамические представления.

При анализе важно учитывать:

- SQL ID;
- количество выполнений;
- суммарное время;
- CPU-время;
- чтения;
- планы выполнения;
- ожидания.

#### AWR и ASH

AWR и ASH предоставляют исторические данные о нагрузке и активности.

Но их использование может требовать соответствующего лицензирования Oracle Diagnostics Pack.

Поэтому нельзя рекомендовать эти инструменты без проверки лицензии и доступности в используемой редакции.

Для базовой диагностики доступны и другие средства Oracle.

### Тема 23. Внешние системы мониторинга

Встроенные средства СУБД полезны для диагностики, но они не всегда предоставляют удобную долговременную историю и оповещения.

Для этого используются внешние системы мониторинга.

#### Prometheus

Prometheus собирает метрики в виде временных рядов.

Обычно он периодически обращается к HTTP endpoint, предоставляющему метрики.

Для PostgreSQL часто используется postgres_exporter.

Схема:

```text
PostgreSQL
    |
    v
postgres_exporter
    |
    v
Prometheus
    |
    v
Grafana / Alertmanager
```

Exporter преобразует сведения PostgreSQL в формат метрик.

Prometheus сохраняет временные ряды и позволяет выполнять запросы на языке PromQL.

Grafana визуализирует данные.

Alertmanager может обрабатывать и маршрутизировать оповещения.

#### Grafana

Grafana позволяет строить:

- временные графики;
- таблицы;
- панели состояния;
- сравнения периодов;
- дашборды;
- оповещения при соответствующей конфигурации.

Но Grafana сама по себе не создаёт метрики PostgreSQL.

Для этого нужен источник данных.

#### Zabbix

Zabbix обеспечивает мониторинг инфраструктуры, серверов и приложений.

Он поддерживает:

- сбор метрик;
- шаблоны;
- триггеры событий;
- оповещения;
- историю показателей.

Для PostgreSQL могут использоваться соответствующие шаблоны и способы подключения.

#### Percona Monitoring and Management

PMM ориентирована на диагностику и мониторинг баз данных.

Она объединяет:

- системные метрики;
- метрики СУБД;
- анализ запросов;
- панели наблюдаемости;
- средства диагностики.

Конкретные поддерживаемые версии и компоненты необходимо проверять по документации используемой версии PMM.

#### Выбор инструмента

Он зависит от:

- числа серверов;
- СУБД;
- требований к истории;
- необходимых оповещений;
- существующей инфраструктуры;
- компетенций команды;
- стоимости эксплуатации.

Нет необходимости устанавливать одновременно все перечисленные системы.

### Тема 24. Метрики, логи и трассировки

Полноценная наблюдаемость объединяет несколько типов данных.

#### Метрики

Например:

```text
QPS
CPU
Connections
Lock Waits
WAL bytes/sec
```

Метрики удобны для:

- графиков;
- алертов;
- анализа тенденций;
- сравнения периодов.

Но они часто агрегированы и не показывают подробности каждого SQL-вызова.

#### Логи

Журналы содержат отдельные события:

- SQL-ошибки;
- deadlock;
- долгие запросы;
- сбои репликации;
- изменения состояния.

Они полезны для расследования конкретных событий.

Но слишком подробное журналирование способно создавать значительную нагрузку.

#### Трассировки

Распределённая трассировка приложения помогает увидеть путь пользовательского запроса.

Например:

```text
HTTP request
    |
    v
Application
    |
    +-- SQL query A
    |
    +-- External API
    |
    +-- SQL query B
```

Это позволяет понять, какой вклад база данных вносит в общее время операции.

Даже если SQL выполняется за 10 мс, пользовательский запрос может занимать секунды из-за других этапов.

#### Связь диагностических данных

Полезно иметь возможность сопоставить:

- request ID;
- trace ID;
- имя сервиса;
- SQL query identifier;
- время;
- информацию о транзакции.

При этом следует избегать передачи чувствительных данных в незащищённые метки и журналы.

### Тема 25. Построение дашборда

Дашборд должен помогать отвечать на конкретные вопросы.

Не следует добавлять все доступные метрики без понимания их назначения.

#### Базовая панель состояния PostgreSQL

Полезно показать:

| Блок | Основные показатели |
|---|---|
| Доступность | Результат проверки подключения |
| Нагрузка | TPS, QPS, active sessions |
| Задержки | P95/P99 приложения, длительные запросы |
| Транзакции | Commit, rollback, idle in transaction |
| Блокировки | Lock waits, blocking sessions, deadlocks |
| CPU | Загрузка CPU |
| RAM | Использование памяти, OOM-события |
| I/O | Reads, writes, latency |
| WAL | WAL bytes/sec, запись и синхронизация |
| Обслуживание | Autovacuum, dead tuples, checkpoint |
| Репликация | Lag, состояние реплик, replication slots |
| Хранение | Размер БД, свободное место |

#### Почему нужна история

Текущее значение:

```text
CPU = 80%
```

само по себе мало что объясняет.

Но если CPU обычно составлял 20%, а после развёртывания новой версии вырос до 80%, это уже важный сигнал.

Поэтому необходимо хранить историю и отмечать изменения системы:

- релизы;
- миграции;
- массовые загрузки;
- изменения настроек;
- увеличение числа пользователей.

#### Высокая кардинальность метрик

При использовании Prometheus нельзя бездумно добавлять к каждой метрике метки:

- индивидуального SQL-текста;
- случайного request ID;
- пользовательского идентификатора;
- уникального значения каждого параметра.

Это может создать огромное количество временных рядов и перегрузить систему мониторинга.

Для подробного анализа отдельных запросов лучше использовать специализированную статистику, логи и трассировки.

### Тема 26. Алертинг

Алертинг позволяет уведомлять команду о важных изменениях состояния.

Но оповещения должны быть связаны с реальными рисками.

#### Примеры событий

- База недоступна.
- Свободное место близко к исчерпанию.
- P99 критичной операции долго превышает SLO.
- Реплика существенно отстаёт.
- Пул подключений постоянно исчерпан.
- Длительная транзакция удерживает блокировки.
- Автоматическое обслуживание существенно отстаёт.
- WAL или replication slot создаёт риск заполнения диска.

#### Почему фиксированный порог недостаточен

Например:

```text
CPU > 80%
```

не всегда требует немедленного оповещения.

Для некоторых аналитических нагрузок это нормальное состояние.

Более полезно учитывать:

- длительность;
- влияние на latency;
- насыщение ресурса;
- историческую норму;
- критичность сервиса.

#### Alert Fatigue

Если система постоянно отправляет несущественные предупреждения, команда начинает их игнорировать.

Поэтому важно разделять:

- информационные события;
- предупреждения;
- критические инциденты.

Оповещение должно помогать определить необходимое действие.

Например, критический alert на исчерпание места должен сопровождаться сведениями о сервере, диске, текущем объёме и процедуре реагирования.

### Тема 27. Практика: диагностика текущей активности PostgreSQL

Выполним несколько запросов на учебном сервере.

#### Версия PostgreSQL

```sql
SELECT version();
```

#### Текущая база

```sql
SELECT current_database();
```

#### Активные подключения

```sql
SELECT
    pid,
    usename,
    state,
    wait_event_type,
    wait_event,
    query_start,
    query
FROM pg_stat_activity
WHERE datname = current_database()
  AND state = 'active'
ORDER BY query_start;
```

#### Длительные транзакции

```sql
SELECT
    pid,
    usename,
    state,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE datname = current_database()
  AND xact_start IS NOT NULL
ORDER BY xact_start;
```

#### Ожидания блокировок

```sql
SELECT
    pid,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blockers,
    query
FROM pg_stat_activity
WHERE datname = current_database()
  AND cardinality(pg_blocking_pids(pid)) > 0;
```

Эти запросы отражают текущее состояние.

Если блокировок нет, последний запрос не вернёт строк.

Для демонстрации блокировок необходимо создать контролируемый конфликт в двух независимых подключениях к учебной базе.

### Тема 28. Практика: воспроизведение блокировки

Создадим таблицу:

```sql
CREATE TABLE monitoring_demo (
    id INTEGER PRIMARY KEY,
    value INTEGER NOT NULL
);
```

```sql
INSERT INTO monitoring_demo (id, value)
VALUES (1, 100);
```

Откроем два подключения.

#### Сессия A

```sql
BEGIN;

UPDATE monitoring_demo
SET value = value + 10
WHERE id = 1;
```

Транзакцию пока не завершаем.

#### Сессия B

```sql
BEGIN;

UPDATE monitoring_demo
SET value = value + 20
WHERE id = 1;
```

Вторая операция будет ожидать освобождения конфликтующей блокировки.

#### Сессия C

В третьем подключении:

```sql
SELECT
    pid,
    state,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blockers,
    query
FROM pg_stat_activity
WHERE datname = current_database()
  AND cardinality(pg_blocking_pids(pid)) > 0;
```

Должна появиться информация об ожидающей сессии B и блокирующей сессии A.

#### Завершение

В сессии A:

```sql
COMMIT;
```

После освобождения блокировки сессия B сможет продолжить работу.

В сессии B:

```sql
COMMIT;
```

Проверим:

```sql
SELECT *
FROM monitoring_demo;
```

Если обе транзакции выполнились успешно, итоговое значение будет:

```text
130
```

Этот пример демонстрирует, что большая задержка SQL может возникать из-за ожидания блокировки, даже когда сама операция UPDATE проста.

### Тема 29. Практика: сбор статистики запросов

Убедимся, что `pg_stat_statements` доступно.

```sql
SELECT *
FROM pg_extension
WHERE extname = 'pg_stat_statements';
```

Если расширение установлено и корректно настроено, можно выполнить несколько учебных запросов.

Например:

```sql
SELECT COUNT(*)
FROM monitoring_demo;
```

```sql
SELECT SUM(value)
FROM monitoring_demo;
```

```sql
SELECT *
FROM monitoring_demo
WHERE id = 1;
```

Затем:

```sql
SELECT
    query,
    calls,
    ROUND(total_exec_time::numeric, 2) AS total_ms,
    ROUND(mean_exec_time::numeric, 2) AS mean_ms
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

#### Интерпретация

Обратите внимание на:

- число выполнений;
- суммарное время;
- среднее время;
- различия между запросами.

На маленькой учебной таблице время будет небольшим.

Цель примера — познакомиться с механизмом, а не получить значительную нагрузку.

Необходимо также учитывать, что статистика не обязательно отображает каждый запрос немедленно в той же транзакции из-за правил обновления накопленных показателей.

### Тема 30. Практика: включение логирования медленных запросов

Проверим параметр:

```sql
SHOW log_min_duration_statement;
```

Для лабораторного эксперимента, при наличии прав:

```sql
SET log_min_duration_statement = '100ms';
```

Выполним запрос, который займёт более 100 мс:

```sql
SELECT pg_sleep(0.2);
```

После выполнения можно проверить серверный журнал PostgreSQL.

Место размещения журнала зависит от способа запуска PostgreSQL.

В Docker полезно проверить:

```bash
docker logs <container_name>
```

Но журнал не обязательно направляется в stdout/stderr контейнера: конкретное расположение зависит от конфигурации логирования.

`pg_sleep` используется только для демонстрации регистрации медленного выполнения.

Он не создаёт характерную CPU или I/O нагрузку.

Поэтому нельзя использовать этот пример для исследования эффективности индексов.

После эксперимента:

```sql
RESET log_min_duration_statement;
```

Это восстановит прежнее значение параметра для текущей сессии.

### Тема 31. Практика: мониторинг буферного кеша

Получим статистику:

```sql
SELECT
    datname,
    blks_hit,
    blks_read,
    ROUND(
        100.0 * blks_hit /
        NULLIF(blks_hit + blks_read, 0),
        2
    ) AS hit_ratio_percent
FROM pg_stat_database
WHERE datname = current_database();
```

Выполним несколько запросов к одной и той же таблице.

После этого повторим измерение.

Необходимо учитывать:

- накопительный характер счётчиков;
- возможное кеширование статистики внутри транзакции;
- фоновую нагрузку;
- другие запросы той же базы.

Поэтому нельзя приписывать изменение общего hit ratio исключительно одному тестовому SELECT, если параллельно работают другие пользователи.

Для более точного изучения отдельного запроса полезен:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM monitoring_demo;
```

### Тема 32. Практика: диагностика долгого запроса

Общая методика:

#### Шаг 1. Зафиксировать симптом

Например:

```text
Время ответа выросло с 50 до 800 мс
```

#### Шаг 2. Определить период

Найти момент начала деградации.

#### Шаг 3. Проверить общие метрики

- CPU;
- RAM;
- I/O;
- QPS;
- connections;
- lock waits.

#### Шаг 4. Найти запросы

Использовать:

- pg_stat_statements;
- slow query logs;
- pg_stat_activity.

#### Шаг 5. Получить план

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Не выполнять потенциально опасные DML-команды с ANALYZE на продуктивной базе без контроля последствий.

#### Шаг 6. Определить источник стоимости

Например:

- Seq Scan большой таблицы;
- многократный Nested Loop;
- дорогая сортировка;
- неверная оценка строк;
- ожидание блокировки;
- временные файлы.

#### Шаг 7. Сформулировать гипотезу

Например:

> После роста таблицы оптимизатор перестал использовать подходящий индекс.

Или:

> Один долгий UPDATE удерживает блокировки и задерживает пользовательские запросы.

#### Шаг 8. Проверить гипотезу

Сравнить:

- планы;
- статистику;
- время;
- буферы;
- состояние транзакций.

#### Шаг 9. Внести изменение

Возможные действия:

- создать или изменить индекс;
- обновить статистику;
- переписать запрос;
- изменить транзакционные границы;
- настроить пул соединений;
- оптимизировать пакетную обработку.

#### Шаг 10. Измерить результат

Необходимо убедиться, что улучшились не только отдельные запросы, но и показатели системы.

### Тема 33. Практические принципы эксплуатации мониторинга

Для мониторинга необходимо определить:

- какие метрики собираются;
- с какой частотой;
- сколько времени хранятся;
- кто имеет к ним доступ;
- когда формируются оповещения;
- кто отвечает за реакцию;
- как диагностические данные связаны с релизами.

#### Срок хранения

Например, может потребоваться:

- подробная история за несколько дней;
- агрегированные метрики за несколько месяцев;
- длительная история инцидентов.

Конкретные сроки зависят от системы и требований.

#### Безопасность

Мониторинг может содержать:

- тексты SQL;
- имена таблиц;
- данные подключений;
- пользовательские идентификаторы;
- параметры запросов;
- диагностические ошибки.

Поэтому доступ к системам мониторинга необходимо ограничивать.

Не следует отправлять пароли или другие секреты в метки метрик и журналы.

#### Накладные расходы

Мониторинг не является бесплатным.

Высокая частота сбора, подробные логи и большое количество метрик могут создавать дополнительную нагрузку.

Поэтому глубину диагностики следует выбирать в соответствии с требованиями.

## Итоговые выводы

1. **Мониторинг является необходимой частью эксплуатации базы данных.** Он позволяет наблюдать за изменением нагрузки, обнаруживать деградацию и принимать решения на основании измерений.

2. **Производительность нельзя оценивать по одной метрике.** Latency, QPS, TPS, соединения, CPU, I/O и блокировки необходимо анализировать совместно.

3. **Среднее время выполнения не всегда отражает пользовательский опыт.** Для важных операций полезно использовать P95 и P99.

4. **Количество подключений не равно количеству активно вычисляющих запросов.** Важно различать active, idle, idle in transaction и ожидания.

5. **Блокировки способны создавать большие задержки без высокой CPU-нагрузки.** Для диагностики необходимо находить не только ожидающие, но и блокирующие транзакции.

6. **Кеширование влияет на скорость доступа к данным.** Однако высокий cache hit ratio не гарантирует хорошую производительность и должен интерпретироваться с учётом характера нагрузки.

7. **PostgreSQL предоставляет встроенные статистические представления.** Они позволяют анализировать активность, таблицы, индексы, WAL, I/O, VACUUM и другие подсистемы.

8. **Накопленная статистика PostgreSQL не всегда обновляется мгновенно.** Для правильной интерпретации необходимо учитывать задержки и правила кеширования статистических данных.

9. **pg_stat_statements помогает находить запросы с наибольшим вкладом в нагрузку.** Но его агрегированная статистика не заменяет детальную диагностику отдельных вызовов.

10. **Логи медленных запросов помогают обнаруживать проблемные операции.** Но сам факт долгого выполнения не раскрывает причину без анализа планов, блокировок и ресурсов.

11. **PostgreSQL, SQL Server, MySQL и Oracle имеют разные диагностические инструменты.** Их метрики и системные представления нельзя считать полностью взаимозаменяемыми.

12. **Внешние системы мониторинга обеспечивают историю, визуализацию и оповещения.** Prometheus, Grafana, Zabbix и PMM дополняют внутренние средства СУБД.

13. **Дашборд должен отвечать на конкретные эксплуатационные вопросы.** Большое количество графиков само по себе не делает систему наблюдаемой.

14. **Алертинг должен быть связан с реальными рисками и действиями.** Избыточное число предупреждений снижает эффективность реагирования.

15. **Диагностика должна быть воспроизводимой.** Необходимо фиксировать состояние системы, находить конкретную причину, проверять гипотезу и измерять результат изменения.

16. **Мониторинг не заменяет корректную архитектуру и резервное копирование.** Он помогает обнаруживать проблемы, но доступность и восстановимость обеспечиваются дополнительными инженерными механизмами.

Главный результат занятия — понимание мониторинга как непрерывного инженерного процесса, связывающего SQL-запросы, транзакции, внутреннее состояние СУБД, ресурсы сервера и поведение приложения.
