
# План выполнения запроса: чтение и практическое использование

## Превью / аннотация / краткое содержание

Занятие посвящено планам выполнения SQL-запросов и их использованию для диагностики производительности реляционных баз данных.

SQL является преимущественно декларативным языком: разработчик описывает, какие данные необходимо получить, но не задаёт точный физический алгоритм их получения. Решение о способах чтения таблиц, использовании индексов, порядке соединений и других операциях принимает оптимизатор СУБД.

План выполнения позволяет увидеть, как СУБД собирается выполнить запрос или как он фактически выполнялся.

На занятии рассматриваются:

- назначение планов выполнения;
- оценочные и фактические планы;
- наблюдение за выполняющимися запросами;
- структура дерева операторов;
- метрики `cost`, `rows`, `width`, `actual time` и `loops`;
- последовательное и индексное сканирование;
- `Index Seek`, `Index Scan` и `Key Lookup` в SQL Server;
- `Index Only Scan` и проверки видимости PostgreSQL;
- `Bitmap Index Scan` и `Bitmap Heap Scan`;
- селективность и оценки количества строк;
- физические алгоритмы `Nested Loop`, `Hash Join` и `Merge Join`;
- фильтрация, сортировка и агрегация;
- работа с `EXPLAIN (ANALYZE, BUFFERS)`;
- анализ ошибочных оценок оптимизатора;
- поиск узких мест и выбор направления оптимизации;
- отличия инструментов PostgreSQL, SQL Server, MySQL и Oracle.

Основная практика выполняется в PostgreSQL. При сравнении СУБД отдельно рассматриваются различия в терминологии и реализации операторов.

## Основные понятия

**План выполнения (Execution Plan)** — описание физических операций, которые СУБД выбирает для исполнения SQL-запроса.

**Декларативный SQL** — модель программирования, в которой запрос описывает требуемый результат, а не пошаговый алгоритм его вычисления.

**Оптимизатор запросов (Query Optimizer)** — компонент СУБД, выбирающий план выполнения на основе структуры запроса, статистики, индексов и модели стоимости.

**Estimated Plan** — план, содержащий предполагаемые операции и оценки оптимизатора.

**Actual Plan** — план с фактическими сведениями о выполнении запроса, полученными посредством соответствующих механизмов СУБД.

**Live Plan** — механизм наблюдения за выполнением запроса в процессе его работы.

**EXPLAIN** — команда получения плана SQL-запроса в PostgreSQL и MySQL.

**EXPLAIN ANALYZE** — средство выполнения запроса со сбором фактических показателей.

**BUFFERS** — параметр EXPLAIN PostgreSQL, предоставляющий сведения об обращениях к буферным страницам.

**Node** — узел плана выполнения, соответствующий определённой операции.

**Startup Cost** — оценка затрат до начала выдачи результата узлом.

**Total Cost** — оценка стоимости выполнения узла до завершения при предусмотренном оптимизатором объёме работы.

**Rows** — оценочное или фактическое количество строк, выдаваемых узлом.

**Width** — предполагаемый средний размер выходной строки узла в байтах в PostgreSQL.

**Actual Time** — измеренное время выполнения узла в PostgreSQL.

**Loops** — количество повторений выполнения узла.

**Seq Scan** — последовательное сканирование таблицы PostgreSQL.

**Table Scan** — операция чтения таблицы, в частности в SQL Server.

**Index Scan** — индексный доступ; точная семантика оператора различается между СУБД.

**Index Seek** — операция SQL Server по поиску начальных позиций и диапазонов ключей в индексной структуре.

**Range Scan** — чтение диапазона индексных ключей; термин применяется в разных СУБД, включая Oracle.

**Index Only Scan** — операция PostgreSQL, потенциально позволяющая получать необходимые значения из индекса без чтения строк heap.

**Key Lookup** — операция SQL Server по получению дополнительных столбцов из кластерного индекса.

**RID Lookup** — операция SQL Server по получению строки из heap через локатор строки.

**Bitmap Index Scan** — операция PostgreSQL, формирующая набор адресов потенциально подходящих строк с использованием индекса.

**Bitmap Heap Scan** — операция PostgreSQL, получающая строки таблицы на основе построенной bitmap-структуры.

**BitmapAnd / BitmapOr** — операции PostgreSQL по объединению результатов индексных поисков.

**Index Cond** — условие, применяемое в индексном доступе PostgreSQL.

**Filter** — условие, проверяемое после получения кандидатов текущим оператором.

**Recheck Cond** — условие, повторно проверяемое при определённых видах bitmap-доступа.

**Селективность (Selectivity)** — характеристика доли строк, удовлетворяющих условию поиска.

**Cardinality Estimation** — оценка количества строк, проходящих через операции плана.

**Nested Loop** — физический алгоритм соединения, использующий повторный поиск или чтение внутреннего источника.

**Hash Join** — алгоритм соединения с использованием хеш-таблицы.

**Merge Join** — алгоритм соединения упорядоченных потоков строк.

**Hash** — операция построения хеш-таблицы.

**Sort** — сортировка строк.

**Incremental Sort** — сортировка PostgreSQL, использующая уже упорядоченный префикс входных данных.

**HashAggregate** — агрегирование с использованием хеш-структуры.

**GroupAggregate** — группировка с использованием упорядоченных данных.

**Materialize** — узел PostgreSQL для сохранения промежуточного результата, который может повторно использоваться вышестоящими операциями.

**Memoize** — узел PostgreSQL для кеширования результатов параметризованного внутреннего доступа.

**Parallel Query** — выполнение некоторых операций SQL-запроса несколькими рабочими процессами или потоками.

**Gather** — оператор PostgreSQL, собирающий результаты параллельных работников.

**Gather Merge** — оператор PostgreSQL, объединяющий отсортированные результаты параллельных работников с сохранением необходимого порядка.

**Статистика оптимизатора** — сведения о распределении значений и размере данных, используемые при оценке альтернативных планов.

**Bottleneck** — операция или ресурс, ограничивающие производительность запроса.

## Основная часть

### Тема 1. План выполнения как модель физического исполнения SQL

SQL-запрос описывает желаемый результат.

Например:

```sql
SELECT
    order_id,
    customer_id,
    total_amount
FROM orders
WHERE customer_id = 1001;
```

Разработчик указывает:

- какие столбцы нужны;
- из какой таблицы;
- по какому условию.

Но запрос не определяет, каким способом PostgreSQL должен получить строки.

Возможные варианты:

- последовательное сканирование таблицы;
- индексное сканирование;
- bitmap-доступ;
- другие допустимые способы.

Оптимизатор оценивает доступные планы и выбирает вариант, который по внутренней модели считается наиболее выгодным.

#### Что показывает план

План выполнения позволяет установить:

1. Какие таблицы и индексы используются.
2. Какие условия применяются для поиска.
3. Какие условия проверяются после чтения.
4. Какие алгоритмы соединения применяются.
5. Где выполняются сортировка и агрегация.
6. Какой объём строк ожидается на разных этапах.
7. Какие операции фактически выполнялись, если собрана runtime-статистика.

#### План не равен SQL-запросу

Один SQL-запрос может иметь несколько физически допустимых планов.

Например, при изменении размера таблицы оптимизатор может заменить Index Scan на Seq Scan.

После создания индекса может измениться алгоритм JOIN.

После обновления статистики может измениться порядок соединения таблиц.

Поэтому план выполнения — это результат выбора оптимизатора в конкретных условиях, а не неизменная характеристика SQL-текста.

#### Зачем анализировать план

План позволяет проверять инженерные гипотезы.

Например:

> Запрос медленный, потому что отсутствует подходящий индекс.

Проверяем план.

Если видим последовательное сканирование большой таблицы и фильтр, возвращающий небольшое количество строк, гипотеза может быть обоснованной.

Но если запрос возвращает 80% таблицы, Seq Scan может быть правильным решением.

Следовательно, план нужен не для поиска «плохих» операторов по названию, а для понимания объёма работы.

### Тема 2. Виды планов выполнения

В зависимости от СУБД и используемого инструмента можно получить разные виды информации о плане.

#### Estimated Plan

Оценочный план показывает предполагаемый способ выполнения запроса.

В PostgreSQL:

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Команда не выполняет сам SELECT ради получения результата.

Она показывает выбранный план и прогнозируемые показатели.

Преимущества:

- подходит для предварительного анализа;
- позволяет увидеть предполагаемые индексы;
- показывает оценочные строки и стоимость;
- не выполняет массовое изменение данных при обычном EXPLAIN.

Ограничения:

- нет фактического времени;
- нет фактического количества строк;
- невозможно проверить реальные ошибки оценки кардинальности;
- не видно всей картины ожиданий и ресурсов.

Для DML обычный `EXPLAIN` также позволяет получить план без выполнения соответствующего изменения.

Но планирование не следует считать абсолютно бесплатной операцией: оно использует CPU, метаданные и статистику.

#### Actual Plan

Фактический план показывает результаты реального выполнения.

В PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Появляются показатели:

- actual time;
- actual rows;
- loops;
- статистика обращений к буферам;
- итоговое время выполнения.

Важно:

**EXPLAIN ANALYZE действительно выполняет запрос.**

Для UPDATE:

```sql
EXPLAIN (ANALYZE, BUFFERS)
UPDATE orders
SET status = 'completed'
WHERE order_id = 1001;
```

изменение реально выполняется.

Поэтому такие команды необходимо запускать в учебной среде или внутри контролируемой транзакции.

#### Live Plan

Наблюдение за выполняющимся запросом особенно развито в SQL Server через Live Query Statistics.

Оно позволяет увидеть сведения об обработке операторов во время исполнения.

В PostgreSQL стандартный EXPLAIN не предоставляет полностью аналогичного встроенного интерактивного live-представления.

Для наблюдения за длительными запросами используются:

- pg_stat_activity;
- pg_stat_progress_* для поддерживаемых операций;
- журналы;
- внешние инструменты мониторинга;
- специализированные расширения.

Поэтому Estimated, Actual и Live — полезная классификация, но не три одинаково реализованных стандартных вида планов во всех СУБД.

### Тема 3. Структура дерева плана PostgreSQL

План PostgreSQL представлен деревом операций.

Пример условного плана:

```text
Nested Loop
  -> Index Scan on customers
  -> Index Scan on orders
```

Здесь Nested Loop получает результаты двух дочерних источников.

Дерево следует читать через отношения между узлами.

Нижние узлы формируют строки для вышестоящих.

Но не следует понимать дерево как строгое расписание, в котором каждый нижний узел всегда полностью завершается до начала следующего.

Многие операторы работают потоково.

Например, Nested Loop может:

1. Получить строку внешнего источника.
2. Выполнить внутренний поиск.
3. Выдать найденные строки.
4. Перейти к следующей внешней строке.

То есть исполнение узлов может чередоваться.

#### Пример

```sql
EXPLAIN
SELECT
    c.customer_name,
    o.order_id
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.customer_id
WHERE c.customer_id = 1001;
```

В зависимости от индексов и данных возможен план Nested Loop.

Но возможны и другие алгоритмы.

#### Корневой узел

Верхний узел плана представляет итоговую операцию запроса.

Например:

```text
Aggregate
  -> Seq Scan
```

означает, что Aggregate получает данные из последовательного сканирования.

При этом общий `cost` верхнего узла уже учитывает стоимость дочерних операций.

Поэтому нельзя складывать стоимости всех узлов как независимые величины.

#### План и параллелизм

В PostgreSQL план может содержать:

```text
Gather
  -> Parallel Seq Scan
```

Здесь часть работы выполняется параллельными работниками, а Gather собирает результаты.

Для упорядоченного объединения используется Gather Merge.

Параллельный план не обязательно быстрее последовательного: дополнительные процессы имеют собственную стоимость запуска, координации и передачи данных.

### Тема 4. Основные метрики cost, rows и width

Рассмотрим пример:

```text
Index Scan using idx_orders_customer on orders
  (cost=0.42..8.45 rows=5 width=40)
```

Это условный пример плана.

#### Cost

```text
cost=0.42..8.45
```

Первое значение — startup cost.

Второе — total cost.

Startup cost показывает оценочные затраты до начала выдачи строк.

Total cost показывает оценочную стоимость выполнения узла до завершения.

Стоимость выражается во внутренних условных единицах PostgreSQL.

Это не миллисекунды.

#### Rows

```text
rows=5
```

Оптимизатор ожидает, что узел вернёт пять строк.

Это не обязательно число всех строк, которые пришлось прочитать или проверить.

Например, Seq Scan может проверить миллион строк, но вернуть только 10.

#### Width

```text
width=40
```

Предполагаемый средний размер выходной строки — 40 байт.

Эта оценка используется для расчёта стоимости обработки, сортировки и передачи промежуточных данных между узлами.

`width` не обязательно равен точному физическому размеру строки на диске.

#### Почему rows часто важнее cost при диагностике

Рассмотрим:

```text
rows=10
```

в оценочном плане.

Фактически:

```text
actual rows=100000
```

Ошибка составляет несколько порядков.

Оптимизатор рассчитывал стоимость для небольшого набора, а фактически обработал гораздо больше строк.

Это может объяснять выбор неудачного Nested Loop или недостаточную оценку стоимости сортировки.

Однако само расхождение не доказывает, что запрос медленный.

Необходимо проверить, повлияло ли оно на физический план и фактические ресурсы.

### Тема 5. Фактические метрики actual time, rows и loops

Пример:

```text
Index Scan
  (actual time=0.020..0.150 rows=10 loops=100)
```

#### Actual time

Два значения отражают измеренное время до первой строки и до завершения выдачи строк узлом.

В PostgreSQL при повторном выполнении узла показатели времени обычно представлены как средние на одно выполнение.

#### Actual rows

Показатель `rows=10` здесь означает в среднем десять строк на один цикл.

#### Loops

```text
loops=100
```

Узел выполнен сто раз.

Следовательно, приблизительное суммарное количество выданных узлом строк:

```text
10 × 100 = 1000
```

Необходимо учитывать округление показателей.

#### Почему loops особенно важен

В Nested Loop внутренний индексный поиск может выполняться много раз.

Каждый отдельный поиск может быть дешёвым.

Но если он повторяется миллион раз, суммарная стоимость становится значительной.

Поэтому оценивать узел только по небольшому `actual time` без учёта `loops` неправильно.

#### Нельзя суммировать времена всех узлов

Время родительского узла включает время выполнения дочерних операций.

Поэтому:

```text
Nested Loop: 100 ms
Index Scan A: 30 ms
Index Scan B: 70 ms
```

не означает, что общий запрос обязательно занял 200 мс.

Также параллельные узлы могут исполняться одновременно.

Для анализа нужно учитывать структуру дерева, повторения и общее Execution Time.

### Тема 6. Операторы доступа: Seq Scan и Table Scan

Seq Scan PostgreSQL выполняет последовательное чтение таблицы.

Например:

```sql
SELECT *
FROM orders
WHERE status = 'completed';
```

Если большинство заказов завершено, оптимизатор может выбрать Seq Scan.

Это может быть рационально.

#### Когда Seq Scan полезен

- небольшая таблица;
- большая доля подходящих строк;
- отсутствие выгодного индекса;
- необходимость чтения значительной части таблицы;
- стоимость индексных обращений выше стоимости последовательного чтения.

#### Когда стоит исследовать Seq Scan

Если таблица содержит миллионы строк, а запрос ищет одну запись:

```sql
SELECT *
FROM orders
WHERE order_id = 1001;
```

последовательное сканирование может быть подозрительным.

Проверяем:

1. Есть ли индекс по `order_id`.
2. Совпадают ли типы.
3. Как написано условие.
4. Актуальна ли статистика.
5. Какой размер таблицы.
6. Сколько строк действительно возвращается.

#### SQL Server: Table Scan и Clustered Index Scan

В SQL Server терминология другая.

`Table Scan` относится к чтению heap-таблицы.

Если таблица имеет clustered index, полное чтение кластерной структуры обычно отображается как `Clustered Index Scan`.

Поэтому нельзя считать `Table Scan` универсальным названием полного чтения любой таблицы SQL Server.

### Тема 7. Index Scan, Index Seek и Range Scan

Индекс позволяет сократить область поиска или получить данные в определённом порядке.

Но термин `Index Scan` в разных СУБД означает разные операции.

#### PostgreSQL Index Scan

```sql
CREATE INDEX idx_orders_customer
ON orders (customer_id);
```

Запрос:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001;
```

может получить план:

```text
Index Scan using idx_orders_customer
```

PostgreSQL использует индекс, чтобы найти соответствующие записи, а затем получает строки таблицы.

Важно: такой Index Scan может быть точечным поиском.

Его не нужно автоматически приравнивать к полному сканированию индекса в терминологии SQL Server.

#### SQL Server Index Seek

В SQL Server `Index Seek` означает использование индексной структуры для нахождения начальных позиций поиска.

Но Seek может читать диапазон из большого количества строк.

Например, условие:

```sql
WHERE created_at >= '2026-01-01'
```

может использовать Seek и затем читать значительную часть индекса.

Поэтому `Index Seek` не обязательно означает малую стоимость.

#### SQL Server Index Scan

`Index Scan` просматривает индексную структуру или её часть в соответствии с планом.

Но сканирование компактного покрывающего индекса может быть выгоднее множества точечных обращений к таблице.

Следовательно:

**Seek не всегда хорош, Scan не всегда плох.**

#### Oracle Index Range Scan

Oracle использует, в частности:

```text
INDEX RANGE SCAN
```

для чтения соответствующего диапазона ключей.

Также встречаются:

- INDEX UNIQUE SCAN;
- INDEX FULL SCAN;
- INDEX FAST FULL SCAN.

У этих операторов различаются порядок чтения, условия использования и стоимость.

#### MySQL

MySQL EXPLAIN использует собственные категории доступа:

```text
const
eq_ref
ref
range
index
ALL
```

Например:

- `range` — доступ по диапазону;
- `index` — сканирование индексной структуры;
- `ALL` — полное сканирование таблицы.

Эти категории нельзя механически сопоставлять один к одному с узлами PostgreSQL.

### Тема 8. Index Only Scan и покрывающие индексы

Index Only Scan PostgreSQL потенциально позволяет вернуть данные, используя индекс без обычного чтения heap-строк.

Пример:

```sql
CREATE INDEX idx_orders_customer_amount
ON orders (customer_id)
INCLUDE (total_amount);
```

Запрос:

```sql
SELECT
    customer_id,
    total_amount
FROM orders
WHERE customer_id = 1001;
```

может использовать `Index Only Scan`.

Индекс содержит необходимые значения.

Но PostgreSQL использует MVCC.

Чтобы вернуть строку, СУБД должна проверить её видимость текущему снимку.

Для этого PostgreSQL использует visibility map.

Если соответствующая страница heap не помечена как полностью видимая, потребуется дополнительное обращение к таблице.

Поэтому в плане необходимо смотреть:

```text
Heap Fetches
```

#### Почему Index Only Scan не всегда быстрее

Если большинство страниц не имеет отметки all-visible, количество дополнительных heap-обращений может быть большим.

Кроме того, широкий покрывающий индекс занимает больше места.

Он может увеличивать стоимость:

- INSERT;
- UPDATE;
- DELETE;
- обслуживания индексов;
- хранения.

Поэтому покрывающие индексы следует проектировать под реальные запросы.

#### SQL Server Key Lookup

Если некластерный индекс позволяет найти подходящие строки, но не содержит нужные столбцы, SQL Server может использовать `Key Lookup`.

Например:

```sql
SELECT *
FROM dbo.orders
WHERE customer_id = 1001;
```

Некластерный индекс по `customer_id` может найти строки, после чего `Key Lookup` получает дополнительные столбцы из кластерного индекса.

Для heap-таблицы соответствующая операция называется `RID Lookup`.

Небольшое количество lookup-операций обычно не является проблемой.

Но большое количество случайных обращений может оказаться дорогим.

Возможные решения:

- сократить список возвращаемых столбцов;
- использовать покрывающий индекс;
- изменить способ фильтрации;
- позволить оптимизатору использовать сканирование.

Выбор необходимо подтверждать измерениями.

### Тема 9. Селективность и выбор способа доступа

Селективность описывает, насколько условие сокращает набор строк.

Например, таблица содержит миллион строк.

Условию соответствует 100 строк.

Доля подходящих строк:

```text
100 / 1 000 000 = 0.0001
```

Это 0,01%.

Такой фильтр является высокоизбирательным.

Однако в разных источниках численное определение селективности может отличаться.

Поэтому полезнее говорить непосредственно о доле возвращаемых строк.

#### Пример высокоизбирательного условия

```sql
WHERE order_id = 1001
```

Если `order_id` уникален, ожидается не более одной строки.

Индекс обычно полезен.

#### Пример слабого фильтра

```sql
WHERE status = 'completed'
```

Если 90% заказов завершены, индекс по `status` может оказаться невыгодным для `SELECT *`.

#### Неравномерное распределение

Нельзя оценивать пользу индекса только по количеству различных значений.

Например:

- status = completed — 90%;
- status = created — 9,9%;
- status = cancelled — 0,1%.

Один и тот же индекс может быть полезен для `cancelled` и невыгоден для `completed`.

#### Почему оптимизатор ошибается

Причины:

- устаревшая статистика;
- зависимости между столбцами;
- перекошенное распределение;
- сложные выражения;
- параметры запроса;
- отсутствие полезных статистических сведений.

Поэтому фактическое число строк необходимо сравнивать с оценочным.

### Тема 10. Bitmap Index Scan и Bitmap Heap Scan

PostgreSQL поддерживает bitmap-доступ к таблицам.

Типичный план:

```text
Bitmap Heap Scan on orders
  Recheck Cond: (...)
  -> Bitmap Index Scan on idx_orders_customer
       Index Cond: (...)
```

#### Первый этап

`Bitmap Index Scan` использует индекс и формирует информацию о подходящих позициях строк.

#### Второй этап

`Bitmap Heap Scan` организует чтение соответствующих страниц таблицы.

Это позволяет сократить случайные обращения по сравнению с отдельными heap-переходами в порядке индексных записей.

#### Когда bitmap-подход полезен

Часто он эффективен для промежуточной селективности:

- подходящих строк слишком много для дешёвого точечного чтения;
- подходящих строк недостаточно, чтобы читать всю таблицу.

Но конкретный выбор зависит от стоимости и характеристик данных.

#### BitmapAnd и BitmapOr

PostgreSQL может комбинировать разные индексы.

Например:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001
  AND status = 'completed';
```

Если существуют отдельные индексы, оптимизатор может применить BitmapAnd.

Для условий `OR` возможен BitmapOr.

Но это не означает, что PostgreSQL обязан использовать два индекса.

Составной индекс или другой план может оказаться выгоднее.

#### Recheck Cond

Bitmap Heap Scan может повторно проверять условия.

Например, при потере точности bitmap из-за ограничений памяти часть адресов может представлять страницы целиком.

Тогда необходимо проверить отдельные строки.

В плане могут отображаться:

```text
Heap Blocks: exact=...
Heap Blocks: lossy=...
```

При `lossy`-блоках возможны дополнительные проверки и отбрасывание неподходящих строк.

Однако наличие `Recheck Cond` в плане само по себе не означает, что bitmap потеряла точность или что повторная проверка выполнялась для каждой строки.

#### Bitmap и сортировка

Bitmap Heap Scan обычно организует чтение по физическому расположению страниц.

Он не гарантирует порядок строк, соответствующий порядку индексных ключей.

Поэтому если запрос требует `ORDER BY`, может понадобиться отдельная сортировка.

Это отличие важно при сравнении Bitmap Heap Scan и обычного Index Scan.

### Тема 11. Физические алгоритмы соединения данных

SQL JOIN описывает логическую операцию соединения.

Физически СУБД может применить разные алгоритмы.

Основные:

- Nested Loop;
- Hash Join;
- Merge Join.

Пример:

```sql
SELECT
    o.order_id,
    c.customer_name
FROM orders AS o
JOIN customers AS c
    ON c.customer_id = o.customer_id;
```

Сама запись `JOIN` не определяет конкретный физический алгоритм.

Оптимизатор выбирает его по оценкам стоимости.

### Тема 12. Nested Loop

Nested Loop работает по принципу повторного обращения к внутреннему источнику.

Упрощённо:

```text
Для каждой строки A:
    найти подходящие строки B
```

Например:

```text
Nested Loop
  -> Index Scan on customers
  -> Index Scan on orders
```

Если внешний источник содержит 10 клиентов, а внутренний поиск использует индекс, выполнение может быть быстрым.

Если внешний источник содержит миллион строк, а внутренний доступ дорогой, стоимость может сильно вырасти.

#### Что смотреть в плане

1. Количество строк внешнего источника.
2. Количество повторений внутреннего узла.
3. Тип внутреннего доступа.
4. Используемые индексы.
5. Фактические строки.
6. Буферные обращения.

#### Пример потенциальной проблемы

```text
Nested Loop
  -> Seq Scan on customers
  -> Seq Scan on orders
```

Если внутренний Seq Scan выполняется много раз, работа может оказаться чрезмерной.

Но это необходимо подтвердить через `loops` и фактическую статистику.

#### Memoize

В современных PostgreSQL может применяться `Memoize`.

Он кеширует результаты параметризованного внутреннего поиска.

Если внешние строки повторяют одинаковые ключи, некоторые внутренние поиски можно не выполнять заново.

В плане полезно смотреть:

- Cache Hits;
- Cache Misses;
- Cache Evictions;
- Memory Usage.

Наличие Memoize не гарантирует ускорение при любом распределении ключей.

### Тема 13. Hash Join

Hash Join применяется для соединений с подходящими условиями равенства.

Упрощённая схема:

1. Получить строки одной стороны соединения.
2. Построить хеш-таблицу.
3. Прочитать другую сторону.
4. Найти совпадения по хеш-ключам.
5. Проверить необходимые условия соединения.

Пример плана:

```text
Hash Join
  Hash Cond: (o.customer_id = c.customer_id)
  -> Seq Scan on orders
  -> Hash
       -> Seq Scan on customers
```

Здесь хеш-таблица строится по результату чтения `customers`.

#### Почему Hash Join может быть эффективен

Алгоритм особенно полезен для больших наборов, если не существует дешёвого индексного доступа для каждого ключа соединения.

#### Память

Hash Join использует память для хеш-структуры.

Если данные не помещаются в выбранный бюджет памяти, операция может выполнять несколько партий обработки с использованием временных файлов.

В PostgreSQL в плане полезны показатели:

```text
Buckets
Batches
Memory Usage
```

Увеличение `Batches` может указывать на необходимость дополнительной обработки данных.

Но сама по себе партия обработки не является доказательством проблемы без анализа стоимости.

#### Какую сторону хешировать

Часто выгодно строить хеш по меньшему входному набору.

Но речь идёт о фактических входных данных после соответствующих фильтров, а не обязательно о меньшей исходной таблице.

Кроме того, выбор может зависеть от ограничений соединения, оценки стоимости и особенностей плана.

#### Hash Join не всегда лучший

Если один источник очень мал, а другой имеет эффективный индекс, Nested Loop может оказаться дешевле.

Если данные уже упорядочены, Merge Join также может быть выгодным.

Следовательно, Hash Join не является универсально лучшим алгоритмом.

### Тема 14. Merge Join

Merge Join соединяет два упорядоченных потока.

Например:

```text
Merge Join
  Merge Cond: (o.customer_id = c.customer_id)
  -> Sort
       -> Seq Scan on orders
  -> Index Scan on customers
```

В этом условном примере одна сторона сортируется, другая уже поступает в подходящем порядке.

#### Преимущества

Merge Join может быть эффективным, если:

- входные наборы большие;
- порядок данных подходит для соединения;
- имеются подходящие индексы;
- требуется сохранить или использовать сортировку.

#### Недостатки

Если оба источника необходимо предварительно сортировать, стоимость сортировок может перевесить преимущества самого соединения.

Также алгоритм должен корректно обрабатывать повторяющиеся значения ключей, что влияет на фактическую работу.

#### Что анализировать

- Есть ли Sort перед Merge Join.
- Сколько строк сортируется.
- Используются ли временные файлы.
- Насколько велики входные наборы.
- Можно ли получить порядок из индекса.
- Требуется ли такой порядок другим операциям запроса.

### Тема 15. Sort, Aggregate и промежуточные результаты

Помимо чтения и JOIN, существенную стоимость могут создавать:

- сортировки;
- агрегаты;
- материализация промежуточных данных;
- DISTINCT;
- оконные вычисления.

#### Sort

Пример:

```sql
SELECT *
FROM orders
ORDER BY created_at DESC;
```

Если индекс не обеспечивает нужный порядок, СУБД может выполнить сортировку.

В PostgreSQL в плане можно увидеть:

```text
Sort Method: quicksort
Memory: ...
```

Или:

```text
Sort Method: external merge
Disk: ...
```

Второй вариант указывает на использование временных файлов при сортировке.

Но решение не всегда заключается в увеличении `work_mem`.

Возможно, полезнее:

- сократить набор строк;
- использовать подходящий индекс;
- выполнить более раннюю фильтрацию;
- устранить ненужную сортировку.

#### Incremental Sort

Если данные уже упорядочены по части ключей, PostgreSQL может использовать Incremental Sort.

Например, вход отсортирован по `customer_id`, а требуется:

```sql
ORDER BY customer_id, created_at
```

Тогда PostgreSQL может сортировать группы по дополнительному ключу.

Это способно уменьшить стоимость и потребление памяти.

#### HashAggregate

Пример:

```sql
SELECT
    customer_id,
    COUNT(*)
FROM orders
GROUP BY customer_id;
```

PostgreSQL может использовать HashAggregate.

Он строит хеш-структуру групп.

#### GroupAggregate

Если данные уже упорядочены по ключу группировки, может использоваться GroupAggregate.

Иногда это позволяет избежать большой хеш-структуры.

Но для получения нужного порядка может потребоваться Sort.

Поэтому ни HashAggregate, ни GroupAggregate не является безусловно лучшим.

CREATE TABLE plan_demo.orders (

INSERT INTO plan_demo.customers (

    n,

INSERT INTO plan_demo.orders (

### Тема 17. Практика: Seq Scan и Index Scan

Сначала выполним:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM plan_demo.orders
WHERE customer_id = 1001;
```

Без отдельного индекса по `customer_id` PostgreSQL может выбрать Seq Scan.

Создадим индекс:

```sql
CREATE INDEX idx_plan_orders_customer
ON plan_demo.orders (customer_id);
```

Повторим запрос:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM plan_demo.orders
WHERE customer_id = 1001;
```

Теперь индексный доступ может оказаться выгоднее.

#### Что сравнивать

| Показатель | До индекса | После индекса |
|---|---|---|
| Тип доступа | Заполнить по плану | Заполнить по плану |
| Estimated Rows | Измерить | Измерить |
| Actual Rows | Измерить | Измерить |
| Execution Time | Измерить | Измерить |
| Shared Hit | Измерить | Измерить |
| Shared Read | Измерить | Измерить |

Не следует заранее подставлять ожидаемое время выполнения.

Оно зависит от объёма таблицы, кеша, оборудования и настроек.

#### Повторение эксперимента

Запрос необходимо выполнить несколько раз.

Полезно сравнивать варианты в разном порядке.

Это позволяет уменьшить влияние прогрева кеша и случайной фоновой нагрузки.

### Тема 18. Практика: селективность

Рассмотрим два запроса.

Редкий статус:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM plan_demo.orders
WHERE status = 'cancelled';
```

Частый статус:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM plan_demo.orders
WHERE status = 'completed';
```

Добавим индекс:

```sql
CREATE INDEX idx_plan_orders_status
ON plan_demo.orders (status);
```

Повторим оба запроса.

#### Ожидаемая логика

Статус `cancelled` встречается примерно у 1% заказов.

Статус `completed` — у большинства строк.

Поэтому индекс может оказаться полезнее для первого условия.

Однако конкретный план зависит от стоимости чтений и статистики.

Следует проверить, использует ли PostgreSQL:

- Index Scan;
- Bitmap Heap Scan;
- Seq Scan.

Цель упражнения — понять, почему один и тот же индекс может иметь разную полезность для разных значений.

### Тема 19. Практика: покрывающий индекс и Index Only Scan

Рассмотрим запрос:

```sql
SELECT
    customer_id,
    total_amount
FROM plan_demo.orders
WHERE customer_id = 1001;
```

Создадим покрывающий индекс:

```sql
CREATE INDEX idx_plan_orders_covering
ON plan_demo.orders (customer_id)
INCLUDE (total_amount);
```

Проверим:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    customer_id,
    total_amount
FROM plan_demo.orders
WHERE customer_id = 1001;
```

PostgreSQL может выбрать Index Only Scan.

#### Проверка видимости

Выполним в учебной базе:

```sql
VACUUM (ANALYZE) plan_demo.orders;
```

Затем повторим EXPLAIN.

Необходимо сравнить:

- тип доступа;
- Heap Fetches;
- обращения к буферам;
- время выполнения.

VACUUM может обновить visibility map и уменьшить необходимость обращаться к heap.

Но нельзя гарантировать, что после VACUUM любой Index Only Scan будет выполнять ноль Heap Fetches.

Это зависит от состояния данных и конкурентных изменений.

### Тема 20. Практика: Bitmap Heap Scan

Создадим два индекса:

```sql
CREATE INDEX idx_plan_orders_amount
ON plan_demo.orders (total_amount);
```

```sql
CREATE INDEX idx_plan_orders_created
ON plan_demo.orders (created_at);
```

Проверим запрос с несколькими условиями:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM plan_demo.orders
WHERE total_amount BETWEEN 1000 AND 2000
  AND created_at >= TIMESTAMP '2026-03-01';
```

В зависимости от статистики PostgreSQL может:

- использовать один индекс;
- применить BitmapAnd;
- выбрать Bitmap Heap Scan;
- выполнить Seq Scan.

Наличие нескольких индексов не гарантирует их объединение.

#### Анализ

Если появился Bitmap Heap Scan, обратите внимание на:

```text
Recheck Cond
Heap Blocks
Rows Removed by Index Recheck
```

При необходимости изучите, какие индексы участвовали в построении bitmap.

Не следует искусственно отключать методы доступа только ради получения определённого оператора в итоговом плане.

Для учебного исследования такие настройки возможны, но их необходимо возвращать в исходное состояние.

### Тема 21. Практика: сравнение алгоритмов JOIN

Рассмотрим:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    c.customer_id,
    c.customer_name,
    o.order_id,
    o.total_amount
FROM plan_demo.customers AS c
JOIN plan_demo.orders AS o
    ON o.customer_id = c.customer_id
WHERE c.customer_id BETWEEN 1 AND 100;
```

При небольшом количестве клиентов Nested Loop с индексным поиском заказов может быть эффективным.

Теперь расширим условие:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    c.customer_id,
    c.customer_name,
    o.order_id,
    o.total_amount
FROM plan_demo.customers AS c
JOIN plan_demo.orders AS o
    ON o.customer_id = c.customer_id;
```

Для больших наборов PostgreSQL может выбрать Hash Join.

#### Что сравнивать

1. Выбранный алгоритм.
2. Количество строк каждого входа.
3. Размер промежуточного результата.
4. Использование индексов.
5. Количество loops.
6. Потребление памяти.
7. Обращения к буферам.
8. Время выполнения.

#### Не подменять оптимизацию принудительным алгоритмом

PostgreSQL позволяет в учебных целях менять параметры:

```sql
SET enable_hashjoin = off;
```

```sql
SET enable_mergejoin = off;
```

```sql
SET enable_nestloop = off;
```

Но это не означает полного физического запрета всех соответствующих операций в любых обстоятельствах.

Некоторые способы соединения могут оказаться необходимыми для корректного плана.

Для экспериментов лучше использовать транзакционную локальную настройку:

```sql
BEGIN;

SET LOCAL enable_hashjoin = off;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    c.customer_id,
    o.order_id
FROM plan_demo.customers AS c
JOIN plan_demo.orders AS o
    ON o.customer_id = c.customer_id;

ROLLBACK;
```

После завершения транзакции локальная настройка перестаёт действовать.

Такие переключения помогают исследовать альтернативы, но не должны становиться первым способом исправления производительности в рабочей системе.

### Тема 22. Как читать план для поиска причины замедления

Для практического анализа полезен последовательный алгоритм.

#### Шаг 1. Проверить фактическое время

Посмотреть:

```text
Planning Time
Execution Time
```

Если запрос действительно медленный, определить, какая часть времени относится к планированию и выполнению.

#### Шаг 2. Посмотреть дерево операций

Определить:

- основные источники данных;
- алгоритмы соединения;
- сортировки;
- агрегации;
- повторно выполняемые узлы.

#### Шаг 3. Сравнить estimated rows и actual rows

Искать сильные расхождения.

Например:

```text
rows=5
actual rows=500000
```

Это повод исследовать статистику и селективность.

#### Шаг 4. Проверить loops

Особенно у внутренней стороны Nested Loop.

Узел, выполняющийся миллион раз, может быть дорогим даже при небольшом времени одного прохода.

#### Шаг 5. Посмотреть условия доступа

В PostgreSQL различаются:

```text
Index Cond
Filter
Recheck Cond
Join Filter
Hash Cond
Merge Cond
```

`Index Cond` показывает условие, применяемое при индексном доступе.

`Filter` может указывать на проверку уже полученных кандидатов.

Если большое количество строк удаляется фильтром, стоит понять, можно ли уменьшить входной набор раньше.

Но нельзя считать любую фильтрацию после индексного доступа ошибкой.

#### Шаг 6. Проверить BUFFERS

Определить:

- сколько страниц было найдено в кеше;
- сколько потребовалось читать;
- использовались ли временные файлы.

Не путать shared read с гарантированным физическим чтением SSD.

#### Шаг 7. Найти дорогие повторные операции

Например:

- многократные индексные поиски;
- большая сортировка;
- повторное сканирование;
- крупное хеширование;
- большой промежуточный JOIN.

#### Шаг 8. Сформулировать гипотезу

Примеры:

- отсутствует индекс;
- неверный порядок ключей индекса;
- условие не использует индекс;
- устарела статистика;
- слишком много строк проходит через JOIN;
- запрос возвращает лишние столбцы;
- нужна предварительная агрегация;
- сортировка использует временные файлы.

#### Шаг 9. Проверить изменение

После изменения SQL или индекса повторить измерение.

План должен подтвердить, что изменилась именно та операция, которую планировалось оптимизировать.

#### Шаг 10. Оценить общую стоимость

Даже если SELECT ускорился, новый индекс может увеличить стоимость записи.

Поэтому следует учитывать общую нагрузку системы.

### Тема 23. Сравнение инструментов четырёх СУБД

#### PostgreSQL

Оценочный план:

```sql
EXPLAIN
SELECT *
FROM orders;
```

Фактический план:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders;
```

Для машинной обработки:

```sql
EXPLAIN (FORMAT JSON)
SELECT *
FROM orders;
```

#### SQL Server

SQL Server предоставляет:

- Estimated Execution Plan;
- Actual Execution Plan;
- Live Query Statistics;
- `SET STATISTICS IO`;
- `SET STATISTICS TIME`;
- Query Store.

Пример:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT *
FROM dbo.orders
WHERE customer_id = 1001;

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
```

В плане SQL Server особенно важно различать:

- Table Scan;
- Clustered Index Scan;
- Clustered Index Seek;
- Nonclustered Index Scan;
- Nonclustered Index Seek;
- Key Lookup;
- RID Lookup;
- Nested Loops;
- Hash Match;
- Merge Join.

#### MySQL/InnoDB

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 1001;
```

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 1001;
```

В MySQL 8.4 поддерживается вывод runtime-информации через `EXPLAIN ANALYZE` для поддерживаемых операторов.

Но его формат и метрики отличаются от PostgreSQL.

#### Oracle

Предполагаемый план:

```sql
EXPLAIN PLAN FOR
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Вывод:

```sql
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY()
);
```

Для анализа фактических операций может использоваться `DBMS_XPLAN.DISPLAY_CURSOR` при наличии соответствующей статистики.

#### Сравнительная таблица

| Возможность | PostgreSQL | SQL Server | MySQL | Oracle |
|---|---|---|---|---|
| Оценочный план | EXPLAIN | Estimated Plan | EXPLAIN | EXPLAIN PLAN |
| Фактический план | EXPLAIN ANALYZE | Actual Plan | EXPLAIN ANALYZE | DISPLAY_CURSOR с runtime-статистикой |
| Live-наблюдение | Мониторинг и расширения | Live Query Statistics | Performance Schema и мониторинг | SQL Monitor |
| Индексный точечный поиск | Index Scan | Index Seek | const/ref/eq_ref и другие | INDEX UNIQUE/RANGE SCAN |
| Получение недостающих столбцов | Heap-доступ в Index Scan | Key Lookup / RID Lookup | Доступ к clustered index после secondary index | TABLE ACCESS BY INDEX ROWID |
| Алгоритмы JOIN | Nested Loop / Hash / Merge | Nested Loops / Hash / Merge | Nested-loop и hash join для подходящих случаев | Nested Loops / Hash / Sort Merge |

Названия операторов похожи, но их физическая реализация и критерии выбора различаются.

Поэтому необходимо анализировать планы в терминологии конкретной СУБД.

### Тема 24. Типичные ошибки при чтении планов

#### Ошибка 1. «Seq Scan всегда плохо»

Неверно.

Последовательное сканирование может быть оптимальным.

#### Ошибка 2. «Index Seek всегда хорошо»

Неверно.

Seek может читать большой диапазон и запускать множество дополнительных обращений.

#### Ошибка 3. «Самый большой cost показывает самое долгое действие»

Не обязательно.

Cost — прогноз, а стоимость родительского узла включает дочерние операции.

#### Ошибка 4. «Actual rows — это всегда итоговое число строк узла»

Неверно для повторно выполняемых узлов PostgreSQL.

Необходимо учитывать `loops`.

#### Ошибка 5. «Index Only Scan никогда не читает таблицу»

Неверно.

В PostgreSQL могут выполняться Heap Fetches.

#### Ошибка 6. «Hash Join означает отсутствие индекса»

Неверно.

Оптимизатор может выбрать Hash Join даже при наличии индексов, если такой вариант дешевле.

#### Ошибка 7. «Recheck Cond означает неисправный индекс»

Неверно.

Повторная проверка является нормальной частью работы некоторых методов доступа.

#### Ошибка 8. «Один запуск показывает объективную производительность»

Неверно.

Кеширование и конкурентная нагрузка могут существенно изменить результат.

#### Ошибка 9. «Одинаковые SQL-запросы всегда имеют одинаковый план»

Неверно.

План зависит от статистики, параметров, версии СУБД, индексов и условий выполнения.

#### Ошибка 10. «План показывает всё время пользователя»

Неверно.

Передача большого результата по сети и его обработка приложением могут создавать дополнительные задержки.

## Итоговые выводы

1. **План выполнения связывает декларативный SQL с физическими операциями СУБД.** Он показывает, как оптимизатор решил получить или изменить данные.

2. **Оценочный и фактический планы решают разные задачи.** Estimated Plan показывает прогноз, а Actual Plan позволяет проверить фактическое поведение.

3. **План представляет собой дерево операторов.** Для его понимания необходимо учитывать связи между узлами и поток данных, а не читать строки как независимый последовательный список.

4. **Cost не равен времени выполнения.** Это внутренняя оценка оптимизатора, используемая для сравнения альтернативных планов.

5. **Rows и loops являются ключевыми показателями диагностики.** Большие расхождения оценочных и фактических строк могут объяснять неудачный выбор алгоритма.

6. **Последовательное сканирование и индексный доступ имеют разные области эффективности.** Наличие индекса не означает, что его использование всегда дешевле.

7. **Терминология индексных операций отличается между СУБД.** Особенно важно различать PostgreSQL Index Scan и SQL Server Index Scan/Seek.

8. **Index Only Scan в PostgreSQL зависит от видимости строк.** Покрывающий индекс не гарантирует полного отсутствия обращений к heap.

9. **Bitmap Index Scan и Bitmap Heap Scan позволяют сочетать индексный поиск с более упорядоченным чтением страниц таблицы.** Их появление не является само по себе признаком проблемы.

10. **Nested Loop, Hash Join и Merge Join имеют разные алгоритмы и стоимость.** Их эффективность определяется размерами входных данных, индексами, памятью и сортировкой.

11. **Фильтрация, сортировка и агрегация могут быть существенной частью стоимости запроса.** Но устранение отдельного узла не всегда улучшает итоговый план.

12. **EXPLAIN ANALYZE действительно выполняет запрос.** Поэтому при анализе DML необходимо учитывать изменения данных и транзакционные побочные эффекты.

13. **Чтение плана — это метод проверки гипотез.** Нужно определить источник затрат, предложить конкретное изменение и подтвердить результат измерением.

14. **Производительность необходимо оценивать воспроизводимо.** Важны состояние статистики, кеш, порядок запусков, параметры запроса и конкурентная нагрузка.

Главный результат занятия — способность читать план выполнения как инженерный инструмент: понимать, сколько данных обрабатывается, почему выбран конкретный физический алгоритм, где расходуются ресурсы и какие изменения действительно стоит проверять.
