
# Представления, последовательности и триггеры в SQL

## Превью / аннотация / краткое содержание

Занятие посвящено объектам реляционных СУБД, которые позволяют организовывать логический доступ к данным, автоматически генерировать значения и выполнять действия в ответ на изменения таблиц.

Помимо обычных таблиц, индексов и ограничений, современные СУБД предоставляют дополнительные механизмы: представления, последовательности и триггеры.

Эти механизмы решают разные задачи и не являются взаимозаменяемыми.

На занятии рассматриваются:

- обычные и материализованные представления;
- использование представлений для упрощения запросов и разграничения доступа;
- создание и изменение представлений;
- обновляемые представления и `WITH CHECK OPTION`;
- последовательности и автоматическая генерация идентификаторов;
- различия между `SEQUENCE`, `IDENTITY`, `SERIAL` и `AUTO_INCREMENT`;
- функции управления последовательностями;
- транзакционные особенности генерации значений;
- триггеры `BEFORE`, `AFTER` и `INSTEAD OF`;
- строковые и операторные триггеры;
- псевдозаписи `NEW` и `OLD`;
- автоматическое заполнение служебных полей;
- аудит изменения данных;
- производительность, рекурсия и другие риски триггеров;
- различия PostgreSQL, SQL Server, MySQL/InnoDB и Oracle.

Основные практические примеры приведены для PostgreSQL. Дополнительно рассматриваются особенности реализации в остальных СУБД курса.

## Основные понятия

**Представление (View)** — именованный объект базы данных, определяющий результат SQL-запроса и позволяющий обращаться к нему как к таблице.

**Обычное представление (Regular View)** — представление, которое, как правило, не хранит отдельную копию результата определяющего запроса.

**Материализованное представление (Materialized View)** — объект, сохраняющий результат запроса физически и требующий предусмотренного СУБД механизма обновления этого результата.

**CREATE VIEW** — команда создания представления.

**CREATE OR REPLACE VIEW** — команда создания или изменения определения представления в СУБД, поддерживающих соответствующий синтаксис.

**Обновляемое представление (Updatable View)** — представление, через которое при соблюдении определённых условий можно изменять данные базовых таблиц.

**WITH CHECK OPTION** — механизм проверки того, что изменения через обновляемое представление соответствуют условиям его определения.

**Security Invoker** — режим выполнения с использованием прав вызывающего пользователя.

**Security Definer** — модель выполнения с использованием определённых прав владельца объекта. Конкретная реализация зависит от типа объекта и СУБД.

**Последовательность (Sequence)** — объект базы данных, предназначенный для генерации числовых значений.

**CREATE SEQUENCE** — команда создания последовательности.

**nextval** — функция PostgreSQL, возвращающая следующее значение последовательности.

**currval** — функция PostgreSQL, возвращающая последнее значение последовательности, полученное в текущей сессии.

**setval** — функция PostgreSQL, позволяющая изменить состояние последовательности.

**IDENTITY** — механизм автоматической генерации значений для столбца, предусмотренный SQL и реализованный в нескольких СУБД.

**SERIAL** — специальная форма объявления столбца PostgreSQL, исторически используемая для автоматической генерации идентификаторов через последовательность.

**AUTO_INCREMENT** — механизм автоматического формирования числовых значений в MySQL.

**NEXT VALUE FOR** — выражение получения следующего значения последовательности, используемое, в частности, в SQL Server.

**CACHE** — параметр последовательности, позволяющий резервировать значения для уменьшения стоимости их генерации.

**CYCLE** — режим повторного использования числового диапазона после достижения границы последовательности.

**Триггер (Trigger)** — объект базы данных, автоматически выполняющий заданную логику при наступлении поддерживаемого события.

**Триггерная функция (Trigger Function)** — функция PostgreSQL, вызываемая триггером и содержащая его логику.

**BEFORE Trigger** — триггер, выполняемый до соответствующей операции изменения данных.

**AFTER Trigger** — триггер, выполняемый после соответствующей операции изменения данных.

**INSTEAD OF Trigger** — триггер, выполняющий действия вместо исходной операции, обычно при работе с представлениями.

**ROW-level Trigger** — триггер, выполняемый отдельно для каждой затронутой строки.

**STATEMENT-level Trigger** — триггер, выполняемый один раз на SQL-оператор.

**NEW** — псевдозапись с новым состоянием строки в поддерживаемых строковых триггерах.

**OLD** — псевдозапись с прежним состоянием строки в поддерживаемых строковых триггерах.

**Transition Table** — набор строк, отражающий изменения, выполненные одним SQL-оператором, доступный определённым триггерам.

**Аудит изменений (Change Audit)** — фиксация факта изменения данных, времени операции и необходимых сведений о старом и новом состоянии.

**Каскадное действие (Cascading Action)** — автоматически выполняемая операция над связанными данными, например через внешний ключ с `ON DELETE CASCADE`.

**Рекурсия триггеров (Trigger Recursion)** — повторный вызов триггерной логики вследствие операций, выполняемых самими триггерами.

## Основная часть

### Тема 1. Представления как виртуальный слой доступа к данным

Представление позволяет сохранить SQL-запрос под определённым именем и обращаться к его результату как к таблице.

Например, в приложении существует таблица заказов:

```sql
-- PostgreSQL

CREATE TABLE orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Добавим несколько записей:

```sql
INSERT INTO orders (
    customer_id,
    status,
    total_amount
)
VALUES
    (101, 'created', 1500),
    (102, 'completed', 2500),
    (101, 'processing', 3200),
    (103, 'cancelled', 900);
```

Предположим, приложение регулярно обращается только к активным заказам.

Вместо многократного написания:

```sql
SELECT
    order_id,
    customer_id,
    status,
    total_amount
FROM orders
WHERE status IN ('created', 'processing');
```

можно создать представление.

```sql
CREATE VIEW active_orders AS
SELECT
    order_id,
    customer_id,
    status,
    total_amount
FROM orders
WHERE status IN ('created', 'processing');
```

Теперь запрос становится проще:

```sql
SELECT *
FROM active_orders;
```

Результат:

| order_id | customer_id | status | total_amount |
|---|---|---|---:|
| 1 | 101 | created | 1500 |
| 3 | 101 | processing | 3200 |

Здесь идентификаторы предполагают выполнение примера в новой пустой таблице.

#### Как работает обычное представление

Обычное представление хранит определение запроса, а не самостоятельную копию всех полученных строк.

Если данные базовой таблицы изменяются, последующие запросы к представлению работают с актуальными данными с учётом правил видимости транзакций.

Например:

```sql
UPDATE orders
SET status = 'completed'
WHERE order_id = 1;
```

После изменения заказ больше не соответствует условию представления `active_orders`.

При следующем чтении представления эта строка не будет возвращена, если изменение видно текущей транзакции.

Важно: представление не обязательно выполняется как полностью отдельный запрос с последующим чтением готового результата.

Оптимизатор СУБД может раскрывать определение представления, объединять условия и выбирать общий план выполнения.

Поэтому нельзя считать представление обязательной дополнительной стадией физической обработки.

#### Назначение представлений

Представления применяются для:

1. Упрощения сложных SQL-запросов.
2. Повторного использования логики.
3. Создания стабильного интерфейса доступа к данным.
4. Скрытия ненужных столбцов.
5. Ограничения доступного набора строк.
6. Формирования удобных структур для отчётов.
7. Разграничения доступа.
8. Постепенного изменения структуры базы без немедленного изменения всех клиентов.

Например, представление может объединять несколько таблиц:

```sql
CREATE TABLE customers (
    customer_id BIGINT PRIMARY KEY,
    customer_name TEXT NOT NULL,
    email TEXT NOT NULL
);

CREATE VIEW order_details AS
SELECT
    o.order_id,
    c.customer_name,
    o.status,
    o.total_amount
FROM orders AS o
JOIN customers AS c
    ON c.customer_id = o.customer_id;
```

Для использования такого представления необходимо, чтобы соответствующие клиенты существовали в таблице `customers`.

Теперь прикладной код может получать имя клиента и сведения о заказе через один объект.

```sql
SELECT *
FROM order_details;
```

#### Представления и безопасность

Представления позволяют показывать пользователю только необходимые данные.

Например, таблица клиентов содержит:

- идентификатор;
- имя;
- email;
- номер телефона;
- служебные атрибуты.

Аналитику нужны только идентификатор и имя.

```sql
CREATE VIEW public_customers AS
SELECT
    customer_id,
    customer_name
FROM customers;
```

Права можно предоставить на представление, не предоставляя прямой доступ к таблице.

Пример PostgreSQL:

```sql
GRANT SELECT ON public_customers TO analyst_role;
```

Предполагается, что роль `analyst_role` уже создана и имеет право `USAGE` на схему представления.

Но представление не становится безопасным автоматически.

В PostgreSQL по умолчанию доступ к базовым отношениям представления проверяется с учётом прав владельца представления.

Начиная с PostgreSQL 15 доступна опция:

```sql
CREATE VIEW customer_view
WITH (security_invoker = true)
AS
SELECT
    customer_id,
    customer_name
FROM customers;
```

Для такого представления права на базовые таблицы проверяются от имени вызывающего пользователя.

Если задача заключается именно в предоставлении ограниченного доступа без прав на базовую таблицу, режим `security_invoker` может не подходить.

Для чувствительных данных необходимо также учитывать:

- Row-Level Security;
- права владельца;
- исполняемые функции;
- возможные утечки через выражения и ошибки;
- параметры `security_barrier`;
- доступ к другим представлениям и таблицам.

В PostgreSQL `security_barrier` позволяет ограничить некоторые преобразования порядка вычисления условий, важные для безопасности представлений.

Однако такая опция может влиять на оптимизацию запросов.

#### Материализованные представления

Обычное представление обычно не хранит собственную копию результата.

Материализованное представление — другой механизм.

В PostgreSQL:

```sql
CREATE MATERIALIZED VIEW order_statistics AS
SELECT
    customer_id,
    COUNT(*) AS orders_count,
    SUM(total_amount) AS total_amount
FROM orders
GROUP BY customer_id;
```

В отличие от обычного представления, результат такого запроса сохраняется физически.

Чтение:

```sql
SELECT *
FROM order_statistics;
```

не требует каждый раз заново выполнять исходную агрегацию.

Но результат не обновляется автоматически после каждого изменения `orders`.

В PostgreSQL для обновления используется:

```sql
REFRESH MATERIALIZED VIEW order_statistics;
```

Пока обновление не выполнено, сохранённые данные могут устареть.

PostgreSQL также поддерживает `REFRESH MATERIALIZED VIEW CONCURRENTLY` при выполнении соответствующих требований, включая наличие подходящего уникального индекса.

Материализованные представления особенно полезны для некоторых аналитических запросов, но требуют контроля актуальности, затрат на обновление и хранения.

#### Представления в четырёх СУБД

| Возможность | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| CREATE VIEW | Да | Да | Да | Да |
| Обновляемые простые представления | Да | Да | Да | Да |
| WITH CHECK OPTION | Да | Да | Да | Да |
| Материализованное представление | Да | Индексируемые представления | Нет нативного аналога обычного MATERIALIZED VIEW | Да |
| INSTEAD OF trigger на представлении | Да | Да | Нет | Да |
| Особые настройки безопасности | security_invoker, security_barrier | Владение объектами, права, execution context | DEFINER / INVOKER | Права владельца и механизмы безопасности Oracle |

В SQL Server indexed view и в Oracle materialized view имеют собственные требования и поведение. Они не являются полностью взаимозаменяемыми с материализованными представлениями PostgreSQL.

### Тема 2. Создание представлений и ограничения их изменения

#### Синтаксис PostgreSQL

```sql
CREATE [ OR REPLACE ] VIEW view_name AS
SELECT ...
[ WITH [ LOCAL | CASCADED ] CHECK OPTION ];
```

Дополнительные параметры позволяют управлять отдельными свойствами представления.

#### Изменение определения

Предположим, требуется добавить дату создания заказа:

```sql
CREATE OR REPLACE VIEW active_orders AS
SELECT
    order_id,
    customer_id,
    status,
    total_amount,
    created_at
FROM orders
WHERE status IN ('created', 'processing');
```

PostgreSQL позволяет добавить столбцы в конец существующего списка.

Но `CREATE OR REPLACE VIEW` не разрешает произвольно изменять имена, порядок и типы уже существующих столбцов.

Поэтому изменение контракта представления может потребовать миграции зависимых объектов.

В SQL Server используется синтаксис:

```sql
CREATE OR ALTER VIEW dbo.active_orders AS
SELECT
    order_id,
    customer_id,
    status,
    total_amount
FROM dbo.orders
WHERE status IN ('created', 'processing');
```

В MySQL и Oracle также существуют средства изменения определений представлений, но синтаксис и ограничения отличаются.

#### Обновляемые представления

Некоторые представления позволяют выполнять:

```sql
INSERT
UPDATE
DELETE
```

Например:

```sql
CREATE VIEW created_orders AS
SELECT
    order_id,
    customer_id,
    status,
    total_amount,
    created_at
FROM orders
WHERE status = 'created';
```

В PostgreSQL это представление автоматически обновляемое, поскольку его определение достаточно простое и обращается к одной таблице.

Выполним:

```sql
UPDATE created_orders
SET total_amount = 1800
WHERE order_id = 1;
```

Изменится базовая таблица `orders`.

Однако представления, содержащие:

- агрегацию;
- `GROUP BY`;
- `DISTINCT`;
- сложные соединения;
- операции над множествами;
- некоторые вычисляемые столбцы,

могут оказаться необновляемыми либо поддерживать только ограниченный набор изменений.

Нельзя считать, что каждое представление доступно для INSERT, UPDATE и DELETE.

#### WITH CHECK OPTION

Предположим, создано представление:

```sql
CREATE VIEW created_orders_check AS
SELECT
    order_id,
    customer_id,
    status,
    total_amount,
    created_at
FROM orders
WHERE status = 'created'
WITH CHECK OPTION;
```

Теперь попробуем через представление изменить статус:

```sql
UPDATE created_orders_check
SET status = 'completed'
WHERE order_id = 1;
```

Если строка доступна для обновления, PostgreSQL отклонит изменение, поскольку после UPDATE строка перестанет соответствовать условию представления.

Без `WITH CHECK OPTION` такая операция для автоматически обновляемого представления могла бы быть разрешена.

В результате строка исчезла бы из результата представления после изменения.

`WITH CHECK OPTION` позволяет предотвратить подобное поведение.

#### LOCAL и CASCADED

PostgreSQL поддерживает:

```sql
WITH LOCAL CHECK OPTION
```

и:

```sql
WITH CASCADED CHECK OPTION
```

`LOCAL` проверяет условия непосредственно текущего представления.

`CASCADED` также учитывает условия нижележащих представлений в поддерживаемых случаях.

Но существуют ограничения при использовании триггеров `INSTEAD OF`, правил и некоторых видов обновляемых представлений.

Поэтому сложные цепочки представлений необходимо тестировать отдельно.

#### Производительность представлений

Обычное представление не создаёт автоматически новый индекс.

Для ускорения запроса используются индексы базовых таблиц или другие подходящие механизмы.

Например:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM active_orders
WHERE customer_id = 101;
```

В плане PostgreSQL можно увидеть операции над базовой таблицей `orders`, а не обязательно отдельный узел, соответствующий представлению.

СУБД может объединить фильтр `customer_id` с условиями представления.

Однако оптимизация сложных представлений не всегда позволяет выполнить все преобразования.

Агрегации, ограничения безопасности и другие особенности определения могут ограничивать свободу оптимизатора.

**Главный вывод:** представление прежде всего упрощает доступ и организует интерфейс к данным. Ускорение запросов не гарантируется самим фактом его создания.

### Тема 3. Последовательности как механизм генерации числовых значений

Последовательность — объект базы данных, предназначенный для генерации чисел по заданным правилам.

Она может использоваться для:

- идентификаторов строк;
- технических номеров;
- генерации значений для нескольких таблиц;
- распределения диапазонов идентификаторов;
- других сценариев, где требуется независимый источник числовых значений.

#### Создание последовательности PostgreSQL

```sql
CREATE SEQUENCE order_number_seq
    AS BIGINT
    START WITH 1
    INCREMENT BY 1
    MINVALUE 1
    NO MAXVALUE
    CACHE 1
    NO CYCLE;
```

Основные параметры:

| Параметр | Назначение |
|---|---|
| AS | Тип числового значения |
| START WITH | Начальное значение |
| INCREMENT BY | Шаг изменения |
| MINVALUE | Минимальное значение |
| MAXVALUE | Максимальное значение |
| CACHE | Количество резервируемых значений |
| CYCLE | Повтор диапазона после достижения границы |

Последовательность может увеличиваться или уменьшаться.

Например:

```sql
CREATE SEQUENCE reverse_seq
    START WITH 100
    INCREMENT BY -1
    MINVALUE 1
    MAXVALUE 100;
```

#### nextval

Получение следующего значения:

```sql
SELECT nextval('order_number_seq');
```

При первом вызове для приведённой последовательности результат:

```text
1
```

Повторный вызов:

```sql
SELECT nextval('order_number_seq');
```

возвращает:

```text
2
```

Каждый успешный вызов выделяет новое значение согласно текущему состоянию последовательности.

#### currval

```sql
SELECT currval('order_number_seq');
```

Возвращает последнее значение последовательности, полученное через `nextval` в текущей сессии.

Если в текущей сессии ещё не был выполнен `nextval` для этой последовательности, вызов `currval` приведёт к ошибке.

Важно: `currval` не означает глобальное последнее значение, полученное всеми пользователями.

Другая сессия может получить следующее значение между вызовами `nextval` и `currval`.

При этом `currval` текущей сессии останется связанным с последним значением, выделенным именно ей.

#### setval

Функция `setval` позволяет изменить состояние последовательности.

```sql
SELECT setval('order_number_seq', 1000, true);
```

После такого вызова следующий `nextval` при шаге 1 обычно возвращает `1001`.

Третий параметр определяет, считается ли установленное значение уже использованным.

Например:

```sql
SELECT setval('order_number_seq', 1000, false);
```

После этого следующий `nextval` возвращает `1000`.

Изменять состояние последовательности необходимо осторожно, особенно если значения уже используются в таблицах.

#### Последовательности и транзакции

Очень важная особенность PostgreSQL:

**Значения, полученные из последовательности, не возвращаются при ROLLBACK.**

Пример:

```sql
BEGIN;

SELECT nextval('order_number_seq');

ROLLBACK;
```

Выделенное значение не возвращается в последовательность.

Следующий вызов может вернуть следующее число.

Это означает, что последовательности не гарантируют непрерывную нумерацию без пропусков.

Пропуски могут появляться из-за:

- откатов транзакций;
- конфликтов вставки;
- неудачных операций;
- кеширования последовательности;
- перезапусков процессов и серверов;
- удаления строк.

Поэтому обычную последовательность нельзя использовать как готовый механизм юридически значимой нумерации документов без пропусков.

#### Порядок значений и порядок фиксации

Числа последовательности не определяют порядок подтверждения транзакций.

Например:

- транзакция A получила значение 100;
- транзакция B получила значение 101;
- транзакция B выполнила COMMIT;
- транзакция A выполнила COMMIT позднее.

Значит, более высокий идентификатор может быть подтверждён раньше более низкого.

Для определения времени операции лучше использовать соответствующие временные метки, но и они требуют понимания семантики их формирования.

Для строгого порядка фиксации транзакций нужны другие механизмы.

#### CYCLE

Параметр `CYCLE` разрешает повтор диапазона значений после достижения границы последовательности.

Но повторение чисел может создавать конфликты с уже существующими значениями первичных ключей.

Поэтому для обычных технических идентификаторов чаще используется `NO CYCLE`.

### Тема 4. Связывание последовательностей с таблицами

Последовательность может существовать независимо или использоваться для автоматического заполнения столбца.

#### Явное использование DEFAULT

В PostgreSQL:

```sql
CREATE SEQUENCE delivery_event_seq
    AS BIGINT
    START WITH 1;
```

Создадим таблицу:

```sql
CREATE TABLE delivery_events (
    event_id BIGINT PRIMARY KEY
        DEFAULT nextval('delivery_event_seq'),
    event_type TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
        DEFAULT CURRENT_TIMESTAMP
);
```

Теперь можно не указывать идентификатор:

```sql
INSERT INTO delivery_events (event_type)
VALUES ('order_created');
```

Значение `event_id` будет получено из последовательности.

Однако в данном примере последовательность остаётся отдельно созданным объектом.

Чтобы связать её жизненный цикл со столбцом:

```sql
ALTER SEQUENCE delivery_event_seq
OWNED BY delivery_events.event_id;
```

Эта команда формирует зависимость последовательности от столбца.

#### SERIAL

Раньше в PostgreSQL часто использовали:

```sql
CREATE TABLE products (
    product_id BIGSERIAL PRIMARY KEY,
    product_name TEXT NOT NULL
);
```

`BIGSERIAL` — не самостоятельный базовый числовой тип.

Это удобная форма объявления столбца, которая приводит к созданию связанной последовательности, значения по умолчанию и соответствующих зависимостей.

#### IDENTITY

Современный стандартный способ:

```sql
CREATE TABLE products_identity (
    product_id BIGINT
        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_name TEXT NOT NULL
);
```

PostgreSQL поддерживает:

```sql
GENERATED ALWAYS AS IDENTITY
```

и:

```sql
GENERATED BY DEFAULT AS IDENTITY
```

Различие связано с возможностью передачи явно заданного значения.

Для `GENERATED ALWAYS` обычная вставка произвольного явного значения ограничена, но существует специальная конструкция `OVERRIDING SYSTEM VALUE`.

Для `GENERATED BY DEFAULT` явные значения допускаются.

При этом `IDENTITY` не заменяет ограничение уникальности.

Поэтому для идентификатора первичного ключа дополнительно указывают `PRIMARY KEY`.

#### SQL Server

SQL Server поддерживает как столбцы `IDENTITY`, так и отдельные `SEQUENCE`.

Пример последовательности:

```sql
CREATE SEQUENCE dbo.order_id_seq
    AS BIGINT
    START WITH 1
    INCREMENT BY 1
    NO CYCLE;
```

Получение значения:

```sql
SELECT NEXT VALUE FOR dbo.order_id_seq;
```

Использование в DEFAULT:

```sql
CREATE TABLE dbo.delivery_orders (
    order_id BIGINT NOT NULL
        CONSTRAINT DF_delivery_orders_id
        DEFAULT (NEXT VALUE FOR dbo.order_id_seq),
    order_status VARCHAR(30) NOT NULL,
    CONSTRAINT PK_delivery_orders
        PRIMARY KEY (order_id)
);
```

SQL Server также предоставляет:

```sql
order_id BIGINT IDENTITY(1,1)
```

Однако `IDENTITY` — свойство столбца, а `SEQUENCE` — независимый объект.

#### MySQL/InnoDB

MySQL использует `AUTO_INCREMENT`.

```sql
CREATE TABLE products (
    product_id BIGINT
        NOT NULL AUTO_INCREMENT PRIMARY KEY,
    product_name VARCHAR(200) NOT NULL
) ENGINE = InnoDB;
```

MySQL/InnoDB не предоставляет отдельный универсальный объект `CREATE SEQUENCE`, аналогичный последовательностям PostgreSQL, SQL Server и Oracle.

Значения `AUTO_INCREMENT` также не гарантируют непрерывной последовательности без пропусков.

#### Oracle

Oracle поддерживает отдельные последовательности:

```sql
CREATE SEQUENCE order_id_seq
    START WITH 1
    INCREMENT BY 1
    NOCYCLE;
```

Получение значения:

```sql
SELECT order_id_seq.NEXTVAL
FROM dual;
```

В Oracle также поддерживаются identity-столбцы:

```sql
CREATE TABLE products (
    product_id NUMBER
        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_name VARCHAR2(200) NOT NULL
);
```

#### Сравнение

| Механизм | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| CREATE SEQUENCE | Да | Да | Нет отдельного универсального объекта | Да |
| IDENTITY | Да | Да | AUTO_INCREMENT | Да |
| Получение следующего значения | nextval | NEXT VALUE FOR | Через INSERT / AUTO_INCREMENT | NEXTVAL |
| Ручное изменение последовательности | setval, ALTER SEQUENCE | ALTER SEQUENCE | ALTER TABLE AUTO_INCREMENT и другие механизмы | ALTER SEQUENCE |
| Гарантия отсутствия пропусков | Нет | Нет | Нет | Нет |

#### Когда нужен отдельный объект SEQUENCE

Отдельная последовательность оправданна, когда:

- идентификаторы формируются независимо от конкретной таблицы;
- несколько таблиц должны использовать общий источник значений;
- требуется специальный шаг или диапазон;
- значения нужны ещё до выполнения INSERT;
- стандартного механизма identity-столбца недостаточно.

Однако единая последовательность сама по себе не гарантирует глобальную уникальность между независимыми экземплярами СУБД.

В распределённых системах требуется отдельная стратегия генерации идентификаторов.

Например:

- выделение диапазонов;
- различающиеся шаги;
- централизованный источник;
- UUID или другой распределённый идентификатор.

### Тема 5. Триггеры как механизм автоматической реакции базы данных

Триггер — объект базы данных, автоматически вызывающий определённую логику при наступлении поддерживаемого события.

Например, после изменения заказа может потребоваться сохранить сведения о старом и новом статусе.

Триггер позволяет реализовать такую реакцию непосредственно на уровне БД.

#### Основные события

В PostgreSQL триггеры могут реагировать на:

- `INSERT`;
- `UPDATE`;
- `DELETE`;
- `TRUNCATE`.

Но поддержка комбинаций событий, момента и уровня срабатывания ограничена.

Например, строковый триггер для `TRUNCATE` в PostgreSQL создать нельзя.

#### BEFORE

Триггер выполняется до изменения строки.

Он подходит для некоторых сценариев:

- заполнение служебных полей;
- нормализация значений;
- проверка дополнительных условий;
- изменение значения `NEW`.

Пример:

```sql
CREATE TABLE documents (
    document_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Создадим функцию:

```sql
CREATE OR REPLACE FUNCTION set_document_updated_at()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at := clock_timestamp();
    RETURN NEW;
END;
$$;
```

Создадим триггер:

```sql
CREATE TRIGGER trg_documents_updated_at
BEFORE UPDATE ON documents
FOR EACH ROW
EXECUTE FUNCTION set_document_updated_at();
```

Теперь при изменении строки значение `updated_at` будет обновляться автоматически.

#### Почему используется clock_timestamp

PostgreSQL предоставляет несколько функций времени.

Например:

```sql
CURRENT_TIMESTAMP
```

возвращает время, связанное с началом текущей транзакции.

`statement_timestamp()` соответствует началу текущего SQL-оператора.

`clock_timestamp()` возвращает текущее фактическое время на момент вызова.

Если требуется время начала транзакции, `CURRENT_TIMESTAMP` подходит.

Если необходимо фиксировать момент выполнения самой триггерной логики, можно использовать `clock_timestamp()`.

Выбор зависит от требований к смыслу временной метки.

#### AFTER

`AFTER`-триггер выполняется после соответствующего изменения строки или оператора.

Он подходит, например, для аудита.

Важно понимать, что `AFTER` не означает «после COMMIT».

Обычный `AFTER`-триггер выполняется в рамках транзакции, а не после её окончательной фиксации.

Если транзакция будет отменена, обычные изменения, выполненные таким триггером в той же транзакции, тоже будут отменены.

#### INSTEAD OF

Триггеры `INSTEAD OF` позволяют заменить обычное действие собственной логикой.

Например, сложное представление может быть необновляемым автоматически.

Через `INSTEAD OF`-триггер можно определить, какие операции над базовыми таблицами должны выполняться при попытке изменить представление.

В PostgreSQL `INSTEAD OF`-триггеры используются только для строковых операций над представлениями.

Они не являются универсальным режимом для любых таблиц и событий.

### Тема 6. Строковые и операторные триггеры

Триггеры отличаются не только временем выполнения, но и уровнем срабатывания.

#### ROW-level

Строковый триггер выполняется для каждой затронутой строки.

```sql
CREATE TRIGGER trg_documents_updated_at
BEFORE UPDATE ON documents
FOR EACH ROW
EXECUTE FUNCTION set_document_updated_at();
```

Если UPDATE изменяет 1000 строк, строковая триггерная функция может выполниться 1000 раз.

Это удобно для работы с конкретными значениями `NEW` и `OLD`.

Однако при массовых операциях количество вызовов может быть значительным.

#### STATEMENT-level

Операторный триггер выполняется один раз на SQL-оператор.

Например:

```sql
CREATE OR REPLACE FUNCTION log_document_statement()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    RAISE NOTICE 'Executed operation: %', TG_OP;
    RETURN NULL;
END;
$$;
```

Создадим:

```sql
CREATE TRIGGER trg_documents_statement
AFTER UPDATE ON documents
FOR EACH STATEMENT
EXECUTE FUNCTION log_document_statement();
```

Такой триггер выполняется один раз для UPDATE-оператора, даже если он затронул много строк.

В PostgreSQL операторный триггер может сработать даже при изменении нуля строк.

Но следует учитывать особенности событий, выполняемых внутри более сложных SQL-конструкций.

#### Transition Tables в PostgreSQL

Для некоторых `AFTER`-триггеров PostgreSQL поддерживает transition tables.

Они позволяют получить набор старых или новых строк, затронутых одним SQL-оператором.

Это особенно полезно при массовом аудите.

Пример определения:

```sql
CREATE TRIGGER trg_orders_audit_statement
AFTER UPDATE ON orders
REFERENCING
    OLD TABLE AS old_rows
    NEW TABLE AS new_rows
FOR EACH STATEMENT
EXECUTE FUNCTION audit_orders_statement();
```

Здесь предполагается, что функция `audit_orders_statement()` уже создана.

Внутри функции можно обращаться к `old_rows` и `new_rows` как к наборам строк.

Это позволяет выполнять операции над изменениями сразу как над таблицами, вместо отдельной обработки каждой строки.

Transition tables поддерживаются не для всех видов триггеров.

Например, они не применяются к произвольным `BEFORE`-триггерам.

#### Различия четырёх СУБД

| Возможность | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| ROW-level DML trigger | Да | Нет в обычной модели DML-триггеров | Да | Да |
| STATEMENT-level DML trigger | Да | Да | Нет | Да |
| BEFORE INSERT/UPDATE/DELETE | Да | Нет обычного BEFORE DML-триггера | Да | Да |
| AFTER INSERT/UPDATE/DELETE | Да | Да | Да | Да |
| INSTEAD OF на представлении | Да | Да | Нет | Да |
| NEW / OLD | Да | inserted / deleted | Да | Да |
| Срабатывание на TRUNCATE | Да, statement-level | Нет как обычный DML-триггер на TRUNCATE | Нет | Нет как обычный DML-триггер на TRUNCATE |

В SQL Server DML-триггеры выполняются на уровне оператора.

Они работают с логическими таблицами:

```sql
inserted
deleted
```

Эти таблицы могут содержать несколько строк.

Поэтому SQL Server-триггер нельзя писать с предположением, что один UPDATE всегда изменяет ровно одну строку.

В MySQL триггеры работают построчно с `OLD` и `NEW`.

В Oracle поддерживаются как строковые, так и операторные триггеры, а также compound triggers.

### Тема 7. NEW и OLD в триггерной логике

В PostgreSQL строковые триггеры получают доступ к специальным псевдозаписям.

#### INSERT

Для INSERT доступно новое состояние строки:

```text
NEW
```

Прежней строки ещё не существовало.

Поэтому `OLD` для INSERT не содержит прежнее состояние строки.

#### UPDATE

При UPDATE доступны:

```text
OLD
NEW
```

`OLD` содержит прежние значения.

`NEW` содержит новое состояние строки.

Например:

```sql
IF OLD.status IS DISTINCT FROM NEW.status THEN
    -- статус действительно изменился
END IF;
```

Использование `IS DISTINCT FROM` важно, поскольку оно корректно учитывает сравнение со значениями `NULL`.

Обычное выражение:

```sql
OLD.status <> NEW.status
```

может вернуть `NULL`, если одно из значений отсутствует.

#### DELETE

Для DELETE доступно старое состояние:

```text
OLD
```

Новой строки после удаления не существует.

#### Возвращаемое значение

Для строкового `BEFORE`-триггера PostgreSQL возвращаемое значение имеет значение.

Обычно:

```sql
RETURN NEW;
```

используется для INSERT и UPDATE.

Для DELETE обычно используется:

```sql
RETURN OLD;
```

Если строковый `BEFORE`-триггер возвращает `NULL`, PostgreSQL пропускает дальнейшую обработку соответствующей строки в рамках операции.

Это может предотвратить её вставку, обновление или удаление.

Такое поведение необходимо использовать осторожно, поскольку запрос может завершиться без SQL-ошибки, но затронуть меньше строк, чем ожидалось.

Для обычного `AFTER`-триггера возвращаемое значение триггерной функции игнорируется.

Для `INSTEAD OF`-триггера на представлении возвращаемое значение также имеет специальный смысл.

#### Специальные переменные PostgreSQL

Кроме `NEW` и `OLD`, триггерные функции PL/pgSQL могут использовать:

| Переменная | Назначение |
|---|---|
| TG_OP | Тип операции: INSERT, UPDATE, DELETE, TRUNCATE |
| TG_NAME | Имя триггера |
| TG_TABLE_NAME | Имя таблицы |
| TG_TABLE_SCHEMA | Имя схемы |
| TG_LEVEL | ROW или STATEMENT |
| TG_WHEN | BEFORE, AFTER или INSTEAD OF |

Эти значения полезны при создании универсальных триггерных функций.

Но универсальность не всегда является преимуществом.

Слишком сложная функция, обслуживающая множество разных таблиц, может быть труднее для понимания и сопровождения.

### Тема 8. Практика: триггер аудита изменений

Рассмотрим пример аудита статусов заказов.

Необходимо сохранять:

- идентификатор заказа;
- прежний статус;
- новый статус;
- время изменения;
- пользователя базы данных.

#### Таблица аудита

```sql
CREATE TABLE order_status_audit (
    audit_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    old_status VARCHAR(30),
    new_status VARCHAR(30),
    changed_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    changed_by TEXT NOT NULL
);
```

#### Триггерная функция

```sql
CREATE OR REPLACE FUNCTION audit_order_status_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF OLD.status IS DISTINCT FROM NEW.status THEN
        INSERT INTO order_status_audit (
            order_id,
            old_status,
            new_status,
            changed_by
        )
        VALUES (
            NEW.order_id,
            OLD.status,
            NEW.status,
            session_user
        );
    END IF;

    RETURN NEW;
END;
$$;
```

#### Создание триггера

```sql
CREATE TRIGGER trg_orders_status_audit
AFTER UPDATE OF status ON orders
FOR EACH ROW
EXECUTE FUNCTION audit_order_status_change();
```

Теперь при изменении статуса:

```sql
UPDATE orders
SET status = 'completed'
WHERE order_id = 3;
```

будет создана запись аудита.

Проверка:

```sql
SELECT *
FROM order_status_audit
ORDER BY audit_id;
```

Важно учитывать, что `UPDATE OF status` срабатывает, когда столбец `status` указан среди изменяемых столбцов команды.

При этом значение может фактически остаться прежним.

Поэтому внутри функции выполняется дополнительная проверка:

```sql
OLD.status IS DISTINCT FROM NEW.status
```

#### Аудит и транзакции

Поскольку запись в таблицу аудита выполняется обычным триггером, она входит в ту же транзакцию.

Например:

```sql
BEGIN;

UPDATE orders
SET status = 'cancelled'
WHERE order_id = 2;

ROLLBACK;
```

Изменение заказа будет отменено.

Соответствующая запись в таблице аудита также не сохранится.

Это важно для понимания границ такого аудита.

**Триггерный аудит не является автоматически независимым или неизменяемым журналом безопасности.**

Если необходимо фиксировать также неуспешные попытки, откаты транзакций или действия высокопривилегированных пользователей, потребуются дополнительные механизмы:

- журналы СУБД;
- специализированный database audit;
- CDC;
- внешняя система журналирования;
- защищённое централизованное хранение событий.

Также значение `session_user` указывает пользователя подключения к PostgreSQL, а не обязательно конечного пользователя приложения.

Если приложение использует общий технический аккаунт, все изменения могут выполняться от имени одной роли базы данных.

Идентификатор конечного пользователя должен передаваться отдельным контролируемым способом.

При этом нельзя без проверки доверять произвольному значению, которое приложение может передать в переменную сессии.

#### Аудит через JSONB

Если структура таблицы сложная и требуется сохранять состояние строки целиком, можно использовать JSONB.

```sql
CREATE TABLE order_change_audit (
    audit_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    operation TEXT NOT NULL,
    old_data JSONB,
    new_data JSONB,
    changed_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);
```

Пример функции:

```sql
CREATE OR REPLACE FUNCTION audit_order_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO order_change_audit (
            order_id,
            operation,
            old_data,
            new_data
        )
        VALUES (
            NEW.order_id,
            TG_OP,
            NULL,
            to_jsonb(NEW)
        );

        RETURN NEW;

    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO order_change_audit (
            order_id,
            operation,
            old_data,
            new_data
        )
        VALUES (
            NEW.order_id,
            TG_OP,
            to_jsonb(OLD),
            to_jsonb(NEW)
        );

        RETURN NEW;

    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO order_change_audit (
            order_id,
            operation,
            old_data,
            new_data
        )
        VALUES (
            OLD.order_id,
            TG_OP,
            to_jsonb(OLD),
            NULL
        );

        RETURN OLD;
    END IF;

    RETURN NULL;
END;
$$;
```

Создадим триггер:

```sql
CREATE TRIGGER trg_orders_change_audit
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW
EXECUTE FUNCTION audit_order_change();
```

Такой вариант позволяет фиксировать исходное и новое состояние строки.

Однако он имеет расходы:

- сериализация строк в JSONB;
- дополнительная запись на каждое изменение;
- увеличение объёма хранения;
- дополнительная нагрузка на WAL;
- возможное сохранение чувствительных данных.

Для большой системы аудита необходимо заранее определить, какие поля действительно требуется сохранять и как долго хранить историю.

В приведённых примерах можно использовать либо специализированный аудит статуса, либо полный аудит строки. Если оставить оба триггера, изменение статуса приведёт к записям в обе таблицы аудита.

Это может быть осознанным решением, но не должно происходить случайно.

### Тема 9. Практика: автоматическое обновление служебных полей

Другой распространённый сценарий использования триггеров — поддержка технических атрибутов записи.

Например:

```text
created_at
updated_at
```

Для времени создания удобно использовать DEFAULT.

```sql
CREATE TABLE articles (
    article_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL,
    body TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Но DEFAULT применяется при вставке, а не автоматически при каждом UPDATE.

Для обновления `updated_at` можно использовать триггер.

```sql
CREATE OR REPLACE FUNCTION update_articles_timestamp()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at := clock_timestamp();
    RETURN NEW;
END;
$$;
```

```sql
CREATE TRIGGER trg_articles_updated_at
BEFORE UPDATE ON articles
FOR EACH ROW
EXECUTE FUNCTION update_articles_timestamp();
```

Вставим статью:

```sql
INSERT INTO articles (title, body)
VALUES (
    'Введение в SQL',
    'Учебный материал'
);
```

Изменим содержимое:

```sql
UPDATE articles
SET body = 'Обновлённый учебный материал'
WHERE article_id = 1;
```

Проверим:

```sql
SELECT
    article_id,
    title,
    created_at,
    updated_at
FROM articles;
```

`updated_at` будет изменён.

Но у такого триггера есть особенность: он выполняется при любом UPDATE строки, даже если новое значение фактически не отличается от прежнего.

При необходимости можно ограничить обновление временной метки только реальными изменениями бизнес-полей.

Например, сравнивать определённый набор столбцов.

#### Нужно ли всегда использовать триггер для updated_at

Не обязательно.

Возможные варианты:

- явное обновление поля приложением;
- триггер БД;
- специальные механизмы конкретной СУБД.

Например, MySQL поддерживает для `TIMESTAMP` и `DATETIME` конструкцию `ON UPDATE CURRENT_TIMESTAMP`.

В SQL Server нет полностью эквивалентного универсального синтаксиса автоматического обновления обычного datetime-столбца при каждом UPDATE.

Также не следует путать SQL Server `rowversion` с временной меткой.

`rowversion` — бинарное значение для отслеживания изменений, а не дата и время.

Выбор механизма зависит от требований к точности, прозрачности и согласованности работы разных приложений.

### Тема 10. Практические риски использования триггеров

Триггеры полезны, но усложняют поведение базы данных.

Операция, выглядящая как один UPDATE, может запускать дополнительные запросы, триггеры и изменения связанных таблиц.

#### Скрытая логика

Например:

```sql
UPDATE orders
SET status = 'completed'
WHERE order_id = 10;
```

Может вызвать:

- запись в таблицу аудита;
- обновление служебного поля;
- добавление события в outbox;
- изменение производных данных.

Разработчик приложения должен понимать эти последствия.

Поэтому триггеры необходимо документировать и включать в миграции вместе с изменениями таблиц.

#### Производительность

Строковый триггер выполняется для каждой затронутой строки.

Если массовый UPDATE затрагивает миллион строк, триггерная функция может быть вызвана миллион раз.

Это не означает, что строковые триггеры всегда неприемлемы.

Но важно учитывать:

- количество вызываемых SQL-команд;
- наличие индексов на связанных таблицах;
- объём записываемого аудита;
- стоимость JSON-преобразований;
- количество строк в операции;
- блокировки;
- рост WAL и транзакционного журнала.

При массовых изменениях операторные триггеры и transition tables могут оказаться более подходящими.

#### Рекурсия

Рассмотрим опасный шаблон:

```text
UPDATE table_a
    → trigger_a
        → UPDATE table_a
            → trigger_a
                → ...
```

Если триггер изменяет ту же таблицу, на которой сам срабатывает, возможна повторная активация.

Рекурсия также может возникать через цепочку разных таблиц.

Например:

```text
table_a → table_b → table_c → table_a
```

В PostgreSQL существует функция:

```sql
SELECT pg_trigger_depth();
```

Она возвращает текущую глубину вложенного выполнения триггеров.

Но использование глубины триггеров как универсального способа предотвращения рекурсии рискованно.

Такой подход может зависеть от посторонних триггеров и скрывать неправильную архитектуру.

Лучше проектировать операции так, чтобы они не вызывали бесконтрольные повторные изменения.

Например, для изменения `NEW.updated_at` подходит `BEFORE UPDATE`, а не дополнительный UPDATE той же строки внутри `AFTER UPDATE`.

#### Порядок выполнения

В PostgreSQL несколько триггеров одного вида для одного события выполняются в алфавитном порядке их имён.

Однако не следует строить сложную бизнес-логику, зависящую от неочевидных правил сортировки имён триггеров.

В других СУБД правила могут отличаться.

Например, MySQL поддерживает `FOLLOWS` и `PRECEDES`, а SQL Server предоставляет отдельные механизмы определения первого и последнего триггера для некоторых событий.

Если порядок принципиален, его необходимо выражать явно поддерживаемыми средствами либо объединять зависимые действия в контролируемую процедуру.

#### Триггеры и внешние вызовы

Нежелательно выполнять из обычной триггерной логики длительные внешние обращения.

Например:

```text
UPDATE orders
    → trigger
        → HTTP-запрос
            → ожидание ответа внешнего сервиса
```

Такой подход может привести к:

- удержанию транзакции открытой;
- увеличению времени блокировок;
- зависанию операции записи;
- ошибкам при недоступности внешнего сервиса;
- невозможности автоматически отменить внешний эффект при ROLLBACK.

Для надёжной передачи событий между системой и внешними обработчиками часто используется transactional outbox.

Суть подхода:

1. В той же транзакции изменяются бизнес-данные.
2. В таблицу outbox добавляется событие.
3. Транзакция подтверждается.
4. Отдельный обработчик читает события и передаёт их внешним системам.

Триггер может использоваться для формирования outbox-записи, но это не обязательно лучший вариант.

Во многих системах запись события выполняется явно на уровне прикладной транзакции.

#### Ограничения и каскадные действия

Триггеры не должны без необходимости заменять стандартные ограничения.

Например, если требуется обеспечить уникальность:

```sql
UNIQUE
```

обычно предпочтительнее триггера, выполняющего предварительный SELECT.

А если требуется автоматическое удаление дочерних записей при удалении родительской:

```sql
FOREIGN KEY (...) REFERENCES ...
ON DELETE CASCADE
```

обычно лучше выражает ссылочное правило, чем ручной триггер.

Ограничения СУБД корректнее отражают инварианты и учитывают конкурентный доступ.

Проверка вида:

```sql
IF NOT EXISTS (...) THEN
    INSERT ...
END IF;
```

сама по себе не гарантирует уникальности при конкурентных транзакциях.

#### Транзакционность триггеров

В PostgreSQL обычный триггер выполняется в контексте SQL-команды и её транзакции.

Если триггерная функция вызывает необработанную ошибку, это влияет на выполнение исходной операции.

Если транзакция откатывается, её обычные табличные изменения, в том числе выполненные триггерами, откатываются вместе с ней.

Но не все побочные эффекты одинаково транзакционны.

Например, изменения последовательностей и внешние действия могут не откатываться обычным ROLLBACK.

Это необходимо учитывать при проектировании триггерной логики.

### Тема 11. Триггеры в SQL Server, MySQL и Oracle

Реализация триггеров существенно отличается между СУБД.

#### SQL Server: таблицы inserted и deleted

В SQL Server DML-триггер создаётся непосредственно с SQL-кодом.

Например:

```sql
CREATE OR ALTER TRIGGER dbo.trg_orders_audit
ON dbo.orders
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO dbo.order_status_audit (
        order_id,
        old_status,
        new_status,
        changed_at
    )
    SELECT
        i.order_id,
        d.status,
        i.status,
        SYSDATETIME()
    FROM inserted AS i
    JOIN deleted AS d
        ON d.order_id = i.order_id
    WHERE i.status <> d.status
       OR (i.status IS NULL AND d.status IS NOT NULL)
       OR (i.status IS NOT NULL AND d.status IS NULL);
END;
```

В примере предполагается, что таблицы и соответствующие столбцы существуют.

Ключевая особенность: `inserted` и `deleted` — наборы строк.

Если один UPDATE изменил 500 строк, триггер должен корректно обработать все 500.

Неверный подход:

```sql
SELECT @id = order_id
FROM inserted;
```

если разработчик предполагает, что в `inserted` всегда находится одна строка.

Такой код может некорректно работать при массовых операциях.

SQL Server поддерживает также `INSTEAD OF`-триггеры.

#### MySQL/InnoDB: NEW и OLD

В MySQL триггеры выполняются для каждой строки.

Пример обновления временной метки:

```sql
CREATE TRIGGER trg_articles_updated_at
BEFORE UPDATE ON articles
FOR EACH ROW
SET NEW.updated_at = CURRENT_TIMESTAMP;
```

В MySQL используются:

```text
NEW.column_name
OLD.column_name
```

Но операторных триггеров `FOR EACH STATEMENT` в MySQL 8.4 нет.

Также MySQL не поддерживает обычные триггеры на представлениях.

MySQL-триггеры ограничены `INSERT`, `UPDATE` и `DELETE` и не создаются непосредственно на событие `TRUNCATE`.

#### Oracle: строковые и операторные триггеры

Oracle поддерживает разные виды DML-триггеров.

Пример:

```sql
CREATE OR REPLACE TRIGGER trg_articles_updated_at
BEFORE UPDATE ON articles
FOR EACH ROW
BEGIN
    :NEW.updated_at := SYSTIMESTAMP;
END;
/
```

Для доступа к псевдозаписям используются:

```text
:NEW
:OLD
```

Oracle также поддерживает compound triggers.

Они позволяют объединять обработку разных моментов и уровней выполнения в рамках одного определения.

Такой механизм полезен в отдельных сценариях массовой обработки, когда необходимо накапливать данные на строковом уровне и обрабатывать их на уровне оператора.

#### Переносимость триггеров

| Характеристика | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| Отдельная триггерная функция | Обычно да | Нет, код внутри триггера | Код внутри триггера | Код внутри триггера |
| Основной процедурный язык | PL/pgSQL и другие | T-SQL | SQL/PSM-подобный синтаксис MySQL | PL/SQL |
| Обработка множества строк одним триггером | Transition Tables | inserted / deleted | Нет statement-level trigger | Statement/compound triggers |
| BEFORE ROW | Да | Нет | Да | Да |
| INSTEAD OF VIEW | Да | Да | Нет | Да |

Таким образом, перенос триггеров между СУБД обычно требует переписывания логики, а не только изменения отдельных команд.

### Тема 12. Соотношение представлений, последовательностей и триггеров

Представления, последовательности и триггеры решают разные задачи.

#### Представления

Используются, когда требуется:

- скрыть сложный SELECT;
- предоставить логический интерфейс к данным;
- ограничить видимость столбцов;
- сформировать удобную структуру для отчёта;
- уменьшить зависимость приложения от изменений базовых таблиц.

Представление не должно рассматриваться как универсальный механизм ускорения запросов.

#### Последовательности

Используются, когда требуется:

- автоматически генерировать числовые значения;
- получать идентификаторы до вставки;
- использовать общий источник чисел;
- управлять шагом и диапазоном генерации.

Последовательность не гарантирует нумерацию без пропусков и не задаёт порядок подтверждения транзакций.

#### Триггеры

Используются, когда требуется:

- автоматически обновлять технические атрибуты;
- вести аудит изменений;
- выполнять дополнительные действия при изменении строк;
- реализовывать определённые правила, которые нельзя удобно выразить обычными ограничениями.

При этом триггер не должен становиться неконтролируемым местом хранения всей бизнес-логики приложения.

#### Сравнение механизмов

| Задача | Подходящий механизм |
|---|---|
| Сохранить сложный SELECT | VIEW |
| Скрыть отдельные столбцы | VIEW + корректные права |
| Физически сохранить результат аналитического запроса | MATERIALIZED VIEW или аналог |
| Сгенерировать идентификатор строки | IDENTITY / AUTO_INCREMENT / SEQUENCE |
| Использовать общий источник чисел для нескольких таблиц | SEQUENCE |
| Автоматически обновить updated_at | Триггер или механизм СУБД |
| Сохранить историю изменения строки | Аудит через триггер, CDC или другой механизм |
| Обеспечить уникальность | UNIQUE |
| Обеспечить ссылочную целостность | FOREIGN KEY |
| Автоматически удалить дочерние строки | FOREIGN KEY с ON DELETE CASCADE, если соответствует бизнес-правилу |
| Передать событие внешнему сервису | Outbox / очередь / отдельный обработчик |

Выбор должен определяться требованиями к целостности, производительности, безопасности и сопровождению.

## Итоговые выводы

1. **Представления формируют логический слой доступа к данным.** Они позволяют сохранить SQL-запрос и использовать его как объект базы данных, но обычное представление не обязательно хранит результат физически.

2. **Представления могут использоваться для ограничения доступа.** Однако безопасность зависит от прав, режима выполнения, RLS и других механизмов СУБД.

3. **Не все представления автоматически обновляемы.** Сложные запросы с агрегациями, соединениями и другими конструкциями могут ограничивать операции INSERT, UPDATE и DELETE.

4. **WITH CHECK OPTION позволяет контролировать изменения через обновляемые представления.** Он предотвращает определённые изменения, после которых строка перестала бы удовлетворять условиям представления.

5. **Материализованные представления сохраняют результаты запросов, но требуют отдельного управления актуальностью.** Их использование оправданно там, где стоимость повторного вычисления превышает расходы на хранение и обновление.

6. **Последовательности предназначены для генерации числовых значений.** Они могут быть независимыми объектами либо использоваться для автоматического заполнения столбцов.

7. **Последовательности не гарантируют отсутствия пропусков.** Откаты транзакций, кеширование и другие обстоятельства могут приводить к пропущенным значениям.

8. **IDENTITY, SERIAL, AUTO_INCREMENT и SEQUENCE имеют различную реализацию.** Нельзя переносить их синтаксис и поведение между СУБД без проверки.

9. **Триггеры автоматически выполняют логику при изменении данных.** Они подходят для отдельных служебных операций и аудита, но увеличивают скрытую сложность системы.

10. **Строковые и операторные триггеры отличаются по уровню выполнения.** PostgreSQL и Oracle поддерживают оба подхода, SQL Server использует операторные DML-триггеры, а MySQL/InnoDB — строковые.

11. **NEW и OLD позволяют получать старое и новое состояние строки.** В SQL Server аналогичные задачи выполняются через наборы строк inserted и deleted.

12. **Обычный триггерный аудит не гарантирует независимого хранения событий.** Записи аудита, выполняемые в той же транзакции, откатываются вместе с её изменениями.

13. **Триггеры требуют контроля производительности и рекурсии.** Массовые операции могут вызывать большое количество дополнительных действий, а цепочки триггеров — создавать неожиданные зависимости.

14. **Представления, последовательности и триггеры не заменяют ограничения целостности.** Если правило можно корректно выразить через PRIMARY KEY, UNIQUE, FOREIGN KEY или CHECK, обычно следует рассматривать эти механизмы в первую очередь.

Главный результат занятия — понимание того, как представления, последовательности и триггеры расширяют возможности реляционной базы данных и где проходят границы их разумного применения.
