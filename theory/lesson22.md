
# Оптимизация чтения данных в SQL

## Превью / аннотация / краткое содержание

Занятие посвящено оптимизации SQL-запросов, ориентированных на чтение данных из реляционных баз данных.

Главная задача оптимизации чтения — уменьшить количество ненужных операций при сохранении корректности результата: сократить объём обрабатываемых строк, использовать подходящие способы доступа и избежать чрезмерных промежуточных вычислений.

Один и тот же результат можно получить разными SQL-конструкциями. Но разные формы запроса могут приводить к разным физическим планам, количеству прочитанных страниц, сортировок, соединений и повторных вычислений.

На занятии рассматриваются:

- связь формы SQL-запроса с физическим планом выполнения;
- фильтрация до и после агрегации;
- различия между `WHERE` и `HAVING`;
- использование `COUNT(DISTINCT)`;
- причины дублирования строк при соединениях;
- оконные функции и их стоимость;
- устранение избыточности через `DISTINCT`;
- индексопригодные условия поиска;
- функции и преобразования типов над индексируемыми столбцами;
- оптимизация временных диапазонов;
- использование полуоткрытых интервалов;
- условия `OR` и механизмы `BitmapOr`;
- декомпозиция запросов через `UNION ALL`;
- коррелированные подзапросы;
- предварительные вычисления через CTE;
- материализация и повторное использование результатов;
- оптимизация поиска ближайших пространственных объектов;
- анализ эффективности изменений через планы выполнения.

Основные практические примеры приведены для PostgreSQL. Особенности Microsoft SQL Server, MySQL/InnoDB и Oracle рассматриваются отдельно.

## Основные понятия

**Оптимизация чтения данных** — изменение SQL-запроса, индексов или структуры данных для уменьшения затрат на получение результата при сохранении его корректности.

**Фильтрация** — отбор строк по заданному условию.

**WHERE** — конструкция SQL для фильтрации строк до логической группировки и вычисления агрегатов.

**HAVING** — конструкция для фильтрации групп по условиям, в том числе с использованием агрегатных функций.

**GROUP BY** — группировка строк по указанным выражениям.

**Агрегация** — вычисление одного результата по набору значений, например через `COUNT`, `SUM`, `AVG`, `MIN` или `MAX`.

**COUNT(DISTINCT)** — подсчёт различных ненулевых значений выражения.

**DISTINCT** — устранение дублирующихся строк результата по выбранным выражениям.

**Оконная функция (Window Function)** — функция, вычисляющая значение по набору связанных строк без обычного сворачивания результата в одну строку на группу.

**OVER** — конструкция SQL, задающая окно вычисления.

**PARTITION BY** — логическое разделение строк на независимые группы внутри оконного вычисления.

**Window Frame** — часть раздела окна, участвующая в вычислении функций, учитывающих границы рамки.

**Селективность (Selectivity)** — характеристика доли строк, удовлетворяющих условию отбора.

**Sargable Predicate** — условие, форма которого позволяет эффективно применять поддерживаемые индексом операции поиска.

**Индексный доступ** — получение строк с использованием индексной структуры.

**Index Only Scan** — операция PostgreSQL, потенциально позволяющая получить необходимые значения из индекса без обычного чтения heap-строк.

**Bitmap Index Scan** — операция PostgreSQL, получающая адреса подходящих строк через индекс.

**Bitmap Heap Scan** — операция PostgreSQL, читающая страницы таблицы по результату bitmap-поиска.

**BitmapOr** — оператор PostgreSQL, объединяющий результаты нескольких bitmap-поисков по логическому OR.

**Индекс по выражению (Expression Index)** — индекс, построенный по результату вычисления выражения.

**Computed Column** — вычисляемый столбец SQL Server.

**Generated Column** — вычисляемый столбец MySQL или другой СУБД с аналогичными возможностями.

**Function-Based Index** — индекс по выражению в Oracle.

**Диапазонный поиск (Range Scan)** — поиск значений внутри заданного диапазона.

**Полуоткрытый интервал** — диапазон, включающий нижнюю границу и исключающий верхнюю.

**BETWEEN** — SQL-оператор проверки принадлежности включительному диапазону.

**OR** — логическое объединение альтернативных условий.

**UNION** — объединение результатов запросов с устранением повторяющихся строк.

**UNION ALL** — объединение результатов запросов с сохранением повторов.

**Коррелированный подзапрос** — подзапрос, использующий значения внешнего уровня запроса.

**CTE (Common Table Expression)** — именованное выражение, задаваемое через `WITH`.

**Материализация** — физическое сохранение промежуточного результата для последующего использования.

**LATERAL** — механизм PostgreSQL, позволяющий элементу `FROM` зависеть от значений предыдущих элементов.

**APPLY** — конструкция SQL Server для выполнения зависимого табличного выражения.

**KNN (K-Nearest Neighbors)** — поиск ближайших соседей.

**GiST** — индексный метод PostgreSQL, широко используемый для пространственных данных.

**План выполнения (Execution Plan)** — выбранный оптимизатором набор физических операций выполнения SQL-запроса.

**Cardinality Estimation** — оценка количества строк на определённом этапе выполнения.

**Baseline** — исходный результат измерения, используемый для сравнения после оптимизации.

## Основная часть

### Тема 1. Оптимизация чтения как управление объёмом обрабатываемых данных

Запрос может возвращать небольшое количество строк, но выполнять значительную работу.

Например:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Если таблица содержит миллион строк, а клиенту принадлежит только десять заказов, СУБД может:

- прочитать большую часть таблицы;
- найти нужные строки через индекс;
- использовать bitmap-доступ;
- применить другие способы выполнения.

Количество возвращённых строк одинаково, но физическая стоимость может существенно отличаться.

#### Главный принцип

Оптимизация чтения направлена на сокращение:

- ненужных чтений страниц;
- лишних строк в соединениях;
- чрезмерных промежуточных результатов;
- повторных вычислений;
- ненужных сортировок;
- операций передачи данных клиенту.

Но важно различать логическую и физическую обработку запроса.

SQL-запрос:

```sql
SELECT *
FROM orders
WHERE status = 'completed';
```

не означает, что PostgreSQL сначала выполняет все операции в буквальном текстовом порядке.

Оптимизатор строит физический план.

Он может:

- переставлять соединения;
- переносить условия;
- преобразовывать подзапросы;
- использовать индексы;
- выполнять агрегацию разными способами.

Поэтому ранняя фильтрация является полезной целью оптимизации, но не обязательно требует вручную переставлять части SQL-текста.

Если оптимизатор уже выполняет нужное преобразование, переписывание запроса может не дать выигрыша.

#### Три вопроса перед оптимизацией

1. Сколько строк действительно необходимо вернуть?
2. Сколько строк и страниц обрабатывает текущий план?
3. Можно ли уменьшить физическую работу, сохранив тот же результат?

Последний пункт принципиален.

**Быстрый запрос, возвращающий неправильные данные, не является успешной оптимизацией.**

### Тема 2. Связь формы SQL и плана выполнения

Разные записи логически эквивалентного запроса иногда приводят к одинаковому плану.

Например:

```sql
SELECT *
FROM orders
WHERE customer_id = 1001
  AND status = 'completed';
```

И:

```sql
SELECT *
FROM orders
WHERE status = 'completed'
  AND customer_id = 1001;
```

Для обычных детерминированных сравнений эти условия логически эквивалентны.

Оптимизатор не обязан учитывать текстовый порядок условий `AND` как порядок их физического исполнения.

Поэтому перестановка условий сама по себе не является надёжным способом ускорения.

#### Когда форма действительно имеет значение

Например:

```sql
WHERE created_at::date = DATE '2026-03-15'
```

и:

```sql
WHERE created_at >= TIMESTAMP '2026-03-15 00:00:00'
  AND created_at < TIMESTAMP '2026-03-16 00:00:00'
```

Для столбца `timestamp without time zone` эти условия при обычной интерпретации календарной даты задают один и тот же дневной интервал.

Но вторая форма может эффективнее использовать обычный B-tree индекс по `created_at`.

Различие возникает не из-за расположения условия в SQL, а из-за того, что во втором случае индексируемый столбец сравнивается напрямую с границами диапазона.

#### Проверка через EXPLAIN

В PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE created_at >= TIMESTAMP '2026-03-15'
  AND created_at < TIMESTAMP '2026-03-16';
```

Нужно смотреть:

- `Seq Scan`;
- `Index Scan`;
- `Bitmap Heap Scan`;
- `Index Cond`;
- `Filter`;
- количество строк;
- обращения к буферам;
- время выполнения.

Если оба варианта используют одинаковый план и обрабатывают одинаковое количество страниц, ожидаемый эффект переписывания может отсутствовать.

### Тема 3. WHERE и HAVING

`WHERE` и `HAVING` относятся к разным логическим этапам обработки данных.

`WHERE` фильтрует исходные строки.

`HAVING` фильтрует группы после их формирования.

#### Пример

Пусть существует таблица заказов:

```sql
CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status TEXT NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Нужно посчитать суммы завершённых заказов по клиентам.

```sql
SELECT
    customer_id,
    SUM(total_amount) AS total_amount
FROM orders
WHERE status = 'completed'
GROUP BY customer_id;
```

`WHERE` определяет, какие заказы участвуют в агрегации.

#### Фильтрация групп

Если нужны только клиенты с суммой завершённых заказов более 10 000:

```sql
SELECT
    customer_id,
    SUM(total_amount) AS total_amount
FROM orders
WHERE status = 'completed'
GROUP BY customer_id
HAVING SUM(total_amount) > 10000;
```

Здесь:

- `WHERE` отбирает завершённые заказы;
- `GROUP BY` формирует группы;
- `HAVING` отбирает группы по агрегированному результату.

#### Почему нельзя всегда заменить HAVING на WHERE

Условие:

```sql
HAVING SUM(total_amount) > 10000
```

нельзя просто перенести в `WHERE`, поскольку сумма группы ещё не определена на логическом этапе фильтрации исходных строк.

Также перенос условия способен изменить смысл.

Например:

```sql
SELECT
    customer_id,
    COUNT(*) AS orders_count
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 10;
```

здесь требуется выбрать клиентов, у которых более десяти заказов.

Нельзя заменить это фильтрацией каждой отдельной строки до группировки.

#### Обычные условия на группирующие столбцы

Рассмотрим:

```sql
SELECT
    customer_id,
    COUNT(*)
FROM orders
GROUP BY customer_id
HAVING customer_id = 1001;
```

Для этого запроса условие по ключу группировки можно выразить через `WHERE`:

```sql
SELECT
    customer_id,
    COUNT(*)
FROM orders
WHERE customer_id = 1001
GROUP BY customer_id;
```

Но это не означает, что первый вариант обязательно выполняется хуже.

Современный оптимизатор может самостоятельно перенести безопасное условие.

Поэтому после переписывания нужно проверять фактический план.

### Тема 4. Фильтрация до агрегации

Агрегация большого количества строк может требовать значительных ресурсов.

Например:

```sql
SELECT
    customer_id,
    SUM(total_amount)
FROM orders
GROUP BY customer_id;
```

Если в таблице десять миллионов строк, группировка обрабатывает большой набор.

Если бизнес-задача требует только заказов за март:

```sql
SELECT
    customer_id,
    SUM(total_amount)
FROM orders
WHERE created_at >= TIMESTAMP '2026-03-01'
  AND created_at < TIMESTAMP '2026-04-01'
GROUP BY customer_id;
```

фильтр может уменьшить объём данных, поступающий в агрегацию.

#### Почему это полезно

Меньший входной набор может уменьшить:

- количество строк для HashAggregate;
- стоимость сортировки;
- объём рабочей памяти;
- количество временных файлов;
- общую стоимость чтения.

Но если условие выбирает почти всю таблицу, существенного выигрыша может не быть.

#### Фильтрация при JOIN

Например:

```sql
SELECT
    c.customer_id,
    SUM(o.total_amount)
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.customer_id
WHERE o.created_at >= TIMESTAMP '2026-03-01'
  AND o.created_at < TIMESTAMP '2026-04-01'
GROUP BY c.customer_id;
```

Оптимизатор может применить временной фильтр к `orders` до выполнения JOIN.

Не следует предполагать, что сначала физически соединяются все строки, а только затем применяется WHERE.

#### Осторожно с OUTER JOIN

Перенос условий особенно опасен при внешних соединениях.

Например:

```sql
SELECT
    c.customer_id,
    o.order_id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.customer_id
WHERE o.status = 'completed';
```

Условие в `WHERE` исключает строки, в которых правая сторона не найдена и `o.status` равен `NULL`.

В результате такой запрос по смыслу близок к INNER JOIN для этого условия.

Но:

```sql
SELECT
    c.customer_id,
    o.order_id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.customer_id
   AND o.status = 'completed';
```

сохраняет клиентов даже при отсутствии завершённых заказов.

Поэтому перемещение условий между `ON` и `WHERE` не всегда сохраняет результат.

### Тема 5. COUNT(DISTINCT) и корректный подсчёт

При соединении таблиц одна логическая сущность может появляться несколько раз.

Предположим, есть таблицы:

```text
flights
tickets
```

Один рейс может иметь множество билетов.

При соединении:

```sql
SELECT
    f.flight_id,
    t.ticket_id
FROM flights AS f
JOIN tickets AS t
    ON t.flight_id = f.flight_id;
```

один `flight_id` повторяется столько раз, сколько найдено связанных билетов.

#### COUNT(*)

```sql
SELECT COUNT(*)
FROM flights AS f
JOIN tickets AS t
    ON t.flight_id = f.flight_id;
```

Возвращает число строк соединения.

Если на один рейс приходится сто билетов, рейс участвует в результате сто раз.

#### COUNT(DISTINCT)

Если нужно количество различных рейсов, по которым есть билеты:

```sql
SELECT COUNT(DISTINCT f.flight_id)
FROM flights AS f
JOIN tickets AS t
    ON t.flight_id = f.flight_id;
```

Такой запрос считает уникальные идентификаторы рейсов.

`COUNT(DISTINCT expression)` не учитывает SQL NULL.

#### Стоимость DISTINCT

Для определения различных значений СУБД может использовать:

- хеширование;
- сортировку;
- индекс;
- специальные операции агрегации.

Наличие `DISTINCT` может увеличивать стоимость запроса.

Но он необходим, если именно такая уникальность требуется по смыслу задачи.

#### Альтернатива через EXISTS

Если нужно просто посчитать рейсы, у которых существует хотя бы один билет, можно использовать `EXISTS`.

```sql
SELECT COUNT(*)
FROM flights AS f
WHERE EXISTS (
    SELECT 1
    FROM tickets AS t
    WHERE t.flight_id = f.flight_id
);
```

Этот запрос не размножает рейсы из-за количества билетов.

Оптимизатор может реализовать его как semi join или другим подходящим способом.

Для задачи проверки существования связи `EXISTS` часто выражает намерение понятнее, чем JOIN с последующим `DISTINCT`.

Но утверждать, что `EXISTS` всегда быстрее, нельзя.

### Тема 6. Дублирование строк как следствие JOIN

Повторы в результате соединения не обязательно означают ошибку СУБД или дублирование в исходной таблице.

Они могут быть естественным следствием кардинальности связей.

#### Один ко многим

Например:

```text
orders
  1
  |
  N
order_items
```

Один заказ связан с несколькими позициями.

Запрос:

```sql
SELECT
    o.order_id,
    o.total_amount,
    i.product_id
FROM orders AS o
JOIN order_items AS i
    ON i.order_id = o.order_id;
```

повторит `o.total_amount` для каждой позиции заказа.

Если затем выполнить:

```sql
SELECT SUM(o.total_amount)
FROM orders AS o
JOIN order_items AS i
    ON i.order_id = o.order_id;
```

общая сумма заказов может оказаться завышенной.

Причина — сумма вычисляется по строкам результата JOIN.

#### Предварительная агрегация

Если необходимо получить число позиций для каждого заказа:

```sql
SELECT
    o.order_id,
    o.total_amount,
    x.items_count
FROM orders AS o
JOIN (
    SELECT
        order_id,
        COUNT(*) AS items_count
    FROM order_items
    GROUP BY order_id
) AS x
    ON x.order_id = o.order_id;
```

Внутренний результат содержит одну строку на заказ.

Поэтому после JOIN не возникает размножения заказа из-за отдельных позиций.

#### Выбор решения

| Задача | Возможное решение |
|---|---|
| Посчитать строки соединения | COUNT(*) |
| Посчитать уникальные сущности | COUNT(DISTINCT) |
| Проверить наличие связи | EXISTS |
| Получить агрегат дочерних записей | Предварительная GROUP BY |
| Получить одну запись по определённому правилу | ROW_NUMBER, LATERAL или другой Top-N подход |

Не следует использовать `DISTINCT` как универсальный способ скрыть неправильную кардинальность соединения.

### Тема 7. Оконные функции в задачах чтения

Оконные функции позволяют получать агрегаты без обычного сворачивания строк.

Например, таблица рейсов:

```sql
CREATE TABLE flights (
    flight_id BIGINT PRIMARY KEY,
    departure_airport TEXT NOT NULL,
    arrival_airport TEXT NOT NULL,
    scheduled_departure TIMESTAMP NOT NULL,
    duration_minutes INTEGER NOT NULL
);
```

Необходимо показать длительность каждого рейса и минимальную длительность среди рейсов в тот же аэропорт.

```sql
SELECT
    flight_id,
    arrival_airport,
    duration_minutes,
    MIN(duration_minutes) OVER (
        PARTITION BY arrival_airport
    ) AS min_duration_to_airport
FROM flights;
```

Здесь строки рейсов сохраняются.

`PARTITION BY` задаёт отдельную логическую группу для каждого аэропорта прибытия.

#### Отличие от GROUP BY

Агрегация:

```sql
SELECT
    arrival_airport,
    MIN(duration_minutes)
FROM flights
GROUP BY arrival_airport;
```

возвращает одну строку на аэропорт.

Оконная функция сохраняет все рейсы.

Это разные задачи.

#### Стоимость оконных вычислений

Оконный запрос может требовать:

- сортировки;
- группировки строк по partition key;
- временного хранения;
- обработки большого числа строк.

Но нельзя утверждать, что оконная функция обязательно вычисляет один и тот же агрегат заново для каждой строки с нуля.

СУБД использует специализированные алгоритмы оконной обработки.

Повторение значения в результате не означает повторного полного сканирования всей группы для каждой строки.

#### Фильтрация до окна

Если нужны рейсы только за март:

```sql
SELECT
    flight_id,
    arrival_airport,
    duration_minutes,
    MIN(duration_minutes) OVER (
        PARTITION BY arrival_airport
    ) AS min_duration
FROM flights
WHERE scheduled_departure >= TIMESTAMP '2026-03-01'
  AND scheduled_departure < TIMESTAMP '2026-04-01';
```

Минимум вычисляется по рейсам марта, а не по всем рейсам таблицы.

Это важно для корректности.

Если требуется минимум по всей истории, но отобразить только мартовские рейсы, фильтрацию нужно разместить на другом уровне запроса.

Следовательно, раннее сокращение набора не всегда допустимо без изменения смысла окна.

### Тема 8. COUNT DISTINCT и оконные функции

Рассмотрим задачу:

> Для каждого рейса показать количество различных аэропортов прибытия в его группе.

В PostgreSQL нельзя просто написать:

```sql
COUNT(DISTINCT arrival_airport) OVER (...)
```

в обычном оконном агрегате: такая конструкция не поддерживается.

#### Вариант с предварительной агрегацией

Предположим, требуется число разных аэропортов назначения на каждую дату.

```sql
WITH airport_counts AS (
    SELECT
        scheduled_departure::date AS flight_date,
        COUNT(DISTINCT arrival_airport)
            AS distinct_airports
    FROM flights
    GROUP BY scheduled_departure::date
)
SELECT
    f.flight_id,
    f.scheduled_departure,
    f.arrival_airport,
    a.distinct_airports
FROM flights AS f
JOIN airport_counts AS a
    ON a.flight_date = f.scheduled_departure::date;
```

Этот запрос сначала вычисляет число различных направлений по дням, затем присоединяет показатель к каждому рейсу.

Для больших таблиц может быть полезно отдельно исследовать стоимость преобразования даты и доступность соответствующего индекса.

#### Различия СУБД

| СУБД | COUNT(DISTINCT ...) OVER |
|---|---|
| PostgreSQL | Не поддерживается напрямую |
| SQL Server | Не поддерживается напрямую |
| MySQL 8.4 | Не поддерживается для оконной формы DISTINCT-агрегата |
| Oracle | Поддерживаются определённые формы аналитического COUNT(DISTINCT) с ограничениями |

Поэтому перенос подобного оконного запроса между СУБД требует отдельной проверки.

### Тема 9. DISTINCT и устранение избыточности

`DISTINCT` удаляет повторяющиеся строки из результата по выбранным выражениям.

Например:

```sql
SELECT DISTINCT arrival_airport
FROM flights;
```

Возвращает уникальный список аэропортов прибытия.

Это полезно для:

- справочников;
- фильтров интерфейса;
- построения отчётов;
- промежуточных наборов;
- определения разных значений.

#### DISTINCT и GROUP BY

Для простого списка уникальных значений:

```sql
SELECT DISTINCT arrival_airport
FROM flights;
```

и:

```sql
SELECT arrival_airport
FROM flights
GROUP BY arrival_airport;
```

логически эквивалентны по набору возвращаемых значений.

Но план выполнения может отличаться.

PostgreSQL может применять:

- HashAggregate;
- Sort + Unique;
- индексный доступ;
- другие преобразования.

Нельзя утверждать, что DISTINCT всегда быстрее или медленнее GROUP BY.

#### DISTINCT как симптом проблемы

Если запрос выглядит так:

```sql
SELECT DISTINCT
    c.customer_id,
    c.customer_name
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.customer_id;
```

нужно понять, почему появляются повторы.

Если задача — найти клиентов хотя бы с одним заказом, возможно, лучше выразить её через `EXISTS`.

```sql
SELECT
    c.customer_id,
    c.customer_name
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.customer_id
);
```

Но итоговый выбор определяется смыслом задачи и планом.

### Тема 10. Индексопригодные условия поиска

Для эффективного использования B-tree индекса условие обычно должно позволять определить диапазон ключей.

Например:

```sql
WHERE customer_id = 1001
```

```sql
WHERE created_at >= TIMESTAMP '2026-03-01'
```

```sql
WHERE total_amount BETWEEN 1000 AND 5000
```

Эти условия могут использовать обычные индексные операции.

#### Sargability

Термин sargable используется для условий, которые оптимизатор может эффективно применить при поиске по индексу.

Но это не самостоятельное свойство синтаксиса, одинаково работающее для всех типов индексов.

Например:

```sql
WHERE lower(customer_name) = 'anna'
```

может быть неэффективным для обычного индекса по `customer_name`.

Но индекс по выражению:

```sql
CREATE INDEX idx_customers_name_lower
ON customers (lower(customer_name));
```

может поддерживать такой поиск.

Поэтому утверждение «любая функция над столбцом отключает индекс» неверно.

Правильнее говорить:

> Условие должно соответствовать структуре и поддерживаемым операциям конкретного индекса.

#### Вычисления над столбцом

Например:

```sql
WHERE price * 1.20 > 1200
```

Если `price` неотрицательная числовая величина и используются обычные правила числовой арифметики, математически условие можно выразить как:

```sql
WHERE price > 1000
```

Вторая форма лучше соответствует индексу по `price`.

Но при таких преобразованиях необходимо учитывать:

- тип данных;
- округление;
- переполнение;
- точность чисел;
- NULL;
- свойства используемых функций.

Не всякое алгебраическое преобразование безопасно для SQL-типов без дополнительных условий.

### Тема 11. Преобразование поиска по строке в диапазон

Рассмотрим:

```sql
SELECT *
FROM passengers
WHERE substr(passenger_name, 1, 1) = 'A';
```

Если существует обычный B-tree индекс по `passenger_name`, он не обязательно подходит для такого выражения.

Один из возможных вариантов — использовать поиск по префиксу:

```sql
SELECT *
FROM passengers
WHERE passenger_name LIKE 'A%';
```

Для PostgreSQL при подходящей collation и операторном классе индекс может использоваться для префиксного поиска.

Например:

```sql
CREATE INDEX idx_passengers_name_pattern
ON passengers (passenger_name text_pattern_ops);
```

#### Диапазон A–B

Иногда предлагают переписывать:

```sql
substr(passenger_name, 1, 1) = 'A'
```

как:

```sql
passenger_name >= 'A'
AND passenger_name < 'B'
```

Но такое преобразование не является универсально эквивалентным.

Результат зависит от:

- collation;
- правил сравнения;
- регистра;
- Unicode;
- символов с диакритикой;
- локали;
- особенностей сортировки.

В бинарно упорядоченном ограниченном наборе символов это может быть корректно.

Но для произвольного Unicode-текста и лингвистических collation механически заменять префиксный поиск таким диапазоном нельзя.

В большинстве случаев для поиска по префиксу понятнее:

```sql
WHERE passenger_name LIKE 'A%'
```

с подходящим индексом и правилами сравнения.

#### Подстрочный поиск

Если требуется:

```sql
WHERE passenger_name ILIKE '%anna%'
```

обычный B-tree индекс обычно не обеспечивает эффективный префиксный поиск.

В PostgreSQL можно рассмотреть расширение `pg_trgm`.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

```sql
CREATE INDEX idx_passengers_name_trgm
ON passengers
USING GIN (passenger_name gin_trgm_ops);
```

Такой индекс способен ускорять определённые запросы `LIKE`, `ILIKE` и регулярные выражения.

Но эффективность зависит от возможности выделить триграммы из шаблона.

Короткий шаблон без полезных триграмм может оказаться неэффективным. 

### Тема 12. Оптимизация временных условий

Временные фильтры часто встречаются в запросах к:

- заказам;
- событиям;
- журналам;
- рейсам;
- платежам;
- истории изменений.

#### Функция над столбцом

Например:

```sql
SELECT *
FROM orders
WHERE created_at::date = DATE '2026-03-15';
```

Такой запрос корректен для `timestamp without time zone`.

Но обычный B-tree индекс по `created_at` может оказаться менее полезным для выражения с приведением типа.

#### Полуоткрытый диапазон

```sql
SELECT *
FROM orders
WHERE created_at >= TIMESTAMP '2026-03-15 00:00:00'
  AND created_at < TIMESTAMP '2026-03-16 00:00:00';
```

Для обычного `timestamp without time zone` это задаёт весь календарный день 15 марта.

Преимущества:

- не зависит от точности долей секунды;
- не требует вычислять функцию над столбцом;
- соответствует диапазонному B-tree поиску;
- удобно для месячных и дневных периодов.

#### Почему BETWEEN не всегда удобен

`BETWEEN` включает обе границы:

```sql
created_at BETWEEN start_time AND end_time
```

Эквивалентно:

```sql
created_at >= start_time
AND created_at <= end_time
```

Если написать:

```sql
WHERE created_at BETWEEN
    TIMESTAMP '2026-03-15 00:00:00'
    AND TIMESTAMP '2026-03-15 23:59:59'
```

будут пропущены значения с долями секунды после `23:59:59`.

Поэтому обычно удобнее:

```sql
WHERE created_at >= TIMESTAMP '2026-03-15'
  AND created_at < TIMESTAMP '2026-03-16'
```

При этом `BETWEEN` сам по себе не является неиндексопригодным.

Он также может использовать B-tree индекс.

Преимущество полуоткрытого интервала здесь прежде всего в корректном определении границ.

#### TIMESTAMPTZ и часовые пояса

Для `timestamptz` необходимо учитывать часовой пояс.

Например, календарный день в Москве не обязательно соответствует календарному дню UTC.

Если требуется выбрать события за локальный день определённой временной зоны, границы нужно преобразовать в конкретные моменты времени.

Особенно важно учитывать переходы на летнее и зимнее время в регионах, где они существуют.

Поэтому нельзя всегда заменять локальный день интервалом ровно 24 часа в UTC.

### Тема 13. Перенос временных вычислений на сторону константы

Рассмотрим условие:

```sql
SELECT *
FROM flights
WHERE scheduled_departure + INTERVAL '2 hours'
      >= TIMESTAMP '2026-03-15 12:00:00';
```

Математически его можно переписать:

```sql
SELECT *
FROM flights
WHERE scheduled_departure
      >= TIMESTAMP '2026-03-15 10:00:00';
```

Вторая форма лучше соответствует индексу по `scheduled_departure`.

Но эквивалентность требует учитывать семантику типов и интервалов.

Например, арифметика с календарными месяцами и временными зонами может иметь особенности, не позволяющие произвольно переносить выражения через сравнение.

Поэтому преобразование должно быть проверено для конкретного типа.

#### Индекс

```sql
CREATE INDEX idx_flights_departure
ON flights (scheduled_departure);
```

Для диапазонного условия оптимизатор получает возможность использовать упорядоченность B-tree.

Но наличие индекса не гарантирует его использование.

Если запрос возвращает большую часть рейсов, Seq Scan может оказаться дешевле.

### Тема 14. OR и выбор плана

Условие `OR` объединяет альтернативные критерии.

Например:

```sql
SELECT *
FROM flights
WHERE departure_airport = 'SVO'
   OR arrival_airport = 'SVO';
```

Если существуют индексы по обоим столбцам, PostgreSQL может использовать:

```text
Bitmap Heap Scan
  -> BitmapOr
       -> Bitmap Index Scan
       -> Bitmap Index Scan
```

Это нормальный механизм выполнения.

#### BitmapOr

Оператор объединяет результаты нескольких bitmap-поисков.

Он позволяет найти строки, соответствующие хотя бы одному условию.

Важная особенность: одна физическая строка, подходящая под обе ветки `OR`, должна возвращаться только один раз.

BitmapOr обеспечивает объединение кандидатов, а не конкатенацию двух результирующих наборов строк.

#### Когда OR может быть дорогим

Если каждое условие возвращает значительную часть таблицы, bitmap-поиск может обрабатывать множество страниц.

Кроме того, отдельные условия могут иметь совершенно разные характеристики селективности.

В некоторых случаях полезно исследовать альтернативную форму через `UNION ALL`.

Но это не универсальное правило.

### Тема 15. UNION ALL вместо сложного OR

Рассмотрим исходный запрос:

```sql
SELECT *
FROM flights
WHERE departure_airport = 'SVO'
   OR arrival_airport = 'SVO';
```

Наивная замена:

```sql
SELECT *
FROM flights
WHERE departure_airport = 'SVO'

UNION ALL

SELECT *
FROM flights
WHERE arrival_airport = 'SVO';
```

не всегда эквивалентна.

Если рейс удовлетворяет обоим условиям, он будет возвращён дважды.

Исходный `OR` вернул бы его один раз.

#### Безопасное разделение веток

Можно явно исключить пересечение:

```sql
SELECT *
FROM flights
WHERE departure_airport = 'SVO'

UNION ALL

SELECT *
FROM flights
WHERE arrival_airport = 'SVO'
  AND departure_airport IS DISTINCT FROM 'SVO';
```

В PostgreSQL условие `IS DISTINCT FROM` корректно учитывает NULL.

Теперь ветки не пересекаются по исходным строкам.

При этом сохраняется кратность разных строк исходной таблицы, даже если они имеют одинаковые значения проецируемых столбцов.

#### UNION

Другой вариант:

```sql
SELECT *
FROM flights
WHERE departure_airport = 'SVO'

UNION

SELECT *
FROM flights
WHERE arrival_airport = 'SVO';
```

Но `UNION` удаляет дубли по всем выбранным значениям.

Если две разные строки таблицы имеют одинаковые значения в результатах проекции, они могут объединиться в одну.

Поэтому `UNION` не всегда эквивалентен исходному `OR` с точки зрения кратности строк.

#### Когда UNION ALL полезен

- ветки логически не пересекаются;
- каждая ветка использует подходящий индекс;
- у веток разная селективность;
- оптимизатору сложно выбрать выгодный общий план;
- отдельные ветки проще анализировать.

Но `UNION ALL` может также привести к повторному чтению одной таблицы.

Поэтому результат необходимо проверять экспериментально.

### Тема 16. Коррелированные подзапросы

Коррелированный подзапрос использует значение внешней строки.

Например:

```sql
SELECT
    c.customer_id,
    c.customer_name,
    (
        SELECT COUNT(*)
        FROM orders AS o
        WHERE o.customer_id = c.customer_id
    ) AS orders_count
FROM customers AS c;
```

Подзапрос зависит от:

```sql
c.customer_id
```

#### Возможная физическая стоимость

Если клиентов много, а оптимизатор реализует подзапрос как повторный параметризованный доступ, внутренний запрос может выполняться множество раз.

Это может быть дорого.

Но нельзя утверждать, что каждый коррелированный подзапрос обязательно физически исполняется заново для каждой строки.

Оптимизатор может:

- преобразовать запрос в соединение;
- использовать индекс;
- использовать кеширование;
- применить другие оптимизации.

Поэтому необходимо смотреть фактический план и `loops`.

#### Альтернатива через предварительную агрегацию

```sql
SELECT
    c.customer_id,
    c.customer_name,
    COALESCE(x.orders_count, 0) AS orders_count
FROM customers AS c
LEFT JOIN (
    SELECT
        customer_id,
        COUNT(*) AS orders_count
    FROM orders
    GROUP BY customer_id
) AS x
    ON x.customer_id = c.customer_id;
```

Внутренний запрос считает количество заказов сразу по всем клиентам.

Затем результат соединяется с таблицей клиентов.

Этот подход может оказаться эффективнее, когда внешних строк много.

Но если нужны данные только для одного клиента, повторный индексный поиск может быть дешевле полной агрегации всей таблицы заказов.

### Тема 17. CTE и предварительные вычисления

CTE позволяет вынести часть запроса в именованное выражение.

Например:

```sql
WITH customer_totals AS (
    SELECT
        customer_id,
        SUM(total_amount) AS total_amount
    FROM orders
    WHERE status = 'completed'
    GROUP BY customer_id
)
SELECT
    c.customer_id,
    c.customer_name,
    ct.total_amount
FROM customers AS c
JOIN customer_totals AS ct
    ON ct.customer_id = c.customer_id;
```

Такой запрос разделяется на две логические части:

1. Вычисление сумм по клиентам.
2. Соединение результатов со справочником.

#### CTE не обязательно материализуется

В современных PostgreSQL обычный CTE без побочных эффектов, используемый один раз, часто может быть встроен в основной запрос.

Это называется CTE inlining.

Поэтому CTE не означает автоматически:

> Сначала полностью выполнить подзапрос и сохранить все строки.

#### MATERIALIZED

В PostgreSQL можно явно указать:

```sql
WITH customer_totals AS MATERIALIZED (
    SELECT
        customer_id,
        SUM(total_amount) AS total_amount
    FROM orders
    GROUP BY customer_id
)
SELECT *
FROM customer_totals;
```

`MATERIALIZED` позволяет потребовать отдельного вычисления результата CTE и ограничить определённые преобразования оптимизатора.

Но это не всегда ускоряет запрос.

Материализация может потребовать дополнительных ресурсов и помешать переносу фильтров внутрь выражения.

#### NOT MATERIALIZED

```sql
WITH customer_totals AS NOT MATERIALIZED (
    SELECT
        customer_id,
        SUM(total_amount) AS total_amount
    FROM orders
    GROUP BY customer_id
)
SELECT *
FROM customer_totals;
```

`NOT MATERIALIZED` позволяет предложить объединение CTE с внешним запросом в поддерживаемых случаях.

Но это может приводить к повторному вычислению CTE при нескольких обращениях.

Возможность такого управления ограничена, например, для рекурсивных и содержащих побочные эффекты выражений.

#### Отличия СУБД

SQL Server CTE не является самостоятельной материализованной таблицей.

При нескольких ссылках на одно CTE оптимизатор может выполнять соответствующую логику повторно, хотя физические планы могут применять внутренние промежуточные механизмы.

В MySQL и Oracle используются собственные правила слияния и материализации подзапросов.

Поэтому нельзя переносить утверждение «CTE всегда выполняется один раз» на любую СУБД.

### Тема 18. JOIN вместо повторяющихся скалярных подзапросов

Предположим, нужно получить количество заказов и сумму заказов для каждого клиента.

Вариант со скалярными подзапросами:

```sql
SELECT
    c.customer_id,
    (
        SELECT COUNT(*)
        FROM orders AS o
        WHERE o.customer_id = c.customer_id
    ) AS orders_count,
    (
        SELECT SUM(o.total_amount)
        FROM orders AS o
        WHERE o.customer_id = c.customer_id
    ) AS orders_total
FROM customers AS c;
```

Здесь два коррелированных подзапроса работают с одной таблицей.

Оптимизатор может выполнить их через отдельные параметризованные обращения.

#### Предварительная агрегация

```sql
WITH order_totals AS (
    SELECT
        customer_id,
        COUNT(*) AS orders_count,
        SUM(total_amount) AS orders_total
    FROM orders
    GROUP BY customer_id
)
SELECT
    c.customer_id,
    COALESCE(x.orders_count, 0) AS orders_count,
    x.orders_total
FROM customers AS c
LEFT JOIN order_totals AS x
    ON x.customer_id = c.customer_id;
```

Здесь оба агрегата рассчитываются в одном проходе логической группировки.

Это может уменьшить повторные вычисления.

Однако если внешнее условие выбирает одного клиента:

```sql
WHERE c.customer_id = 1001
```

оптимизатор может выбрать очень дешёвые индексные поиски.

Поэтому предпочтительный вариант зависит от:

- количества внешних строк;
- индексов;
- размера заказов;
- распределения клиентов;
- фактического плана.

### Тема 19. Поиск ближайшего объекта через коррелированный подзапрос

Рассмотрим географическую задачу.

Есть таблицы аэропортов и рейсов.

Необходимо для каждого аэропорта определить ближайший другой аэропорт.

Предположим, в PostgreSQL установлено расширение PostGIS.

```sql
CREATE EXTENSION IF NOT EXISTS postgis;
```

Таблица:

```sql
CREATE TABLE airports (
    airport_code TEXT PRIMARY KEY,
    airport_name TEXT NOT NULL,
    location geography(Point, 4326) NOT NULL
);
```

Пример данных:

```sql
INSERT INTO airports (
    airport_code,
    airport_name,
    location
)
VALUES
(
    'SVO',
    'Sheremetyevo',
    ST_SetSRID(
        ST_MakePoint(37.4146, 55.9726),
        4326
    )::geography
),
(
    'DME',
    'Domodedovo',
    ST_SetSRID(
        ST_MakePoint(37.9063, 55.4088),
        4326
    )::geography
),
(
    'VKO',
    'Vnukovo',
    ST_SetSRID(
        ST_MakePoint(37.2615, 55.5915),
        4326
    )::geography
);
```

#### Коррелированный поиск

```sql
SELECT
    a.airport_code,
    (
        SELECT b.airport_code
        FROM airports AS b
        WHERE b.airport_code <> a.airport_code
        ORDER BY ST_Distance(
            a.location,
            b.location
        )
        LIMIT 1
    ) AS nearest_airport
FROM airports AS a;
```

Запрос корректно выражает логику поиска ближайшего аэропорта по геодезическому расстоянию.

Но если аэропортов тысячи, а внешних строк очень много, повторная сортировка кандидатов может оказаться дорогой.

#### LATERAL

В PostgreSQL можно выразить зависимый поиск через LATERAL.

```sql
SELECT
    a.airport_code,
    nearest.airport_code AS nearest_airport
FROM airports AS a
LEFT JOIN LATERAL (
    SELECT
        b.airport_code
    FROM airports AS b
    WHERE b.airport_code <> a.airport_code
    ORDER BY ST_Distance(
        a.location,
        b.location
    )
    LIMIT 1
) AS nearest ON TRUE;
```

Это делает зависимость подзапроса явной.

Но само использование LATERAL не гарантирует ускорения.

#### GiST и KNN

Создадим пространственный индекс:

```sql
CREATE INDEX idx_airports_location
ON airports
USING GIST (location);
```

Для индексного поиска ближайших объектов PostGIS поддерживает оператор:

```sql
<->
```

Пример:

```sql
SELECT
    a.airport_code,
    nearest.airport_code AS nearest_airport
FROM airports AS a
LEFT JOIN LATERAL (
    SELECT
        b.airport_code
    FROM airports AS b
    WHERE b.airport_code <> a.airport_code
    ORDER BY b.location <-> a.location
    LIMIT 1
) AS nearest ON TRUE;
```

GiST может поддерживать KNN-поиск по расстоянию.

Важно: для geography оператор `<->` использует сферическую метрику, тогда как `ST_Distance` по умолчанию вычисляет расстояние по сфероиду.

Поэтому результаты ранжирования могут не полностью совпадать в редких пограничных случаях.

Если требуется строгое ранжирование по сфероидальному расстоянию, необходимо учитывать это различие.

Для каждой строки также полезно добавлять детерминированное правило разрешения равных расстояний, если результат должен быть воспроизводимым.

Например:

```sql
ORDER BY
    b.location <-> a.location,
    b.airport_code
```

Но дополнительная сортировка и требования к точности также могут влиять на использование индекса и стоимость плана.

### Тема 20. Предварительный расчёт ближайших соответствий

Если одни и те же аэропорты используются многократно в большой таблице рейсов, повторный поиск ближайшего аэропорта для каждой строки рейса может быть избыточным.

Можно сначала вычислить соответствие на уровне справочника аэропортов.

```sql
WITH nearest_airports AS MATERIALIZED (
    SELECT
        a.airport_code,
        nearest.airport_code AS nearest_airport
    FROM airports AS a
    LEFT JOIN LATERAL (
        SELECT
            b.airport_code
        FROM airports AS b
        WHERE b.airport_code <> a.airport_code
        ORDER BY b.location <-> a.location
        LIMIT 1
    ) AS nearest ON TRUE
)
SELECT
    f.flight_id,
    f.arrival_airport,
    n.nearest_airport
FROM flights AS f
LEFT JOIN nearest_airports AS n
    ON n.airport_code = f.arrival_airport;
```

Здесь ближайший аэропорт рассчитывается для каждой строки справочника, а затем используется при соединении с рейсами.

Если рейсов намного больше, чем аэропортов, подход может уменьшить число повторных пространственных поисков.

Но результат зависит от:

- количества аэропортов;
- числа рейсов;
- индексов;
- фактического плана;
- режима материализации;
- используемой метрики расстояния.

#### Постоянная таблица соответствий

Если справочник редко изменяется, можно рассмотреть заранее сохраняемый результат:

```text
airport_nearest_airport
```

Тогда основной запрос будет выполнять обычный JOIN.

Но появится отдельная задача поддержания актуальности при изменении координат или состава аэропортов.

Таким образом, предварительный расчёт переносит стоимость с чтения на обслуживание подготовленных данных.

### Тема 21. Различия четырёх СУБД при оптимизации чтения

Основные принципы похожи, но поддерживаемый синтаксис и способы доступа отличаются.

#### PostgreSQL

Предоставляет:

- B-tree и специализированные индексы;
- индексы по выражению;
- `EXPLAIN (ANALYZE, BUFFERS)`;
- `BitmapOr`;
- `LATERAL`;
- `MATERIALIZED` / `NOT MATERIALIZED` для подходящих CTE;
- PostGIS и KNN GiST.

#### SQL Server

Предоставляет:

- clustered и nonclustered indexes;
- computed columns;
- `Index Seek`;
- `Index Scan`;
- `Key Lookup`;
- `RID Lookup`;
- Query Store;
- actual execution plan;
- `CROSS APPLY` и `OUTER APPLY`.

Например, зависимый Top-N поиск:

```sql
SELECT
    c.customer_id,
    x.order_id
FROM dbo.customers AS c
OUTER APPLY (
    SELECT TOP (1)
        o.order_id
    FROM dbo.orders AS o
    WHERE o.customer_id = c.customer_id
    ORDER BY o.created_at DESC, o.order_id DESC
) AS x;
```

Для такого запроса может быть полезен составной индекс:

```sql
CREATE INDEX idx_orders_customer_date
ON dbo.orders (
    customer_id,
    created_at DESC,
    order_id DESC
);
```

Но необходимость дополнительных включённых столбцов зависит от структуры итоговой выборки.

#### MySQL/InnoDB

Предоставляет:

- B-tree индексы;
- generated columns;
- functional indexes;
- `EXPLAIN ANALYZE`;
- semijoin-оптимизации;
- CTE и derived tables;
- собственные механизмы materialization и derived-table merging.

MySQL поддерживает LATERAL для определённых derived tables в современных версиях, но правила и ограничения отличаются от PostgreSQL.

В MySQL также действуют специфические правила преобразований типов и collation.

#### Oracle

Предоставляет:

- B-tree и другие виды индексов;
- function-based indexes;
- cost-based optimizer;
- `DBMS_XPLAN`;
- различные виды преобразований подзапросов;
- CTE;
- `CROSS APPLY`, `OUTER APPLY` и lateral-подобные возможности;
- специализированные методы аналитической и пространственной обработки.

#### Сравнение

| Возможность | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| Индекс по выражению | Да | Через подходящий computed column | Functional index / generated column | Function-based index |
| BitmapOr | Да | Собственные стратегии объединения индексного доступа | Собственные Index Merge стратегии | Bitmap-операции в соответствующих планах |
| LATERAL / APPLY | LATERAL | CROSS/OUTER APPLY | LATERAL с ограничениями | LATERAL, APPLY |
| CTE | Да | Да | Да | Да |
| Явная MATERIALIZED-подсказка CTE как в PostgreSQL | Да | Нет | Нет идентичного синтаксиса | Иные механизмы оптимизации |
| Фактический план | EXPLAIN ANALYZE | Actual Execution Plan | EXPLAIN ANALYZE | DBMS_XPLAN с runtime-статистикой |

Нельзя считать похожие конструкции полностью эквивалентными по оптимизации.

```sql
INSERT INTO read_optimization.customers (
```

### Тема 23. Практика: фильтрация и агрегация

Исходный запрос:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    customer_id,
    COUNT(*) AS orders_count,
    SUM(total_amount) AS total_amount
FROM read_optimization.orders
WHERE status = 'completed'
GROUP BY customer_id
HAVING COUNT(*) > 10;
```

Необходимо определить:

- сколько строк соответствует WHERE;
- сколько групп сформировано;
- какой алгоритм агрегации выбран;
- сколько групп удалено HAVING;
- сколько буферных страниц обработано.

Теперь ограничим период:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    customer_id,
    COUNT(*) AS orders_count,
    SUM(total_amount) AS total_amount
FROM read_optimization.orders
WHERE status = 'completed'
  AND created_at >= TIMESTAMP '2026-03-01'
  AND created_at < TIMESTAMP '2026-04-01'
GROUP BY customer_id
HAVING COUNT(*) > 1;
```

Это уже другая бизнес-задача, поэтому время нельзя использовать как прямое доказательство оптимизации первого запроса.

Сравнение нужно проводить между логически эквивалентными запросами.

Оба примера полезны для изучения влияния селективности и объёма агрегации.

### Тема 25. Практика: проблема размножения строк

```sql
SELECT
    SUM(o.total_amount) AS total_amount
```

```sql
SELECT SUM(total_amount)
```

```sql
SELECT SUM(o.total_amount)
FROM read_optimization.orders AS o
WHERE EXISTS (
    SELECT 1
    FROM read_optimization.order_items AS i
    WHERE i.order_id = o.order_id
);
```

Здесь каждый заказ учитывается один раз.

Сравните планы и результаты.

### Тема 29. Методика проверки переписанного запроса

Для корректной оптимизации необходимо убедиться не только в сокращении времени, но и в сохранении результата.

#### Шаг 1. Зафиксировать исходный запрос

Сохранить:

- SQL-текст;
- параметры;
- версию СУБД;
- индексы;
- набор данных;
- исходный план.

#### Шаг 2. Сформулировать гипотезу

Например:

> Функция над timestamp мешает диапазонному поиску через B-tree.

Или:

> Коррелированный подзапрос выполняет слишком много повторных индексных обращений.

#### Шаг 3. Переписать запрос

Изменить конкретную часть:

- временное условие;
- структуру JOIN;
- способ агрегации;
- OR;
- коррелированный подзапрос.

#### Шаг 4. Проверить корректность

В PostgreSQL для сравнения результатов можно использовать `EXCEPT ALL`.

Например:

```sql
WITH old_result AS (
    SELECT *
    FROM read_optimization.orders
    WHERE created_at::date = DATE '2026-03-15'
),
new_result AS (
    SELECT *
    FROM read_optimization.orders
    WHERE created_at >= TIMESTAMP '2026-03-15'
      AND created_at < TIMESTAMP '2026-03-16'
)
SELECT *
FROM old_result

EXCEPT ALL

SELECT *
FROM new_result;
```

Для полной проверки эквивалентности необходимо выполнить сравнение в обоих направлениях.

`EXCEPT ALL` учитывает кратность строк.

Это полезнее обычного `EXCEPT`, если требуется убедиться, что переписывание не создало и не удалило дубли.

При этом сравнение нужно выполнять на одном согласованном состоянии данных.

#### Шаг 5. Получить фактический план

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

#### Шаг 6. Сравнить стоимость

Смотреть:

- Execution Time;
- Planning Time;
- Actual Rows;
- Loops;
- Buffers;
- временные файлы;
- объём промежуточных данных.

#### Шаг 7. Повторить измерения

Выполнить варианты несколько раз в разном порядке.

Один запуск недостаточен для надёжного вывода.

#### Шаг 8. Проверить влияние на общую нагрузку

Если новый запрос стал быстрее, но увеличил потребление CPU или памяти, нужно оценить эффект при конкурентной нагрузке.

Цель — не просто уменьшить время одного запуска, а улучшить поведение системы.

## Итоговые выводы

1. **Оптимизация чтения направлена на сокращение ненужной физической работы.** Важно уменьшать количество обработанных строк, чтений страниц, сортировок и повторных вычислений.

2. **SQL-запрос не выполняется буквально в порядке написанных конструкций.** Оптимизатор самостоятельно выбирает физический план и может преобразовывать запрос.

3. **WHERE и HAVING имеют разную семантику.** WHERE фильтрует исходные строки, а HAVING — группы. Перенос условий допустим только при сохранении результата.

4. **COUNT(DISTINCT) необходим для подсчёта уникальных значений.** Но он не должен использоваться как универсальный способ исправления неправильных соединений.

5. **JOIN может размножать строки из-за кардинальности связей.** Для корректных агрегатов необходимо учитывать уровень детализации данных.

6. **Оконные функции позволяют сохранять детализацию и одновременно получать агрегированный контекст.** Однако их стоимость зависит от объёма входных данных и необходимых сортировок.

7. **DISTINCT полезен для устранения содержательно ненужных повторов.** Но он может скрывать ошибку структуры запроса и создавать дополнительную вычислительную работу.

8. **Индексопригодность условия зависит от его соответствия конкретной индексной структуре.** Функция над столбцом не всегда запрещает индексный доступ, но может потребовать индекса по выражению.

9. **Префиксный поиск и диапазонные условия требуют внимания к collation.** Не все строковые диапазоны эквивалентны поиску по шаблону.

10. **Для временных данных обычно удобны полуоткрытые интервалы.** Они позволяют точно задавать границы без зависимости от точности долей секунды.

11. **OR может использовать эффективные bitmap-планы.** Его не следует автоматически переписывать через UNION ALL.

12. **UNION ALL сохраняет повторы.** Для эквивалентности с OR необходимо учитывать пересечение веток и кратность строк.

13. **Коррелированный подзапрос не обязательно выполняется заново для каждой внешней строки.** Физическое поведение зависит от оптимизатора, индексов и плана.

14. **Предварительная агрегация и JOIN могут уменьшить повторную работу.** Но при небольшом внешнем наборе параметризованный индексный поиск иногда эффективнее.

15. **CTE является логическим средством организации SQL, а не гарантией материализации.** В PostgreSQL доступны MATERIALIZED и NOT MATERIALIZED, но их применение должно быть обосновано.

16. **Пространственный поиск ближайших объектов может использовать специализированные индексы.** В PostgreSQL/PostGIS для этого применяются GiST и KNN, с учётом различий геодезических метрик.

17. **Переписывание запроса должно сохранять правильный результат.** Для проверки полезно сравнивать наборы с учётом кратности строк, а не только общее количество записей.

18. **Эффект оптимизации необходимо подтверждать измерениями.** Фактические планы, строки, циклы, буферы и время выполнения важнее общих правил.

Главный результат занятия — умение перерабатывать SQL-запросы на чтение так, чтобы сохранялся их смысл, а СУБД получала возможность выполнять меньший объём физической работы.
