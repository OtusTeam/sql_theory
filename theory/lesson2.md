## Превью / аннотация / краткое содержание

На этом занятии мы продолжим знакомство с реляционными СУБД и посмотрим, что находится «внутри» системы управления базами данных.

Разберём:

- чем отличаются популярные реляционные СУБД и почему нельзя выбрать «лучшую вообще»;
- как соотносятся PostgreSQL, Microsoft SQL Server, MySQL, Oracle и SQLite;
- что понимают под внешним, концептуальным и внутренним уровнями представления данных;

В практической части познакомимся с базовыми операциями работы через SQL-клиент и создадим несколько простых объектов базы данных.

# Основная часть

## Тема 1. Как выбирать СУБД

Реляционные СУБД решают похожие базовые задачи:

- хранят данные;
- выполняют SQL-запросы;
- поддерживают транзакции;
- контролируют конкурентный доступ;
- обеспечивают ограничения целостности;
- разграничивают права;
- ведут журналы, необходимые для восстановления;
- предоставляют инструменты диагностики и администрирования.

Из этого не следует, что все СУБД одинаковы.

Они отличаются:

- SQL-диалектом;
- архитектурой;
- реализацией конкурентного доступа;
- типами данных;
- индексами;
- средствами высокой доступности;
- возможностями репликации;
- расширяемостью;
- инструментами администрирования;
- моделью лицензирования;
- экосистемой.

Поэтому вопрос:

> Какая СУБД лучше?

обычно поставлен неправильно.

Полезнее спрашивать:

> Какая СУБД лучше соответствует требованиям конкретной системы и команды?

При выборе учитывают, например:

- предполагаемую нагрузку;
- объём данных;
- требования к доступности;
- требования к восстановлению после сбоев;
- необходимый функционал;
- существующую инфраструктуру;
- опыт команды;
- стоимость лицензий и эксплуатации;
- требования к поддержке;
- доступность специалистов.

## Тема 2. Oracle Database

Oracle Database — одна из наиболее зрелых промышленных реляционных СУБД.

Она широко используется в системах, где важны:

- высокая доступность;
- масштабирование;
- сложные транзакционные нагрузки;
- развитая модель безопасности;
- централизованное администрирование;
- работа с большими корпоративными системами.

Экосистема Oracle включает большое количество технологий и вариантов развёртывания.

Некоторые возможности относятся к определённым редакциям, лицензируемым опциям или специализированной инфраструктуре. Поэтому нельзя воспринимать весь функционал Oracle как автоматически доступный в любой установке.

### Лицензирование

У Oracle существуют коммерческие редакции и сервисы, однако есть и бесплатная редакция для разработки и обучения.

В рамках курса используется **Oracle AI Database Free**.

Это полноценная база данных с ограничениями по доступным вычислительным ресурсам и объёму пользовательских данных.

Поэтому утверждение:

> Oracle можно использовать только крупным компаниям из-за высокой стоимости

некорректно.

Корпоративные конфигурации Oracle действительно могут иметь значительную стоимость лицензирования и эксплуатации, но для обучения, разработки и небольших сценариев существуют бесплатные варианты.

---

## Тема 3. Microsoft SQL Server

Microsoft SQL Server — промышленная реляционная СУБД с развитой экосистемой средств разработки, администрирования, безопасности и диагностики.

Исторически SQL Server тесно связан с Windows и экосистемой Microsoft.

Однако современный SQL Server нельзя считать исключительно Windows-продуктом.

SQL Server поддерживает работу:

- на Windows;
- на поддерживаемых Linux-дистрибутивах;
- в контейнерах;
- в облачных инфраструктурах.

Поэтому выбор SQL Server не требует обязательного построения всей системы исключительно на технологиях Microsoft.

Сильными сторонами платформы являются, например:

- развитый Database Engine;
- мощный оптимизатор запросов;
- развитые средства диагностики;
- средства высокой доступности;
- интеграция с Microsoft-инфраструктурой;
- развитые инструменты администрирования.

При этом набор функций зависит от:

- версии;
- редакции;
- операционной системы;
- способа развёртывания.

Нельзя считать все сервисы экосистемы Microsoft SQL Server частью собственно Database Engine.

Например, аналитические, интеграционные и отчётные сервисы являются отдельными компонентами экосистемы и могут иметь собственные ограничения по платформам и редакциям.

---

## Тема 4. PostgreSQL

PostgreSQL — свободная объектно-реляционная СУБД с открытым исходным кодом.

Она используется как в небольших приложениях, так и в крупных высоконагруженных системах.

К особенностям PostgreSQL относятся:

- расширяемость;
- развитая поддержка SQL;
- пользовательские типы данных;
- функции и процедурные языки;
- JSON и JSONB;
- полнотекстовый поиск;
- различные типы индексов;
- развитая модель конкурентного доступа;
- возможность подключения расширений.

Одним из известных расширений является **PostGIS**, которое добавляет развитые средства работы с географическими и геометрическими данными.

PostgreSQL не следует характеризовать только как «более дешёвую альтернативу коммерческим СУБД».

Это самостоятельная платформа со своей архитектурой, сильными сторонами и экосистемой.

Также некорректно утверждать, что PostgreSQL подходит только для систем «среднего размера».

Размер системы сам по себе не является достаточным критерием выбора СУБД.

Гораздо важнее:

- характер нагрузки;
- архитектура приложения;
- модель масштабирования;
- требования к доступности;
- качество запросов и модели данных;
- эксплуатационная компетенция команды.

---

## Тема 5. MySQL и InnoDB

MySQL — широко используемая клиент-серверная реляционная СУБД.

Она применяется:

- в веб-приложениях;
- backend-сервисах;
- SaaS-системах;
- интернет-магазинах;
- корпоративных приложениях;
- облачных сервисах.

Одной из особенностей MySQL является архитектура со **storage engines** — движками хранения.

Разные движки могут предоставлять различные механизмы хранения и обработки таблиц.

Однако в современных версиях MySQL основным и используемым по умолчанию движком является **InnoDB**.

Именно InnoDB используется на курсе.

Он предоставляет:

- транзакции;
- `COMMIT` и `ROLLBACK`;
- внешние ключи;
- блокировки строк;
- многоверсионный конкурентный доступ;
- crash recovery;
- кластеризованное хранение по первичному ключу.

Поэтому при изучении MySQL в рамках курса мы фактически рассматриваем связку:

> MySQL + InnoDB.

Некорректно считать MySQL системой, подходящей только для небольших сайтов или прототипов.

Как и у других СУБД, практические пределы определяются конкретной архитектурой, моделью данных, запросами, инфраструктурой и требованиями системы.

## Тема 6. SQLite

SQLite заметно отличается от остальных рассматриваемых систем.

PostgreSQL, SQL Server, MySQL и Oracle обычно работают как отдельный сервер СУБД.

SQLite — **встраиваемая serverless-СУБД**.

Она работает как библиотека внутри приложения.

Типичная архитектура выглядит так:

```text
Приложение
    │
    ▼
Библиотека SQLite
    │
    ▼
Файл базы данных
```

Для работы не требуется запускать отдельный сервер SQLite.

База обычно хранится в одном файле.

При этом SQLite — не просто «формат файла».

Она поддерживает:

- SQL;
- транзакции;
- ACID-семантику;
- индексы;
- представления;
- триггеры;
- ограничения.

SQLite хорошо подходит для:

- мобильных приложений;
- desktop-приложений;
- локального хранения;
- встроенных устройств;
- тестов;
- небольших автономных приложений.

Но её модель конкурентного доступа и эксплуатации отличается от клиент-серверных СУБД.

Поэтому SQLite не является прямой заменой PostgreSQL, SQL Server, MySQL или Oracle в любой многопользовательской серверной системе.

В основной практике курса SQLite не используется, но она хорошо показывает, что архитектура реляционной СУБД не обязана быть клиент-серверной.

## Тема 7. Три уровня представления данных

В теории архитектуры баз данных часто используют трёхуровневую модель:

1. внешний уровень;
2. концептуальный уровень;
3. внутренний уровень.

Эта идея восходит к архитектуре ANSI/SPARC.

Важно понимать:

> это концептуальная модель разделения представлений данных, а не буквальное описание трёх программных модулей внутри каждой современной СУБД.

---

### Внешний уровень

Внешний уровень описывает то, **какую часть данных видит конкретный пользователь или приложение**.

Разным потребителям можно предоставить разные представления одной базы.

Например, оператор доставки может видеть:

```text
номер заказа
адрес
курьер
статус
```

а финансовая система:

```text
номер заказа
стоимость
оплата
возврат
```

При этом физически данные могут находиться в одних и тех же таблицах.

В SQL внешний уровень может частично реализовываться через:

- `VIEW`;
- права доступа;
- API;
- специализированные запросы;
- слой приложения.

SQL-клиент или IDE **не являются самим внешним уровнем архитектуры**.

DBeaver, DataGrip или SSMS — это лишь инструменты, через которые человек взаимодействует с СУБД.

---

### Концептуальный уровень

Концептуальный, или логический, уровень описывает общую структуру данных независимо от деталей их физического размещения.

Здесь нас интересуют:

- таблицы;
- столбцы;
- сущности;
- связи;
- ключи;
- ограничения;
- типы данных;
- правила предметной области.

Например:

```text
Customer
    │
    │ 1:N
    ▼
Order
    │
    │ 1:N
    ▼
OrderItem
```

На этом уровне важно, **какие данные существуют и как они связаны**, а не то, в каком файле или блоке они находятся на диске.

---

### Внутренний уровень

Внутренний, или физический, уровень связан с тем, **как СУБД реально организует хранение и доступ к данным**.

Здесь появляются такие понятия, как:

- файлы данных;
- страницы или блоки;
- индексы;
- буферный кэш;
- журналы;
- сегменты;
- tablespaces;
- filegroups;
- структуры хранения конкретного движка.

Конкретная реализация сильно зависит от СУБД.

Пользователь обычно работает с SQL и логическими объектами, не указывая СУБД:

> прочитай байты с такого-то смещения файла.

Физическими деталями управляет сама СУБД.

Это одна из важных идей абстракции данных.

## Тема 8. SQL-клиент — не часть базы данных

Для работы с серверной СУБД необходим клиент.

Это может быть:

- DBeaver;
- DataGrip;
- pgAdmin;
- SQL Server Management Studio;
- Oracle SQL Developer;
- MySQL Workbench;
- консольный клиент;
- собственное приложение.

Клиент:

1. устанавливает соединение;
2. отправляет SQL;
3. получает ответ;
4. показывает результат пользователю.

Например:

```text
DBeaver
   │
   │ SQL
   ▼
PostgreSQL
   │
   │ результат
   ▼
DBeaver
```

Если закрыть DBeaver, сервер PostgreSQL продолжит работать.

Если заменить DBeaver другим клиентом, данные тоже никуда не исчезнут.

Это важно для понимания разделения:

> SQL-клиент ≠ СУБД ≠ база данных.

---

## Тема 9. Логическая модель и ограничения

На логическом уровне мы описываем структуру предметной области.

Например, для системы доставки существуют сущности:

```text
Customer
Store
Product
Order
Payment
Courier
Delivery
```

Между ними существуют связи.

Например:

```text
Customer 1 ───── N Order
Store    1 ───── N Order
Order    1 ───── N OrderItem
```

Кроме структуры, необходимо определить правила допустимых данных.

Например:

```text
цена >= 0
```

или:

```text
зарезервированное количество <= фактического остатка
```

Часть таких правил можно выразить ограничениями самой базы данных.

Например:

```sql
CHECK (price >= 0)
```

или:

```sql
FOREIGN KEY (customer_id)
    REFERENCES customers(customer_id)
```

Более сложные бизнес-правила могут контролироваться:

- SQL-кодом;
- функциями;
- процедурами;
- триггерами;
- приложением.

Как именно распределять проверки между БД и приложением — отдельная архитектурная задача.

## Тема 10. Как СУБД хранит данные

Логическая таблица, которую мы видим в SQL:

```text
orders
```

не является на диске обычной текстовой таблицей.

СУБД использует внутренние структуры хранения.

Во многих системах данные организованы в **страницы или блоки**.

Упрощённо:

```text
Таблица
  │
  ├── страница
  ├── страница
  ├── страница
  └── ...
```

Терминология и размеры таких структур зависят от СУБД.

Кроме основных данных СУБД может хранить:

- индексы;
- метаданные;
- журналы изменений;
- временные данные;
- служебную информацию.

Пользователь обычно не управляет отдельными страницами вручную.

Он выполняет:

```sql
SELECT ...
```

а СУБД самостоятельно определяет, какие внутренние структуры необходимо прочитать.

---

### Буферный кэш

Работа с оперативной памятью значительно быстрее постоянного чтения данных с накопителя.

Поэтому СУБД стараются держать часто используемые страницы данных в памяти.

Упрощённо:

```text
SQL-запрос
    │
    ▼
буферный кэш
    │
    ├── данные уже есть → используем
    │
    └── данных нет
            │
            ▼
           диск
```

Повторное выполнение одного и того же запроса поэтому может иметь другое время выполнения: часть нужных данных уже находится в памяти.

Это одна из причин, почему производительность нельзя оценивать только по одному измерению времени.

---

### Tablespace и аналогичные понятия

Термин `TABLESPACE` встречается сразу в нескольких СУБД, но его точное значение и возможности различаются.

Например:

- PostgreSQL использует tablespace для выбора расположения объектов в файловой системе;
- Oracle активно использует tablespaces как часть логической организации хранения;
- MySQL/InnoDB имеет собственную систему tablespaces;
- SQL Server использует другие основные понятия, в частности data files и filegroups.

Поэтому нельзя описывать tablespace как универсальную одинаковую сущность всех реляционных СУБД.

## Тема 11. Основные компоненты СУБД

У разных СУБД внутренняя архитектура различается.

Тем не менее на концептуальном уровне можно выделить несколько функциональных частей.

Упрощённо обработка выглядит так:

```text
SQL
 │
 ▼
Parser / Analyzer
 │
 ▼
Optimizer
 │
 ▼
Executor
 │
 ├─────────────► системный каталог
 │
 ├─────────────► буферный кэш
 │
 ├─────────────► механизм транзакций
 │
 └─────────────► система хранения
```

Это не означает, что в каждой СУБД существуют процессы или классы именно с такими названиями.

Это функциональная схема.

---

### Parser

Parser разбирает текст SQL и проверяет его синтаксическую структуру.

Например:

```sql
SELEC * FORM orders;
```

не является корректным SQL-запросом.

СУБД обнаружит синтаксическую ошибку ещё до выполнения запроса.

---

### Анализ запроса

После синтаксического разбора необходимо определить:

- существуют ли таблицы;
- существуют ли столбцы;
- подходят ли типы данных;
- какие объекты имеются в виду;
- есть ли у пользователя необходимые права.

Например:

```sql
SELECT nonexistent_column
FROM orders;
```

может быть синтаксически правильным, но выполнить его невозможно, если такого столбца нет.

---

### Оптимизатор

Один и тот же SQL-запрос часто можно выполнить несколькими способами.

Например:

```sql
SELECT *
FROM orders
WHERE customer_id = 100;
```

СУБД может:

- просмотреть таблицу;
- использовать индекс;
- выбрать другой доступный путь.

Для сложного `JOIN` вариантов становится намного больше.

**Query optimizer** оценивает возможные планы и выбирает подходящий.

Для этого он использует информацию, в том числе о:

- статистике;
- индексах;
- условиях запроса;
- количестве строк;
- способах соединения.

Оптимизатор не «угадывает идеальное решение».

Он принимает решение на основе доступных оценок, поэтому ошибочная или устаревшая статистика может привести к неудачному плану.

Эту тему подробно разберём в модуле производительности.

---

### Executor

После выбора плана его необходимо выполнить.

Executor выполняет операции плана:

- читает данные;
- применяет фильтры;
- выполняет соединения;
- сортирует;
- группирует;
- рассчитывает выражения;
- формирует результат.

---

### Системный каталог

СУБД должна где-то хранить сведения о собственной структуре.

Например:

- какие существуют таблицы;
- какие у них столбцы;
- какие созданы индексы;
- какие существуют ограничения;
- какие есть пользователи и права;
- какие существуют функции.

Эти сведения называют **метаданными**.

Они хранятся в системном каталоге или data dictionary.

Терминология зависит от платформы.

Например, PostgreSQL предоставляет системные каталоги в `pg_catalog`.

Системный каталог — это не пользовательская документация базы, а данные, которые сама СУБД использует для работы со своими объектами.

---

### Менеджер транзакций и конкурентный доступ

СУБД должна поддерживать ситуацию, когда множество клиентов одновременно читают и изменяют данные.

Для этого используются механизмы:

- транзакций;
- блокировок;
- многоверсионности;
- уровней изоляции;
- обнаружения или обработки конфликтов.

Конкретная реализация отличается между PostgreSQL, SQL Server, MySQL/InnoDB и Oracle.

Этой теме будет посвящено отдельное занятие.

---

### Буферный менеджер

Буферный менеджер управляет страницами данных, находящимися в оперативной памяти.

Он решает, например:

- какие страницы необходимо прочитать с диска;
- какие уже находятся в памяти;
- какие изменённые страницы необходимо сохранить;
- какие страницы можно вытеснить из кэша.

Конкретная архитектура кэширования зависит от СУБД.

---

### Журналирование

Современная СУБД не может просто изменить байты основного файла и надеяться, что питание никогда не пропадёт.

Для обеспечения восстановления используются журнальные механизмы.

В разных системах можно встретить термины:

- WAL;
- transaction log;
- redo log;
- redo records.

Названия и архитектура различаются, но общая идея похожа:

> информация об изменении фиксируется таким образом, чтобы после сбоя СУБД могла восстановить согласованное состояние.

Например:

- PostgreSQL использует WAL;
- SQL Server использует transaction log;
- MySQL/InnoDB использует redo log и другие журнальные структуры;
- Oracle использует redo log.

Подробная реализация у каждой системы своя.

---

## Тема 12. Транзакции, COMMIT, ROLLBACK и autocommit

**Транзакция** позволяет рассматривать несколько операций как логически связанную единицу работы.

Представим перевод денег:

```text
1. уменьшить баланс счёта A
2. увеличить баланс счёта B
```

Нельзя допустить ситуацию:

```text
шаг 1 выполнен
↓
сбой
↓
шаг 2 не выполнен
```

Иначе деньги исчезнут.

Обе операции должны рассматриваться как одна логическая работа.

---

### COMMIT

`COMMIT` подтверждает изменения текущей транзакции.

После успешной фиксации они становятся частью сохранённого состояния базы в соответствии с транзакционной моделью СУБД.

Пример:

```sql
UPDATE accounts
SET balance = balance - 100
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE account_id = 2;

COMMIT;
```

---

### ROLLBACK

`ROLLBACK` отменяет незафиксированные изменения текущей транзакции.

```sql
UPDATE accounts
SET balance = balance - 100
WHERE account_id = 1;

ROLLBACK;
```

После отката изменение не должно остаться как результат этой транзакции.

---

### Autocommit

Во многих клиентах и СУБД используется режим **autocommit**.

Общая идея:

> если пользователь явно не открыл транзакцию, отдельная команда может автоматически выполняться и фиксироваться как самостоятельная транзакция.

Однако конкретное поведение зависит:

- от СУБД;
- от драйвера;
- от SQL-клиента;
- от настроек соединения.

Поэтому перед изменением важных данных необходимо понимать режим транзакций текущего подключения.

---

### DDL и транзакции

Особенно осторожно необходимо относиться к DDL:

```sql
CREATE
ALTER
DROP
```

Нельзя считать универсальным правило:

> любой DDL всегда можно отменить с помощью `ROLLBACK`.

Поведение существенно различается между СУБД.

Некоторые платформы позволяют откатывать многие DDL-операции внутри транзакции, а другие выполняют неявную фиксацию для определённых DDL-команд.

Подробно транзакции и платформенные различия будут изучаться на отдельном занятии.

---

## Тема 13. DDL и создание объектов базы

SQL-команды часто условно делят на несколько групп.

**DDL — Data Definition Language** — команды определения структуры данных.

К ним обычно относят:

- `CREATE`;
- `ALTER`;
- `DROP`.

Например:

```sql
CREATE TABLE customers (
    customer_id INTEGER NOT NULL,
    full_name VARCHAR(200) NOT NULL,
    email VARCHAR(320),

    CONSTRAINT pk_customers
        PRIMARY KEY (customer_id),

    CONSTRAINT uq_customers_email
        UNIQUE (email)
);
```

Эта команда создаёт таблицу.

---

### CREATE

`CREATE` создаёт новый объект.

Например:

```sql
CREATE TABLE products (
    product_id INTEGER NOT NULL,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(12, 2),

    CONSTRAINT pk_products
        PRIMARY KEY (product_id),

    CONSTRAINT chk_products_price
        CHECK (price >= 0)
);
```

---

### ALTER

`ALTER` изменяет уже существующий объект.

Например, с его помощью можно:

- добавить столбец;
- удалить столбец;
- добавить ограничение;
- изменить некоторые свойства объекта.

Конкретный синтаксис изменения таблиц заметно различается между СУБД, поэтому дальше на курсе мы будем учитывать выбранную платформу.

---

### DROP

`DROP` удаляет объект.

Например:

```sql
DROP TABLE products;
```

Эта команда удаляет саму таблицу.

Использовать `DROP` необходимо осторожно.

Перед выполнением важно понимать:

- какой объект удаляется;
- какие другие объекты от него зависят;
- можно ли восстановить данные;
- допускает ли текущая СУБД откат этой операции.

---

### DDL и DML — разные задачи

DDL описывает структуру.

Например:

```sql
CREATE TABLE customers (...);
```

А добавление строк относится уже к операциям изменения данных:

```sql
INSERT INTO customers (
    customer_id,
    full_name,
    email
)
VALUES (
    1,
    'Анна Иванова',
    'anna@example.com'
);
```

После вставки можно получить данные:

```sql
SELECT *
FROM customers;
```

---

## Тема 14. Работа через DBeaver

Для работы с СУБД можно использовать разные клиенты.

Один из универсальных вариантов — **DBeaver**.

Он поддерживает подключения к разным СУБД и позволяет:

- выполнять SQL;
- просматривать таблицы;
- смотреть метаданные;
- редактировать данные;
- импортировать и экспортировать данные;
- просматривать планы выполнения для поддерживаемых платформ;
- работать с несколькими подключениями.

---

### Подключение к СУБД

Для соединения обычно необходимы:

- тип СУБД;
- адрес сервера;
- порт;
- имя базы данных или сервиса;
- пользователь;
- пароль.

Например, концептуально:

```text
Host: localhost
Port: ...
Database / Service: ...
User: ...
Password: ...
```

Конкретные параметры зависят от выбранной платформы.

DBeaver использует соответствующий драйвер для подключения к серверу.

---

### SQL Editor

После подключения можно открыть SQL Editor и выполнить запрос.

Например:

```sql
SELECT 1;
```

Это простейшая проверка того, что соединение работает и сервер может выполнять SQL.

---

### Создание таблицы

Далее можно выполнить:

```sql
CREATE TABLE customers (
    customer_id INTEGER NOT NULL,
    full_name VARCHAR(200) NOT NULL,

    CONSTRAINT pk_customers
        PRIMARY KEY (customer_id)
);
```

После выполнения таблица появится среди объектов базы.

Иногда клиенту требуется обновить дерево объектов, чтобы увидеть изменения.

---

### Добавление данных

```sql
INSERT INTO customers (
    customer_id,
    full_name
)
VALUES (
    1,
    'Анна Иванова'
);
```

И затем:

```sql
SELECT *
FROM customers;
```

---

### GUI не заменяет SQL

DBeaver позволяет создавать многие объекты через графический интерфейс.

Например, таблицу можно создать через меню.

Однако на курсе важно уметь выполнять те же операции через SQL.

Причины:

- SQL воспроизводим;
- SQL можно сохранить в файл;
- SQL можно выполнить повторно;
- SQL удобно хранить в Git;
- SQL можно проверить и отревьюить;
- SQL не зависит от расположения кнопки в конкретной версии GUI.

Поэтому графический интерфейс полезен для навигации и изучения объектов, но основным способом описания изменений базы на курсе остаётся SQL.

---

# Как проходит SQL-запрос

Соберём изученные компоненты вместе.

Пользователь выполняет:

```sql
SELECT o.order_id,
       o.total_amount
FROM orders AS o
WHERE o.customer_id = 100;
```

Упрощённо дальнейший путь выглядит так:

```text
SQL-клиент
    │
    ▼
сервер СУБД
    │
    ▼
разбор и анализ запроса
    │
    ▼
системный каталог
    │
    ▼
оптимизатор
    │
    ▼
план выполнения
    │
    ▼
executor
    │
    ▼
buffer cache / storage
    │
    ▼
результат
    │
    ▼
SQL-клиент
```

Это сильно упрощённая модель.

У конкретной СУБД реальная архитектура значительно сложнее.

Но уже сейчас важно понимать несколько вещей:

1. SQL-клиент не выполняет запрос сам — он отправляет его СУБД.
2. Таблица в SQL и физическое хранение данных — разные уровни абстракции.
3. СУБД сама выбирает физический способ выполнения декларативного запроса.
4. Для выбора плана ей нужны метаданные и статистика.
5. Часть данных может находиться в памяти, поэтому физическое чтение с диска требуется не всегда.
6. Транзакционные механизмы обеспечивают корректность конкурентных изменений и восстановление после сбоев.

---

# Сравнение рассматриваемых СУБД

Ни одну из платформ не следует считать «лучшей вообще».

| СУБД | Архитектурный акцент |
|---|---|
| PostgreSQL | Open source, расширяемость, развитый SQL, богатая экосистема расширений |
| Microsoft SQL Server | Развитый Database Engine, инструменты диагностики и экосистема Microsoft |
| MySQL/InnoDB | Популярная клиент-серверная СУБД, InnoDB как основной транзакционный движок |
| Oracle Database | Зрелая промышленная платформа с развитой корпоративной экосистемой |
| SQLite | Встраиваемая serverless-СУБД без отдельного серверного процесса |

При выборе необходимо сравнивать не рекламные характеристики, а требования конкретной системы.

---

# Что важно запомнить

- СУБД — это значительно больше, чем программа, которая «хранит таблицы».
- SQL-клиент и СУБД — разные компоненты системы.
- Внешний, концептуальный и внутренний уровни — это уровни абстракции данных, а не «GUI, SQL и файлы».
- Реальное физическое хранение скрыто за логической моделью SQL.
- Современная СУБД включает механизмы обработки запросов, оптимизации, транзакций, кэширования, журналирования, безопасности и хранения метаданных.
- Оптимизатор выбирает способ выполнения запроса, а пользователь обычно описывает желаемый результат декларативно.
- Системный каталог содержит метаданные о самой базе данных и её объектах.
- Журналирование необходимо для надёжности и восстановления.
- `COMMIT` фиксирует транзакцию, а `ROLLBACK` отменяет её незафиксированные изменения.
- Autocommit зависит от СУБД, клиента, драйвера и настроек подключения.
- Транзакционное поведение DDL различается между платформами.
- PostgreSQL, SQL Server, MySQL и Oracle нельзя объективно расположить в универсальном рейтинге от «лучшей» к «худшей».
- DBeaver — лишь один из SQL-клиентов; основные навыки работы должны переноситься между инструментами.
