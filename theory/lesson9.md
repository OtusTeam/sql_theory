
# Работа с JSON в SQL и особенности обработки JSONB в реляционных СУБД

## Превью / аннотация / краткое содержание

Занятие посвящено работе с JSON в реляционных системах управления базами данных: хранению, извлечению, преобразованию, изменению и индексированию полуструктурированных данных.

JSON широко применяется для обмена информацией между приложениями, передачи событий, хранения параметров, интеграционных сообщений и данных с изменяющейся структурой. Современные реляционные СУБД позволяют не только хранить JSON-документы, но и обращаться к их отдельным элементам средствами SQL.

Однако использование JSON не отменяет принципов реляционного проектирования. Выбор между обычными столбцами, связанными таблицами и JSON-документами влияет на целостность данных, удобство запросов, стоимость обновлений и производительность.

На занятии рассматриваются:

- структура JSON и поддерживаемые типы значений;
- различия между текстовым и бинарным представлением JSON;
- извлечение вложенных объектов, массивов и отдельных значений;
- SQL/JSON Path и особенности реализации путей в различных СУБД;
- проверка структуры и типов JSON-данных;
- изменение JSON-документов;
- преобразование JSON-массивов в табличное представление;
- агрегирование данных, извлечённых из JSON;
- индексирование JSON и анализ планов выполнения;
- выбор между JSON-хранением и реляционной моделью.

Основные примеры приведены для PostgreSQL. Дополнительно рассматриваются соответствующие возможности Microsoft SQL Server, MySQL/InnoDB и Oracle.

## Основные понятия

**JSON (JavaScript Object Notation)** — текстовый формат представления структурированных данных, определённый стандартом RFC 8259.

**JSON-документ** — значение JSON, которое может быть объектом, массивом, строкой, числом, логическим значением или `null`.

**JSON-объект** — набор пар «ключ — значение», заключённый в фигурные скобки.

**JSON-массив** — упорядоченная последовательность значений, заключённая в квадратные скобки.

**Вложенный объект** — JSON-объект, расположенный внутри другого объекта или массива.

**JSON null** — специальное значение формата JSON, которое необходимо отличать от SQL `NULL`.

**JSONB** — бинарное представление JSON в PostgreSQL, предназначенное для эффективной обработки документов и поддержки дополнительных операторов и индексов.

**SQL/JSON Path** — язык выражений для обращения к элементам JSON-документа.

**Извлечение по пути** — получение значения из JSON по последовательности ключей и индексов массива.

**Табличная функция** — функция, результат которой представлен набором строк и столбцов.

**JSON_TABLE** — механизм преобразования JSON-документа в реляционное представление.

**Агрегация JSON** — формирование JSON-массивов и объектов из результатов SQL-запросов либо агрегирование значений, извлечённых из JSON.

**GIN (Generalized Inverted Index)** — тип инвертированного индекса PostgreSQL, применяемый, в частности, для поиска по элементам `jsonb`.

**Функциональный индекс** — индекс, построенный по результату выражения, например извлечения значения из JSON.

**Вычисляемый или виртуальный столбец** — столбец, значение которого определяется выражением и который в некоторых СУБД может использоваться для индексирования JSON-полей.

**План выполнения запроса** — выбранная оптимизатором последовательность операций обработки SQL-запроса.

**Нормализация данных** — организация данных в реляционные таблицы для уменьшения избыточности и обеспечения целостности.

## Основная часть

### Тема 1. JSON как формат структурированных данных в интеграционных сценариях

JSON является одним из основных форматов обмена данными между современными приложениями.

Он широко используется в:

- REST API;
- интеграциях между сервисами;
- системах обработки событий;
- очередях сообщений;
- ETL/ELT-процессах;
- журналах и результатах аудита;
- конфигурационных данных;
- импорте и экспорте информации.

Пример JSON-документа с информацией о заказе:

```json
{
  "order_id": 1001,
  "customer": {
    "id": 15,
    "name": "Анна"
  },
  "status": "created",
  "delivery": {
    "city": "Москва",
    "address": "ул. Лесная, 10"
  },
  "items": [
    {
      "product_id": 101,
      "quantity": 2,
      "price": 450.50
    },
    {
      "product_id": 205,
      "quantity": 1,
      "price": 1200
    }
  ]
}
```

В одном документе находятся:

- скалярные значения;
- вложенные объекты;
- массив объектов;
- идентификаторы и числовые показатели.

Такую структуру удобно передавать между системами одним сообщением.

В реляционной базе аналогичные данные можно разместить в нескольких связанных таблицах:

- `orders`;
- `customers`;
- `order_items`;
- `products`;
- `delivery_addresses`.

Эти способы представления данных решают разные задачи.

Реляционная модель удобна для обеспечения ссылочной целостности, поиска, соединения таблиц, обновления отдельных сущностей и аналитических запросов.

JSON удобен для приёма документов извне, передачи вложенных структур и хранения атрибутов, набор которых может изменяться.

При этом JSON и реляционная модель не исключают друг друга.

Например, основные поля заказа можно хранить в обычных столбцах, а дополнительные параметры доставки — в JSON.

```sql
-- PostgreSQL

CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    delivery_details JSONB
);
```

Такой подход называется гибридным хранением: стабильные данные представлены реляционно, а переменные атрибуты — внутри JSON-документа.

Важно понимать, что JSON сам по себе не обеспечивает внешние ключи между вложенными объектами, уникальность вложенных идентификаторов и другие ограничения реляционной модели.

Если эти свойства необходимы, их нужно реализовать отдельно либо вынести соответствующие данные в обычные таблицы.

### Тема 2. Структура JSON и типы значений

JSON поддерживает шесть категорий значений:

| Тип | Пример |
|---|---|
| Object | `{"name": "Anna"}` |
| Array | `[10, 20, 30]` |
| String | `"Москва"` |
| Number | `125.50` |
| Boolean | `true`, `false` |
| Null | `null` |

Корневым значением JSON может быть не только объект или массив, но и отдельное скалярное значение.

Например, все следующие записи являются допустимыми JSON-значениями:

```json
{"id": 10}
```

```json
[1, 2, 3]
```

```json
"hello"
```

```json
125
```

```json
null
```

При этом поддержка и ограничения для отдельных видов корневых значений могут различаться между типами данных и функциями конкретных СУБД.

#### Объекты и массивы

JSON-объект содержит пары «ключ — значение»:

```json
{
  "name": "Анна",
  "age": 30,
  "active": true
}
```

Ключи объекта представляют собой строки.

JSON-массив содержит упорядоченную последовательность элементов:

```json
[
  {"id": 1, "name": "SQL"},
  {"id": 2, "name": "Python"}
]
```

В массиве допускаются элементы разных типов:

```json
[10, "text", true, null, {"x": 1}]
```

Однако на практике смешение типов усложняет обработку.

#### Типизация и изменяющаяся структура

В одном документе поле может содержать число:

```json
{"price": 1500}
```

В другом — строку:

```json
{"price": "1500"}
```

В третьем — значение `null`:

```json
{"price": null}
```

А в четвёртом поле может вообще отсутствовать:

```json
{}
```

Для SQL это разные ситуации.

Число и строка могут потребовать различных преобразований. Отсутствующее поле и JSON `null` могут по-разному обрабатываться функциями СУБД.

Поэтому при проектировании JSON-структур рекомендуется определять ожидаемые типы, обязательность полей и допустимые значения.

#### JSON null и SQL NULL

Следует различать:

1. SQL `NULL` — отсутствие определённого SQL-значения.
2. JSON `null` — допустимое значение внутри JSON-документа.
3. Отсутствующий ключ JSON-объекта.

В PostgreSQL:

```sql
SELECT
    jsonb_typeof('null'::jsonb) AS json_null_type,
    jsonb_typeof(NULL::jsonb) AS sql_null_type;
```

Результат:

| json_null_type | sql_null_type |
|---|---|
| null (текст) | NULL |

В первом случае функция возвращает текстовое название типа JSON — `'null'`.

Во втором — SQL `NULL`.

При извлечении значений текстовыми операторами различие может исчезать:

```sql
SELECT
    '{"a": null}'::jsonb ->> 'a' AS a,
    '{}'::jsonb ->> 'a' AS missing_a;
```

Оба выражения возвращают SQL `NULL`.

Если важно определить, присутствует ли ключ, необходимо дополнительно проверить его наличие:

```sql
SELECT
    '{"a": null}'::jsonb ? 'a' AS has_a,
    '{}'::jsonb ? 'a' AS missing_a;
```

Первое выражение возвращает `true`, второе — `false`.

#### Дублирующиеся ключи

В JSON-тексте могут встретиться повторяющиеся ключи:

```json
{
  "status": "new",
  "status": "paid"
}
```

Такую структуру не следует использовать.

Стандарт JSON требует уникальности ключей для предсказуемой совместимости: разные реализации могут обрабатывать повторения по-разному.

Например, PostgreSQL `jsonb` сохраняет последнее значение повторяющегося ключа, тогда как тип `json` сохраняет исходный текст документа.

Поэтому проверка корректности JSON-синтаксиса не всегда означает, что структура соответствует ожиданиям приложения.

### Тема 3. Обработка JSON в реляционных СУБД и её ресурсная стоимость

Современные СУБД поддерживают JSON разными способами.

JSON может храниться:

- как обычный текст;
- как специализированный тип данных;
- во внутреннем бинарном представлении;
- в сочетании с вычисляемыми столбцами и индексами.

Нельзя утверждать, что при каждом обращении к одному JSON-полю СУБД обязательно полностью разбирает документ заново.

Это зависит от способа хранения, реализации функций, структуры документа и версии СУБД.

#### PostgreSQL: json и jsonb

PostgreSQL поддерживает два основных типа:

**`json`** — хранит текстовое представление JSON с проверкой синтаксиса при записи.

**`jsonb`** — хранит документ во внутреннем бинарном формате, подготовленном для обработки.

Сравнение:

| Характеристика | json | jsonb |
|---|---|---|
| Проверка синтаксиса при вставке | Да | Да |
| Хранение исходного текстового представления | Да | Нет |
| Сохранение порядка ключей объекта | Да | Не гарантируется |
| Сохранение дублирующихся ключей | Да | Нет |
| Дополнительная обработка при записи | Меньше | Больше |
| Операторы поиска и сравнения | Ограничены | Шире |
| GIN-индексирование документа | Нет | Да |

Пример:

```sql
CREATE TABLE json_example (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    raw_data JSON,
    processed_data JSONB
);
```

Тип `json` целесообразен, когда важно сохранить исходное представление документа, включая порядок ключей и форматирование.

Для большинства прикладных задач, связанных с поиском, фильтрацией и модификацией JSON в PostgreSQL, обычно выбирают `jsonb`.

Однако `jsonb` не означает, что извлечение любого вложенного значения имеет постоянную стоимость или что документ хранится как набор отдельно адресуемых реляционных столбцов.

Обработка может требовать обхода внутренней структуры, распаковки значений и дополнительных затрат процессорного времени.

Большие значения также могут храниться с использованием TOAST — механизма PostgreSQL для размещения крупных значений вне основной строки таблицы.

#### SQL Server

В SQL Server начиная с версии 2016 появились функции для работы с JSON, хранящимся в строковых столбцах, например `nvarchar(max)`.

В SQL Server 2025 появился нативный тип `json`, использующий бинарное представление данных.

Он рассчитан на более эффективную обработку JSON-документов и поддерживает оптимизации изменения отдельных значений.

При этом конкретные возможности индексирования и обновления зависят от версии SQL Server.

#### MySQL/InnoDB

MySQL поддерживает специальный тип `JSON`.

Документы проверяются при вставке и хранятся в оптимизированном бинарном представлении.

MySQL также поддерживает частичные обновления бинарного JSON при выполнении определённых условий.

Это не означает, что любое обновление вложенного поля всегда выполняется без изменения значительного объёма данных.

#### Oracle

Oracle поддерживает работу с JSON в текстовых и бинарных представлениях.

В современных версиях доступен нативный тип `JSON`, связанный с бинарным форматом OSON.

Oracle предоставляет развитые SQL/JSON-функции, механизмы поиска, преобразования JSON в таблицы и специализированные способы индексирования.

#### Когда JSON может быть дорогим

Дополнительные расходы возникают при:

- хранении крупных документов;
- многократном извлечении вложенных значений;
- разворачивании больших массивов;
- преобразовании строк в числа и даты;
- обновлении крупных документов;
- фильтрации по неиндексированным JSON-полям;
- работе с большим количеством строк, содержащих JSON.

Однако сравнивать JSON и обычные столбцы нужно по конкретному сценарию нагрузки.

Для некоторых операций оптимизированный бинарный JSON и подходящий индекс обеспечивают достаточно высокую производительность.

### Тема 4. Способы обращения к вложенным данным и JSONPath-подобная навигация

Для обращения к JSON используются специальные операторы и выражения путей.

Рассмотрим документ:

```json
{
  "customer": {
    "name": "Анна",
    "contacts": {
      "email": "anna@example.com"
    }
  },
  "items": [
    {"product_id": 10, "price": 500},
    {"product_id": 20, "price": 1200}
  ]
}
```

Чтобы получить адрес электронной почты, необходимо пройти последовательность:

`customer` → `contacts` → `email`.

#### Обращение к JSON в PostgreSQL

В PostgreSQL используются операторы:

| Оператор | Назначение |
|---|---|
| `->` | Извлечение поля или элемента с сохранением JSON-типа |
| `->>` | Извлечение значения как SQL-текста |
| `#>` | Извлечение JSON по составному пути |
| `#>>` | Извлечение текста по составному пути |

Пример:

```sql
SELECT
    '{"customer":{"name":"Анна"}}'::jsonb
        -> 'customer' AS customer;
```

Результат:

```json
{"name": "Анна"}
```

Получение текста:

```sql
SELECT
    '{"customer":{"name":"Анна"}}'::jsonb
        -> 'customer'
        ->> 'name' AS customer_name;
```

Результат:

```text
Анна
```

Использование составного пути:

```sql
SELECT
    '{"customer":{"contacts":{"email":"anna@example.com"}}}'::jsonb
        #>> '{customer,contacts,email}' AS email;
```

При обращении к массивам индексация начинается с нуля:

```sql
SELECT
    '[10,20,30]'::jsonb -> 0 AS first_element;
```

Результат — JSON-значение `10`.

#### SQL/JSON Path

Во многих СУБД для обращения к JSON применяется язык путей SQL/JSON.

Типичные элементы:

| Выражение | Значение |
|---|---|
| `$` | Корень JSON-документа |
| `$.customer` | Поле customer |
| `$.customer.name` | Вложенное поле name |
| `$.items[0]` | Первый элемент массива |
| `$.items[*]` | Все элементы массива |
| `$.items[*].price` | Значения price для элементов массива |

Синтаксис и поведение расширений SQL/JSON Path отличаются между СУБД.

Например, PostgreSQL поддерживает тип `jsonpath` и функции `jsonb_path_query`, `jsonb_path_exists` и другие.

```sql
SELECT jsonb_path_query(
    '{"items":[{"price":500},{"price":1200}]}'::jsonb,
    '$.items[*].price'
);
```

Результат представлен двумя строками:

```text
500
1200
```

Фильтрация элементов массива:

```sql
SELECT jsonb_path_query(
    '{"items":[{"price":500},{"price":1200}]}'::jsonb,
    '$.items[*] ? (@.price > 1000)'
);
```

Результат:

```json
{"price": 1200}
```

#### Особенности отсутствующих элементов

При обращении к отсутствующему ключу PostgreSQL-операторы извлечения обычно возвращают SQL `NULL`:

```sql
SELECT
    '{"name":"Анна"}'::jsonb ->> 'age' AS age;
```

Но обработка отсутствующих значений и ошибок JSONPath в разных СУБД зависит от режима выполнения.

В SQL/JSON существуют режимы и конструкции управления поведением при отсутствии значения или ошибке, например `lax`, `strict`, `ON EMPTY` и `ON ERROR`.

Поэтому перенос JSONPath-запросов между СУБД требует проверки семантики, а не только синтаксиса.

### Тема 5. Функции проверки, извлечения и преобразования JSON в PostgreSQL и других СУБД

Помимо обычного извлечения полей, СУБД предоставляют функции проверки структуры и типов JSON-данных.

#### Проверка наличия ключа в PostgreSQL

Для `jsonb` доступны операторы:

| Оператор | Назначение |
|---|---|
| `?` | Проверка наличия ключа или строкового элемента на верхнем уровне |
| `?|` | Проверка наличия хотя бы одного элемента из списка |
| `?&` | Проверка наличия всех элементов из списка |
| `@>` | Проверка вложенности или включения JSON-структуры |

Примеры:

```sql
SELECT '{"name":"Анна","age":30}'::jsonb ? 'name';
```

Результат: `true`.

```sql
SELECT '{"name":"Анна","age":30}'::jsonb
       ?| ARRAY['email', 'age'];
```

Результат: `true`.

```sql
SELECT '{"name":"Анна","age":30}'::jsonb
       ?& ARRAY['name', 'age'];
```

Результат: `true`.

Проверка содержания:

```sql
SELECT '{"name":"Анна","age":30}'::jsonb
       @> '{"age":30}'::jsonb;
```

Результат: `true`.

Операторы `?`, `?|` и `?&` работают с ключами объекта или строковыми элементами массива на верхнем уровне проверяемого JSON-значения, а не выполняют произвольный рекурсивный поиск.

#### Определение типа значения

```sql
SELECT jsonb_typeof('{"x":1}'::jsonb);
```

Результат:

```text
object
```

```sql
SELECT jsonb_typeof('[1,2,3]'::jsonb);
```

Результат:

```text
array
```

```sql
SELECT jsonb_typeof('"hello"'::jsonb);
```

Результат:

```text
string
```

Тип значения полезно проверять перед преобразованиями.

Например, поле `price` может быть числом, строкой или `null`.

Прямое преобразование неподходящей строки в числовой тип приведёт к ошибке.

#### Работа с массивами

Количество элементов массива:

```sql
SELECT jsonb_array_length('[10,20,30]'::jsonb);
```

Результат: `3`.

Преобразование элементов массива в строки:

```sql
SELECT value
FROM jsonb_array_elements('[10,20,30]'::jsonb) AS t(value);
```

Результат:

```text
10
20
30
```

Получение текстовых значений:

```sql
SELECT value
FROM jsonb_array_elements_text(
    '["SQL","Python","Java"]'::jsonb
) AS t(value);
```

#### Сравнение возможностей четырёх СУБД

| Операция | PostgreSQL | SQL Server | MySQL | Oracle |
|---|---|---|---|---|
| Извлечь скаляр | `->>`, `#>>`, `json_value` | `JSON_VALUE` | `JSON_VALUE`, `JSON_EXTRACT`, `->>` | `JSON_VALUE` |
| Извлечь JSON-фрагмент | `->`, `#>`, `json_query` | `JSON_QUERY` | `JSON_EXTRACT`, `->` | `JSON_QUERY` |
| Проверить наличие значения по пути | `jsonb_path_exists` | `JSON_PATH_EXISTS` (в поддерживаемых версиях) | `JSON_CONTAINS_PATH` | `JSON_EXISTS` |
| Развернуть JSON в таблицу | `jsonb_to_recordset`, `JSON_TABLE` | `OPENJSON` | `JSON_TABLE` | `JSON_TABLE` |
| Изменить JSON | `jsonb_set` и другие | `JSON_MODIFY`, `modify` для нативного json | `JSON_SET`, `JSON_REPLACE` | `JSON_TRANSFORM` |
| Сформировать JSON | `jsonb_build_object`, `jsonb_agg` | `FOR JSON`, `JSON_OBJECT` в поддерживаемых версиях | `JSON_OBJECT`, `JSON_ARRAYAGG` | `JSON_OBJECT`, `JSON_ARRAYAGG` |

Набор функций зависит от версии и совместимости СУБД.

Например, в PostgreSQL `JSON_TABLE` появился начиная с версии 17, тогда как в более ранних версиях для аналогичных задач используются другие JSON-функции.

### Тема 6. Модификация JSON и управление изменяющейся структурой

JSON-документы могут изменяться средствами SQL.

Типичные операции:

- добавление нового поля;
- обновление значения;
- удаление поля;
- изменение элемента массива;
- добавление элементов массива;
- изменение вложенной структуры.

#### PostgreSQL: изменение значения

Функция `jsonb_set` позволяет заменить значение по указанному пути.

```sql
SELECT jsonb_set(
    '{"name":"Анна","age":30}'::jsonb,
    '{age}',
    '31'::jsonb
);
```

Результат:

```json
{"name": "Анна", "age": 31}
```

Добавление нового поля:

```sql
SELECT jsonb_set(
    '{"name":"Анна"}'::jsonb,
    '{city}',
    '"Москва"'::jsonb,
    true
);
```

Результат:

```json
{"name": "Анна", "city": "Москва"}
```

Четвёртый аргумент определяет, можно ли создать отсутствующий конечный элемент пути.

При этом `jsonb_set` не создаёт автоматически произвольную цепочку отсутствующих вложенных объектов.

#### Удаление поля

```sql
SELECT
    '{"name":"Анна","age":30}'::jsonb - 'age';
```

Результат:

```json
{"name": "Анна"}
```

Удаление вложенного элемента:

```sql
SELECT
    '{"customer":{"name":"Анна","age":30}}'::jsonb
        #- '{customer,age}';
```

Результат:

```json
{"customer": {"name": "Анна"}}
```

#### Обновление JSON в таблице

```sql
CREATE TABLE customer_profiles (
    customer_id BIGINT PRIMARY KEY,
    profile JSONB NOT NULL
);

INSERT INTO customer_profiles (customer_id, profile)
VALUES (
    1,
    '{"name":"Анна","city":"Москва"}'
);
```

Изменение города:

```sql
UPDATE customer_profiles
SET profile = jsonb_set(
    profile,
    '{city}',
    '"Казань"'::jsonb
)
WHERE customer_id = 1;
```

Важный момент: изменение JSON-поля является обновлением строки таблицы с обычными последствиями для транзакций, MVCC и журналирования.

В PostgreSQL построение нового `jsonb`-значения не означает изменения произвольного вложенного байтового фрагмента на месте.

Физическая стоимость операции зависит в том числе от размера значения, хранения TOAST, индексов и характеристик обновления строки.

#### MySQL

В MySQL используются функции:

```sql
JSON_SET()
JSON_INSERT()
JSON_REPLACE()
JSON_REMOVE()
```

Пример:

```sql
SELECT JSON_SET(
    '{"name":"Anna","age":30}',
    '$.age',
    31
);
```

#### SQL Server

Для изменения JSON применяется `JSON_MODIFY`:

```sql
SELECT JSON_MODIFY(
    N'{"name":"Anna","age":30}',
    '$.age',
    31
);
```

В SQL Server 2025 для нативного типа `json` также доступен метод `modify`.

#### Oracle

В Oracle используется `JSON_TRANSFORM`, позволяющая объединять несколько операций изменения документа.

Пример:

```sql
SELECT JSON_TRANSFORM(
    '{"name":"Anna","age":30}',
    SET '$.age' = 31
)
FROM dual;
```

Результат функции нужно использовать в `UPDATE`, если требуется сохранить изменение в таблице.

#### Контроль структуры

Перед изменением JSON необходимо учитывать:

- наличие указанного пути;
- текущий тип значения;
- допустимость преобразования;
- поведение при отсутствующем ключе;
- возможность появления новых полей;
- необходимость проверки бизнес-ограничений.

JSON позволяет менять структуру документа без обычного `ALTER TABLE`, но это не означает, что изменение схемы данных не затрагивает приложение.

Добавление, переименование или удаление JSON-полей может потребовать изменения SQL-запросов, индексов, обработчиков и интеграций.

### Тема 7. Табличные функции и разворачивание JSON в реляционную форму

Одна из важнейших возможностей SQL/JSON — преобразование вложенных массивов и объектов в обычные строки и столбцы.

Рассмотрим заказ:

```json
{
  "order_id": 1001,
  "items": [
    {"product_id": 10, "quantity": 2, "price": 500},
    {"product_id": 20, "quantity": 1, "price": 1200}
  ]
}
```

Для вычисления суммы заказа необходимо обработать каждый элемент массива `items`.

#### PostgreSQL: jsonb_array_elements

```sql
WITH orders AS (
    SELECT
        1001 AS order_id,
        '{
          "items": [
            {"product_id":10,"quantity":2,"price":500},
            {"product_id":20,"quantity":1,"price":1200}
          ]
        }'::jsonb AS details
)
SELECT
    o.order_id,
    item.value ->> 'product_id' AS product_id,
    (item.value ->> 'quantity')::integer AS quantity,
    (item.value ->> 'price')::numeric AS price
FROM orders AS o
CROSS JOIN LATERAL jsonb_array_elements(
    o.details -> 'items'
) AS item(value);
```

Результат:

| order_id | product_id | quantity | price |
|---|---|---|---|
| 1001 | 10 | 2 | 500 |
| 1001 | 20 | 1 | 1200 |

Функция `jsonb_array_elements` возвращает элементы JSON-массива.

Конструкция `LATERAL` позволяет табличной функции обращаться к значениям текущей строки `orders`.

В PostgreSQL табличные функции, расположенные в `FROM`, могут ссылаться на предыдущие элементы `FROM` и без явного слова `LATERAL`, но его указание помогает сделать зависимость понятнее.

#### Преобразование JSON в типизированные столбцы

В PostgreSQL также доступна функция `jsonb_to_recordset`.

```sql
SELECT *
FROM jsonb_to_recordset(
    '[
      {"product_id":10,"quantity":2,"price":500},
      {"product_id":20,"quantity":1,"price":1200}
    ]'::jsonb
) AS items(
    product_id INTEGER,
    quantity INTEGER,
    price NUMERIC
);
```

Здесь структура результата задаётся явно.

Это удобнее, когда нужно извлечь несколько известных полей.

Но автоматическое преобразование значений в указанные SQL-типы может завершиться ошибкой, если входящие данные некорректны.

#### PostgreSQL 17+: JSON_TABLE

Начиная с PostgreSQL 17 доступна функция `JSON_TABLE`.

```sql
SELECT *
FROM JSON_TABLE(
    '{
      "items": [
        {"product_id":10,"quantity":2},
        {"product_id":20,"quantity":1}
      ]
    }'::jsonb,
    '$.items[*]'
    COLUMNS (
        product_id INTEGER PATH '$.product_id',
        quantity INTEGER PATH '$.quantity'
    )
) AS jt;
```

Она позволяет описать строки и столбцы через SQL/JSON Path.

Это приближает работу PostgreSQL с JSON к возможностям MySQL и Oracle.

#### SQL Server: OPENJSON

В SQL Server применяется функция `OPENJSON`.

```sql
DECLARE @data NVARCHAR(MAX) = N'
{
  "items": [
    {"product_id":10,"quantity":2},
    {"product_id":20,"quantity":1}
  ]
}';

SELECT *
FROM OPENJSON(@data, '$.items')
WITH (
    product_id INT '$.product_id',
    quantity INT '$.quantity'
);
```

#### MySQL: JSON_TABLE

```sql
SELECT *
FROM JSON_TABLE(
    '{
      "items": [
        {"product_id":10,"quantity":2},
        {"product_id":20,"quantity":1}
      ]
    }',
    '$.items[*]'
    COLUMNS (
        product_id INT PATH '$.product_id',
        quantity INT PATH '$.quantity'
    )
) AS jt;
```

#### Oracle: JSON_TABLE

```sql
SELECT jt.product_id, jt.quantity
FROM JSON_TABLE(
    '{
      "items": [
        {"product_id":10,"quantity":2},
        {"product_id":20,"quantity":1}
      ]
    }',
    '$.items[*]'
    COLUMNS (
        product_id NUMBER PATH '$.product_id',
        quantity NUMBER PATH '$.quantity'
    )
) jt;
```

Синтаксис функций похож, но правила типизации, обработки отсутствующих полей, ошибок и вложенных массивов могут различаться.

#### Агрегация после разворачивания

После преобразования массива в строки становятся доступны обычные SQL-агрегаты.

Пример PostgreSQL:

```sql
WITH orders AS (
    SELECT
        1001 AS order_id,
        '{
          "items": [
            {"product_id":10,"quantity":2,"price":500},
            {"product_id":20,"quantity":1,"price":1200}
          ]
        }'::jsonb AS details
)
SELECT
    o.order_id,
    SUM(
        (item.value ->> 'quantity')::numeric *
        (item.value ->> 'price')::numeric
    ) AS total_amount
FROM orders AS o
CROSS JOIN LATERAL jsonb_array_elements(
    o.details -> 'items'
) AS item(value)
GROUP BY o.order_id;
```

Результат:

| order_id | total_amount |
|---|---|
| 1001 | 2200 |

Важно учитывать, что `CROSS JOIN LATERAL` не возвращает строку заказа, если табличная функция возвращает пустой набор.

Если необходимо сохранить заказы с пустыми массивами, можно использовать `LEFT JOIN LATERAL ... ON TRUE`, учитывая появление SQL `NULL` в столбцах развёрнутого результата.

Также необходимо правильно выбирать уровень группировки, чтобы не получить ошибочное умножение строк при соединении нескольких вложенных массивов.

#### Обратная операция: формирование JSON из строк

SQL позволяет не только разворачивать JSON, но и собирать документы из реляционных данных.

В PostgreSQL:

```sql
SELECT jsonb_agg(
    jsonb_build_object(
        'product_id', product_id,
        'quantity', quantity
    )
)
FROM (
    VALUES
        (10, 2),
        (20, 1)
) AS items(product_id, quantity);
```

Результат — JSON-массив объектов.

Порядок элементов агрегированного массива не следует считать гарантированным без явного задания порядка внутри агрегата.

JSON-агрегация применяется при формировании API-ответов, экспорте данных и подготовке вложенных структур.

### Тема 8. План выполнения запроса и влияние структуры JSON на производительность

Наличие JSON в запросе не отменяет обычных принципов работы SQL-оптимизатора.

Для выполнения запроса СУБД может использовать:

- последовательное сканирование;
- индексный поиск;
- соединения;
- табличные функции;
- фильтрацию;
- сортировку;
- группировку;
- материализацию промежуточных результатов.

Стоимость выполнения зависит не только от размера JSON-документов, но и от количества строк, селективности условий, доступных индексов и выбранного плана.

#### Последовательное сканирование

Пример PostgreSQL:

```sql
SELECT *
FROM customer_profiles
WHERE profile ->> 'city' = 'Москва';
```

Если подходящего индекса нет, PostgreSQL может выполнить последовательное сканирование таблицы.

Для каждой проверяемой строки потребуется получить значение поля `city`.

На небольшой таблице такой план может быть оптимальным.

На большой таблице с высокоселективным условием может оказаться выгоднее индексный поиск.

#### Разворачивание больших массивов

Предположим, что таблица содержит 100 000 заказов, а каждый JSON-документ — массив из 50 товаров.

Полное разворачивание всех массивов потенциально создаст 5 миллионов строк.

```sql
SELECT
    o.order_id,
    item.value
FROM orders AS o
CROSS JOIN LATERAL jsonb_array_elements(
    o.details -> 'items'
) AS item(value);
```

Если требуется информация только о заказах конкретного клиента, желательно сначала сократить набор заказов.

```sql
SELECT
    o.order_id,
    item.value
FROM orders AS o
CROSS JOIN LATERAL jsonb_array_elements(
    o.details -> 'items'
) AS item(value)
WHERE o.customer_id = 15;
```

Оптимизатор может применить фильтрацию по `customer_id` до вызова функции для соответствующих строк.

Однако фактический порядок операций необходимо проверять по плану выполнения.

Нельзя считать, что написанный раньше или позже в SQL условный блок автоматически выполняется в том же порядке.

#### EXPLAIN ANALYZE

В PostgreSQL для анализа используется:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    o.order_id,
    item.value
FROM orders AS o
CROSS JOIN LATERAL jsonb_array_elements(
    o.details -> 'items'
) AS item(value)
WHERE o.customer_id = 15;
```

При анализе плана необходимо обращать внимание на:

- `Seq Scan` — последовательное сканирование;
- `Index Scan` и `Bitmap Index Scan` — способы использования индексов;
- `Function Scan` — выполнение табличной функции;
- `Nested Loop` — вложенное соединение;
- `Filter` — фильтрация строк;
- `Rows Removed by Filter` — количество отброшенных строк;
- `actual rows` — фактическое число строк;
- `loops` — количество повторений узла;
- `Buffers` — обращения к буферам.

Если табличная функция вызывается много раз, это может заметно увеличить стоимость обработки.

Но наличие `Nested Loop` или `Function Scan` само по себе не означает плохой план.

Для зависимой табличной функции такой способ выполнения может быть естественным и эффективным.

#### Корректное сравнение производительности

При измерениях необходимо учитывать:

1. Размер и распределение данных.
2. Наличие индексов.
3. Состояние кеша.
4. Фактический план выполнения.
5. Количество возвращаемых строк.
6. Затраты на преобразование и передачу результата клиенту.
7. Версию СУБД.

`EXPLAIN ANALYZE` выполняет запрос и измеряет его выполнение, но не обязательно отражает полную стоимость сериализации и передачи результата приложению.

Поэтому для оценки реальной нагрузки полезно сравнивать как планы, так и фактическое время получения результатов клиентом.

Особенно важно избегать выводов по единственному запуску запроса.

### Тема 9. JSONB, индексирование и ускорение поиска

JSON-данные можно индексировать, но способы индексирования отличаются между СУБД.

Не существует одного универсального JSON-индекса, одинаково работающего для всех SQL-запросов.

Выбор зависит от того, какие операции чаще выполняются:

- поиск по конкретному полю;
- проверка наличия ключа;
- поиск вложенного объекта;
- проверка вхождения значения;
- фильтрация по диапазону;
- поиск элементов массивов.

#### PostgreSQL: GIN-индекс

Для `jsonb` можно создать GIN-индекс:

```sql
CREATE INDEX idx_profiles_json
ON customer_profiles
USING GIN (profile);
```

Такой индекс поддерживает определённые операции поиска по JSONB, в частности `@>` и операторы наличия ключей.

Пример:

```sql
SELECT *
FROM customer_profiles
WHERE profile @> '{"city":"Москва"}'::jsonb;
```

При подходящих условиях оптимизатор может использовать GIN-индекс.

Но следующий запрос не обязан использовать тот же индекс:

```sql
SELECT *
FROM customer_profiles
WHERE profile ->> 'city' = 'Москва';
```

Оператор `->>` возвращает текст, а не выполняет непосредственно индексируемую GIN-операцию над документом.

Для такого условия часто подходит индекс по выражению.

#### Индекс по выражению

```sql
CREATE INDEX idx_profiles_city
ON customer_profiles ((profile ->> 'city'));
```

Теперь условие:

```sql
SELECT *
FROM customer_profiles
WHERE profile ->> 'city' = 'Москва';
```

может использовать B-tree индекс по извлечённому полю.

Если по JSON-полю регулярно выполняется поиск по равенству или диапазону, индекс по выражению может быть удобнее, чем индексирование всего документа.

Например:

```sql
CREATE INDEX idx_profiles_age
ON customer_profiles (((profile ->> 'age')::integer));
```

Такой индекс предполагает, что все индексируемые значения корректно преобразуются в `integer`.

Если в JSON встречаются произвольные строки, индекс необходимо проектировать с учётом проверки и очистки данных.

#### Операторные классы GIN

В PostgreSQL для `jsonb` доступны два основных операторных класса:

**`jsonb_ops`** — используется по умолчанию, поддерживает более широкий набор операций, в том числе проверку наличия ключей.

**`jsonb_path_ops`** — поддерживает более узкий набор операций, включая `@>` и определённые операции JSONPath, но не поддерживает операторы `?`, `?|` и `?&`.

Пример:

```sql
CREATE INDEX idx_profiles_path
ON customer_profiles
USING GIN (profile jsonb_path_ops);
```

Выбор между операторными классами зависит от запросов.

`jsonb_path_ops` нередко обеспечивает более компактный и эффективный индекс для поддерживаемых операций поиска по содержимому, но подходит не для всех условий.

#### Hash-индекс

В PostgreSQL существуют hash-индексы, применяемые для операций равенства по поддерживаемым типам.

Однако hash-индекс по JSONB не является универсальным средством поиска по вложенным ключам и значениям.

Он не заменяет GIN-индекс и обычно не является первым выбором для JSON-запросов.

Для проверки вхождения объектов, существования ключей и JSONPath необходимо рассматривать подходящие GIN-индексы, а для поиска по отдельным скалярным полям — индексы по выражениям.

#### MySQL: индексы по извлечённым значениям

В MySQL нельзя создать обычный B-tree индекс непосредственно на всём JSON-документе как на стандартном скалярном столбце.

Распространённый подход — использовать вычисляемый столбец:

```sql
CREATE TABLE customers (
    id BIGINT PRIMARY KEY,
    profile JSON,
    city VARCHAR(100)
        GENERATED ALWAYS AS (
            JSON_UNQUOTE(JSON_EXTRACT(profile, '$.city'))
        ) STORED,
    INDEX idx_customers_city (city)
);
```

Теперь индекс может использоваться при фильтрации по столбцу `city`.

В MySQL также доступны функциональные индексы по подходящим выражениям, включая извлечение JSON-значений с явным возвращаемым SQL-типом.

Для отдельных сценариев поиска по массивам поддерживаются multi-valued indexes.

#### SQL Server: индексирование JSON

В SQL Server традиционный способ ускорения поиска по JSON предполагает вычисляемые столбцы.

Пример для хранения JSON в `nvarchar(max)`:

```sql
CREATE TABLE customers (
    id BIGINT PRIMARY KEY,
    profile NVARCHAR(MAX),
    city AS JSON_VALUE(profile, '$.city')
);
```

Далее можно создать индекс:

```sql
CREATE INDEX idx_customers_city
ON customers(city);
```

В SQL Server 2025 также появился механизм `CREATE JSON INDEX`.

Он расширяет возможности индексирования JSON, однако его доступность, требования и ограничения необходимо учитывать отдельно от обычных индексов по вычисляемым столбцам.

#### Oracle: индексирование JSON

Oracle предоставляет несколько вариантов оптимизации:

- функциональные индексы по `JSON_VALUE`;
- виртуальные столбцы с индексами;
- JSON search indexes;
- multi-value индексы для поддерживаемых сценариев;
- материализованные представления с извлечёнными JSON-данными.

Например, функциональный индекс может строиться по значению определённого JSON-поля.

JSON search index применяется для более широкого поиска по документам и вложенным элементам.

#### Индекс — не всегда ускорение

Любой индекс имеет стоимость:

- занимает место;
- требует обслуживания при изменении данных;
- увеличивает расходы на вставку и обновление;
- может быть бесполезен для недостаточно селективных запросов.

Поэтому индексы необходимо проектировать под реальные условия `WHERE`, `JOIN` и `ORDER BY`, а их эффективность проверять планами выполнения.

### Тема 10. Практические сценарии работы с JSON в прикладных задачах

JSON применяется в различных прикладных сценариях, но подход к его хранению зависит от требований к данным.

#### Сценарий 1. Профили пользователей

Предположим, у пользователей есть фиксированные атрибуты:

- идентификатор;
- имя;
- адрес электронной почты;
- дата регистрации.

Также существуют дополнительные настройки:

- тема интерфейса;
- язык;
- параметры уведомлений;
- пользовательские предпочтения.

Основные атрибуты удобно хранить в обычных столбцах, а изменяемые настройки — в JSON.

```sql
CREATE TABLE users (
    user_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    settings JSONB NOT NULL DEFAULT '{}'::jsonb
);
```

Добавление пользователя:

```sql
INSERT INTO users (email, settings)
VALUES (
    'anna@example.com',
    '{"theme":"dark","language":"ru"}'
);
```

Получение настройки:

```sql
SELECT
    user_id,
    settings ->> 'theme' AS theme
FROM users;
```

Такой вариант оправдан, если настройки не требуют сложной ссылочной целостности и большого количества аналитических запросов.

#### Сценарий 2. Заказы и товары

Для заказов часто требуется:

- искать товары по идентификатору;
- объединять продажи с каталогом;
- рассчитывать выручку;
- контролировать остатки;
- выполнять аналитику по товарам.

Если хранить позиции заказа только внутри JSON, многие запросы потребуют разворачивания массивов.

В таком сценарии обычно лучше использовать отдельную таблицу `order_items`.

При этом JSON может хранить снимок исходного сообщения заказа, полученного от внешней системы.

Таким образом, возможна архитектура:

- реляционные таблицы для основной бизнес-логики;
- исходный JSON-документ для интеграции и аудита.

#### Сценарий 3. События и журналы

Для журналов событий JSON особенно удобен, поскольку события разных типов могут содержать различные наборы полей.

```sql
CREATE TABLE application_events (
    event_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    payload JSONB NOT NULL
);
```

Пример записи:

```sql
INSERT INTO application_events (event_type, payload)
VALUES (
    'order_created',
    '{
      "order_id":1001,
      "source":"mobile",
      "metadata":{"application_version":"2.1"}
    }'
);
```

Поиск событий:

```sql
SELECT *
FROM application_events
WHERE event_type = 'order_created'
  AND payload @> '{"source":"mobile"}'::jsonb;
```

Если объём событий велик, кроме JSON-индексов могут потребоваться индексы по времени и типу события, партиционирование и политика хранения.

#### Сценарий 4. Статьи и документы

JSON может содержать метаданные документов:

```json
{
  "title": "Работа с SQL",
  "tags": ["database", "sql", "education"],
  "author": {
    "id": 10,
    "name": "Anna"
  }
}
```

При этом обычный поиск по JSON-полям не следует автоматически считать полнотекстовым поиском.

Для полнотекстового поиска применяются отдельные механизмы СУБД:

- PostgreSQL Full Text Search с `tsvector` и соответствующими индексами;
- Full-Text Search в SQL Server;
- FULLTEXT-индексы MySQL;
- Oracle Text и соответствующие возможности поиска.

JSON может быть источником текста для индексации, но наличие JSON-индекса само по себе не решает все задачи полнотекстового поиска.

#### Когда выбирать JSON, а когда таблицы

| Ситуация | Предпочтительный подход |
|---|---|
| Стабильные поля с ограничениями и связями | Обычные столбцы и таблицы |
| Набор дополнительных атрибутов часто меняется | JSON или гибридная модель |
| Частые соединения по вложенным сущностям | Реляционные таблицы |
| Хранение исходных API-сообщений | JSON |
| Массовая аналитика по вложенным значениям | Табличное представление или предварительное преобразование |
| Гибкие пользовательские настройки | JSON |
| Частый поиск по одному JSON-полю | Индекс по извлечённому значению либо отдельный столбец |
| События с неоднородной структурой | JSON с выделенными основными атрибутами |

Выбор формата должен определяться не только удобством записи данных, но и тем, как эти данные будут читаться, обновляться и контролироваться.

## Итоговые выводы

1. **JSON является полноценным инструментом работы с полуструктурированными данными в современных реляционных СУБД.** Он позволяет хранить вложенные объекты и массивы, выполнять SQL-запросы по их содержимому и преобразовывать документы в табличную форму.

2. **Реализация JSON существенно различается между СУБД.** PostgreSQL использует `json` и `jsonb`, MySQL — нативный бинарный JSON, SQL Server поддерживает как строковое хранение, так и нативный тип `json` в современных версиях, а Oracle предоставляет развитые возможности SQL/JSON и бинарного хранения.

3. **JSON не заменяет реляционную модель.** Если данные имеют устойчивую структуру, используются в соединениях и требуют ограничений целостности, обычные таблицы часто удобнее и эффективнее.

4. **При работе с JSON необходимо учитывать типы данных, отсутствующие поля и различие между JSON null и SQL NULL.** Ошибки преобразования и неоднородная структура могут приводить к неверным результатам запросов.

5. **Табличные функции связывают JSON и реляционную обработку.** Они позволяют разворачивать массивы, извлекать типизированные столбцы и использовать привычные SQL-операции: фильтрацию, соединения и агрегацию.

6. **Бинарный формат и индексы помогают оптимизировать работу с JSON, но не устраняют все расходы.** Производительность зависит от размера документов, характера запросов, способа обновления, индексов и выбранного плана выполнения.

7. **Индекс должен соответствовать конкретному запросу.** В PostgreSQL GIN подходит для определённых операций над `jsonb`, а индексы по выражениям — для поиска по отдельным значениям. В других СУБД используются вычисляемые столбцы, функциональные и специализированные JSON-индексы.

8. **Производительность JSON-запросов необходимо проверять экспериментально.** Важно анализировать планы выполнения, объём обработанных строк, стоимость разворачивания массивов и фактическое время получения данных.

Главный результат занятия — понимание того, что JSON и реляционное хранение являются взаимодополняющими механизмами. Грамотное проектирование состоит в выборе подходящего представления данных под конкретные операции, требования к целостности и характер нагрузки.
