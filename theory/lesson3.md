# Нормализация и денормализация данных: связи между таблицами и нормальные формы

## Превью / аннотация / краткое содержание

На этом занятии мы разберём, как проектировать структуру реляционной базы данных так, чтобы данные оставались согласованными, не дублировались без необходимости и были удобны для дальнейшей работы.

Рассмотрим:

- как реализуются связи `1:1`, `1:N` и `M:N`;
- какую роль играют первичные и внешние ключи;
- что такое ссылочная целостность;
- как работают каскадные действия внешних ключей;
- что называют аномалиями вставки, обновления и удаления;
- зачем нужна нормализация;
- что означают первая, вторая и третья нормальные формы;
- чем естественные ключи отличаются от суррогатных;
- когда денормализация может быть оправдана;
- почему модели аналитических хранилищ нельзя сводить просто к «ненормализованным таблицам».

Главная цель занятия — научиться видеть зависимости между данными и принимать осознанные решения о структуре таблиц.

# Основная часть

## Тема 1. Зачем разделять данные на несколько таблиц

Представим, что информацию о заказах решили хранить в одной таблице:

| order_id | customer_name | customer_phone | product_name | quantity |
|---:|---|---|---|---:|
| 1001 | Анна Иванова | +79990000001 | Кофе | 2 |
| 1001 | Анна Иванова | +79990000001 | Молоко | 1 |
| 1002 | Иван Петров | +79990000002 | Хлеб | 3 |

На первый взгляд структура кажется удобной: вся информация находится в одном месте.

Но здесь сразу появляется дублирование:

```text
Анна Иванова
+79990000001
```

повторяются для каждой позиции её заказа.

Если клиент сделает ещё десять заказов, имя и телефон будут записаны снова.

Это приводит к проблемам:

- данные занимают больше места;
- одно и то же значение приходится обновлять в нескольких строках;
- разные копии одного факта могут начать противоречить друг другу;
- некоторые данные невозможно сохранить независимо от других.

В реляционной модели такие данные обычно разделяют на сущности.

Например:

```text
customers
orders
order_items
products
```

а связи между ними задают ключами.

## Тема 2. Связи между сущностями

Между сущностями предметной области существуют отношения.

Обычно выделяют три основных типа:

- `1:1` — один к одному;
- `1:N` — один ко многим;
- `M:N` — многие ко многим.

---

### Связь один ко многим — 1:N

Это наиболее распространённый тип связи.

Например:

> один клиент может создать много заказов, но каждый заказ принадлежит одному клиенту.

```text
Customer 1 ───── N Order
```

В таблицах это можно реализовать внешним ключом:

```sql
CREATE TABLE customers (
    customer_id INTEGER PRIMARY KEY,
    full_name VARCHAR(200) NOT NULL
);

CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,

    FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);
```

`orders.customer_id` хранит идентификатор клиента.

При этом имя клиента не нужно копировать в каждую строку заказа.

---

### Связь один к одному — 1:1

При связи `1:1` одной строке первой таблицы соответствует не более одной строки второй таблицы.

Например:

```text
Customer 1 ───── 1 CustomerProfile
```

Такая структура может быть полезна, когда:

- часть атрибутов существует не для всех объектов;
- данные имеют другой жизненный цикл;
- необходимо разделить области ответственности;
- часть информации требуется хранить отдельно по архитектурным или организационным причинам.

Важно: связь `1:1` не возникает автоматически только потому, что таблицы соединены внешним ключом.

Необходимо также обеспечить уникальность ссылки.

Например:

```sql
CREATE TABLE customer_profiles (
    customer_id INTEGER PRIMARY KEY,
    birth_date DATE,

    FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);
```

Здесь `customer_id` одновременно является:

- первичным ключом `customer_profiles`;
- внешним ключом на `customers`.

Следовательно, для одного клиента невозможно создать несколько строк профиля.

---

### Связь многие ко многим — M:N

Представим:

> один заказ содержит несколько товаров, а один товар может встречаться во множестве заказов.

Это связь:

```text
Order M ───── N Product
```

В реляционной базе связь `M:N` обычно преобразуют в две связи `1:N` через промежуточную таблицу.

```text
Order 1 ───── N OrderItem N ───── 1 Product
```

Например:

```sql
CREATE TABLE order_items (
    order_id INTEGER NOT NULL,
    product_id INTEGER NOT NULL,
    quantity INTEGER NOT NULL,

    PRIMARY KEY (order_id, product_id),

    FOREIGN KEY (order_id)
        REFERENCES orders(order_id),

    FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);
```

Промежуточная таблица может содержать собственные атрибуты связи:

```text
quantity
unit_price
discount
```

То есть `order_items` — не просто техническая таблица, а полноценная сущность предметной области.

## Тема 3. Ссылочная целостность

Внешний ключ используется для поддержания **ссылочной целостности**.

Если существует:

```text
orders.customer_id = 10
```

то в родительской таблице должен существовать соответствующий клиент.

```text
customers.customer_id = 10
```

Если такого клиента нет, вставка строки должна завершиться ошибкой.

Пример:

```sql
INSERT INTO orders (
    order_id,
    customer_id
)
VALUES (
    1001,
    999999
);
```

Если клиента `999999` не существует, внешний ключ не позволит создать некорректную ссылку.

## Тема 4. Что происходит при удалении родительской строки

Рассмотрим связь:

```text
Customer 1 ───── N Order
```

Пусть существуют заказы клиента `10`.

Что должно произойти, если попытаться удалить клиента?

Внешний ключ может задавать разное поведение.

---

### NO ACTION / RESTRICT

Самый безопасный вариант по смыслу:

> не разрешать удаление родительской строки, пока существуют зависимые данные.

Пример:

```sql
FOREIGN KEY (customer_id)
    REFERENCES customers(customer_id)
```

Во многих СУБД именно запрещающее поведение используется по умолчанию.

Точные различия между `NO ACTION` и `RESTRICT` зависят от платформы.

---

### ON DELETE CASCADE

```sql
FOREIGN KEY (order_id)
    REFERENCES orders(order_id)
    ON DELETE CASCADE
```

Теперь при удалении заказа автоматически удаляются связанные дочерние строки.

Например:

```text
orders
    ↓
order_items
```

Для `order_items` это часто логично:

> строка позиции заказа не имеет смысла без самого заказа.

Но каскад необходимо применять осознанно.

Например, связь:

```text
Product ← OrderItem
```

обычно не означает, что удаление товара должно автоматически удалить историю всех заказов, в которых этот товар участвовал.

---

### ON DELETE SET NULL

Если связь является необязательной, иногда используется:

```sql
ON DELETE SET NULL
```

Например:

```text
Product → ProductManager
```

После удаления менеджера сам товар должен остаться, а ссылка на менеджера может стать `NULL`.

Для этого внешний ключ должен допускать `NULL`.

---

### ON UPDATE

Некоторые СУБД поддерживают аналогичные действия при изменении значения родительского ключа.

Например:

```sql
ON UPDATE CASCADE
```

Однако набор поддерживаемых действий различается между PostgreSQL, SQL Server, MySQL и Oracle.

Поэтому конкретное поведение всегда необходимо проверять для выбранной платформы.

---

## Тема 5. Каскад — это бизнес-решение

`CASCADE` удобен, но его нельзя включать автоматически для всех связей.

Представим цепочку:

```text
customer
   ↓
order
   ↓
order_item
```

Если настроить каскадное удаление на каждом уровне, команда:

```sql
DELETE FROM customers
WHERE customer_id = 10;
```

может удалить:

```text
клиента
+
все его заказы
+
все позиции этих заказов
```

Технически это может быть корректно.

Но с точки зрения бизнеса история заказов часто должна сохраняться.

Поэтому при проектировании внешнего ключа нужно спрашивать:

> существует ли дочерняя сущность независимо от родительской и допустимо ли физически удалить её вместе с родителем?

Ответ определяется предметной областью, а не удобством SQL.

## Тема 6. Проверка ограничений при массовой загрузке

В исходных данных, миграциях и больших загрузках может возникнуть желание временно отключить ограничения ради скорости.

С этим необходимо быть осторожным.

Нельзя считать универсальным алгоритм:

```text
1. отключить foreign key
2. загрузить данные
3. включить foreign key
```

без дополнительных проверок.

Если ограничение было отключено, в базе могут появиться некорректные ссылки.

Например:

```text
orders.customer_id = 100500
```

при отсутствии такого клиента.

После загрузки необходимо убедиться, что все данные действительно удовлетворяют ограничениям.

---

### Отложенная проверка ограничений

Некоторые СУБД позволяют создать ограничения как **откладываемые — DEFERRABLE**.

Это означает, что нарушение может временно существовать внутри транзакции, но к моменту проверки или `COMMIT` данные должны снова стать корректными.

Например, такая возможность существует в PostgreSQL и Oracle для поддерживаемых типов ограничений.

Концептуально:

```text
BEGIN

промежуточное состояние временно нарушает связь

другие команды исправляют состояние

COMMIT
    ↓
проверка ограничения
```

Однако механизм `DEFERRABLE` **не является универсальным для всех четырёх СУБД курса**.

Например, SQL Server и MySQL/InnoDB имеют другие механизмы управления проверкой ограничений.

Поэтому при массовой загрузке нельзя переносить один и тот же рецепт между платформами без проверки.

## Тема 7. Что такое нормализация

**Нормализация** — метод проектирования реляционной структуры, при котором данные организуют таким образом, чтобы уменьшить нежелательную избыточность и устранить определённые зависимости, приводящие к аномалиям.

Важно:

> цель нормализации — не просто «создать побольше таблиц».

Нормализация основана на анализе зависимостей между атрибутами.

Например, пусть существует таблица:

| order_id | order_date | customer_id | customer_name |
|---:|---|---:|---|
| 1001 | 2026-10-01 | 10 | Анна |
| 1002 | 2026-10-02 | 10 | Анна |
| 1003 | 2026-10-03 | 10 | Анна |

Здесь:

```text
customer_id → customer_name
```

То есть имя клиента определяется идентификатором клиента.

Но оно повторяется в каждой строке заказа.

Логичнее разделить данные:

```text
customers
    customer_id
    customer_name

orders
    order_id
    order_date
    customer_id
```

Теперь факт:

```text
customer_id = 10 → customer_name = Анна
```

хранится в одном месте.

## Тема 8. Аномалии ненормализованных данных

Нежелательная избыточность приводит к нескольким типичным проблемам.

---

### Аномалия обновления

Есть таблица:

| order_id | customer_id | customer_phone |
|---:|---:|---|
| 1001 | 10 | +70000000001 |
| 1002 | 10 | +70000000001 |
| 1003 | 10 | +70000000001 |

Клиент изменил телефон.

Необходимо обновить три строки.

Если одну забыли:

| order_id | customer_id | customer_phone |
|---:|---:|---|
| 1001 | 10 | +70000000002 |
| 1002 | 10 | +70000000002 |
| 1003 | 10 | +70000000001 |

Теперь база содержит два разных телефона одного клиента.

---

### Аномалия вставки

Предположим, информация о клиенте хранится только внутри строк заказов.

Новый клиент зарегистрировался, но ещё ничего не заказал.

Где сохранить:

```text
customer_id
full_name
phone
```

если строки заказа ещё не существует?

Структура вынуждает создавать фиктивный заказ или вообще не позволяет сохранить клиента.

---

### Аномалия удаления

Если последний заказ клиента является одновременно единственным местом, где хранится его информация, удаление заказа приведёт к потере данных о клиенте.

То есть удаление одного факта:

```text
заказ
```

случайно удаляет другой независимый факт:

```text
существование клиента
```

Нормализация помогает разделить такие факты.

---

## Тема 9. Функциональные зависимости

Для понимания нормальных форм полезно понятие **функциональной зависимости**.

Запись:

```text
A → B
```

означает:

> значение A однозначно определяет значение B.

Например:

```text
customer_id → full_name
```

Если `customer_id` является идентификатором клиента, каждому его значению соответствует конкретное имя клиента.

Другой пример:

```text
product_id → product_name
```

При нормализации нас интересует, от чего именно зависит каждый атрибут.

# Первая нормальная форма — 1NF

## Тема 10. Первая нормальная форма

Упрощённо для практического проектирования таблица в первой нормальной форме должна представлять каждый факт через отдельные строки и атрибуты без повторяющихся групп внутри одной строки.

Плохой пример:

| order_id | products |
|---:|---|
| 1001 | Кофе, Молоко, Хлеб |

Здесь в одном атрибуте фактически хранится список нескольких значений.

Ещё хуже:

| order_id | product1 | product2 | product3 |
|---:|---|---|---|
| 1001 | Кофе | Молоко | Хлеб |

Количество товаров искусственно ограничено структурой таблицы.

Правильнее представить позиции отдельными строками:

| order_id | product_id |
|---:|---:|
| 1001 | 1 |
| 1001 | 2 |
| 1001 | 3 |

---

### Что значит «атомарное значение»

Часто 1NF объясняют фразой:

> в каждой ячейке должно быть атомарное значение.

Это полезное учебное упрощение, но слово **атомарное** зависит от предметной области.

Например:

```text
"Москва, Тверская улица, 10"
```

может рассматриваться как одно значение адреса в одной модели.

А если необходимо отдельно искать:

```text
город
улицу
дом
```

адрес лучше разложить на отдельные атрибуты.

Поэтому вопрос не в том, можно ли технически записать строку через запятую.

Важно:

> воспринимается ли это значение системой как один неделимый атрибут или как набор отдельных фактов, с которыми необходимо работать независимо.

---

# Вторая нормальная форма — 2NF

## Тема 11. Вторая нормальная форма

Вторая нормальная форма связана с зависимостью неключевых атрибутов от **всего кандидатного ключа**, а не только от его части.

Особенно хорошо проблема видна на составном ключе.

Представим таблицу:

| order_id | product_id | product_name | quantity |
|---:|---:|---|---:|
| 1001 | 1 | Кофе | 2 |
| 1001 | 2 | Молоко | 1 |
| 1002 | 1 | Кофе | 3 |

Пусть ключ:

```text
(order_id, product_id)
```

Количество зависит от всей пары:

```text
(order_id, product_id) → quantity
```

Но название товара зависит только от:

```text
product_id → product_name
```

То есть `product_name` зависит только от части составного ключа.

Это называется **частичной зависимостью**.

Чтобы устранить её, данные разделяют:

```text
products
    product_id
    product_name

order_items
    order_id
    product_id
    quantity
```

Теперь каждый факт хранится в подходящей таблице.

---

### Важное замечание про простой ключ

Если кандидатный ключ состоит из одного столбца, частичной зависимости от части такого ключа быть не может.

Поэтому проблема 2NF особенно заметна в таблицах с составными кандидатными ключами.

# Суррогатные и естественные ключи

## Тема 12. Естественный ключ

**Естественный ключ** образован из данных предметной области.

Например, в некоторой системе естественным ключом могут выступать:

```text
country_code + tax_number
```

если бизнес действительно гарантирует уникальность такой комбинации.

Преимущество естественного ключа:

- он имеет бизнес-смысл.

Недостатки возможны, если значение:

- длинное;
- состоит из многих столбцов;
- может измениться;
- определяется внешней системой;
- содержит чувствительную информацию;
- перестаёт быть уникальным при изменении бизнес-правил.

---

## Тема 13. Суррогатный ключ

**Суррогатный ключ** — технический идентификатор, который вводится специально для идентификации строки.

Например:

```text
customer_id
order_id
product_id
```

Он может генерироваться:

- последовательностью;
- identity-механизмом;
- UUID;
- другим способом.

Суррогатный ключ удобен тем, что обычно:

- короткий;
- стабилен;
- не зависит от изменения бизнес-атрибутов;
- удобен во внешних ключах.

Но добавление суррогатного ключа **не устраняет бизнес-правило уникальности**.

Например:

```text
customer_id
email
```

Если по правилам системы email должен быть уникальным, наличие `customer_id` не отменяет этого требования.

Правило следует отдельно выразить ограничением, например:

```sql
UNIQUE (email)
```

если именно такая уникальность требуется предметной областью.

Иначе база сможет содержать:

```text
customer_id = 1, email = a@example.com
customer_id = 2, email = a@example.com
```

несмотря на разные суррогатные идентификаторы.

---

# Третья нормальная форма — 3NF

## Тема 14. Транзитивная зависимость

Рассмотрим таблицу:

| employee_id | department_id | department_name |
|---:|---:|---|
| 1 | 10 | IT |
| 2 | 10 | IT |
| 3 | 20 | Finance |

Здесь:

```text
employee_id → department_id
```

и:

```text
department_id → department_name
```

Следовательно:

```text
employee_id → department_name
```

через `department_id`.

Это пример **транзитивной зависимости**.

Название подразделения является фактом о подразделении, а не о сотруднике.

Поэтому данные лучше разделить:

```text
departments
    department_id
    department_name

employees
    employee_id
    department_id
```

---

## Тема 15. Третья нормальная форма

Упрощённо, таблица находится в 3NF, если:

1. она удовлетворяет требованиям 2NF;
2. неключевые атрибуты не зависят транзитивно от ключа через другие неключевые атрибуты.

Практический смысл:

> факт должен храниться в таблице той сущности, которую он описывает.

Например:

```text
customer_name
```

является фактом о клиенте.

```text
product_name
```

— фактом о товаре.

```text
quantity
```

в позиции заказа — фактом о связи конкретного товара с конкретным заказом.

Такое разделение уменьшает количество мест, в которых приходится хранить один и тот же факт.

---

# Нормализация не означает «максимум таблиц»

## Тема 16. До какой нормальной формы нормализовать

Помимо 1NF, 2NF и 3NF существуют более строгие формы:

- BCNF;
- 4NF;
- 5NF и другие.

Но это не означает, что каждую прикладную базу необходимо механически разложить до максимально возможной формы.

В большинстве прикладных OLTP-моделей 3NF является полезной практической точкой отсчёта.

Однако реальное проектирование учитывает:

- предметную область;
- характер запросов;
- частоту изменений;
- требования к истории;
- производительность;
- удобство сопровождения;
- платформенные особенности.

Нормальные формы — это инструмент анализа модели, а не соревнование по количеству таблиц.

---

# Денормализация

## Тема 17. Что такое денормализация

**Денормализация** — осознанное введение избыточности или хранение заранее вычисленных данных ради конкретной цели.

Чаще всего цель связана с производительностью чтения.

Например, сумма заказа теоретически может каждый раз вычисляться:

```text
SUM(order_items.quantity * order_items.unit_price)
```

Но система может также хранить:

```text
orders.total_amount
```

Это создаёт избыточность:

```text
итог можно вычислить из строк заказа,
но он одновременно хранится отдельно
```

Преимущество:

- итог можно читать без повторного вычисления.

Риск:

```text
order_items говорят 1000 ₽
orders.total_amount говорит 900 ₽
```

Теперь необходимо обеспечивать согласованность двух представлений одного факта.

---

## Тема 18. Когда денормализация оправдана

Денормализация может быть оправдана, если существует измеренная проблема.

Например:

- часто выполняемый тяжёлый запрос;
- дорогостоящие агрегаты;
- необходимость быстро читать подготовленные показатели;
- специализированный аналитический слой;
- требования к задержке ответа.

Плохая причина:

> JOIN кажется сложным, поэтому скопируем всё в одну таблицу.

Хорошая последовательность:

```text
1. построить корректную модель
2. получить реальную нагрузку
3. измерить проблему
4. выбрать способ оптимизации
5. при необходимости денормализовать
6. определить механизм поддержания согласованности
```

---

## Тема 19. Цена денормализации

Если один факт хранится в нескольких местах, необходимо понимать:

> кто отвечает за их синхронизацию?

Это может быть:

- приложение;
- транзакционная процедура;
- триггер;
- периодический процесс;
- ETL/ELT;
- механизм CDC;
- отдельный аналитический pipeline.

Денормализованные данные требуют сопровождения.

Поэтому денормализация — не бесплатное ускорение чтения.

Мы меняем:

```text
меньше вычислений при чтении
```

на:

```text
больше сложности при записи и сопровождении
```

---

# Операционная и аналитическая модель

## Тема 20. Нормализация и OLTP

В операционных системах часто важно:

- часто изменять данные;
- предотвращать противоречия;
- выполнять небольшие транзакции;
- хранить каждый факт в одном контролируемом месте.

Поэтому нормализованные модели особенно естественны для OLTP-нагрузки.

Но это не означает:

```text
OLTP = обязательно строго 3NF
```

Реальная модель может содержать осознанные исключения.

---

## Тема 21. Аналитические модели

Аналитические системы имеют другие задачи.

Например:

```text
выручка по магазинам
по дням
по категориям товаров
по городам
```

Для такой нагрузки могут использоваться специальные модели данных.

---

### Схема звезды

В центре находится **таблица фактов**.

Например:

```text
fact_sales
```

В ней могут храниться:

```text
date_key
store_key
product_key
customer_key
quantity
amount
```

Вокруг расположены таблицы измерений:

```text
dim_date
dim_store
dim_product
dim_customer
```

Схематично:

```text
           dim_date
              │
              │
dim_store ─ fact_sales ─ dim_product
              │
              │
         dim_customer
```

Измерения в схеме звезды нередко содержат намеренно удобное для аналитики представление атрибутов и могут быть менее нормализованы, чем OLTP-модель.

---

### Схема снежинки

В snowflake-модели измерения дополнительно нормализуются.

Например:

```text
dim_product
    │
    ▼
dim_category
```

Это уменьшает часть дублирования, но увеличивает число связей.

Поэтому:

- звезда обычно проще для аналитических запросов;
- снежинка может сильнее нормализовать измерения.

---

### One Big Table

В некоторых аналитических сценариях данные могут быть собраны в одну широкую таблицу.

Например:

```text
date
city
store
category
product
customer_segment
quantity
amount
...
```

Это может упростить определённые аналитические запросы.

Но появляется значительная избыточность.

Такой подход применяют осознанно под конкретный движок и нагрузку.

---

## Тема 22. Data Vault — это не просто денормализация

Data Vault решает другую задачу.

Это метод моделирования хранилища, ориентированный, в частности, на:

- интеграцию данных из разных источников;
- сохранение истории;
- прослеживаемость происхождения данных;
- устойчивость модели к изменениям источников.

Основные сущности классической модели:

```text
Hub
Link
Satellite
```

Упрощённо:

- **Hub** хранит бизнес-ключ;
- **Link** описывает связь между бизнес-сущностями;
- **Satellite** хранит описательные атрибуты и их историю.

Например:

```text
Hub_Customer
      │
      │
Link_Customer_Order
      │
      ▼
Hub_Order
```

А исторические характеристики могут находиться в satellites.

Data Vault нельзя просто классифицировать как:

> ещё один способ денормализовать таблицы ради скорости.

Наоборот, Raw Vault часто получается достаточно нормализованным и содержит множество таблиц.

Для удобного аналитического потребления поверх него обычно строятся дополнительные слои и витрины.

---

# Практический пример нормализации

## Тема 23. Исходная таблица

Представим таблицу:

```text
orders_raw
```

| order_id | order_date | customer_id | customer_name | product_id | product_name | quantity |
|---:|---|---:|---|---:|---|---:|
| 1 | 2026-10-01 | 10 | Анна | 100 | Кофе | 2 |
| 1 | 2026-10-01 | 10 | Анна | 101 | Молоко | 1 |
| 2 | 2026-10-02 | 20 | Иван | 100 | Кофе | 3 |

Здесь одновременно хранятся факты о:

```text
заказе
клиенте
товаре
позиции заказа
```

---

## Шаг 1. Выделяем клиентов

```text
customers
```

| customer_id | full_name |
|---:|---|
| 10 | Анна |
| 20 | Иван |

---

## Шаг 2. Выделяем товары

```text
products
```

| product_id | name |
|---:|---|
| 100 | Кофе |
| 101 | Молоко |

---

## Шаг 3. Выделяем заказы

```text
orders
```

| order_id | order_date | customer_id |
|---:|---|---:|
| 1 | 2026-10-01 | 10 |
| 2 | 2026-10-02 | 20 |

---

## Шаг 4. Выделяем позиции заказа

```text
order_items
```

| order_id | product_id | quantity |
|---:|---:|---:|
| 1 | 100 | 2 |
| 1 | 101 | 1 |
| 2 | 100 | 3 |

Теперь:

```text
customer_id → customer_name
```

хранится в `customers`.

```text
product_id → product_name
```

хранится в `products`.

Дата заказа хранится в `orders`.

Количество товара в конкретном заказе хранится в `order_items`.

Схема:

```text
customers
    │
    │ 1:N
    ▼
orders
    │
    │ 1:N
    ▼
order_items
    ▲
    │ N:1
    │
products
```

Один факт больше не приходится копировать в каждую строку.

---

# Как принимать решения при проектировании

Для каждого атрибута полезно задавать несколько вопросов.

### 1. Какой факт хранит этот столбец?

Например:

```text
product_name
```

— факт о товаре.

Значит, естественное место — `products`.

---

### 2. От какого ключа он зависит?

Например:

```text
quantity
```

в позиции заказа зависит от комбинации:

```text
order_id + product_id
```

а не просто от товара.

---

### 3. Не хранится ли один факт несколько раз?

Если номер телефона клиента повторяется в тысячах заказов, стоит проверить модель.

---

### 4. Что произойдёт при изменении значения?

Если изменение одного факта требует обновить сотни строк, возможно, присутствует нежелательная избыточность.

---

### 5. Что произойдёт при удалении строки?

Не приведёт ли удаление одного факта к случайной потере другого?

---

### 6. Нужна ли эта избыточность намеренно?

Иногда ответ — да.

Но тогда необходимо понимать:

- какую проблему она решает;
- как будет обеспечиваться согласованность.

---

# Платформенные особенности ссылочной целостности

Важно не переносить синтаксис и поведение внешних ключей между СУБД автоматически.

## PostgreSQL

PostgreSQL поддерживает референциальные действия, включая:

```text
NO ACTION
RESTRICT
CASCADE
SET NULL
SET DEFAULT
```

для соответствующих операций.

Поддерживаются и `DEFERRABLE`-ограничения.

Проверку подходящего deferrable constraint можно отложить до конца транзакции.

---

## Microsoft SQL Server

SQL Server поддерживает для внешних ключей действия:

```text
NO ACTION
CASCADE
SET NULL
SET DEFAULT
```

для удаления и обновления в поддерживаемых случаях.

При проектировании каскадов существуют дополнительные ограничения, например связанные с возможными путями каскадных действий.

Механизма `DEFERRABLE`, аналогичного PostgreSQL и Oracle, у обычных foreign key constraints SQL Server нет.

---

## MySQL/InnoDB

InnoDB поддерживает внешние ключи и референциальные действия, включая:

```text
RESTRICT
CASCADE
SET NULL
NO ACTION
```

для поддерживаемых операций.

Поведение и синтаксис необходимо проверять именно для InnoDB.

`DEFERRABLE` foreign keys в стиле PostgreSQL/Oracle в MySQL не поддерживаются.

---

## Oracle

Oracle поддерживает внешние ключи и откладываемую проверку `DEFERRABLE`-ограничений.

Для удаления родительских строк доступны, в частности:

```text
ON DELETE CASCADE
ON DELETE SET NULL
```

Но набор referential actions отличается от PostgreSQL, SQL Server и MySQL.

Например, универсального `ON UPDATE CASCADE` для обычного Oracle foreign key нет.

---

# Итоговые выводы

- Связи `1:1`, `1:N` и `M:N` отражают отношения между сущностями предметной области.
- Внешний ключ поддерживает ссылочную целостность между связанными таблицами.
- `CASCADE` — не просто удобная опция, а бизнес-решение с последствиями для зависимых данных.
- Поведение внешних ключей и поддерживаемые referential actions различаются между СУБД.
- Отложенная проверка ограничений поддерживается не одинаково на всех платформах.
- Нормализация помогает уменьшить нежелательное дублирование данных и устранять аномалии вставки, обновления и удаления.
- 1NF связана с корректным представлением атрибутов и отсутствием повторяющихся групп.
- 2NF устраняет частичные зависимости неключевых атрибутов от части составного кандидатного ключа.
- 3NF устраняет нежелательные транзитивные зависимости неключевых атрибутов.
- Суррогатный ключ не отменяет необходимость контролировать естественные бизнес-правила уникальности.
- Денормализация — осознанное введение избыточности ради конкретной цели, а не способ исправить неудобную модель без измерений.
- Схема звезды, снежинка, One Big Table и Data Vault решают разные задачи и не являются просто вариантами одной и той же денормализации.
- Хорошая модель определяется не количеством таблиц, а тем, насколько точно она отражает зависимости данных и требования системы.
