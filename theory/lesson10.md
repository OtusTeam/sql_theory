
# PostGIS: типы геоданных, расширения и пространственные запросы в PostgreSQL

## Превью / аннотация / краткое содержание

Занятие посвящено хранению и обработке пространственных данных в реляционных СУБД на примере PostgreSQL и расширения PostGIS.

Пространственные данные применяются в логистике, доставке, навигации, геоаналитике, картографических сервисах и системах мониторинга. Они позволяют хранить не только координаты объектов, но и их геометрическую форму, вычислять расстояния, определять пересечения, находить ближайшие объекты и проверять принадлежность точек заданным территориям.

Основные темы занятия:

- назначение PostGIS и его место в архитектуре PostgreSQL;
- подготовка окружения и подключение расширения;
- работа с системным каталогом и пространственными метаданными;
- типы `geometry` и `geography`;
- системы координат, SRID и преобразование координат;
- создание пространственных объектов и базовые геометрические функции;
- вычисление расстояний, длин и площадей;
- пространственные отношения и поиск объектов в заданном радиусе;
- основные типы пространственных объектов;
- GeoJSON как формат обмена геоданными;
- пространственные индексы и прикладные задачи геоаналитики.

Практические примеры приведены преимущественно для PostgreSQL/PostGIS. Дополнительно рассматриваются аналогичные возможности Microsoft SQL Server, MySQL/InnoDB и Oracle.

## Основные понятия

**Пространственные данные (Spatial Data)** — данные, описывающие положение, форму и пространственные отношения объектов.

**Геоданные (Geospatial Data)** — пространственные данные, привязанные к географическому пространству Земли.

**PostGIS** — расширение PostgreSQL, добавляющее пространственные типы данных, функции, операторы и возможности индексирования.

**Geometry** — тип PostGIS для хранения геометрических объектов и выполнения операций в системе координат, определяемой SRID.

**Geography** — тип PostGIS для геодезических вычислений с учётом кривизны Земли.

**SRID (Spatial Reference System Identifier)** — идентификатор системы пространственной привязки.

**WGS 84** — широко применяемая геодезическая система отсчёта, используемая в том числе для представления географических координат.

**EPSG:4326** — распространённая система координат на основе WGS 84, в которой координаты выражаются в градусах широты и долготы.

**Проекция** — математическое преобразование координат, позволяющее представлять поверхность Земли на плоскости.

**Point** — точка.

**LineString** — линия, состоящая из последовательности точек.

**Polygon** — полигон, ограниченный одним внешним кольцом и, при необходимости, внутренними кольцами.

**MultiPoint** — набор точек.

**MultiLineString** — набор линий.

**MultiPolygon** — набор полигонов.

**GeometryCollection** — коллекция геометрических объектов различных типов.

**PolyhedralSurface** — поверхность, представленная набором многоугольных граней.

**TIN (Triangulated Irregular Network)** — нерегулярная триангуляционная сеть.

**WKT (Well-Known Text)** — текстовый формат представления геометрических объектов.

**WKB (Well-Known Binary)** — бинарный формат представления геометрии.

**GeoJSON** — формат обмена пространственными данными на основе JSON.

**ST_SetSRID** — функция назначения геометрии идентификатора системы координат без изменения самих координат.

**ST_SRID** — функция получения SRID объекта.

**ST_Transform** — функция преобразования геометрии между системами координат.

**ST_MakePoint** — функция создания точки по координатам.

**ST_Distance** — функция вычисления минимального расстояния между пространственными объектами.

**ST_DWithin** — функция проверки нахождения объектов в пределах заданного расстояния.

**ST_Within** — функция проверки пространственного отношения «находится внутри».

**ST_Contains** — функция проверки отношения «содержит».

**ST_Intersects** — функция проверки пересечения объектов.

**ST_Buffer** — функция построения буферной области вокруг пространственного объекта.

**GiST (Generalized Search Tree)** — обобщённая индексная структура PostgreSQL, широко используемая для пространственного индексирования.

**KNN (K-Nearest Neighbors)** — поиск ближайших соседей.

**Bounding Box** — минимальный прямоугольный диапазон координат, охватывающий пространственный объект.

**Системный каталог** — набор системных таблиц и представлений PostgreSQL, содержащих метаданные объектов базы данных.

## Основная часть

### Тема 1. PostGIS как расширение для пространственных данных

PostgreSQL является реляционной СУБД с расширяемой архитектурой.

Расширения позволяют добавлять новые типы данных, функции, операторы, индексные методы и другие возможности без изменения основного SQL-интерфейса PostgreSQL.

Одним из наиболее известных расширений является PostGIS.

PostGIS добавляет поддержку пространственных объектов и операций над ними.

Например, обычный SQL позволяет сравнивать значения и выполнять арифметические операции:

```sql
SELECT 10 + 20;
```

PostGIS позволяет выполнять операции над геометрическими объектами:

```sql
SELECT ST_Distance(
    ST_MakePoint(0, 0),
    ST_MakePoint(3, 4)
);
```

Результат:

```text
5
```

Это расстояние в декартовой системе координат, а не расстояние между географическими точками на Земле.

#### Где используется PostGIS

Типичные задачи:

- определение ближайшего склада или пункта выдачи;
- поиск курьеров в заданном радиусе;
- проверка попадания адреса в зону доставки;
- хранение границ административных территорий;
- поиск пересечений маршрутов;
- расчёт площадей земельных участков;
- анализ зон покрытия связи;
- обработка координат транспортных средств;
- подготовка данных для картографических приложений.

Пример прикладной задачи:

> Найти все склады на расстоянии не более 5 километров от клиента.

Если координаты представлены просто двумя числовыми столбцами, разработчику потребуется самостоятельно реализовать расчёт расстояния и учитывать географические особенности координат.

PostGIS предоставляет соответствующие типы, функции и индексы.

#### PostGIS не является отдельной СУБД

Важно различать PostgreSQL и PostGIS.

PostgreSQL отвечает за:

- хранение таблиц и индексов;
- выполнение SQL;
- транзакции;
- управление конкурентным доступом;
- безопасность;
- резервное копирование;
- управление данными.

PostGIS расширяет PostgreSQL пространственными возможностями.

Поэтому для использования PostGIS не требуется отдельный сервер геоданных или отдельный контейнер PostGIS рядом с контейнером PostgreSQL.

Обычно используется один экземпляр PostgreSQL, в котором установлены необходимые файлы расширения.

После этого расширение подключается в нужной базе данных.

#### Другие пространственные СУБД курса

Пространственные данные поддерживает не только PostgreSQL.

| СУБД | Основные пространственные возможности |
|---|---|
| PostgreSQL/PostGIS | `geometry`, `geography`, функции `ST_*`, GiST/SP-GiST и другие пространственные индексы |
| SQL Server | `geometry`, `geography`, пространственные методы и spatial indexes |
| MySQL/InnoDB | пространственные типы, функции `ST_*`, R-tree spatial indexes |
| Oracle | `SDO_GEOMETRY`, Oracle Spatial, пространственные операторы и индексы |

При этом нельзя считать, что функции с похожими названиями имеют совершенно одинаковую семантику во всех четырёх СУБД.

Различаются правила обработки координат, системы отсчёта, возвращаемые единицы измерения, требования к геометрии и возможности индексирования.

### Тема 2. Настройка окружения и способы подключения

Для работы с PostGIS необходимо иметь экземпляр PostgreSQL, в серверную установку которого включены компоненты PostGIS.

Это может быть:

- PostgreSQL с установленными пакетами PostGIS;
- Docker-образ, содержащий PostgreSQL и PostGIS;
- управляемая PostgreSQL, поддерживающая расширение.

#### Подключение PostGIS

Если PostGIS установлен на уровне сервера, его можно подключить в базе:

```sql
CREATE EXTENSION IF NOT EXISTS postgis;
```

Команда регистрирует необходимые типы, функции, операторы и другие объекты расширения в текущей базе данных.

Важно: расширение подключается **в конкретной базе данных**, а не автоматически во всех базах экземпляра PostgreSQL.

Для выполнения команды необходимы соответствующие права.

Проверить установленную версию:

```sql
SELECT PostGIS_Full_Version();
```

В ответе отображается информация о PostGIS и некоторых используемых компонентах.

#### Работа в Docker

В учебном окружении удобно использовать Docker, поскольку он позволяет фиксировать версию PostgreSQL и PostGIS.

Например, можно запустить образ семейства `postgis/postgis`, выбрав совместимый поддерживаемый тег.

Пример для локальной лабораторной среды:

```bash
docker run -d \
  --name sql-postgis \
  -e POSTGRES_USER=student \
  -e POSTGRES_PASSWORD=change_me \
  -e POSTGRES_DB=sql_course \
  -p 127.0.0.1:5432:5432 \
  -v postgis_data:/var/lib/postgresql/data \
  postgis/postgis:17-3.5
```

Указанный тег является примером сочетания версий, а не требованием использовать именно эти версии. Перед развёртыванием следует проверить наличие и актуальность выбранного образа.

Путь постоянного хранения данных может отличаться в зависимости от версии образа PostgreSQL.

В рабочей среде рекомендуется фиксировать конкретную версию образа, а при необходимости — digest.

В приведённом примере:

- `sql-postgis` — имя контейнера;
- `student` — пользователь PostgreSQL;
- `sql_course` — создаваемая база данных;
- `5432` — порт PostgreSQL;
- `127.0.0.1:5432:5432` — публикация порта только на loopback-интерфейсе хоста;
- `postgis_data` — Docker volume для хранения данных.

Пароль `change_me` используется только как демонстрационное значение.

В учебном проекте курса развёртывание выполняется по отдельной Docker-инструкции. Если рабочий контейнер с PostGIS уже подготовлен, второй контейнер создавать не требуется.

#### Способы подключения

К PostgreSQL можно подключаться через различные клиенты:

- `psql`;
- pgAdmin;
- DBeaver;
- DataGrip;
- другие SQL-клиенты, поддерживающие PostgreSQL.

Например, из командной строки:

```bash
psql -h 127.0.0.1 -p 5432 -U student -d sql_course
```

Для работы внутри контейнера:

```bash
docker exec -it sql-postgis \
  psql -U student -d sql_course
```

В SQL-клиенте можно проверить наличие расширения:

```sql
SELECT extname, extversion
FROM pg_extension
WHERE extname = 'postgis';
```

Если запрос не возвращает строк, расширение не зарегистрировано в текущей базе.

Само наличие исполняемых файлов или пакета PostGIS на сервере ещё не означает, что расширение подключено к конкретной базе.

### Тема 3. Метаданные, системный каталог и управление расширениями

PostgreSQL хранит информацию об объектах базы данных в системном каталоге.

Это касается таблиц, столбцов, индексов, функций, расширений и других объектов.

Работа с метаданными особенно полезна при исследовании неизвестной базы данных или диагностике установленного расширения.

#### Просмотр расширений

Установленные в текущей базе расширения:

```sql
SELECT
    extname,
    extversion
FROM pg_extension
ORDER BY extname;
```

Доступные для установки расширения:

```sql
SELECT
    name,
    default_version,
    installed_version
FROM pg_available_extensions
ORDER BY name;
```

Здесь важно различать:

- расширение, доступное на сервере;
- расширение, установленное в текущей базе.

#### Просмотр таблиц

Использование системного каталога:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name
FROM pg_class AS c
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'p')
  AND n.nspname NOT IN (
      'pg_catalog',
      'information_schema'
  )
ORDER BY n.nspname, c.relname;
```

Здесь:

- `pg_class` содержит информацию об отношениях PostgreSQL;
- `pg_namespace` содержит информацию о схемах;
- `relkind = 'r'` соответствует обычной таблице;
- `relkind = 'p'` соответствует партиционированной таблице.

Для стандартного получения метаданных также можно использовать `information_schema`.

#### Пространственные метаданные

PostGIS предоставляет представление `geometry_columns`.

```sql
SELECT
    f_table_schema,
    f_table_name,
    f_geometry_column,
    coord_dimension,
    srid,
    type
FROM geometry_columns
ORDER BY f_table_schema, f_table_name;
```

Оно помогает определить:

- таблицу;
- геометрический столбец;
- размерность координат;
- SRID;
- тип геометрии.

Для географических столбцов предусмотрено представление `geography_columns`.

```sql
SELECT *
FROM geography_columns;
```

Важно учитывать, что эти представления отражают зарегистрированные пространственные столбцы и соответствующие метаданные. Они не заменяют проверку фактического качества данных внутри таблицы.

#### Нагрузка от просмотра метаданных

Графические SQL-клиенты используют системные каталоги для отображения схем, таблиц, индексов и зависимостей.

На больших базах интенсивное исследование метаданных иногда приводит к выполнению большого числа системных запросов.

Однако неверно утверждать, что графические клиенты всегда существенно нагружают PostgreSQL или что обращение к системным каталогам обязательно является дорогой операцией.

Стоимость зависит от конкретных запросов, числа объектов и поведения клиента.

Практический вывод: при исследовании сложных схем полезно уметь обращаться к метаданным непосредственно через SQL, особенно если требуется получить строго определённую информацию.

### Тема 4. Тип данных geometry и его логика

`geometry` — один из основных пространственных типов PostGIS.

Он позволяет хранить:

- точки;
- линии;
- полигоны;
- коллекции объектов;
- отдельные виды поверхностей и других геометрических структур.

Координаты геометрии интерпретируются в соответствии с используемой системой координат.

Важнейшая особенность: многие вычисления над `geometry`, включая `ST_Distance`, используют **плоскую декартову модель**.

Единицы измерения определяются системой координат.

#### Создание точки

```sql
SELECT ST_MakePoint(37.6173, 55.7558);
```

Результат представляет точку с координатами:

```text
POINT(37.6173 55.7558)
```

Функция принимает сначала X, затем Y.

Для привычных географических координат в EPSG:4326:

- X — долгота;
- Y — широта.

То есть в PostGIS при создании точки через `ST_MakePoint` обычно используется порядок:

```text
longitude, latitude
```

Перепутанные широта и долгота — распространённый источник ошибок в геоинформационных системах.

#### Создание точки с SRID

```sql
SELECT ST_SetSRID(
    ST_MakePoint(37.6173, 55.7558),
    4326
);
```

Здесь координатам назначается SRID 4326.

Для наглядного просмотра:

```sql
SELECT ST_AsEWKT(
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )
);
```

Результат:

```text
SRID=4326;POINT(37.6173 55.7558)
```

#### Создание таблицы с геометрией

```sql
CREATE TABLE city_objects (
    object_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    object_name TEXT NOT NULL,
    location geometry(Point, 4326) NOT NULL
);
```

Объявление:

```sql
geometry(Point, 4326)
```

задаёт ограничение на тип геометрии и SRID.

Это лучше, чем использование совершенно неограниченного `geometry`, если структура пространственных данных заранее известна.

Добавление объектов:

```sql
INSERT INTO city_objects (object_name, location)
VALUES
(
    'Объект 1',
    ST_SetSRID(ST_MakePoint(37.6173, 55.7558), 4326)
),
(
    'Объект 2',
    ST_SetSRID(ST_MakePoint(37.6050, 55.7500), 4326)
);
```

Просмотр:

```sql
SELECT
    object_id,
    object_name,
    ST_AsText(location) AS location_wkt
FROM city_objects;
```

#### Почему geometry(4326) нельзя считать метрической системой

Рассмотрим:

```sql
SELECT ST_Distance(
    ST_SetSRID(ST_MakePoint(37.0, 55.0), 4326),
    ST_SetSRID(ST_MakePoint(38.0, 55.0), 4326)
);
```

Результат:

```text
1
```

Это **один градус долготы**, а не один метр и не один километр.

В системе EPSG:4326 координаты выражаются в угловых единицах.

Следовательно, использовать:

```sql
ST_Distance(geometry_4326_a, geometry_4326_b)
```

для получения расстояния в метрах нельзя.

Для таких расчётов следует использовать `geography` или подходящую метрическую проекцию.

### Тема 5. SRID и преобразование систем координат

Одна и та же точка на Земле может иметь разные числовые координаты в разных системах координат.

Поэтому координаты необходимо интерпретировать вместе с информацией о пространственной системе отсчёта.

#### Что такое SRID

SRID идентифицирует пространственную систему, в которой представлены координаты.

Распространённые примеры:

| SRID | Назначение |
|---|---|
| 4326 | Географические координаты WGS 84 |
| 3857 | Web Mercator, широко используется в веб-картах |
| 32637 | WGS 84 / UTM zone 37N |
| 0 | Неизвестная или неуказанная система координат в контексте PostGIS |

SRID 3857 использует метры в качестве координатных единиц, но искажает расстояния и площади.

Поэтому нельзя считать Web Mercator универсальной метрической проекцией для точных геодезических вычислений.

Для локальных задач иногда используют подходящую региональную проекцию, выбранную с учётом расположения объектов и требований к точности.

#### ST_SRID

Функция возвращает SRID геометрии:

```sql
SELECT ST_SRID(
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )
);
```

Результат:

```text
4326
```

#### ST_SetSRID

`ST_SetSRID` назначает системе координат идентификатор.

```sql
SELECT ST_SetSRID(
    ST_MakePoint(37.6173, 55.7558),
    4326
);
```

**Функция не изменяет сами координаты.**

Если точка реально представлена в другой системе координат, простая замена SRID не делает данные корректными.

Например, такой запрос:

```sql
SELECT ST_SetSRID(
    ST_MakePoint(37.6173, 55.7558),
    3857
);
```

не переводит долготу и широту в Web Mercator.

Он только присваивает этим числам новую пространственную интерпретацию.

Это может привести к неправильным расстояниям и местоположению.

#### ST_Transform

Для настоящего преобразования используется `ST_Transform`.

```sql
SELECT ST_AsText(
    ST_Transform(
        ST_SetSRID(
            ST_MakePoint(37.6173, 55.7558),
            4326
        ),
        3857
    )
);
```

В этом случае числовые координаты действительно преобразуются из EPSG:4326 в EPSG:3857.

Принципиальное отличие:

| Функция | Что делает |
|---|---|
| `ST_SRID` | Показывает SRID |
| `ST_SetSRID` | Назначает SRID, не преобразуя координаты |
| `ST_Transform` | Преобразует координаты в другую систему |

При выполнении `ST_Transform` PostGIS использует компоненты библиотеки PROJ.

Возможность преобразования зависит от наличия и корректности определений соответствующих пространственных систем.

#### Почему важно правильно выбирать систему координат

Неподходящая система координат может приводить к:

- неправильным расстояниям;
- искажённым площадям;
- ошибкам пересечения объектов;
- неверным результатам пространственного поиска;
- некорректному отображению на карте.

Также нельзя просто объединять произвольные геометрии с различными SRID в одном пространственном расчёте.

Сначала необходимо обеспечить совместимую систему координат.

### Тема 6. Базовые геометрические функции

PostGIS предоставляет функции для создания, преобразования и анализа геометрических объектов.

#### Создание точек

```sql
SELECT ST_AsText(
    ST_MakePoint(10, 20)
);
```

Результат:

```text
POINT(10 20)
```

#### Создание линии

Линию можно получить из массива точек:

```sql
SELECT ST_AsText(
    ST_MakeLine(
        ARRAY[
            ST_MakePoint(0, 0),
            ST_MakePoint(10, 0),
            ST_MakePoint(10, 10)
        ]
    )
);
```

Результат:

```text
LINESTRING(0 0,10 0,10 10)
```

#### Создание полигона

Полигон можно создать из замкнутой линии.

```sql
SELECT ST_AsText(
    ST_MakePolygon(
        ST_MakeLine(
            ARRAY[
                ST_MakePoint(0, 0),
                ST_MakePoint(10, 0),
                ST_MakePoint(10, 10),
                ST_MakePoint(0, 10),
                ST_MakePoint(0, 0)
            ]
        )
    )
);
```

Результат:

```text
POLYGON((0 0,10 0,10 10,0 10,0 0))
```

Кольцо должно быть замкнуто, а для корректного полигона также необходимо соблюдать геометрические требования к его структуре.

Для создания геометрии из WKT можно использовать более компактный вариант:

```sql
SELECT ST_GeomFromText(
    'POLYGON((0 0,10 0,10 10,0 10,0 0))'
);
```

#### Вычисление длины

```sql
SELECT ST_Length(
    ST_GeomFromText(
        'LINESTRING(0 0,3 4)'
    )
);
```

Результат:

```text
5
```

Это длина в единицах системы координат геометрии.

Для `geometry` функция `ST_Length` вычисляет плоскую длину линейного объекта.

Она не является универсальной функцией вычисления периметра полигона. Для периметра используется `ST_Perimeter`.

#### Вычисление площади

```sql
SELECT ST_Area(
    ST_GeomFromText(
        'POLYGON((0 0,10 0,10 10,0 10,0 0))'
    )
);
```

Результат:

```text
100
```

Площадь выражена в квадратных единицах координат.

Для `geometry(4326)` результат не будет автоматически выражен в квадратных метрах.

#### Построение буферной области

`ST_Buffer` создаёт геометрическую область на заданном расстоянии от объекта.

```sql
SELECT ST_AsText(
    ST_Buffer(
        ST_MakePoint(0, 0),
        10
    )
);
```

Результатом будет приближение круга радиусом 10 координатных единиц в виде полигона.

Для линейных объектов `ST_Buffer` позволяет построить область вокруг линии.

Для точек — область вокруг точки.

Важно: буфер строится как геометрическое приближение. Его форма зависит от параметров функции и используемой системы координат.

Если построить буфер радиусом 100 вокруг `geometry(Point, 4326)`, значение 100 будет интерпретироваться в градусах, а не в метрах.

Для географических расчётов можно использовать подходящий тип `geography` или преобразование в корректную метрическую систему координат.

#### Центроид

`ST_Centroid` вычисляет геометрический центр объекта.

```sql
SELECT ST_AsText(
    ST_Centroid(
        ST_GeomFromText(
            'POLYGON((0 0,10 0,10 10,0 10,0 0))'
        )
    )
);
```

Результат:

```text
POINT(5 5)
```

Однако для сложного или вогнутого полигона центроид может находиться за его пределами.

Если необходима точка, гарантированно расположенная внутри поверхности, можно рассмотреть `ST_PointOnSurface`.

#### Пересечение объектов

```sql
SELECT ST_AsText(
    ST_Intersection(
        ST_GeomFromText(
            'POLYGON((0 0,4 0,4 4,0 4,0 0))'
        ),
        ST_GeomFromText(
            'POLYGON((2 2,6 2,6 6,2 6,2 2))'
        )
    )
);
```

Функция возвращает геометрическое пересечение двух объектов.

#### Объединение объектов

`ST_Union` возвращает геометрию, представляющую объединение входных объектов.

Это не то же самое, что обычный SQL `UNION`.

SQL `UNION` объединяет наборы строк, а `ST_Union` выполняет пространственную операцию над геометриями.

#### Проверка корректности геометрии

Для пространственных объектов важно не только наличие координат, но и корректность формы.

Например, самопересекающийся полигон может оказаться невалидным.

Проверка:

```sql
SELECT ST_IsValid(
    ST_GeomFromText(
        'POLYGON((0 0,2 2,0 2,2 0,0 0))'
    )
);
```

Для получения причины можно использовать:

```sql
SELECT ST_IsValidReason(
    ST_GeomFromText(
        'POLYGON((0 0,2 2,0 2,2 0,0 0))'
    )
);
```

В PostGIS существует `ST_MakeValid`, которая может исправлять определённые виды невалидной геометрии.

Но исправление способно изменить структуру объекта или вернуть другой геометрический тип, поэтому результат необходимо проверять.

### Тема 7. География как модель криволинейной поверхности Земли

Тип `geography` предназначен для вычислений над географическими объектами с учётом кривизны Земли.

Он особенно полезен для задач, связанных с расстояниями и радиусами в метрах.

#### geometry и geography

| Характеристика | geometry | geography |
|---|---|---|
| Модель измерений | Обычно плоская | Геодезическая, на сфере или сфероиде |
| Единицы расстояния | Единицы системы координат | Метры |
| Единицы площади | Квадратные единицы системы координат | Квадратные метры |
| Системы координат | Различные поддерживаемые системы | Поддерживаемые географические системы |
| Набор доступных функций | Более широкий | Более ограниченный |
| Типичные задачи | Геометрия, карты, локальный анализ | Расстояния, площади, радиусы на Земле |

Необходимо понимать, что `geography` не означает использование идеально точной физической модели Земли во всех операциях.

Для ряда функций применяются модели сферы или сфероида, а отдельные операции реализованы через приближённые вычисления.

#### Создание geography

```sql
SELECT ST_SetSRID(
    ST_MakePoint(37.6173, 55.7558),
    4326
)::geography;
```

Для хранения:

```sql
CREATE TABLE warehouses (
    warehouse_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    warehouse_name TEXT NOT NULL,
    location geography(Point, 4326) NOT NULL
);
```

Добавим несколько складов:

```sql
INSERT INTO warehouses (warehouse_name, location)
VALUES
(
    'Склад Центр',
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography
),
(
    'Склад Север',
    ST_SetSRID(
        ST_MakePoint(37.6200, 55.8000),
        4326
    )::geography
),
(
    'Склад Юг',
    ST_SetSRID(
        ST_MakePoint(37.6100, 55.7000),
        4326
    )::geography
);
```

#### Расстояние в метрах

```sql
SELECT ST_Distance(
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography,
    ST_SetSRID(
        ST_MakePoint(37.6200, 55.8000),
        4326
    )::geography
) AS distance_meters;
```

Результат будет выражен в метрах.

По умолчанию `ST_Distance` для geography выполняет геодезическое вычисление на сфероиде.

При передаче дополнительного параметра `false` используется более простая сферическая модель:

```sql
SELECT ST_Distance(
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography,
    ST_SetSRID(
        ST_MakePoint(37.6200, 55.8000),
        4326
    )::geography,
    false
);
```

В некоторых сценариях сферическая модель вычисляется быстрее, но может давать менее точный результат.

#### Что выбрать

`geometry` подходит, когда:

- используется подходящая проекция;
- выполняются геометрические операции;
- важен широкий набор пространственных функций;
- данные описывают локальную плоскую систему;
- необходима работа с определёнными инженерными объектами.

`geography` подходит, когда:

- координаты представляют широту и долготу;
- необходимо получать расстояния в метрах;
- объекты располагаются в разных географических регионах;
- требуется искать объекты в географическом радиусе;
- не хочется выбирать отдельную метрическую проекцию для каждого региона.

При этом тип `geography` не решает задачи маршрутизации по дорогам.

Расстояние между двумя точками на земной поверхности — это не то же самое, что расстояние или время движения по дорожной сети.

Для дорожной маршрутизации применяются отдельные графовые модели и инструменты, например pgRouting или внешние маршрутизаторы.

### Тема 8. Пространственные запросы и анализ в радиусе

Одна из самых распространённых задач геоаналитики — поиск объектов рядом с заданной точкой.

Например:

> Найти все склады в пределах 5 километров от клиента.

#### Простой расчёт расстояния

```sql
SELECT
    warehouse_id,
    warehouse_name,
    ST_Distance(
        location,
        ST_SetSRID(
            ST_MakePoint(37.6173, 55.7558),
            4326
        )::geography
    ) AS distance_meters
FROM warehouses;
```

Этот запрос возвращает расстояния до всех складов.

Для сортировки:

```sql
SELECT
    warehouse_name,
    ST_Distance(
        location,
        ST_SetSRID(
            ST_MakePoint(37.6173, 55.7558),
            4326
        )::geography
    ) AS distance_meters
FROM warehouses
ORDER BY distance_meters;
```

Но при большом количестве записей вычисление расстояний до всех объектов может оказаться дорогим.

#### Фильтрация через ST_Distance

Логически корректный вариант:

```sql
SELECT
    warehouse_id,
    warehouse_name
FROM warehouses
WHERE ST_Distance(
    location,
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography
) <= 5000;
```

Однако такое выражение не является предпочтительным способом использования пространственного индекса PostGIS для поиска в радиусе.

#### ST_DWithin

Для проверки расстояния лучше использовать `ST_DWithin`.

```sql
SELECT
    warehouse_id,
    warehouse_name
FROM warehouses
WHERE ST_DWithin(
    location,
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography,
    5000
);
```

Здесь `5000` означает 5000 метров.

Функция возвращает `true`, если расстояние между объектами не превышает заданный порог.

Одно из преимуществ `ST_DWithin` — возможность использовать пространственный индекс.

Функция включает предварительную проверку ограничивающих областей, которая помогает исключить заведомо неподходящие объекты.

#### Пространственный индекс

Создадим GiST-индекс:

```sql
CREATE INDEX idx_warehouses_location
ON warehouses
USING GIST (location);
```

Теперь запрос с `ST_DWithin` потенциально может использовать пространственный индекс для ускорения поиска.

Само наличие индекса не гарантирует его использование.

Оптимизатор учитывает размер таблицы, селективность условия, статистику и стоимость альтернативных планов.

Проверка:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    warehouse_id,
    warehouse_name
FROM warehouses
WHERE ST_DWithin(
    location,
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography,
    5000
);
```

#### Поиск ближайших соседей

PostGIS поддерживает оператор расстояния `<->`, который может применяться для KNN-поиска с GiST-индексом.

```sql
SELECT
    warehouse_id,
    warehouse_name
FROM warehouses
ORDER BY location <-> (
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography
)
LIMIT 3;
```

Для `geography` оператор `<->` использует сферическое расстояние, тогда как `ST_Distance` по умолчанию использует сфероид.

Если нужен точный порядок по сфероидальному расстоянию, можно отбирать кандидатов через KNN, а затем пересчитывать их расстояния с помощью `ST_Distance`.

Важно понимать, что приближённый отбор кандидатов не всегда гарантирует получение окончательного точного топ-N, если кандидатов выбрано недостаточно.

#### Пространственные отношения

Для работы с геометрией используются отношения:

| Функция | Назначение |
|---|---|
| `ST_Within(A, B)` | A находится внутри B согласно топологическому определению |
| `ST_Contains(A, B)` | A содержит B |
| `ST_Intersects(A, B)` | A и B имеют общие точки |
| `ST_Touches(A, B)` | A и B соприкасаются границами без пересечения внутренностей |
| `ST_Disjoint(A, B)` | A и B не пересекаются |
| `ST_Covers(A, B)` | Ни одна точка B не находится вне A |

Например:

```sql
SELECT ST_Within(
    ST_MakePoint(5, 5),
    ST_GeomFromText(
        'POLYGON((0 0,10 0,10 10,0 10,0 0))'
    )
);
```

Результат:

```text
true
```

Но у `ST_Within` существует важная особенность.

Если точка находится строго на границе полигона, результат `ST_Within(point, polygon)` будет `false`.

Для задачи, где граница должна считаться частью допустимой зоны, часто подходит `ST_Covers(polygon, point)`.

```sql
SELECT ST_Covers(
    ST_GeomFromText(
        'POLYGON((0 0,10 0,10 10,0 10,0 0))'
    ),
    ST_MakePoint(0, 5)
);
```

Результат:

```text
true
```

Правильный выбор функции зависит от бизнес-правила: считается ли объект на границе принадлежащим территории.

### Тема 9. Типология пространственных объектов

Пространственные данные не ограничиваются точками.

PostGIS поддерживает различные геометрические типы, используемые в картографии, логистике и инженерных моделях.

#### Point

Описывает одну точку.

```text
POINT(10 20)
```

Примеры:

- местоположение склада;
- координаты курьера;
- адрес клиента;
- точка установки датчика.

#### LineString

Описывает линию из последовательности вершин.

```text
LINESTRING(0 0,10 0,10 10)
```

Примеры:

- участок дороги;
- маршрут;
- линия связи;
- участок трубопровода.

LineString описывает геометрическую линию, но не обязательно содержит информацию о направлении движения, ограничениях поворотов и связанности дорожной сети.

#### Polygon

Описывает замкнутую поверхность с внешней границей и возможными отверстиями.

```text
POLYGON((0 0,10 0,10 10,0 10,0 0))
```

Примеры:

- зона доставки;
- территория города;
- земельный участок;
- зона покрытия;
- административный район.

Полигон может иметь внутренние кольца, представляющие исключённые участки.

#### MultiPoint

Набор точек:

```text
MULTIPOINT((0 0),(10 10),(20 20))
```

Применяется для представления множества точечных объектов как одной геометрии.

#### MultiLineString

Набор линий:

```text
MULTILINESTRING(
    (0 0,10 0),
    (20 0,20 10)
)
```

Может применяться для составных маршрутов, дорожных или инженерных объектов.

#### MultiPolygon

Набор полигонов:

```text
MULTIPOLYGON(
    ((0 0,4 0,4 4,0 4,0 0)),
    ((10 10,14 10,14 14,10 14,10 10))
)
```

Подходит, например, для территорий, состоящих из нескольких несвязанных участков.

#### GeometryCollection

Коллекция геометрических объектов различных типов.

```text
GEOMETRYCOLLECTION(
    POINT(0 0),
    LINESTRING(0 0,10 10)
)
```

Позволяет объединять неоднородные геометрии.

#### PolyhedralSurface и TIN

Для более сложных пространственных и инженерных моделей PostGIS поддерживает типы поверхностей.

`PolyhedralSurface` представляет набор многоугольных граней.

`TIN` представляет поверхность в виде сети треугольников.

Они могут применяться в моделировании рельефа и инженерных конструкций.

Однако поддержка операций над сложными поверхностями отличается от поддержки обычных двумерных объектов.

Нельзя предполагать, что любая функция PostGIS одинаково работает со всеми пространственными типами и размерностями.

#### Размерность геометрии

Координаты могут содержать дополнительные компоненты:

- X и Y;
- Z — высоту или третью пространственную координату;
- M — дополнительную меру.

Например:

```sql
SELECT ST_AsText(
    ST_GeomFromText(
        'POINT Z (10 20 30)'
    )
);
```

Третья координата сама по себе не означает, что все операции станут трёхмерными.

Например, обычная `ST_Distance` для `geometry` вычисляет двумерное расстояние.

Для трёхмерных расстояний предусмотрена `ST_3DDistance`.

Необходимо осознанно выбирать функции с учётом размерности данных.

### Тема 10. GeoJSON как формат обмена пространственными данными

GeoJSON — формат представления географических объектов на основе JSON.

Он стандартизован RFC 7946 и широко применяется для обмена геоданными между веб-приложениями, картографическими сервисами и аналитическими системами.

GeoJSON позволяет описывать:

- геометрию;
- отдельный объект с атрибутами;
- коллекцию объектов.

#### Пример Point

```json
{
  "type": "Point",
  "coordinates": [37.6173, 55.7558]
}
```

В GeoJSON координаты географической точки записываются в порядке:

```text
[longitude, latitude]
```

#### Пример Polygon

```json
{
  "type": "Polygon",
  "coordinates": [
    [
      [37.60, 55.75],
      [37.63, 55.75],
      [37.63, 55.77],
      [37.60, 55.77],
      [37.60, 55.75]
    ]
  ]
}
```

#### GeoJSON Feature

`Feature` объединяет геометрию и её свойства.

```json
{
  "type": "Feature",
  "properties": {
    "warehouse_id": 1,
    "name": "Склад Центр"
  },
  "geometry": {
    "type": "Point",
    "coordinates": [37.6173, 55.7558]
  }
}
```

Коллекция таких объектов может быть представлена как `FeatureCollection`.

#### Экспорт геометрии в GeoJSON

В PostgreSQL/PostGIS используется функция `ST_AsGeoJSON`.

```sql
SELECT ST_AsGeoJSON(
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )
);
```

Результат:

```json
{
  "type": "Point",
  "coordinates": [37.6173, 55.7558]
}
```

#### Формирование Feature

В современных версиях PostGIS доступна форма `ST_AsGeoJSON`, принимающая запись таблицы.

Например:

```sql
SELECT ST_AsGeoJSON(w.*)
FROM (
    SELECT
        warehouse_id,
        warehouse_name,
        location::geometry AS geom
    FROM warehouses
) AS w;
```

Она позволяет сформировать GeoJSON Feature на основе строки с геометрическим столбцом.

Точный набор атрибутов и формат результата зависят от переданных столбцов и параметров функции.

#### Преобразование GeoJSON в geometry

Для импорта можно использовать `ST_GeomFromGeoJSON`.

```sql
SELECT ST_GeomFromGeoJSON(
    '{
      "type": "Point",
      "coordinates": [37.6173, 55.7558]
    }'
);
```

Функция предназначена для разбора GeoJSON-фрагмента геометрии, а не произвольного полного документа FeatureCollection.

Для импорта коллекций и их свойств может потребоваться предварительная обработка JSON.

#### Системы координат в GeoJSON

RFC 7946 определяет географические координаты на основе WGS 84 с порядком долгота/широта.

Для корректного обмена геоданными геометрии из других проекций необходимо предварительно преобразовать.

Например:

```sql
SELECT ST_AsGeoJSON(
    ST_Transform(geom, 4326)
)
FROM spatial_objects;
```

Этот пример предполагает существование таблицы `spatial_objects` со столбцом `geom`, содержащим геометрию с корректно заданным исходным SRID.

Сам формат JSON не гарантирует корректности пространственных данных.

Необходимо проверять:

- правильность порядка координат;
- систему координат;
- корректность геометрии;
- соответствие структуры контракту;
- обработку пустых и отсутствующих значений.

### Тема 11. Прикладные задачи пространственного анализа

Рассмотрим несколько типичных задач на примере условной платформы доставки.

#### Задача 1. Поиск ближайшего склада

Есть таблица складов:

```sql
CREATE TABLE delivery_warehouses (
    warehouse_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    warehouse_name TEXT NOT NULL,
    location geography(Point, 4326) NOT NULL
);
```

Добавим данные:

```sql
INSERT INTO delivery_warehouses (
    warehouse_name,
    location
)
VALUES
(
    'Склад Центр',
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography
),
(
    'Склад Север',
    ST_SetSRID(
        ST_MakePoint(37.6200, 55.8000),
        4326
    )::geography
),
(
    'Склад Юг',
    ST_SetSRID(
        ST_MakePoint(37.6100, 55.7000),
        4326
    )::geography
);
```

Необходимо найти ближайший склад относительно точки клиента.

```sql
WITH customer_location AS (
    SELECT ST_SetSRID(
        ST_MakePoint(37.6150, 55.7600),
        4326
    )::geography AS location
)
SELECT
    w.warehouse_id,
    w.warehouse_name,
    ROUND(
        ST_Distance(
            w.location,
            c.location
        )::numeric,
        2
    ) AS distance_meters
FROM delivery_warehouses AS w
CROSS JOIN customer_location AS c
ORDER BY distance_meters
LIMIT 1;
```

Запрос рассчитывает геодезическое расстояние до каждого склада и возвращает ближайший.

Для большой таблицы необходимо рассмотреть GiST-индекс и KNN-поиск.

```sql
CREATE INDEX idx_delivery_warehouses_location
ON delivery_warehouses
USING GIST (location);
```

Пример KNN:

```sql
SELECT
    warehouse_id,
    warehouse_name
FROM delivery_warehouses
ORDER BY location <-> (
    ST_SetSRID(
        ST_MakePoint(37.6150, 55.7600),
        4326
    )::geography
)
LIMIT 1;
```

Этот вариант использует сферическую метрику оператора `<->`.

Если требуется точное ранжирование по сфероиду, результаты необходимо оценивать соответствующим способом.

Кроме того, ближайший по прямой склад не всегда является ближайшим по дорожной сети.

#### Задача 2. Проверка зоны доставки ресторана

Пусть у ресторана есть географическая точка и радиус доставки.

```sql
CREATE TABLE restaurants (
    restaurant_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    restaurant_name TEXT NOT NULL,
    location geography(Point, 4326) NOT NULL,
    delivery_radius_meters INTEGER NOT NULL
        CHECK (delivery_radius_meters > 0)
);
```

Добавим ресторан:

```sql
INSERT INTO restaurants (
    restaurant_name,
    location,
    delivery_radius_meters
)
VALUES (
    'Ресторан Центр',
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography,
    3000
);
```

Проверим, может ли ресторан обслужить клиента.

```sql
SELECT
    restaurant_id,
    restaurant_name,
    ST_DWithin(
        location,
        ST_SetSRID(
            ST_MakePoint(37.6300, 55.7600),
            4326
        )::geography,
        delivery_radius_meters
    ) AS delivery_available
FROM restaurants;
```

Функция возвращает логическое значение.

Если радиус доставки одинаков для всех ресторанов, индексирование такого поиска обычно проще.

Если радиус различается между строками, использование пространственного индекса зависит от формы запроса и стратегии выполнения.

При необходимости могут применяться дополнительные ограничения по максимальному радиусу, предварительная фильтрация и другие способы оптимизации.

Важно: радиус геодезического расстояния — только упрощённая модель зоны доставки.

В реальном сервисе зона может зависеть от:

- дорожной сети;
- рек и других препятствий;
- районов города;
- доступности курьеров;
- времени доставки;
- административных и коммерческих ограничений.

Такие зоны часто хранятся как заранее рассчитанные полигоны или определяются внешним маршрутизатором.

#### Задача 3. Проверка попадания клиента в полигон доставки

Предположим, зона доставки задана не окружностью, а полигоном.

```sql
CREATE TABLE delivery_zones (
    zone_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    zone_name TEXT NOT NULL,
    area geometry(Polygon, 4326) NOT NULL
);
```

Добавим условную территорию:

```sql
INSERT INTO delivery_zones (zone_name, area)
VALUES (
    'Центральная зона',
    ST_GeomFromText(
        'POLYGON((
            37.60 55.74,
            37.64 55.74,
            37.64 55.77,
            37.60 55.77,
            37.60 55.74
        ))',
        4326
    )
);
```

Проверим точку клиента:

```sql
SELECT
    zone_id,
    zone_name
FROM delivery_zones
WHERE ST_Covers(
    area,
    ST_SetSRID(
        ST_MakePoint(37.6150, 55.7550),
        4326
    )
);
```

`ST_Covers` подходит для сценария, в котором точка на границе тоже считается находящейся в зоне обслуживания.

Для ускорения пространственных запросов создадим индекс:

```sql
CREATE INDEX idx_delivery_zones_area
ON delivery_zones
USING GIST (area);
```

Здесь обе геометрии имеют SRID 4326.

Для топологической проверки это допустимо: операция определяет взаимное расположение геометрий в одной системе координат.

Однако полигон с прямыми сторонами в координатах долготы и широты не всегда соответствует геодезическим линиям на поверхности Земли. Это нужно учитывать при построении сложных или протяжённых территорий.

#### Задача 4. Зоны покрытия базовых станций

Предположим, имеются базовые станции связи.

Каждая станция описывается:

- идентификатором;
- координатами;
- радиусом покрытия.

```sql
CREATE TABLE base_stations (
    station_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    location geography(Point, 4326) NOT NULL,
    coverage_radius_meters INTEGER NOT NULL
        CHECK (coverage_radius_meters > 0)
);
```

Добавим станции:

```sql
INSERT INTO base_stations (
    location,
    coverage_radius_meters
)
VALUES
(
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography,
    3000
),
(
    ST_SetSRID(
        ST_MakePoint(37.6500, 55.7800),
        4326
    )::geography,
    2500
);
```

Создадим таблицу клиентов:

```sql
CREATE TABLE coverage_clients (
    client_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    location geography(Point, 4326) NOT NULL
);
```

Добавим клиентов:

```sql
INSERT INTO coverage_clients (location)
VALUES
(
    ST_SetSRID(
        ST_MakePoint(37.6200, 55.7600),
        4326
    )::geography
),
(
    ST_SetSRID(
        ST_MakePoint(37.9000, 55.9000),
        4326
    )::geography
);
```

Найдём клиентов, которые не попадают в радиус ни одной станции.

```sql
SELECT
    c.client_id
FROM coverage_clients AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM base_stations AS s
    WHERE ST_DWithin(
        s.location,
        c.location,
        s.coverage_radius_meters
    )
);
```

Здесь используется комбинация:

- `NOT EXISTS`;
- коррелированного подзапроса;
- пространственной функции `ST_DWithin`.

Запрос возвращает клиентов, для которых не существует ни одной станции, покрывающей их местоположение.

Это пример сочетания обычной реляционной логики с пространственными вычислениями.

Реальное радиопокрытие не является идеальной окружностью. Оно зависит от рельефа, зданий, мощности передатчика, частоты, антенн и других факторов.

Следовательно, такой запрос демонстрирует упрощённую геометрическую модель, а не полноценный расчёт радиосети.

#### Проверка плана выполнения

Для пространственных запросов важно использовать стандартные средства анализа PostgreSQL.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    warehouse_id,
    warehouse_name
FROM delivery_warehouses
WHERE ST_DWithin(
    location,
    ST_SetSRID(
        ST_MakePoint(37.6173, 55.7558),
        4326
    )::geography,
    5000
);
```

При анализе плана необходимо учитывать:

- `Seq Scan`;
- `Index Scan`;
- `Bitmap Index Scan`;
- `Filter`;
- `Index Cond`;
- количество фактических строк;
- количество повторений операций;
- время выполнения;
- обращения к буферам.

Для пространственного индекса предварительная проверка bounding box помогает сократить число кандидатов.

Но точная пространственная функция всё равно может потребоваться для окончательной проверки условия.

На маленькой таблице последовательное сканирование может быть быстрее индексного поиска.

Поэтому наличие пространственного индекса не означает, что любой пространственный запрос обязательно должен его использовать.

### Тема 12. Пространственные возможности других СУБД курса

Хотя основной практический материал посвящён PostGIS, остальные СУБД курса также позволяют хранить и обрабатывать пространственные данные.

#### Microsoft SQL Server

SQL Server поддерживает два основных пространственных типа:

- `geometry`;
- `geography`.

Работа с ними осуществляется через методы соответствующих типов.

Пример:

```sql
DECLARE @point1 geography =
    geography::Point(55.7558, 37.6173, 4326);

DECLARE @point2 geography =
    geography::Point(55.8000, 37.6200, 4326);

SELECT @point1.STDistance(@point2) AS distance_meters;
```

Важно: метод `geography::Point` в SQL Server принимает аргументы в порядке:

```text
latitude, longitude, SRID
```

Это отличается от распространённого способа создания точки в PostGIS через `ST_MakePoint(longitude, latitude)`.

SQL Server предоставляет методы:

- `STDistance`;
- `STIntersects`;
- `STWithin`;
- `STBuffer`;
- `STArea`;
- `STLength`.

Также поддерживаются пространственные индексы.

При использовании `geography` значение расстояния возвращается в единицах, определяемых пространственной системой; для SRID 4326 это метры.

Если пространственные объекты имеют несовместимые SRID, многие методы SQL Server возвращают `NULL`, а не выполняют автоматическое преобразование.

#### MySQL/InnoDB

MySQL поддерживает пространственные типы, включая:

- `POINT`;
- `LINESTRING`;
- `POLYGON`;
- `MULTIPOINT`;
- `MULTILINESTRING`;
- `MULTIPOLYGON`;
- `GEOMETRYCOLLECTION`.

Пример:

```sql
CREATE TABLE warehouses (
    warehouse_id BIGINT PRIMARY KEY,
    location POINT NOT NULL SRID 4326,
    SPATIAL INDEX idx_location (location)
) ENGINE = InnoDB;
```

MySQL/InnoDB поддерживает пространственные индексы.

Для вычисления расстояния между географическими точками может использоваться `ST_Distance` с подходящей пространственной системой или `ST_Distance_Sphere` для сферической модели.

Пример:

```sql
SELECT ST_Distance_Sphere(
    ST_SRID(POINT(37.6173, 55.7558), 4326),
    ST_SRID(POINT(37.6200, 55.8000), 4326)
) AS distance_meters;
```

При использовании географических систем координат в MySQL необходимо учитывать правила порядка координат и параметр `axis-order` при преобразовании из текстовых представлений.

Нельзя автоматически переносить примеры PostGIS в MySQL только потому, что используются функции с одинаковыми именами.

Для пространственного индексирования MySQL также важны SRID-ограничения столбцов.

#### Oracle

Oracle поддерживает пространственные данные через Oracle Spatial.

Основной объектный тип:

```text
SDO_GEOMETRY
```

Он содержит описание типа геометрии, SRID, координат и структуры объекта.

Для работы с пространственными данными доступны, в частности:

- `SDO_DISTANCE`;
- `SDO_WITHIN_DISTANCE`;
- `SDO_RELATE`;
- `SDO_NN`;
- `SDO_GEOM`;
- пространственные индексы.

Пример вычисления расстояния между географическими точками:

```sql
SELECT SDO_GEOM.SDO_DISTANCE(
    SDO_GEOMETRY(
        2001,
        4326,
        SDO_POINT_TYPE(37.6173, 55.7558, NULL),
        NULL,
        NULL
    ),
    SDO_GEOMETRY(
        2001,
        4326,
        SDO_POINT_TYPE(37.6200, 55.8000, NULL),
        NULL,
        NULL
    ),
    0.05,
    'unit=M'
) AS distance_meters
FROM dual;
```

Здесь:

- `2001` обозначает двумерную точечную геометрию;
- `4326` — SRID;
- `SDO_POINT_TYPE` содержит координаты;
- `0.05` — параметр допуска;
- `unit=M` задаёт метры как единицу результата.

Для пространственных запросов по таблицам в Oracle также используются специализированные индексы и операторы.

#### Сравнение подходов

| Возможность | PostgreSQL/PostGIS | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| Хранение точек | `geometry`, `geography` | `geometry`, `geography` | `POINT` | `SDO_GEOMETRY` |
| Хранение полигонов | Да | Да | Да | Да |
| Географические расстояния | `geography`, геодезические функции | `geography` | Географические SRS, `ST_Distance_Sphere` | Oracle Spatial |
| Пространственные индексы | GiST и другие | Spatial index | Spatial index (R-tree) | Spatial index |
| Проверка пересечения | `ST_Intersects` | `STIntersects` | `ST_Intersects` | `SDO_RELATE` |
| Поиск ближайших объектов | KNN и функции расстояния | Пространственные методы и индексы | Функции расстояния, индексы с ограничениями по оптимизации | `SDO_NN` |
| GeoJSON | `ST_AsGeoJSON`, `ST_GeomFromGeoJSON` | JSON и пространственные методы, с дополнительным преобразованием | GeoJSON-функции | JSON/GeoJSON и Oracle Spatial |

Общая идея остаётся одинаковой: пространственные типы и функции позволяют перенести значительную часть геообработки на уровень СУБД.

Однако реализация, синтаксис и оптимизация пространственных операций не являются полностью переносимыми между платформами.

## Итоговые выводы

1. **PostGIS превращает PostgreSQL в пространственно-ориентированную СУБД.** Расширение позволяет хранить геометрические и географические объекты, выполнять вычисления и применять пространственное индексирование непосредственно в SQL.

2. **Для работы с PostGIS не нужен отдельный сервер геоданных.** Расширение устанавливается в серверное окружение PostgreSQL и подключается к конкретной базе данных.

3. **Типы `geometry` и `geography` предназначены для разных моделей вычислений.** `geometry` широко используется для плоских операций, а `geography` — для геодезических расстояний и площадей на поверхности Земли.

4. **SRID определяет интерпретацию координат.** `ST_SetSRID` назначает идентификатор системы координат, а `ST_Transform` действительно преобразует значения координат.

5. **Единицы измерения имеют принципиальное значение.** Расстояние между `geometry` в EPSG:4326 не выражается автоматически в метрах. Неверный выбор системы координат может полностью исказить результаты расчётов.

6. **PostGIS предоставляет функции создания и анализа пространственных объектов.** Среди них `ST_MakePoint`, `ST_MakeLine`, `ST_Area`, `ST_Length`, `ST_Buffer`, `ST_Centroid`, `ST_Intersection` и другие.

7. **Для поиска объектов в заданном радиусе предпочтительна функция `ST_DWithin`.** Она позволяет использовать пространственные индексы и обычно эффективнее фильтрации по вычисленному `ST_Distance`.

8. **Пространственные отношения имеют точную семантику.** Например, `ST_Within` и `ST_Covers` по-разному обрабатывают объекты, находящиеся на границе полигона.

9. **Пространственные индексы ускоряют поиск, но требуют правильной формы SQL-запроса.** Для проверки эффективности необходимо анализировать фактические планы выполнения.

10. **GeoJSON обеспечивает обмен пространственными данными между системами.** При экспорте и импорте необходимо учитывать порядок координат, SRID и корректность геометрии.

11. **Пространственная обработка доступна во всех четырёх СУБД курса.** Однако различия типов, функций и методов индексирования требуют адаптации SQL под конкретную платформу.

Главный результат занятия — понимание того, что геоданные являются не просто набором координат, а отдельным классом структурированных данных с собственными типами, правилами вычислений и способами оптимизации.
