# Соединения, подзапросы, CTE и оконные функции в SQL

## Превью / аннотация / краткое содержание

На этом занятии мы разберём основные способы построения сложных SQL-запросов из нескольких источников и нескольких этапов обработки.

Рассмотрим:

- как работают `INNER JOIN`, `LEFT JOIN`, `RIGHT JOIN`, `FULL OUTER JOIN` и `CROSS JOIN`;
- чем условие `ON` отличается от фильтра в `WHERE`;
- почему соединение может неожиданно размножить строки;
- когда используются `USING`, `NATURAL JOIN` и self join;
- чем `UNION` отличается от `UNION ALL`;
- какие бывают подзапросы;
- чем коррелированный подзапрос отличается от некоррелированного;
- почему нельзя определять производительность подзапроса только по его внешнему виду;
- как CTE помогает разбивать большой запрос на понятные этапы;
- почему CTE не является автоматически временной таблицей;
- как работают рекурсивные CTE;
- как использовать оконные функции вместе с `JOIN`, подзапросами и CTE;
- как `FIRST_VALUE`, `LAST_VALUE`, `LAG`, `LEAD` и frame зависят от порядка строк.

Главная идея занятия:

> сложный SQL становится понятнее, когда мы сначала понимаем гранулярность каждого набора данных, а затем осознанно выбираем способ их соединения или преобразования.

# Основная часть

## Тема 1. Зачем соединять таблицы

В нормализованной реляционной базе связанные факты часто находятся в разных таблицах.

Например:

```text
customers
orders
order_items
products
payments
```

Информация о клиенте хранится в `customers`, а заказ — в `orders`.

Чтобы получить:

```text
номер заказа
+
имя клиента
```

необходимо связать две таблицы.

Например:

```sql
SELECT
    o.order_id,
    c.full_name
FROM orders AS o
JOIN customers AS c
    ON c.customer_id = o.customer_id;
```

`JOIN` формирует результат из строк нескольких источников на основании заданного условия.

Иногда соединение удобно представлять как **горизонтальное объединение** данных:

```text
orders
+
customers
=
строка с атрибутами заказа и клиента
```

Это полезная интуиция, но не формальное определение `JOIN`.

---

# Тема 2. INNER JOIN

`INNER JOIN` возвращает комбинации строк, для которых условие соединения является истинным.

Например:

```sql
SELECT
    o.order_id,
    c.customer_id,
    c.full_name
FROM orders AS o
INNER JOIN customers AS c
    ON c.customer_id = o.customer_id;
```

Если заказ:

```text
customer_id = 10
```

и существует клиент:

```text
customer_id = 10
```

строки могут быть соединены.

Если подходящей строки второй таблицы нет, такая комбинация в результат `INNER JOIN` не попадёт.

---

## INNER JOIN — не «пересечение таблиц»

Иногда его объясняют так:

> INNER JOIN возвращает пересечение двух таблиц.

Это слишком неточная формулировка.

`INTERSECT` действительно является операцией над двумя совместимыми наборами строк.

`JOIN` решает другую задачу:

> формирует комбинации строк из нескольких источников, удовлетворяющие условию соединения.

Например:

```sql
ON c.customer_id = o.customer_id
```

не требует, чтобы строки таблиц целиком были одинаковыми.

---

# Тема 3. Кардинальность соединения

Перед `JOIN` полезно понимать отношения между данными.

Например:

```text
Customer 1 ───── N Order
```

Если клиент имеет три заказа:

```text
Customer
---------
10 Анна
```

и:

```text
Order
---------
1001 customer=10
1002 customer=10
1003 customer=10
```

то после соединения:

```text
Анна 1001
Анна 1002
Анна 1003
```

строка клиента закономерно повторится три раза.

Это не дубликат в смысле ошибки.

Это следствие отношения:

```text
1:N
```

---

# Тема 4. Размножение строк при JOIN

Одна из самых частых ошибок в сложных запросах — неожиданное увеличение числа строк.

Представим:

```text
orders
payments
order_status_history
```

У одного заказа:

```text
2 платежа
```

и:

```text
5 записей истории статусов
```

Если написать:

```sql
FROM orders AS o
JOIN payments AS p
    ON p.order_id = o.order_id
JOIN order_status_history AS h
    ON h.order_id = o.order_id
```

для одного заказа может получиться:

```text
2 × 5 = 10 строк
```

потому что каждая строка `payments` комбинируется с каждой подходящей строкой истории.

---

## Почему это важно

После такого `JOIN` выражение:

```sql
SUM(p.amount)
```

может посчитать один и тот же платёж несколько раз.

Добавление:

```sql
DISTINCT
```

не обязательно исправляет смысл запроса.

Сначала необходимо понять:

```text
какая гранулярность каждой таблицы?
```

и:

```text
какую гранулярность должен иметь результат?
```

Например:

```text
orders                 → одна строка на заказ
payments               → несколько строк на заказ
order_status_history   → несколько строк на заказ
```

Если результат должен иметь:

```text
одну строку на заказ
```

часто необходимо сначала отдельно агрегировать дочерние наборы до уровня заказа, а затем соединять их.

---

# Тема 5. LEFT JOIN

`LEFT JOIN` сохраняет все строки левой таблицы.

Если соответствия справа нет, столбцы правой таблицы получают `NULL`.

Например:

```sql
SELECT
    c.customer_id,
    c.full_name,
    o.order_id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.customer_id;
```

Так можно увидеть и клиентов, у которых пока нет заказов.

Для них:

```text
o.order_id = NULL
```

---

# Тема 6. ON и WHERE при внешнем соединении

Это одно из самых важных различий при работе с `LEFT JOIN`.

Рассмотрим:

```sql
SELECT
    c.customer_id,
    o.order_id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.customer_id
WHERE o.current_status = 'DELIVERED';
```

Мы вроде бы написали `LEFT JOIN`, но затем условием:

```sql
WHERE o.current_status = 'DELIVERED'
```

удалили строки, в которых справа было:

```text
NULL
```

В результате клиенты без подходящего заказа исчезнут.

Запрос по смыслу может стать похожим на `INNER JOIN`.

---

## Если условие относится к сопоставлению строк

Например, нужны:

> все клиенты и только их доставленные заказы.

Тогда условие можно поместить в `ON`:

```sql
SELECT
    c.customer_id,
    o.order_id
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.customer_id
   AND o.current_status = 'DELIVERED';
```

Теперь все клиенты сохраняются.

---

## Главное правило

Не существует механического правила:

```text
условия второй таблицы всегда писать в ON
```

или:

```text
все фильтры всегда писать в WHERE
```

Нужно понимать семантику:

```text
ON    → какие строки двух источников считаются соответствующими
WHERE → какие строки уже сформированного набора оставить
```

Особенно сильно эта разница проявляется при outer joins.

---

# Тема 7. RIGHT JOIN

`RIGHT JOIN` симметричен `LEFT JOIN`.

Он сохраняет все строки правой таблицы.

Например:

```sql
A RIGHT JOIN B
```

часто можно переписать как:

```sql
B LEFT JOIN A
```

Поэтому в реальном коде многие команды предпочитают `LEFT JOIN`: так направление чтения запроса остаётся более привычным.

Но `RIGHT JOIN` сам по себе не является неправильным.

---

# Тема 8. FULL OUTER JOIN

`FULL OUTER JOIN` сохраняет:

- совпавшие строки;
- несовпавшие строки слева;
- несовпавшие строки справа.

Упрощённо:

```text
A
+
совпадения
+
B
```

Например:

```sql
SELECT ...
FROM source_a AS a
FULL OUTER JOIN source_b AS b
    ON b.external_id = a.external_id;
```

Это может быть полезно при сверке двух систем:

```text
есть только в A
есть в обеих
есть только в B
```

---

## Поддержка зависит от СУБД

`FULL OUTER JOIN` поддерживается, например, PostgreSQL, SQL Server и Oracle.

В MySQL нет обычного нативного `FULL OUTER JOIN`.

Если нужна аналогичная логика, её строят другими способами, например через комбинацию запросов и `UNION ALL` с корректной обработкой совпадений.

Поэтому запрос с `FULL JOIN` нельзя считать переносимым на все четыре платформы курса.

---

# Тема 9. CROSS JOIN

`CROSS JOIN` строит декартово произведение.

Если первая таблица содержит:

```text
3 строки
```

а вторая:

```text
4 строки
```

результат содержит:

```text
3 × 4 = 12 строк
```

Пример:

```sql
SELECT
    s.store_id,
    d.calendar_date
FROM stores AS s
CROSS JOIN calendar_days AS d;
```

Так можно получить:

```text
каждый магазин × каждый день
```

Это может быть совершенно правильной бизнес-задачей.

---

## CROSS JOIN не является автоматически ошибкой

Проблема возникает, если декартово произведение получилось случайно.

Например:

```text
1 000 000 строк
×
10 000 строк
```

теоретически дают огромное число комбинаций.

Поэтому всегда нужно понимать ожидаемую кардинальность результата.

---

# Тема 10. Self join

Self join — это не отдельная SQL-команда.

Это обычный `JOIN`, где одна таблица участвует в запросе несколько раз под разными псевдонимами.

Например, таблица:

```text
employees
```

может содержать:

```text
employee_id
manager_id
```

Тогда:

```sql
SELECT
    e.full_name AS employee_name,
    m.full_name AS manager_name
FROM employees AS e
LEFT JOIN employees AS m
    ON m.employee_id = e.manager_id;
```

Здесь:

```text
e
```

и:

```text
m
```

— два логических экземпляра одной таблицы.

Self join полезен для:

- непосредственного родителя;
- предыдущей версии;
- сопоставления строк одной таблицы;
- некоторых иерархических задач.

Но для произвольной глубины дерева одного self join недостаточно.

---

# Тема 11. ON

Самый универсальный способ задания условия соединения:

```sql
ON
```

Например:

```sql
JOIN customers AS c
    ON c.customer_id = o.customer_id
```

Условие может содержать не только равенство.

Например:

```sql
ON event_time >= valid_from
AND event_time < valid_to
```

То есть `JOIN` может быть не только equi-join.

---

# Тема 12. USING

Некоторые SQL-диалекты поддерживают:

```sql
USING (column_name)
```

Например:

```sql
SELECT ...
FROM orders
JOIN customers
USING (customer_id);
```

Это удобно, когда:

- столбец называется одинаково в обеих таблицах;
- именно он используется для соединения.

---

## USING меняет представление результата

При `USING` общий столбец обычно представлен в результате как один объединённый столбец, а не как две отдельные одноимённые колонки.

Это может быть удобно, но отличается от обычного `ON`.

---

## USING поддерживается не везде одинаково

PostgreSQL, MySQL и Oracle поддерживают join-синтаксис с `USING`.

Microsoft SQL Server в обычном T-SQL использует `ON`, а `JOIN ... USING (...)` не поддерживает.

Поэтому для максимально переносимого учебного SQL проще использовать:

```sql
ON a.id = b.id
```

---

# Тема 13. NATURAL JOIN

`NATURAL JOIN` автоматически использует столбцы с одинаковыми именами.

Например, если в двух таблицах есть:

```text
customer_id
```

СУБД может построить соединение по нему автоматически.

На первый взгляд это удобно.

---

## Почему NATURAL JOIN опасен

Представим, что сегодня таблицы имеют общий столбец:

```text
customer_id
```

а завтра в обе добавили:

```text
created_at
```

Теперь `NATURAL JOIN` может начать учитывать и этот столбец.

Запрос изменил семантику, хотя его текст не менялся.

Поэтому в прикладном SQL обычно безопаснее явно писать:

```sql
ON ...
```

---

## Платформенные различия

`NATURAL JOIN` поддерживается не всеми рассматриваемыми диалектами одинаково.

Например, SQL Server не предоставляет обычный `NATURAL JOIN`.

Это ещё одна причина не использовать его как основной стиль курса.

---

# Тема 14. Несколько JOIN подряд

SQL-запрос может соединять много источников:

```sql
SELECT ...
FROM orders AS o
JOIN customers AS c
    ON c.customer_id = o.customer_id
JOIN stores AS s
    ON s.store_id = o.store_id
LEFT JOIN deliveries AS d
    ON d.order_id = o.order_id;
```

Но количество `JOIN` само по себе не говорит о качестве запроса.

Плохой критерий:

```text
много JOIN → медленно
```

Хорошие вопросы:

```text
сколько строк приходит из каждого источника?
какая кардинальность связей?
какие фильтры применяются?
какие существуют индексы?
какой план выбрала СУБД?
```

---

# Тема 15. UNION

`UNION` объединяет результаты нескольких запросов **по строкам**.

Если `JOIN` условно расширяет строку столбцами, `UNION` можно представить как добавление строк одного результата к строкам другого.

Например:

```sql
SELECT email
FROM customers

UNION

SELECT email
FROM couriers;
```

Получаем единый набор email.

---

# Тема 16. Условия совместимости UNION

Запросы должны возвращать одинаковое количество столбцов.

Например:

```sql
SELECT customer_id, email
FROM customers

UNION

SELECT courier_id, email
FROM couriers;
```

имеет:

```text
2 столбца
+
2 столбца
```

Кроме этого, соответствующие выражения должны иметь совместимые типы, чтобы СУБД смогла определить общий тип результата.

Типы не обязаны буквально называться одинаково, но должны быть совместимы по правилам конкретной платформы.

---

## Имена столбцов

В результате имена столбцов обычно определяются первой частью составного запроса.

Например:

```sql
SELECT customer_id AS entity_id
FROM customers

UNION ALL

SELECT courier_id
FROM couriers;
```

результирующий столбец будет называться:

```text
entity_id
```

---

# Тема 17. UNION удаляет дубликаты

`UNION` применяет семантику множества и удаляет одинаковые строки результата.

Например:

```text
A:
1
2

B:
2
3
```

`UNION`:

```text
1
2
3
```

---

# Тема 18. UNION ALL сохраняет строки

`UNION ALL` не выполняет устранение одинаковых строк.

Для тех же данных:

```text
1
2
2
3
```

---

## Что выбирать

Если бизнес-задача допускает повторения и их не нужно удалять, обычно следует использовать:

```sql
UNION ALL
```

Преимущество не только в том, что это обычно требует меньше дополнительной работы.

Главное:

> `UNION` и `UNION ALL` имеют разную семантику.

Не стоит выбирать `UNION ALL` только потому, что он «быстрее», если бизнес-задача требует уникального множества.

И наоборот, не нужно использовать `UNION`, если удалять повторы не требуется.

---

# Тема 19. UNION не заменяет JOIN

Сравним.

`JOIN`:

```text
строка заказа
+
данные клиента
```

`UNION`:

```text
клиенты из системы A
+
клиенты из системы B
```

То есть:

```text
JOIN  → связывает столбцы связанных строк
UNION → объединяет совместимые наборы строк
```

Это разные операции.

---

# Тема 20. Подзапрос

**Подзапрос** — запрос, который находится внутри другого SQL-выражения.

Например:

```sql
SELECT *
FROM orders
WHERE total_amount > (
    SELECT AVG(total_amount)
    FROM orders
);
```

Внутренний запрос:

```sql
SELECT AVG(total_amount)
FROM orders
```

вычисляет среднюю сумму.

Внешний запрос выбирает заказы выше среднего.

---

# Тема 21. Скалярный подзапрос

Скалярный подзапрос должен вернуть:

```text
не более одной строки
и один столбец
```

Например:

```sql
SELECT
    order_id,
    total_amount,
    (
        SELECT AVG(total_amount)
        FROM orders
    ) AS avg_amount
FROM orders;
```

Один результат подзапроса используется как скалярное значение.

---

## Если строк несколько

Если скалярный контекст ожидает одно значение, а подзапрос возвращает несколько строк, запрос обычно завершается ошибкой.

Поэтому нельзя использовать скалярный подзапрос, если логика не гарантирует его гранулярность.

---

# Тема 22. Подзапрос в WHERE

Подзапрос часто используется в условии.

Например:

```sql
SELECT *
FROM orders
WHERE customer_id IN (
    SELECT customer_id
    FROM customers
    WHERE is_active = 1
);
```

Концептуально:

```text
получить активных клиентов
↓
оставить их заказы
```

Но оптимизатор может физически выполнить этот запрос совсем не в таком порядке.

---

# Тема 23. EXISTS

Для проверки существования связанной строки удобно использовать:

```sql
EXISTS
```

Например:

```sql
SELECT
    c.customer_id,
    c.full_name
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.customer_id
);
```

Получаем клиентов, у которых есть хотя бы один заказ.

Подзапрос ссылается на:

```text
c.customer_id
```

из внешнего запроса.

Следовательно, он является **коррелированным**.

---

# Тема 24. Коррелированный подзапрос

Коррелированный подзапрос использует значение из внешнего уровня запроса.

Например:

```sql
SELECT
    c.customer_id,
    c.full_name
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.customer_id
);
```

Внутренний запрос нельзя полностью понять независимо от текущей строки `customers`, потому что он использует:

```text
c.customer_id
```

---

# Тема 25. Некоррелированный подзапрос

Некоррелированный подзапрос не ссылается на текущую строку внешнего запроса.

Например:

```sql
SELECT *
FROM orders
WHERE total_amount > (
    SELECT AVG(total_amount)
    FROM orders
);
```

Внутренний:

```sql
SELECT AVG(total_amount)
FROM orders
```

можно рассмотреть отдельно.

---

# Тема 26. Миф: коррелированный подзапрос всегда выполняется для каждой строки

Частое объяснение:

> коррелированный подзапрос физически запускается отдельно для каждой строки внешнего запроса.

Это может происходить.

Но считать это обязательным поведением современной СУБД нельзя.

Оптимизатор может:

- преобразовать подзапрос в semijoin;
- decorrelate его;
- материализовать результат;
- выбрать другой эквивалентный физический план.

Например, MySQL умеет преобразовывать подходящие `IN` и `EXISTS`-подзапросы в semijoin.

Поэтому внешний вид SQL не определяет автоматически физический алгоритм.

---

# Тема 27. Миф: некоррелированный подзапрос обязательно выполняется ровно один раз

Это также слишком сильное утверждение.

Оптимизатор имеет право преобразовывать запрос.

Он может:

- вычислить результат;
- встроить запрос;
- материализовать его;
- перестроить план.

Поэтому корректнее говорить:

> некоррелированный подзапрос логически не зависит от текущей строки внешнего запроса.

А физическое выполнение определяется оптимизатором.

---

# Тема 28. Подзапрос в FROM

Подзапрос может выступать источником строк.

Например:

```sql
SELECT
    q.store_id,
    q.order_count
FROM (
    SELECT
        store_id,
        COUNT(*) AS order_count
    FROM orders
    GROUP BY store_id
) AS q
WHERE q.order_count >= 100;
```

Внутренний запрос формирует промежуточный набор:

```text
store_id
order_count
```

а внешний продолжает с ним работать.

Такой источник называют:

```text
derived table
```

или inline view в некоторых терминах платформ.

---

# Тема 29. Подзапрос или JOIN

Иногда одна бизнес-задача может быть выражена несколькими способами.

Например:

> получить клиентов, у которых есть заказы.

Через `EXISTS`:

```sql
SELECT c.*
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.customer_id
);
```

Через `JOIN`:

```sql
SELECT DISTINCT c.*
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.customer_id;
```

Эти формы похожи по цели, но не полностью одинаковы по семантике.

`JOIN` сначала формирует комбинации строк.

Если у клиента 10 заказов:

```text
клиент
×
10 заказов
```

может дать 10 строк, которые затем приходится устранять через `DISTINCT`.

`EXISTS` выражает более прямую мысль:

> интересует только наличие хотя бы одной строки.

Поэтому форму запроса следует выбирать прежде всего исходя из семантики.

А производительность подтверждать планом, а не правилом:

```text
EXISTS всегда быстрее JOIN
```

---

# Тема 30. CTE

**CTE — Common Table Expression** задаётся через:

```sql
WITH
```

Например:

```sql
WITH store_stats AS (
    SELECT
        store_id,
        COUNT(*) AS order_count,
        AVG(total_amount) AS avg_amount
    FROM orders
    GROUP BY store_id
)
SELECT *
FROM store_stats
WHERE order_count >= 100;
```

CTE даёт имя промежуточному query expression:

```text
store_stats
```

и позволяет использовать его в основном запросе.

---

# Тема 31. Зачем нужен CTE

CTE особенно полезен для декомпозиции.

Вместо:

```text
один гигантский запрос
из нескольких вложенных уровней
```

можно написать:

```text
шаг 1 → orders_base
шаг 2 → store_stats
шаг 3 → итоговый SELECT
```

Например:

```sql
WITH delivered_orders AS (
    SELECT
        order_id,
        store_id,
        total_amount
    FROM orders
    WHERE current_status = 'DELIVERED'
),
store_stats AS (
    SELECT
        store_id,
        COUNT(*) AS order_count,
        SUM(total_amount) AS amount
    FROM delivered_orders
    GROUP BY store_id
)
SELECT *
FROM store_stats;
```

Так проще читать смысл вычислений.

---

# Тема 32. CTE существует только внутри statement

CTE не создаёт постоянную таблицу базы.

Например:

```sql
WITH x AS (...)
SELECT *
FROM x;
```

После завершения statement объект:

```text
x
```

не появляется в схеме базы данных.

В следующем независимом запросе написать:

```sql
SELECT *
FROM x;
```

уже нельзя.

Это отличает CTE от:

- обычной таблицы;
- временной таблицы;
- представления.

---

# Тема 33. CTE не означает автоматически материализацию

Очень распространённый миф:

> CTE сначала всегда полностью вычисляется в отдельную временную таблицу, а затем читается основным запросом.

Для современных СУБД это неверно как универсальное правило.

Оптимизатор может:

- встроить CTE в основной запрос;
- вычислить отдельно;
- материализовать;
- использовать другие преобразования.

Поведение зависит от:

- СУБД;
- версии;
- запроса;
- количества обращений к CTE;
- свойств самого CTE.

---

# Тема 34. PostgreSQL и материализация CTE

В актуальном PostgreSQL поведение CTE гибкое.

Для side-effect-free CTE, используемого один раз, PostgreSQL может встроить его в основной запрос и оптимизировать совместно.

Можно встретить указания:

```sql
MATERIALIZED
```

и:

```sql
NOT MATERIALIZED
```

для управления поведением в подходящих случаях.

Например концептуально:

```sql
WITH x AS MATERIALIZED (
    ...
)
SELECT ...
FROM x;
```

или:

```sql
WITH x AS NOT MATERIALIZED (
    ...
)
SELECT ...
FROM x;
```

Поэтому старое правило:

> CTE в PostgreSQL всегда optimization fence

для современных версий неверно.

---

# Тема 35. SQL Server и CTE

В SQL Server документация прямо указывает:

> результат обычного CTE сам по себе не материализуется.

Повторное обращение к CTE может означать повторное использование его определения в плане.

Если действительно требуется физически сохранить промежуточный набор для нескольких последующих обращений, могут быть уместны:

- временные таблицы;
- другие физические промежуточные структуры.

То есть:

```text
CTE
```

и:

```text
temporary table
```

— не одно и то же.

---

# Тема 36. MySQL и CTE

MySQL optimizer может для CTE и derived table выбирать между:

```text
merge
```

и:

```text
materialization
```

в зависимости от запроса.

Поэтому и здесь правило:

```text
CTE всегда вычисляется отдельно
```

не работает.

---

# Тема 37. Oracle и WITH

В Oracle `WITH` также называют механизмом:

```text
subquery factoring
```

Оптимизатор может рассматривать именованный query block как:

- inline view;
- временно материализуемый набор;

в зависимости от выбранного плана.

Таким образом, во всех четырёх платформах нужно разделять:

```text
логическую структуру запроса
```

и:

```text
физический способ выполнения
```

---

# Тема 38. CTE не является автоматически быстрее подзапроса

Два варианта:

```sql
WITH x AS (
    SELECT ...
)
SELECT ...
FROM x;
```

и:

```sql
SELECT ...
FROM (
    SELECT ...
) AS x;
```

могут быть преобразованы оптимизатором в одинаковый или очень похожий план.

Поэтому выбирать CTE следует прежде всего ради:

- читаемости;
- декомпозиции;
- повторного логического использования;
- рекурсии;

а не потому, что:

```text
WITH быстрее подзапроса
```

Это нужно проверять на конкретном плане.

---

# Тема 39. Когда временная таблица отличается от CTE

Допустим, промежуточный результат:

- используется в нескольких отдельных SQL statements;
- должен индексироваться отдельно;
- должен пережить завершение одного запроса;
- полезно вычислить один раз и затем многократно исследовать.

Тогда CTE может быть не тем инструментом.

Можно рассмотреть временную таблицу.

Концептуально:

```text
CTE
→ логическая часть одного SQL statement

temporary table
→ отдельный объект, физически существующий некоторое время
```

Это разные механизмы.

---

# Тема 40. Рекурсивный CTE

Обычный self join позволяет пройти один известный уровень.

Например:

```text
employee → manager
```

Но если необходимо получить:

```text
сотрудник
→ руководитель
→ руководитель руководителя
→ ...
```

глубина заранее неизвестна.

Для этого можно использовать рекурсивный CTE.

---

# Тема 41. Структура рекурсивного CTE

Концептуально рекурсивный запрос состоит из двух частей:

```text
anchor member
+
recursive member
```

---

## Anchor member

Начальная выборка.

Например:

```text
корневой сотрудник
```

---

## Recursive member

Получает следующий уровень на основании предыдущего результата.

Концептуально:

```text
уровень 0
    ↓
уровень 1
    ↓
уровень 2
    ↓
...
```

---

# Тема 42. Пример рекурсивного CTE

Пусть:

```text
employees
----------------
employee_id
manager_id
full_name
```

Концептуальный запрос PostgreSQL/MySQL может выглядеть так:

```sql
WITH RECURSIVE employee_tree AS (
    SELECT
        employee_id,
        manager_id,
        full_name,
        0 AS depth
    FROM employees
    WHERE employee_id = 1

    UNION ALL

    SELECT
        e.employee_id,
        e.manager_id,
        e.full_name,
        t.depth + 1
    FROM employees AS e
    JOIN employee_tree AS t
        ON e.manager_id = t.employee_id
)
SELECT *
FROM employee_tree;
```

Первая часть:

```text
anchor
```

находит начало.

Вторая:

```text
recursive member
```

находит следующий уровень.

---

# Тема 43. Синтаксис рекурсии отличается между СУБД

## PostgreSQL

Использует:

```sql
WITH RECURSIVE
```

---

## MySQL

Также использует:

```sql
WITH RECURSIVE
```

---

## SQL Server

Использует CTE с самоссылкой, но отдельное слово:

```text
RECURSIVE
```

после `WITH` не пишется.

Кроме того, SQL Server имеет механизм ограничения глубины рекурсии через `MAXRECURSION`.

---

## Oracle

Oracle поддерживает recursive subquery factoring через `WITH`, но также без синтаксиса:

```text
WITH RECURSIVE
```

Кроме того, Oracle исторически имеет собственный механизм иерархических запросов:

```text
CONNECT BY
```

Современный Oracle поддерживает и recursive `WITH`, включая дополнительные возможности `SEARCH` и `CYCLE`.

---

# Тема 44. Рекурсия должна завершаться

Ошибочная рекурсивная логика может:

```text
A → B
B → C
C → A
```

создать цикл.

Поэтому при работе с иерархией необходимо понимать:

- может ли структура содержать циклы;
- существует ли ограничение глубины;
- как платформа обнаруживает или ограничивает рекурсию.

Некоторые СУБД предоставляют специальные средства.

Например:

- PostgreSQL поддерживает `CYCLE`;
- Oracle поддерживает `CYCLE`;
- SQL Server позволяет ограничить число уровней через `MAXRECURSION`.

Конкретные механизмы различаются.

---

# Тема 45. UNION или UNION ALL в рекурсии

Часто anchor и recursive member объединяются через:

```sql
UNION ALL
```

Почему?

Потому что:

```text
UNION
```

дополнительно выполняет устранение повторов.

Но использование `UNION ALL` требует понимать, не создаёт ли рекурсивная логика повторные строки или цикл.

Нельзя механически считать:

```text
UNION ALL всегда правильнее
```

только из-за производительности.

---

# Тема 46. Оконные функции после JOIN

Оконные функции часто особенно полезны после соединения нескольких таблиц.

Например:

> для каждого клиента пронумеровать его заказы от самого нового к старому.

```sql
SELECT
    c.customer_id,
    c.full_name,
    o.order_id,
    o.created_at,
    ROW_NUMBER() OVER (
        PARTITION BY c.customer_id
        ORDER BY o.created_at DESC, o.order_id DESC
    ) AS rn
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.customer_id;
```

Здесь:

```text
JOIN
```

сначала формирует связанный набор, а оконная функция рассчитывается уже относительно этого набора.

---

# Тема 47. Последняя строка в каждой группе

Один из распространённых паттернов:

> получить последний статус каждого заказа.

Есть таблица:

```text
order_status_history
--------------------
order_id
status
changed_at
```

Сначала нумеруем историю:

```sql
SELECT
    order_id,
    status,
    changed_at,
    ROW_NUMBER() OVER (
        PARTITION BY order_id
        ORDER BY changed_at DESC, order_status_history_id DESC
    ) AS rn
FROM order_status_history;
```

Затем оставляем:

```text
rn = 1
```

Через CTE:

```sql
WITH ranked_statuses AS (
    SELECT
        order_id,
        status,
        changed_at,
        ROW_NUMBER() OVER (
            PARTITION BY order_id
            ORDER BY changed_at DESC,
                     order_status_history_id DESC
        ) AS rn
    FROM order_status_history
)
SELECT
    order_id,
    status,
    changed_at
FROM ranked_statuses
WHERE rn = 1;
```

Это пример того, как CTE и оконная функция хорошо дополняют друг друга.

---

# Тема 48. ROW_NUMBER, RANK и DENSE_RANK

Кратко повторим различие.

Данные:

```text
100
90
90
80
```

`ROW_NUMBER`:

```text
100 → 1
90  → 2
90  → 3
80  → 4
```

`RANK`:

```text
100 → 1
90  → 2
90  → 2
80  → 4
```

`DENSE_RANK`:

```text
100 → 1
90  → 2
90  → 2
80  → 3
```

Выбор зависит от бизнес-смысла рейтинга.

---

# Тема 49. LAG и LEAD

`LAG` получает значение предыдущей строки.

Например:

```sql
LAG(current_status) OVER (
    PARTITION BY order_id
    ORDER BY changed_at
)
```

Можно сравнить:

```text
предыдущий статус
→
текущий статус
```

---

`LEAD` получает следующую строку.

Например:

```sql
LEAD(changed_at) OVER (
    PARTITION BY order_id
    ORDER BY changed_at
)
```

можно использовать для определения момента следующего изменения.

---

# Тема 50. FIRST_VALUE

`FIRST_VALUE` возвращает значение первой строки текущего window frame.

Например:

```sql
FIRST_VALUE(status) OVER (
    PARTITION BY order_id
    ORDER BY changed_at
)
```

может использоваться для получения первого статуса в истории.

Но важно помнить:

> функция работает относительно window frame.

---

# Тема 51. LAST_VALUE — частая ловушка

`LAST_VALUE` часто понимают так:

> вернуть последнее значение всего раздела.

Но это не обязательно произойдёт при стандартном frame.

Например:

```sql
LAST_VALUE(status) OVER (
    PARTITION BY order_id
    ORDER BY changed_at
)
```

может вернуть значение последней строки **текущего frame**, а его конец при стандартных настройках часто связан с текущей строкой или её peers.

В результате:

```text
LAST_VALUE
```

может неожиданно совпадать с текущим `status`.

---

# Тема 52. LAST_VALUE с явным frame

Если требуется последнее значение всего раздела, намерение лучше выразить явно:

```sql
LAST_VALUE(status) OVER (
    PARTITION BY order_id
    ORDER BY changed_at, order_status_history_id
    ROWS BETWEEN UNBOUNDED PRECEDING
             AND UNBOUNDED FOLLOWING
)
```

Теперь frame охватывает весь partition:

```text
первая строка
...
текущая строка
...
последняя строка
```

---

# Тема 53. PARTITION, ORDER и FRAME — три разных понятия

Для оконной функции полезно разделять:

```text
PARTITION BY
```

отвечает:

> какие строки относятся к одной независимой группе?

---

```text
ORDER BY
```

отвечает:

> в каком порядке рассматриваются строки внутри partition?

---

```text
FRAME
```

отвечает:

> какую часть упорядоченного partition использовать для текущего вычисления?

Например:

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
    ORDER BY created_at, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING
             AND CURRENT ROW
)
```

означает:

```text
partition → один клиент

order → его заказы по времени

frame → от первого заказа до текущего
```

---

# Тема 54. ROWS и RANGE

`ROWS` определяет frame через физические позиции строк относительно текущей строки.

Например:

```sql
ROWS BETWEEN 2 PRECEDING
         AND CURRENT ROW
```

означает:

```text
две предыдущие строки
+
текущая
```

---

`RANGE` работает с логикой значений `ORDER BY` и группами peers.

Поэтому:

```text
ROWS
```

и:

```text
RANGE
```

не являются взаимозаменяемыми словами.

Для классического построчного накопительного итога часто удобно явно использовать `ROWS`.

---

# Тема 55. CTE + JOIN + window function

Реальный запрос часто использует сразу несколько механизмов.

Например, задача:

> найти последний статус каждого заказа и показать клиента.

Можно разделить её:

```text
1. ранжировать историю
2. оставить последний статус
3. соединить с заказами
4. соединить с клиентами
```

Например:

```sql
WITH ranked_statuses AS (
    SELECT
        order_id,
        status,
        changed_at,
        ROW_NUMBER() OVER (
            PARTITION BY order_id
            ORDER BY changed_at DESC,
                     order_status_history_id DESC
        ) AS rn
    FROM order_status_history
),
current_statuses AS (
    SELECT
        order_id,
        status,
        changed_at
    FROM ranked_statuses
    WHERE rn = 1
)
SELECT
    o.order_id,
    c.full_name,
    cs.status,
    cs.changed_at
FROM orders AS o
JOIN customers AS c
    ON c.customer_id = o.customer_id
JOIN current_statuses AS cs
    ON cs.order_id = o.order_id;
```

Здесь CTE не добавляет новой бизнес-логики.

Он помогает разделить сложную задачу на понятные этапы.

# Тема 56. Не существует универсальной иерархии «JOIN лучше подзапроса лучше CTE»

Часто можно услышать:

```text
JOIN всегда быстрее подзапроса
```

или:

```text
CTE быстрее вложенного SELECT
```

или:

```text
подзапросы плохие
```

Такие правила ненадёжны.

Современный оптимизатор может преобразовывать SQL очень существенно.

Например:

```text
EXISTS
IN
JOIN
CTE
derived table
```

в определённых условиях могут привести к похожим физическим операциям.

Поэтому выбор конструкции определяется двумя вещами:

1. **семантикой** — правильно ли запрос выражает бизнес-задачу;
2. **реальным планом** — эффективно ли СУБД её выполняет.

---

# Тема 57. Читаемость — тоже характеристика SQL

Рассмотрим запрос из пяти уровней вложенных скобок.

Даже если он работает быстро, его сложно:

- проверить;
- изменить;
- отладить;
- передать другому разработчику.

CTE может сделать этапы явными:

```text
base_orders
↓
paid_orders
↓
customer_stats
↓
final_result
```

Но и обратная крайность плоха:

```text
20 CTE для простого запроса
```

тоже затрудняют чтение.

Цель:

> структура SQL должна помогать понимать преобразование данных.

# Тема 58. Практический пример: финансовая сводка

Задача:

> для каждого магазина показать количество доставленных заказов и сумму успешных платежей.

Наивное соединение:

```text
stores
→ orders
→ payments
```

может быть правильным, если кардинальность соответствует расчёту.

Но если на один заказ существует несколько платежей или попыток, сначала необходимо определить, **что именно означает успешная сумма**.

Например, если нужна сумма бизнес-платежей:

```sql
WITH delivered_orders AS (
    SELECT
        order_id,
        store_id
    FROM orders
    WHERE current_status = 'DELIVERED'
),
payment_stats AS (
    SELECT
        order_id,
        SUM(amount) AS paid_amount
    FROM payments
    WHERE current_status = 'PAID'
    GROUP BY order_id
)
SELECT
    d.store_id,
    COUNT(*) AS order_count,
    SUM(COALESCE(p.paid_amount, 0)) AS paid_amount
FROM delivered_orders AS d
LEFT JOIN payment_stats AS p
    ON p.order_id = d.order_id
GROUP BY d.store_id;
```

Здесь сначала:

```text
payments
```

приведены к гранулярности:

```text
одна строка на заказ
```

и только затем соединены с заказами.

Это защищает агрегат от случайного размножения строк.

# Тема 59. Практический пример: найти строки без соответствия

Задача:

> найти клиентов, у которых нет заказов.

Вариант через `NOT EXISTS`:

```sql
SELECT
    c.customer_id,
    c.full_name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.customer_id
);
```

Вариант через `LEFT JOIN`:

```sql
SELECT
    c.customer_id,
    c.full_name
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
```

Обе конструкции могут выражать требуемую задачу.

Производительность определяется реальным планом и данными.

# Тема 60. NULL и антисоединения

Необходимо особенно осторожно использовать:

```sql
NOT IN (...)
```

если подзапрос способен вернуть `NULL`.

Из-за трёхзначной логики результат может отличаться от ожидаемого.

Например, для проверки отсутствия связанной строки часто более явно выражает намерение:

```sql
NOT EXISTS
```

Но и здесь нельзя применять механическое правило:

```text
NOT EXISTS всегда быстрее NOT IN
```

Важны:

- семантика `NULL`;
- ограничения данных;
- оптимизатор;
- фактический план.

# Платформенные особенности

## PostgreSQL

Поддерживает:

```text
INNER JOIN
LEFT JOIN
RIGHT JOIN
FULL OUTER JOIN
CROSS JOIN
USING
NATURAL JOIN
```

CTE задаётся через:

```sql
WITH
```

для рекурсии:

```sql
WITH RECURSIVE
```

Современный PostgreSQL умеет как встраивать подходящие CTE в основной запрос, так и материализовать их.

В подходящих случаях доступны:

```text
MATERIALIZED
NOT MATERIALIZED
```

Также PostgreSQL поддерживает:

```text
SEARCH
CYCLE
```

для рекурсивных запросов.

---

## Microsoft SQL Server

Поддерживает основные:

```text
INNER
LEFT
RIGHT
FULL
CROSS JOIN
```

Для условий соединения используется:

```sql
ON
```

Синтаксиса:

```sql
JOIN ... USING (...)
```

в обычном T-SQL нет.

`NATURAL JOIN` также не является конструкцией T-SQL.

CTE задаётся через:

```sql
WITH
```

При рекурсивном CTE слово:

```text
RECURSIVE
```

не используется.

Результат обычного CTE сам по себе не является материализованной временной таблицей.

Для управления максимальной глубиной рекурсивного выполнения существует:

```text
MAXRECURSION
```

---

## MySQL/InnoDB

Поддерживает:

```text
INNER JOIN
LEFT JOIN
RIGHT JOIN
CROSS JOIN
USING
NATURAL JOIN
```

Но обычного нативного:

```text
FULL OUTER JOIN
```

нет.

Рекурсивные CTE используют:

```sql
WITH RECURSIVE
```

MySQL optimizer может для CTE и derived tables выбирать между:

```text
merging
materialization
```

Подходящие `IN` и `EXISTS`-подзапросы также могут преобразовываться в semijoin или antijoin.

---

## Oracle

Поддерживает основные виды соединений, включая:

```text
INNER
LEFT
RIGHT
FULL OUTER
CROSS JOIN
```

и ANSI join syntax с:

```text
ON
USING
NATURAL JOIN
```

CTE реализуется через:

```sql
WITH
```

и называется также:

```text
subquery factoring
```

Рекурсивный вариант не использует ключевое слово:

```text
RECURSIVE
```

и имеет собственные правила для anchor и recursive member.

Oracle также поддерживает исторический механизм иерархических запросов:

```text
CONNECT BY
```

и возможности:

```text
SEARCH
CYCLE
```

для recursive subquery factoring.

# Частые ошибки

## 1. Называть INNER JOIN пересечением таблиц

`JOIN` формирует комбинации связанных строк.

Операция множественного пересечения — это `INTERSECT`.

---

## 2. Не понимать кардинальность перед JOIN

Две таблицы `1:N` могут закономерно размножить строки.

Две независимые дочерние таблицы могут дать уже:

```text
N × M
```

строк на одну родительскую.

---

## 3. Исправлять размножение строк через DISTINCT

`DISTINCT` может скрыть ошибку, но не исправить неправильный расчёт агрегатов.

---

## 4. Переносить условие LEFT JOIN из ON в WHERE без проверки смысла

Так можно случайно удалить строки без соответствия и изменить семантику outer join.

---

## 5. Использовать NATURAL JOIN в прикладном коде

Добавление нового одноимённого столбца может незаметно изменить условие соединения.

---

## 6. Считать RIGHT JOIN «неправильным»

Он корректен, хотя запрос часто можно сделать привычнее через перестановку таблиц и `LEFT JOIN`.

---

## 7. Использовать UNION вместо UNION ALL «на всякий случай»

Удаление повторов должно быть частью бизнес-требования.

---

## 8. Считать UNION ALL всегда правильнее только потому, что он дешевле

Если результат должен быть множеством уникальных строк, семантика `UNION` нужна.

---

## 9. Считать коррелированный подзапрос обязательно циклом по строкам

Оптимизатор может преобразовать его.

---

## 10. Считать некоррелированный подзапрос обязательно вычисляемым ровно один раз

Физический план определяет оптимизатор.

---

## 11. Считать CTE временной таблицей

CTE — именованное выражение в рамках statement.

---

## 12. Считать CTE всегда материализованным

Это зависит от СУБД и плана.

---

## 13. Считать CTE автоматически быстрее подзапроса

Они могут привести к одному и тому же физическому плану.

---

## 14. Использовать WITH RECURSIVE одинаково во всех СУБД

SQL Server и Oracle не используют слово `RECURSIVE` в синтаксисе CTE.

---

## 15. Не контролировать завершение рекурсии

Циклические данные могут привести к ошибке или некорректному обходу.

---

## 16. Использовать ROW_NUMBER без полного порядка

Если значения `ORDER BY` совпадают, порядок между строками может быть неопределён.

Добавляйте tie-breaker, если результат должен быть воспроизводимым.

---

## 17. Использовать LAST_VALUE без понимания frame

`LAST_VALUE` работает с концом текущего frame, а не автоматически с последней строкой всего partition.

---

## 18. Считать JOIN всегда быстрее EXISTS

Это определяется конкретным планом и данными.

---

## 19. Использовать NOT IN без учёта NULL

`NULL` внутри набора влияет на трёхзначную логику.

---

# Как выбирать конструкцию

Если нужно:

```text
добавить к строке связанные данные
```

обычно рассматриваем:

```text
JOIN
```

---

Если нужно:

```text
объединить однотипные строки нескольких запросов
```

рассматриваем:

```text
UNION / UNION ALL
```

---

Если нужно:

```text
проверить существование связанных данных
```

часто естественен:

```text
EXISTS
```

---

Если нужно:

```text
вычислить отдельный набор внутри другого запроса
```

может подойти:

```text
подзапрос
```

---

Если нужно:

```text
разбить большой запрос на именованные логические этапы
```

может подойти:

```text
CTE
```

---

Если нужно:

```text
пройти неизвестное заранее число уровней иерархии
```

может подойти:

```text
рекурсивный CTE
```

---

Если нужно:

```text
сохранить строковую детализацию,
но выполнить расчёт относительно других строк
```

используем:

```text
оконные функции
```

---

# Итоговые выводы

- `JOIN` формирует комбинации строк нескольких источников по заданному условию; его нельзя сводить к понятию пересечения множеств.
- Перед соединением необходимо понимать гранулярность и кардинальность каждого источника.
- Соединение нескольких связей `1:N` может многократно увеличить число строк и исказить последующие агрегаты.
- `INNER JOIN` сохраняет только подходящие комбинации, а outer joins позволяют сохранить строки без соответствия.
- Положение условия в `ON` или `WHERE` особенно важно для семантики внешних соединений.
- `FULL OUTER JOIN` поддерживается не во всех СУБД курса: MySQL не имеет обычного нативного `FULL OUTER JOIN`.
- `USING` и `NATURAL JOIN` также платформозависимы; для прозрачного переносимого кода обычно удобнее явно писать `ON`.
- `CROSS JOIN` создаёт декартово произведение и может быть как намеренной операцией, так и причиной огромного результата.
- Self join — обычное соединение таблицы с самой собой под разными псевдонимами.
- `UNION` удаляет одинаковые строки, а `UNION ALL` сохраняет их; выбор определяется бизнес-смыслом результата.
- Подзапрос может быть скалярным, табличным, коррелированным или независимым от внешнего запроса.
- Корреляция описывает логическую зависимость запросов, но не гарантирует конкретный физический алгоритм выполнения.
- Современные оптимизаторы могут преобразовывать подзапросы в joins, semijoins, materialization и другие физические формы.
- CTE помогает структурировать сложный SQL, но не является автоматически временной таблицей или способом ускорения запроса.
- Стратегия materialization/inlining CTE зависит от СУБД и конкретного запроса.
- PostgreSQL и MySQL используют `WITH RECURSIVE`, а SQL Server и Oracle — другой синтаксис recursive CTE.
- Рекурсивный запрос должен иметь корректное начальное условие и способ завершения.
- Оконные функции позволяют выполнять аналитику без потери исходной гранулярности строк.
- `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `LAG` и `LEAD` зависят от правильно выбранного порядка.
- `FIRST_VALUE` и особенно `LAST_VALUE` необходимо использовать с пониманием window frame.
- `JOIN`, подзапрос и CTE нельзя ранжировать по производительности только по синтаксису — необходимо анализировать фактический план выполнения.
