
# Анализ и диагностика индексов в реляционных СУБД

## Превью / аннотация / краткое содержание

Занятие посвящено практической диагностике индексов, анализу их влияния на производительность запросов и обслуживанию структур хранения данных.

Наличие индекса не гарантирует ускорения SQL-запроса. Эффективность зависит от порядка ключей, селективности условий, актуальности статистики, физического состояния таблицы и решений оптимизатора.

Особое внимание уделяется PostgreSQL и механизму MVCC: обновление строк создаёт новые версии данных, а накопление мёртвых версий и состояние visibility map могут влиять на эффективность сканирования таблицы и индексного доступа.

На занятии рассматриваются:

- индекс как структура доступа к данным;
- диагностика эффекта индекса через план выполнения;
- последовательное и индексное сканирование;
- составные индексы и порядок ключей;
- покрывающие индексы и `Index Only Scan`;
- visibility map и проверка видимости строк;
- механизм MVCC и образование мёртвых версий;
- разрастание таблиц и индексов;
- `VACUUM`, `VACUUM FULL` и `ANALYZE`;
- автоматическое обслуживание через autovacuum;
- системные представления статистики;
- диагностика малоиспользуемых и избыточных индексов;
- отличия механизмов обслуживания PostgreSQL, SQL Server, MySQL/InnoDB и Oracle;
- методика измерения результата оптимизации.

Основные практические примеры выполняются на PostgreSQL.

## Основные понятия

**Индекс (Index)** — вспомогательная структура данных, используемая для ускорения определённых операций поиска, соединения, сортировки и чтения.

**B-tree** — сбалансированная древовидная индексная структура, поддерживающая поиск по равенству и диапазонам.

**Ключ индекса (Index Key)** — столбец или выражение, по которому организуются индексные записи.

**Составной индекс (Composite Index)** — индекс, содержащий несколько ключевых столбцов или выражений.

**Порядок ключей** — последовательность столбцов в определении составного индекса.

**Селективность** — характеристика доли строк, удовлетворяющих условию фильтрации.

**Покрывающий индекс (Covering Index)** — индекс, содержащий необходимые для определённого запроса значения.

**INCLUDE** — конструкция PostgreSQL и SQL Server для добавления в индекс неключевых столбцов.

**Seq Scan** — последовательное сканирование таблицы PostgreSQL.

**Parallel Seq Scan** — параллельное последовательное сканирование таблицы PostgreSQL.

**Index Scan** — индексный доступ с возможным обращением к строкам основной таблицы.

**Index Only Scan** — индексный доступ PostgreSQL, при котором необходимые значения можно получить из индекса, а обращения к heap зависят от видимости строк.

**Heap** — основная структура хранения строк обычной таблицы PostgreSQL.

**TID (Tuple Identifier)** — физический идентификатор версии строки PostgreSQL.

**MVCC (Multi-Version Concurrency Control)** — механизм управления конкурентным доступом через версии данных.

**Tuple** — запись или версия строки в физической организации PostgreSQL.

**Dead Tuple** — версия строки, которая больше не нужна для видимости транзакций и может быть очищена.

**Live Tuple** — версия строки, учитываемая как актуальная в соответствующей статистике.

**HOT Update (Heap-Only Tuple Update)** — оптимизация PostgreSQL, позволяющая при выполнении определённых условий обновлять строку без создания новых записей во всех индексах.

**Visibility Map** — служебная структура PostgreSQL, содержащая сведения о полностью видимых и полностью замороженных страницах heap.

**All-visible** — признак страницы, все версии строк которой видимы всем текущим и будущим транзакциям в соответствующем смысле PostgreSQL.

**Heap Fetches** — показатель плана, отражающий обращения к heap при Index Only Scan.

**Free Space Map (FSM)** — структура PostgreSQL, содержащая сведения о доступном свободном пространстве страниц.

**Bloat** — избыточное физическое пространство таблицы или индекса по сравнению с необходимым для хранения актуальных данных и ожидаемого запаса.

**VACUUM** — механизм PostgreSQL для обслуживания таблиц, удаления доступных для очистки мёртвых версий и сопутствующих операций.

**VACUUM FULL** — операция PostgreSQL, переписывающая таблицу для компактного размещения данных.

**ANALYZE** — команда сбора статистики для оптимизатора.

**Autovacuum** — механизм автоматического запуска VACUUM и ANALYZE в PostgreSQL.

**Cardinality Estimation** — оценка количества строк на этапах выполнения запроса.

**pg_stat_all_tables** — системное представление PostgreSQL со статистикой операций и обслуживания таблиц.

**pg_stat_user_tables** — аналогичная статистика для пользовательских таблиц.

**pg_stat_user_indexes** — представление со статистикой использования индексов пользовательских таблиц.

**pg_statio_user_tables** — представление со статистикой буферных обращений к пользовательским таблицам.

**pg_stats** — представление со статистическими характеристиками столбцов.

**pg_class** — системный каталог отношений PostgreSQL.

**pg_index** — системный каталог сведений об индексах.

**n_dead_tup** — оценка количества мёртвых версий строк.

**n_live_tup** — оценка количества живых строк.

**n_mod_since_analyze** — показатель числа изменений строк, учитываемых с последнего ANALYZE.

**idx_scan** — статистический счётчик индексных сканирований.

**idx_tup_read** — количество индексных записей, полученных посредством индекса в статистике PostgreSQL.

**idx_tup_fetch** — количество живых строк heap, полученных через соответствующий индексный доступ в статистике PostgreSQL.

**REINDEX** — перестроение индекса PostgreSQL.

**CREATE INDEX CONCURRENTLY** — создание индекса PostgreSQL с уменьшением блокирования конкурентных операций записи, но с дополнительными расходами и ограничениями.

**REINDEX CONCURRENTLY** — перестроение индекса с уменьшением влияния на конкурентные операции.

**Index Fragmentation** — характеристика физической организации индекса; её точное значение и способы измерения различаются между СУБД.

**Baseline** — исходный набор измерений, с которым сравниваются результаты оптимизации.

## Основная часть

### Тема 1. Индекс как структура доступа к данным

Индекс позволяет находить определённые строки без обязательного полного сканирования таблицы.

Наиболее распространённым индексным методом PostgreSQL является B-tree.

При поиске по ключу СУБД проходит по структуре дерева до нужного диапазона индексных записей.

Но само индексное дерево не содержит автоматически все значения строки.

В обычном PostgreSQL B-tree индексе хранятся ключи и физические ссылки на версии строк таблицы.

Если запросу нужны дополнительные столбцы, СУБД может обращаться к heap.

#### Пример

```sql
SELECT *
FROM orders
WHERE customer_id = 1001;
```

Если существует индекс:

```sql
CREATE INDEX idx_orders_customer
ON orders (customer_id);
```

PostgreSQL может найти соответствующие индексные записи и получить строки таблицы.

Однако оптимизатор не обязан выбирать индекс.

Если условие возвращает большую часть строк, последовательное сканирование может оказаться дешевле.

#### Индекс имеет стоимость

Индекс:

- занимает место;
- требует обслуживания при изменении данных;
- увеличивает расходы на INSERT, UPDATE и DELETE;
- может увеличивать объём WAL;
- потребляет место в буферном кеше.

Поэтому индексирование является компромиссом между производительностью чтения и стоимостью записи.

### Тема 2. Почему индекс может не использоваться

Предположим, индекс по `status` существует.

```sql
CREATE INDEX idx_orders_status
ON orders (status);
```

Запрос:

```sql
SELECT *
FROM orders
WHERE status = 'completed';
```

может использовать Seq Scan.

Возможные причины:

1. Подходящих строк слишком много.
2. Таблица небольшая.
3. Стоимость обращения к heap высока.
4. Индекс не покрывает нужные столбцы.
5. Статистика отражает низкую избирательность условия.
6. Индекс не соответствует конкретному выражению.
7. Оптимизатор оценивает другой план как более дешёвый.

Наличие Seq Scan не означает, что PostgreSQL игнорирует индекс ошибочно.

#### Функции над столбцами

Например:

```sql
SELECT *
FROM orders
WHERE lower(status) = 'completed';
```

Обычный B-tree индекс по `status` не обязательно подходит для такого выражения.

Можно создать индекс по выражению:

```sql
CREATE INDEX idx_orders_status_lower
ON orders (lower(status));
```

Но делать это следует только при наличии реальных запросов, которым такой индекс полезен.

#### Преобразования типов

Нельзя утверждать, что любое неявное приведение типа отключает индекс.

Например:

```sql
WHERE customer_id = '1001'
```

в PostgreSQL может преобразовать строковый литерал к числовому типу столбца и использовать индекс.

А выражение:

```sql
WHERE customer_id::text = '1001'
```

уже изменяет форму условия и может потребовать индекс по выражению или другой способ доступа.

Поэтому необходимо анализировать фактический план, а не применять абсолютные правила.

### Тема 3. Диагностика эффекта индекса

Основной подход:

1. Зафиксировать запрос.
2. Получить план без нового индекса.
3. Измерить время и обращения к данным.
4. Создать индекс.
5. Повторить измерения.
6. Сравнить результат.
7. Оценить стоимость обслуживания индекса.

В PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 1001;
```

#### Что показывает EXPLAIN ANALYZE

Важные показатели:

- тип сканирования;
- estimated rows;
- actual rows;
- loops;
- actual time;
- Execution Time;
- Buffers;
- Heap Fetches при Index Only Scan.

#### BUFFERS

Типичные показатели:

```text
shared hit
shared read
shared dirtied
shared written
```

`shared hit` означает, что страница найдена в shared buffers.

`shared read` означает, что потребовалось чтение страницы в буферный кеш PostgreSQL.

Но оно не доказывает физическое чтение накопителя: страница могла находиться в файловом кеше операционной системы.

Поэтому BUFFERS — важный показатель объёма логической работы с буферными страницами, а не прямой измеритель физических IOPS.

#### Индекс не обязан ускорять каждый запуск

Время зависит от:

- кеша;
- фоновой нагрузки;
- количества подходящих строк;
- состояния таблицы;
- параллельного выполнения;
- планирования;
- передачи результата клиенту.

Один запуск до создания индекса и один после него не позволяют сделать надёжный вывод.

Нужны повторения и сопоставимые условия эксперимента.

### Тема 4. Составные индексы и порядок полей

Составной индекс содержит несколько ключевых столбцов.

Например:

```sql
CREATE INDEX idx_tickets_number_passenger
ON tickets (ticket_no, passenger_name);
```

Индекс организован сначала по `ticket_no`, затем по `passenger_name` внутри соответствующих диапазонов первого ключа.

Для запроса:

```sql
SELECT *
FROM tickets
WHERE ticket_no = '123456';
```

такой индекс может быть эффективным.

Но запрос:

```sql
SELECT *
FROM tickets
WHERE passenger_name = 'Анна Иванова';
```

не обязательно сможет эффективно ограничить чтение того же индексного дерева.

#### Порядок ключей

Если основная нагрузка ищет пассажиров по имени, можно рассмотреть:

```sql
CREATE INDEX idx_tickets_passenger_number
ON tickets (passenger_name, ticket_no);
```

Это другой индекс с другой организацией ключей.

#### Принцип левого префикса

Для B-tree индексов равенство по ведущим столбцам обычно позволяет эффективно сузить диапазон поиска.

Например, индекс:

```text
(passenger_name, ticket_no)
```

хорошо соответствует условию:

```sql
WHERE passenger_name = 'Анна Иванова'
```

и:

```sql
WHERE passenger_name = 'Анна Иванова'
  AND ticket_no = '123456'
```

Однако правило левого префикса не абсолютно.

В PostgreSQL 18 поддерживается B-tree skip scan, позволяющий при определённых условиях использовать ограничения по последующим столбцам даже при отсутствии равенства по ведущему ключу.

Например, при малом числе разных значений первого столбца оптимизатор может выполнять серию поисков с разными значениями этого столбца.

Это не означает, что порядок ключей перестал быть важным.

Skip scan эффективен только в подходящих условиях.

#### Что ставить первым

Нет универсального правила «самый селективный столбец всегда первый».

Необходимо учитывать:

- равенства;
- диапазоны;
- сортировку;
- ведущие ключи частых запросов;
- количество различных значений;
- возможные skip scan;
- необходимость покрытия запроса.

Порядок текстовых условий `WHERE` не определяет порядок ключей индекса.

Например:

```sql
WHERE a = 1 AND b = 2
```

и:

```sql
WHERE b = 2 AND a = 1
```

обычно позволяют оптимизатору рассматривать одинаковые логические условия поиска.

### Тема 5. Покрывающие индексы

Покрывающий индекс содержит необходимые значения для определённого запроса.

Например:

```sql
SELECT
    passenger_name,
    ticket_no
FROM tickets
WHERE passenger_name = 'Анна Иванова';
```

Индекс:

```sql
CREATE INDEX idx_tickets_passenger_covering
ON tickets (passenger_name)
INCLUDE (ticket_no);
```

содержит:

- ключ поиска `passenger_name`;
- дополнительное значение `ticket_no`.

Это может позволить PostgreSQL выполнить Index Only Scan.

#### Ключевые и включённые столбцы

В PostgreSQL `INCLUDE` добавляет неключевые столбцы.

Они хранятся в индексе, но не участвуют в его поисковом порядке так же, как ключевые столбцы.

Если запрос также часто сортирует по `ticket_no`, может быть полезнее составной ключ:

```sql
CREATE INDEX idx_tickets_passenger_number
ON tickets (passenger_name, ticket_no);
```

Но два таких индекса не обязательно нужно создавать одновременно.

Они частично дублируют друг друга.

#### Стоимость покрытия

Покрывающий индекс может быть больше обычного.

Это приводит к:

- росту размера индекса;
- дополнительным расходам на изменение данных;
- увеличению работы WAL;
- расходу буферного кеша.

Поэтому покрывающий индекс оправдан прежде всего для важных и достаточно частых запросов.

### Тема 6. Index Scan и Index Only Scan

В PostgreSQL Index Scan использует индекс для поиска подходящих записей.

Обычно затем происходит обращение к heap.

Index Only Scan потенциально позволяет возвращать значения из индекса.

Но у PostgreSQL есть дополнительное требование: необходимо подтвердить видимость соответствующей версии строки.

#### Почему индекс не хранит полноценную информацию о видимости

Обычный B-tree индекс PostgreSQL не содержит всех MVCC-данных, необходимых для проверки видимости строки конкретной транзакции.

Поэтому даже если запросу нужны только индексируемые столбцы, СУБД иногда должна обращаться к heap.

#### Visibility map

Для оптимизации используется visibility map.

Она содержит сведения о страницах таблицы, включая признак all-visible.

Если heap-страница помечена как all-visible, PostgreSQL может избежать индивидуальной проверки видимости строк этой страницы.

Если признак отсутствует, требуется проверка heap.

При этом отсутствие признака не обязательно означает, что на странице фактически присутствуют невидимые строки.

Visibility map консервативна: отсутствие отметки означает, что PostgreSQL не располагает необходимой гарантией.

#### Heap Fetches

В плане:

```text
Index Only Scan
  Heap Fetches: 0
```

означает, что во время данного выполнения обращения к heap для соответствующих проверок не понадобились.

Если:

```text
Heap Fetches: 50000
```

то индекс содержал необходимые значения, но потребовалось множество проверок в heap.

Это может существенно повлиять на производительность.

Однако нельзя считать, что Index Only Scan с ненулевыми Heap Fetches автоматически хуже обычного Index Scan.

Необходимо сравнивать фактические метрики.

### Тема 7. MVCC и создание версий строк

PostgreSQL использует многоверсионное управление конкурентным доступом.

При UPDATE создаётся новая версия строки.

Прежняя версия может оставаться необходимой для уже выполняющихся транзакций.

Например:

```sql
UPDATE tickets
SET passenger_name = 'Анна Петрова'
WHERE ticket_no = '123456';
```

Для текущего пользователя изменение выглядит как замена значения.

Физически PostgreSQL создаёт новую версию строки.

Прежняя версия не обязательно сразу становится доступной для удаления.

#### Почему старая версия сохраняется

Предположим:

1. Транзакция A получила снимок данных.
2. Транзакция B обновила строку.
3. Транзакция B выполнила COMMIT.
4. Транзакция A продолжает чтение по старому снимку.

Транзакции A может требоваться прежняя версия строки.

Поэтому PostgreSQL не может немедленно удалить все старые версии после каждого UPDATE.

#### Dead tuples

Когда старая версия больше не нужна ни одной допустимой транзакции, она может быть очищена.

Такие версии обычно называют dead tuples.

Но важно различать:

- старую версию, которая ещё нужна активному снимку;
- мёртвую версию, доступную для очистки;
- версию, которая уже очищена;
- свободное пространство, оставшееся после очистки.

Нельзя считать все старые версии автоматически мёртвыми с точки зрения VACUUM.

### Тема 8. HOT Update и влияние индексов

PostgreSQL поддерживает оптимизацию HOT — Heap-Only Tuple Update.

Она позволяет при соблюдении условий обновлять строку без добавления новых записей в обычные индексы.

Например, таблица содержит:

```sql
CREATE TABLE customer_profiles (
    customer_id BIGINT PRIMARY KEY,
    customer_name TEXT NOT NULL,
    last_seen_at TIMESTAMPTZ
);
```

Если обновляется только `last_seen_at`, а соответствующий столбец не используется обычными индексами, PostgreSQL может выполнить HOT-update.

```sql
UPDATE customer_profiles
SET last_seen_at = clock_timestamp()
WHERE customer_id = 1;
```

Но для HOT также требуется возможность разместить новую версию на той же heap-странице.

Поэтому отсутствие индексируемых изменений не гарантирует HOT.

#### Как индекс влияет на HOT

Если создать:

```sql
CREATE INDEX idx_profiles_last_seen
ON customer_profiles (last_seen_at);
```

обновление `last_seen_at` обычно потребует изменения индексной структуры и лишит такую операцию возможности стандартного HOT-update.

Важный вывод:

**Даже индекс, редко используемый в SELECT, может существенно влиять на стоимость UPDATE.**

Поэтому перед созданием индекса нужно учитывать частоту изменения его ключевых и включённых столбцов.

#### Статистика HOT

PostgreSQL предоставляет показатели:

```sql
SELECT
    relname,
    n_tup_upd,
    n_tup_hot_upd
FROM pg_stat_user_tables
WHERE relname = 'customer_profiles';
```

Они помогают оценить, какая часть обновлений выполнялась через HOT.

При этом счётчики являются накопительной статистикой за период наблюдения и могут сбрасываться.

### Тема 9. Мёртвые строки и разрастание таблиц

При интенсивном UPDATE и DELETE могут накапливаться версии строк, которые больше не нужны.

Они занимают место в heap до очистки.

Если таблица содержит большое количество таких версий, возможны:

- рост физического объёма;
- увеличение количества страниц;
- дополнительная работа по очистке;
- изменение эффективности чтения;
- увеличение количества индексных записей и служебных структур.

Но bloat не следует определять просто как количество dead tuples.

#### Что такое bloat

Bloat — избыточный объём хранения по сравнению с полезными данными и необходимым запасом.

Например, после удаления 90% строк таблица может продолжать занимать почти прежний объём.

Обычный VACUUM может освободить место внутри файла для повторного использования, но файл не обязательно сразу уменьшится.

Это состояние может быть нормальным, если вскоре таблица снова будет заполнена.

Если же объём больше не нужен, возникает вопрос физического освобождения места.

#### Dead tuples не равны bloat

Мёртвые версии могут способствовать разрастанию.

Но физический размер также зависит от:

- свободного пространства страниц;
- fillfactor;
- размера строк;
- истории обновлений;
- размещения TOAST;
- организации индексов;
- распределения данных.

Поэтому одного показателя `n_dead_tup` недостаточно для точного измерения bloat.

### Тема 10. VACUUM

Обычный VACUUM обслуживает таблицы PostgreSQL.

Основные задачи:

- очистка мёртвых версий, которые можно безопасно удалить;
- возвращение освободившегося пространства в оборот;
- сопровождение служебной информации;
- обновление visibility map;
- предотвращение проблем с возрастом идентификаторов транзакций.

Пример:

```sql
VACUUM customer_profiles;
```

#### Что делает VACUUM с размером файла

Обычный VACUUM чаще освобождает пространство внутри таблицы для повторного использования.

Он не обязан уменьшать размер файла.

Но при определённых условиях PostgreSQL может вернуть операционной системе свободные страницы в конце отношения.

Поэтому утверждение «обычный VACUUM никогда не уменьшает файл» тоже неверно.

#### VACUUM и visibility map

VACUUM может пометить страницы как all-visible, если выполняются необходимые условия.

Это помогает Index Only Scan избегать обращений к heap.

Но VACUUM не гарантирует, что все страницы станут all-visible.

Например, долгие транзакции могут мешать признать некоторые версии строк видимыми всем.

#### VACUUM и блокировки

Обычный VACUUM обычно позволяет продолжать стандартные операции чтения и записи.

Но он не является полностью бесконфликтной операцией.

Существуют блокировки, ограничения и специальные режимы, в том числе `VACUUM FULL`.

### Тема 11. VACUUM FULL

`VACUUM FULL` переписывает таблицу для компактного размещения актуальных данных.

```sql
VACUUM FULL customer_profiles;
```

После операции физический размер таблицы может заметно уменьшиться.

Но у механизма существенные расходы.

#### Основные ограничения

`VACUUM FULL`:

- требует `ACCESS EXCLUSIVE`-блокировки;
- блокирует конкурентный доступ к таблице на время операции;
- создаёт значительную нагрузку на I/O;
- требует дополнительного дискового пространства для переписывания;
- может занимать продолжительное время;
- перестраивает связанные индексы.

Поэтому его не следует использовать как обычную ежедневную процедуру для всех таблиц.

#### Когда он уместен

Например, после удаления очень большой доли данных, если освободившееся пространство больше не потребуется и его необходимо вернуть файловой системе.

Но перед выполнением следует оценить:

- продолжительность;
- доступное место;
- допустимость блокировки;
- необходимость перестроения;
- возможность альтернативных решений.

В ряде случаев может быть полезнее обычный VACUUM, REINDEX или инструмент реорганизации с другими эксплуатационными свойствами.

### Тема 12. ANALYZE и статистика оптимизатора

`ANALYZE` собирает статистику, используемую планировщиком PostgreSQL.

```sql
ANALYZE customer_profiles;
```

Статистика помогает оценивать:

- количество строк;
- количество различных значений;
- долю NULL;
- распределение значений;
- селективность условий;
- стоимость сканирований;
- стоимость соединений.

#### Ошибка оценки кардинальности

Предположим, оптимизатор ожидает:

```text
rows=10
```

а при фактическом выполнении получает:

```text
actual rows=100000
```

Такое расхождение может привести к неудачному выбору:

- Nested Loop;
- индексного доступа;
- Hash Join;
- сортировки;
- порядка соединения.

Но устаревшая статистика — только одна из возможных причин.

Другие причины:

- неравномерное распределение;
- взаимосвязь столбцов;
- сложные выражения;
- особенности параметризации;
- ограничения статистической модели.

Поэтому `ANALYZE` не является универсальным исправлением любого плохого плана.

#### VACUUM и ANALYZE

Они решают разные задачи.

| Команда | Основное назначение |
|---|---|
| VACUUM | Обслуживание версий строк и служебных структур |
| ANALYZE | Обновление статистики оптимизатора |
| VACUUM (ANALYZE) | Совмещение обслуживания и сбора статистики |
| VACUUM FULL | Переписывание таблицы для компактного хранения |

Пример:

```sql
VACUUM (ANALYZE) customer_profiles;
```

Не следует считать, что ANALYZE физически удаляет мёртвые строки или что VACUUM всегда полностью обновляет статистику распределения без отдельного ANALYZE.

### Тема 13. Autovacuum

PostgreSQL автоматически обслуживает таблицы через autovacuum.

Он запускает:

- VACUUM;
- ANALYZE;
- операции, необходимые для защиты от переполнения идентификаторов транзакций.

Основные параметры включают:

```text
autovacuum
autovacuum_vacuum_threshold
autovacuum_vacuum_scale_factor
autovacuum_analyze_threshold
autovacuum_analyze_scale_factor
```

#### Пороги запуска

Для обычного автоматического VACUUM применяется модель порога, зависящая от базового значения и размера таблицы.

В современных PostgreSQL также существуют дополнительные ограничения и настройки, влияющие на фактический запуск.

Поэтому формулу вида:

```text
threshold + scale_factor × table_size
```

следует воспринимать как основную идею, а не полное описание всех условий работы autovacuum.

#### Почему autovacuum может отставать

Причины:

- интенсивные UPDATE и DELETE;
- недостаточная производительность autovacuum workers;
- ограниченная скорость I/O;
- долгоживущие транзакции;
- неподходящие пороги;
- конфликтующие операции;
- чрезмерное количество обслуживаемых таблиц.

#### Почему нельзя просто отключить autovacuum

Полное отключение автоматического обслуживания может привести к:

- накоплению мёртвых версий;
- ухудшению индексного доступа;
- росту таблиц;
- устаревшей статистике;
- проблемам с возрастом транзакций.

Кроме того, PostgreSQL сохраняет специальные защитные механизмы против transaction ID wraparound даже при некоторых вариантах отключения обычного autovacuum.

Поэтому отключение autovacuum не является нормальным способом ускорения производственной базы.

Лучше настраивать его под профиль нагрузки.

### Тема 14. Системная статистика PostgreSQL

PostgreSQL предоставляет представления для анализа таблиц и индексов.

#### pg_stat_user_tables

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Этот запрос помогает найти таблицы, требующие дальнейшего исследования.

Но значения необходимо интерпретировать правильно.

#### n_live_tup

Оценка количества живых строк.

Это не точный эквивалент:

```sql
SELECT COUNT(*) FROM table_name;
```

#### n_dead_tup

Оценка количества мёртвых версий.

Она может отличаться от фактического состояния из-за:

- способа сбора статистики;
- задержек её обновления;
- конкурентных изменений;
- MVCC;
- особенностей VACUUM.

Поэтому нельзя считать `n_dead_tup` точным счётчиком физических записей, которые можно немедленно удалить.

#### n_mod_since_analyze

Показатель изменений строк с последнего сбора статистики.

Большое значение говорит о существенном количестве изменений.

Но не доказывает, что статистика обязательно стала неточной.

Например, миллион новых строк с тем же распределением значений может повлиять на оценки иначе, чем десять тысяч строк, резко изменивших распределение.

#### Даты обслуживания

Поля:

```text
last_vacuum
last_autovacuum
last_analyze
last_autoanalyze
```

помогают понять, когда выполнялось обслуживание.

Но отсутствие недавнего VACUUM само по себе не означает проблему.

Если таблица практически не изменялась, частое обслуживание может быть не нужно.

### Тема 15. Статистика использования индексов

Для анализа индексов используется `pg_stat_user_indexes`.

```sql
SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan DESC;
```

#### idx_scan

Показывает количество индексных сканирований в рамках накопленной статистики.

Но счётчик не равен числу SQL-запросов.

Один запрос может обращаться к индексу несколько раз.

#### idx_tup_read

Количество индексных записей, полученных при использовании индекса.

#### idx_tup_fetch

Количество живых строк heap, полученных при индексном доступе, в соответствии с семантикой PostgreSQL.

Эти показатели не обязаны совпадать.

Например:

- часть индексных записей может ссылаться на невидимые версии;
- Index Only Scan может избежать heap-обращений;
- bitmap-сканирования учитываются иначе.

Поэтому разница между `idx_tup_read` и `idx_tup_fetch` не является автоматически признаком неисправности индекса.

#### Индексы с низкой активностью

```sql
SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;
```

Так можно найти индексы с небольшим числом зарегистрированных сканирований.

Но нельзя сразу удалять индекс, если `idx_scan = 0`.

Возможные объяснения:

- статистика недавно сброшена;
- сервер недавно перезапущен;
- запрос выполняется редко;
- индекс нужен для уникальности;
- индекс используется для обслуживания целостности;
- индекс нужен в периодических отчётах;
- наблюдаемый период недостаточен.

Кроме того, индекс может ускорять редкий, но критичный запрос.

#### Размер индексов

```sql
SELECT
    indexrelid::regclass AS index_name,
    pg_size_pretty(
        pg_relation_size(indexrelid)
    ) AS index_size
FROM pg_index
ORDER BY pg_relation_size(indexrelid) DESC;
```

Размер важен для оценки стоимости хранения и обслуживания.

Но большой индекс не обязательно является неэффективным.

### Тема 16. Статистика столбцов и оценки оптимизатора

Представление `pg_stats` содержит статистику распределения значений.

```sql
SELECT
    schemaname,
    tablename,
    attname,
    null_frac,
    n_distinct,
    correlation
FROM pg_stats
WHERE tablename = 'tickets';
```

#### null_frac

Оценка доли NULL.

#### n_distinct

Оценка количества различных значений.

В PostgreSQL отрицательное значение `n_distinct` означает оценку количества различных значений как доли числа строк.

Это не означает отрицательное количество значений.

#### correlation

Оценка корреляции между порядком значений и физическим размещением строк.

Высокая корреляция по модулю может снижать стоимость индексного чтения диапазонов, поскольку строки оказываются физически ближе друг к другу.

Но это не единственный фактор выбора плана.

#### Расширенная статистика

Если столбцы связаны, обычная статистика отдельных столбцов может давать плохие оценки.

Например:

```sql
CREATE STATISTICS tickets_name_route_stats
ON passenger_name, route_id
FROM tickets;
```

После этого:

```sql
ANALYZE tickets;
```

PostgreSQL может получить дополнительные сведения для некоторых комбинаций условий.

Однако расширенная статистика не гарантирует улучшение любого запроса и не заменяет анализ плана.

### Тема 17. Диагностика физического размера и bloat

Размер таблицы можно получить:

```sql
SELECT pg_size_pretty(
    pg_relation_size('tickets')
);
```

Размер таблицы вместе с индексами и вспомогательными структурами:

```sql
SELECT pg_size_pretty(
    pg_total_relation_size('tickets')
);
```

Размер индексов:

```sql
SELECT pg_size_pretty(
    pg_indexes_size('tickets')
);
```

Это разные показатели.

#### Почему размер сам по себе недостаточен

Большая таблица может содержать большое количество полезных данных.

Маленькая таблица может иметь высокий процент свободного или неэффективно занятого пространства.

Поэтому bloat нельзя определять только по общему размеру файла.

Для более глубокого исследования PostgreSQL предоставляет расширения и инструменты, например:

- `pgstattuple`;
- `pg_visibility`;
- `pageinspect`.

Они требуют соответствующих прав и могут создавать дополнительную нагрузку.

#### pgstattuple

Например:

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;
```

```sql
SELECT *
FROM pgstattuple('tickets');
```

Расширение позволяет получить сведения о физическом содержимом таблицы.

Но такой анализ может требовать сканирования значительного объёма данных.

Поэтому применять его в рабочей системе необходимо осознанно.

#### pg_visibility

Расширение позволяет исследовать visibility map.

```sql
CREATE EXTENSION IF NOT EXISTS pg_visibility;
```

Например:

```sql
SELECT *
FROM pg_visibility_map_summary('tickets');
```

Результат содержит сведения о числе all-visible и all-frozen страниц.

Но эти показатели следует сопоставлять с фактическим Index Only Scan, а не использовать как универсальный прогноз его скорости.

### Тема 18. Практика: подготовка таблицы

Создадим отдельную учебную схему.

```sql
CREATE SCHEMA IF NOT EXISTS index_diagnostics;
```

Таблица билетов:

```sql
CREATE TABLE index_diagnostics.tickets (
    ticket_id BIGINT PRIMARY KEY,
    ticket_no TEXT NOT NULL,
    passenger_name TEXT NOT NULL,
    route_id INTEGER NOT NULL,
    price NUMERIC(10, 2) NOT NULL,
    updated_at TIMESTAMPTZ
);
```

Добавим 300 000 строк:

```sql
INSERT INTO index_diagnostics.tickets (
    ticket_id,
    ticket_no,
    passenger_name,
    route_id,
    price,
    updated_at
)
SELECT
    n,
    'T-' || lpad(n::text, 8, '0'),
    CASE
        WHEN n % 10000 = 0
            THEN 'Анна Иванова'
        ELSE 'Пассажир ' || n::text
    END,
    (n % 100) + 1,
    (n % 20000 + 100)::numeric,
    CURRENT_TIMESTAMP
FROM generate_series(1, 300000) AS n;
```

Соберём статистику:

```sql
ANALYZE index_diagnostics.tickets;
```

Это синтетический набор.

Значение `Анна Иванова` встречается примерно в 30 строках.

Распределение создано специально для демонстрации высокоизбирательного поиска.

### Тема 19. Практика: запрос без индекса

Выполним:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    ticket_no,
    passenger_name
FROM index_diagnostics.tickets
WHERE passenger_name = 'Анна Иванова';
```

Если отдельного индекса по `passenger_name` нет, PostgreSQL может выполнить Seq Scan или Parallel Seq Scan.

Это зависит от размера таблицы, настроек параллелизма и оценки стоимости.

#### На что обратить внимание

- число прочитанных строк;
- Rows Removed by Filter;
- Actual Rows;
- Shared Hit;
- Shared Read;
- Execution Time.

Если запрос возвращает небольшое число строк, но проверяет сотни тысяч, подходящий индекс может дать выигрыш.

Зафиксируем исходные показатели.

### Тема 20. Практика: создание индекса

Создадим:

```sql
CREATE INDEX idx_tickets_passenger
ON index_diagnostics.tickets (passenger_name);
```

Повторим:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    ticket_no,
    passenger_name
FROM index_diagnostics.tickets
WHERE passenger_name = 'Анна Иванова';
```

PostgreSQL может выбрать Index Scan или Bitmap Heap Scan.

#### Сравнение

Необходимо записать:

| Показатель | Без индекса | С индексом |
|---|---|---|
| Тип доступа | Измерить | Измерить |
| Actual Rows | Измерить | Измерить |
| Execution Time | Измерить | Измерить |
| Shared Hit | Измерить | Измерить |
| Shared Read | Измерить | Измерить |

Не следует заранее утверждать, что индекс сократит время строго в определённое количество раз.

Это зависит от среды.

### Тема 21. Практика: покрывающий индекс

Создадим:

```sql
CREATE INDEX idx_tickets_passenger_cover
ON index_diagnostics.tickets (passenger_name)
INCLUDE (ticket_no);
```

Запрос:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    passenger_name,
    ticket_no
FROM index_diagnostics.tickets
WHERE passenger_name = 'Анна Иванова';
```

Теперь у оптимизатора есть индекс, содержащий необходимые значения.

Но PostgreSQL может выбрать любой выгодный план.

#### Подготовка visibility map

Выполним:

```sql
VACUUM (ANALYZE) index_diagnostics.tickets;
```

Повторим запрос.

Если выбран Index Only Scan, посмотрим:

```text
Heap Fetches
```

Небольшое или нулевое число означает, что большинство или все проверки видимости удалось выполнить без обращения к heap.

При этом эффект может зависеть от состояния таблицы.

### Тема 22. Практика: влияние UPDATE

Теперь выполним массовое обновление:

```sql
UPDATE index_diagnostics.tickets
SET updated_at = clock_timestamp()
WHERE ticket_id % 2 = 0;
```

Это изменит примерно половину строк.

Затем снова:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    passenger_name,
    ticket_no
FROM index_diagnostics.tickets
WHERE passenger_name = 'Анна Иванова';
```

#### Что могло измениться

- Heap Fetches;
- количество буферных обращений;
- физическое размещение версий;
- время выполнения;
- размер таблицы;
- статистика обслуживания.

Важно: запрос может и не показать заметного ухудшения.

Это зависит от расположения изменённых строк, состояния visibility map и повторного использования страниц.

Для более выразительного эксперимента полезно выполнить несколько циклов обновления и отдельно контролировать состояние таблицы.

Но не следует искусственно создавать чрезмерную нагрузку на рабочей базе.

#### HOT Update

Столбец `updated_at` не индексируется в текущей схеме.

Поэтому часть обновлений может быть HOT при наличии места на heap-страницах.

Но отсутствие индекса по `updated_at` не гарантирует HOT для всех обновлений.

Проверим:

```sql
SELECT
    relname,
    n_tup_upd,
    n_tup_hot_upd
FROM pg_stat_user_tables
WHERE schemaname = 'index_diagnostics'
  AND relname = 'tickets';
```

Значения следует рассматривать за соответствующий период наблюдения.

### Тема 23. Практика: VACUUM и восстановление эффективности

Выполним:

```sql
VACUUM (ANALYZE) index_diagnostics.tickets;
```

Повторим:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    passenger_name,
    ticket_no
FROM index_diagnostics.tickets
WHERE passenger_name = 'Анна Иванова';
```

Сравним:

- план до массового UPDATE;
- план после UPDATE;
- план после VACUUM;
- Heap Fetches;
- BUFFERS;
- Execution Time.

Если VACUUM смог установить all-visible для соответствующих страниц, Index Only Scan может выполнять меньше heap-обращений.

Но нулевые Heap Fetches не гарантированы.

На результат влияют активные транзакции и состояние конкретных страниц.

### Тема 24. Практика: оценка мёртвых строк

Получим статистику:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE schemaname = 'index_diagnostics';
```

Сравним её с результатами до обновлений.

#### Интерпретация

Если `n_dead_tup` вырос, это может указывать на накопление мёртвых версий.

Если `n_mod_since_analyze` велик, это повод проверить актуальность статистики.

Если давно не было VACUUM, необходимо оценить, требуется ли обслуживание.

Но ни один из этих показателей сам по себе не является универсальным доказательством проблемы.

Необходимо сопоставлять их с:

- планами;
- размерами таблицы;
- временем выполнения;
- количеством буферных обращений;
- характером нагрузки.

### Тема 25. Диагностика избыточных индексов

Создание индекса не является бесплатным.

Поэтому после анализа производительности необходимо оценивать и существующий набор индексов.

Например, в учебной таблице появились:

```text
idx_tickets_passenger
idx_tickets_passenger_cover
```

Второй индекс частично дублирует первый.

Может оказаться, что отдельный индекс только по `passenger_name` больше не требуется.

Однако решение зависит от:

- размера индексов;
- частых запросов;
- стоимости записи;
- возможности Index Only Scan;
- требований к сортировке;
- периода наблюдения.

#### Проверка использования

```sql
SELECT
    indexrelname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE schemaname = 'index_diagnostics';
```

#### Проверка размера

```sql
SELECT
    indexrelid::regclass AS index_name,
    pg_size_pretty(
        pg_relation_size(indexrelid)
    ) AS index_size
FROM pg_index
WHERE indrelid =
    'index_diagnostics.tickets'::regclass;
```

После этого можно принять решение о необходимости каждого индекса.

Но удалять индекс исключительно по низкому `idx_scan` нельзя.

### Тема 26. REINDEX и обслуживание индексов

PostgreSQL предоставляет команду `REINDEX`.

Например:

```sql
REINDEX INDEX index_diagnostics.idx_tickets_passenger;
```

Она перестраивает индекс.

Это может быть полезно при определённых видах разрастания или необходимости восстановления индексной структуры.

Но `REINDEX` не является обычной заменой VACUUM.

#### REINDEX CONCURRENTLY

Для уменьшения блокирования конкурентных операций в PostgreSQL поддерживается:

```sql
REINDEX INDEX CONCURRENTLY
    index_diagnostics.idx_tickets_passenger;
```

Такая операция имеет ограничения и требует дополнительных ресурсов.

В частности, её нельзя выполнять внутри обычного транзакционного блока.

#### Когда REINDEX не нужен

Если проблема связана с:

- устаревшей статистикой;
- отсутствующим индексом;
- плохим SQL-условием;
- долгими блокировками;
- низкой селективностью;

перестроение индекса может не помочь.

Поэтому необходимость REINDEX должна подтверждаться диагностикой.

### Тема 27. Отличия SQL Server, MySQL и Oracle

Хотя все четыре СУБД поддерживают индексы, механизмы физического хранения и обслуживания различаются.

#### SQL Server

SQL Server использует:

- clustered indexes;
- nonclustered indexes;
- columnstore indexes;
- статистику оптимизатора;
- механизмы реорганизации и перестроения индексов.

Для диагностики доступны:

- `sys.dm_db_index_usage_stats`;
- `sys.dm_db_index_physical_stats`;
- Query Store;
- actual execution plans;
- `SET STATISTICS IO`;
- `SET STATISTICS TIME`.

Например:

```sql
SELECT
    OBJECT_NAME(i.object_id) AS table_name,
    i.name AS index_name,
    s.user_seeks,
    s.user_scans,
    s.user_lookups,
    s.user_updates
FROM sys.indexes AS i
LEFT JOIN sys.dm_db_index_usage_stats AS s
    ON s.object_id = i.object_id
   AND s.index_id = i.index_id
   AND s.database_id = DB_ID()
WHERE i.object_id = OBJECT_ID('dbo.orders');
```

Статистика использования не должна трактоваться как вечная история.

Её значения зависят от жизненного цикла экземпляра и условий сброса соответствующих счётчиков.

Для обслуживания индекса SQL Server применяет:

```sql
ALTER INDEX ...
REORGANIZE;
```

и:

```sql
ALTER INDEX ...
REBUILD;
```

Но не существует универсального правила, что индексы необходимо перестраивать при каждом достижении фиксированного процента фрагментации.

Решение зависит от размера, нагрузки, типа индекса и фактической проблемы.

#### MySQL/InnoDB

InnoDB использует кластерный индекс по первичному ключу и вторичные индексы.

Старые версии данных обслуживаются с использованием undo и механизма purge.

Это отличается от хранения версий строк непосредственно в heap PostgreSQL.

Поэтому понятия PostgreSQL dead tuples, visibility map и Heap Fetches нельзя напрямую переносить на InnoDB.

Для диагностики используются:

- `EXPLAIN`;
- `EXPLAIN ANALYZE`;
- Performance Schema;
- `INFORMATION_SCHEMA.STATISTICS`;
- статистика InnoDB;
- сведения о purge и транзакциях.

Для обновления статистики:

```sql
ANALYZE TABLE orders;
```

При необходимости применяются операции перестроения таблиц и индексов, но их стоимость и блокирующее поведение зависят от конкретной команды и версии MySQL.

#### Oracle

Oracle использует собственные механизмы MVCC и undo.

Обычные heap-organized tables отделены от B-tree индексов.

Для анализа доступны:

- `DBMS_STATS`;
- `DBMS_XPLAN`;
- динамические представления;
- сведения о сегментах и индексах;
- средства мониторинга запросов.

Обновление статистики:

```sql
BEGIN
    DBMS_STATS.GATHER_TABLE_STATS(
        ownname => USER,
        tabname => 'ORDERS'
    );
END;
/
```

Oracle также поддерживает перестроение и другие операции обслуживания индексов.

Но диагностические признаки PostgreSQL нельзя механически заменять терминологией Oracle.

#### Сравнение

| Характеристика | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| Обычная организация строк | Heap | Heap или clustered index | Clustered index | Обычно heap |
| MVCC / версионность | Heap-версии | Row versioning в соответствующих режимах | Undo-based | Undo-based |
| Видимость при Index Only Scan | Visibility map | Иная модель | Иная модель | Иная модель |
| Автоматическое обслуживание старых версий | Autovacuum | Собственные механизмы | Purge | Undo management |
| Обновление статистики | ANALYZE | UPDATE STATISTICS | ANALYZE TABLE | DBMS_STATS |
| Перестроение индекса | REINDEX | ALTER INDEX REBUILD | Перестроение средствами ALTER/OPTIMIZE | ALTER INDEX REBUILD |

### Тема 28. Методика диагностики проблем с индексами

Удобно придерживаться следующего порядка.

#### Шаг 1. Зафиксировать запрос

Необходимо знать:

- SQL-текст;
- параметры;
- частоту выполнения;
- время;
- количество строк;
- версию СУБД.

#### Шаг 2. Получить фактический план

В PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

#### Шаг 3. Проверить количество строк

Сравнить:

```text
rows
actual rows
loops
```

Найти значительные ошибки оценок.

#### Шаг 4. Проверить способ доступа

Определить:

- Seq Scan;
- Parallel Seq Scan;
- Index Scan;
- Index Only Scan;
- Bitmap Heap Scan.

Не оценивать оператор только по названию.

#### Шаг 5. Проверить индексы

Изучить:

- порядок ключей;
- включённые столбцы;
- условия запросов;
- размеры;
- частоту использования.

#### Шаг 6. Проверить физическое состояние

Проанализировать:

- dead tuples;
- visibility map;
- Heap Fetches;
- размеры таблиц;
- признаки bloat;
- статистику HOT.

#### Шаг 7. Проверить статистику оптимизатора

Посмотреть:

- даты ANALYZE;
- n_mod_since_analyze;
- распределение значений;
- pg_stats;
- необходимость расширенной статистики.

#### Шаг 8. Сформулировать гипотезу

Например:

- отсутствует индекс;
- неверный порядок ключей;
- индекс не покрывает запрос;
- таблица нуждается в VACUUM;
- статистика устарела;
- индекс избыточен;
- запрос обрабатывает слишком много строк.

#### Шаг 9. Проверить изменение

Изменить только один существенный фактор.

Повторить измерения.

Сравнить планы, время и обращение к данным.

#### Шаг 10. Оценить влияние на систему

Ускорение отдельного SELECT не должно оцениваться в отрыве от стоимости INSERT, UPDATE, DELETE и общего использования ресурсов.

## Итоговые выводы

1. **Наличие индекса не гарантирует его использования.** Оптимизатор выбирает путь доступа по оценочной стоимости.

2. **Диагностика индекса начинается с фактического плана выполнения.** Необходимо анализировать не только тип доступа, но и количество строк, циклы, буферы и время выполнения.

3. **Составные индексы требуют правильного порядка ключей.** При этом возможности B-tree skip scan в PostgreSQL 18 делают правило левого префикса менее абсолютным.

4. **Покрывающий индекс может обеспечить Index Only Scan.** Но наличие необходимых столбцов в индексе не гарантирует отсутствие обращений к heap.

5. **Visibility map влияет на эффективность Index Only Scan.** При отсутствии отметки all-visible PostgreSQL выполняет дополнительные проверки видимости.

6. **MVCC PostgreSQL создаёт новые версии строк при изменениях.** Старые версии не всегда можно немедленно удалить, поскольку они могут требоваться активным транзакциям.

7. **HOT Update позволяет сократить индексные изменения при определённых условиях.** Избыточные индексы способны повышать стоимость UPDATE и уменьшать долю HOT-обновлений.

8. **Dead tuples и bloat связаны, но не тождественны.** Оценка количества мёртвых версий не является точным измерением избыточного физического пространства.

9. **VACUUM обслуживает физическое состояние таблицы и информацию о видимости.** Он обычно освобождает место для повторного использования, но не обязан уменьшать размер файла.

10. **VACUUM FULL предназначен для более радикального компактирования.** Он требует существенных ресурсов и блокировок, поэтому не должен применяться без необходимости.

11. **ANALYZE обновляет статистику оптимизатора.** Но устаревшая статистика — не единственная причина ошибочного плана.

12. **Autovacuum необходим для нормальной эксплуатации PostgreSQL.** Его следует настраивать с учётом характера изменений, а не отключать ради кратковременного ускорения.

13. **Системные счётчики являются диагностическими показателями, а не абсолютной истиной.** `n_dead_tup`, `n_mod_since_analyze` и `idx_scan` нужно интерпретировать с учётом периода наблюдения.

14. **REINDEX решает определённые проблемы индексной структуры, но не заменяет VACUUM и ANALYZE.** Перестроение должно быть обосновано измерениями.

15. **Физическая диагностика различается между СУБД.** Механизмы PostgreSQL heap, visibility map и VACUUM нельзя считать прямыми аналогами внутреннего обслуживания SQL Server, InnoDB и Oracle.

Главный результат занятия — способность диагностировать индекс как часть системы хранения и выполнения запросов: оценивать не только структуру ключей, но и состояние таблицы, версии строк, статистику, план выполнения и эксплуатационную стоимость.
