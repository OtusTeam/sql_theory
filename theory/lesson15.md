
# Процедурное программирование в SQL

## Превью / аннотация / краткое содержание

Занятие посвящено процедурным расширениям SQL, позволяющим выполнять алгоритмическую логику непосредственно на стороне базы данных.

SQL является преимущественно декларативным языком: разработчик описывает, какие данные необходимо получить или изменить, а СУБД самостоятельно выбирает способ выполнения запроса.

Однако некоторые задачи требуют последовательности действий, промежуточных вычислений, условных переходов, циклов и обработки ошибок. Для их реализации реляционные СУБД предоставляют процедурные языки и конструкции.

На занятии рассматриваются:

- различия декларативного и процедурного подходов;
- назначение процедурных расширений SQL;
- особенности PL/pgSQL, T-SQL, PL/SQL и процедурного языка MySQL;
- структура процедурных блоков;
- переменные, типы данных и присваивание;
- получение результатов SQL-запросов в переменные;
- условные конструкции `IF` и `CASE`;
- циклы `LOOP`, `WHILE`, `FOR` и `FOREACH`;
- управление выполнением через `EXIT`, `CONTINUE` и их аналоги;
- курсоры и последовательная обработка строк;
- обработка исключений;
- транзакционные ограничения процедурного кода;
- производительность построчной и множественной обработки;
- архитектурные границы логики, размещённой в базе данных.

Основные практические примеры приведены для PostgreSQL и PL/pgSQL. Дополнительно рассматриваются соответствующие механизмы Microsoft SQL Server, MySQL/InnoDB и Oracle.

## Основные понятия

**Декларативное программирование** — подход, при котором описывается требуемый результат, а не последовательность элементарных действий для его получения.

**Процедурное программирование** — подход, при котором алгоритм задаётся последовательностью инструкций, условий, циклов и операций изменения состояния.

**Процедурное расширение SQL** — язык или набор конструкций для реализации алгоритмической логики на стороне СУБД.

**PL/pgSQL** — процедурный язык PostgreSQL для функций, процедур, триггерных функций и анонимных блоков.

**T-SQL (Transact-SQL)** — расширение SQL, применяемое в Microsoft SQL Server.

**PL/SQL** — процедурный язык Oracle.

**Stored Program** — сохранённый программный объект СУБД, например процедура или функция.

**Процедурный блок** — логически обособленная последовательность инструкций с собственной областью видимости переменных.

**Анонимный блок** — процедурный код, выполняемый без создания постоянного программного объекта.

**DO** — команда PostgreSQL для выполнения анонимного процедурного блока.

**DECLARE** — секция или оператор объявления переменных и других объектов, в зависимости от процедурного языка.

**BEGIN / END** — границы исполняемого блока в PL/pgSQL и PL/SQL; в T-SQL также используются для группировки инструкций.

**Переменная** — именованное значение, доступное для чтения и изменения во время выполнения программы.

**Область видимости (Scope)** — часть программы, в которой доступна объявленная переменная или другой локальный объект.

**Присваивание** — операция изменения значения переменной.

**SELECT INTO** — конструкция, смысл которой зависит от СУБД: в PL/pgSQL используется для помещения результата запроса в переменную, а в обычном SQL PostgreSQL и T-SQL может означать создание таблицы.

**FOUND** — специальная переменная PL/pgSQL, отражающая результат некоторых ранее выполненных операций.

**GET DIAGNOSTICS** — конструкция PL/pgSQL для получения диагностических сведений, например количества обработанных строк.

**IF / ELSE / ELSIF** — условные конструкции PL/pgSQL.

**CASE** — конструкция выбора; существует как SQL-выражение и как процедурный оператор в поддерживающих его языках.

**LOOP** — цикл с явно заданным завершением.

**WHILE** — цикл, выполняемый пока условие истинно.

**FOR** — цикл по числовому диапазону или набору данных.

**FOREACH** — конструкция PL/pgSQL для перебора элементов массива.

**EXIT** — завершение цикла или допустимого именованного блока PL/pgSQL.

**CONTINUE** — переход к следующей итерации цикла.

**BREAK** — оператор выхода из цикла в T-SQL.

**Курсор (Cursor)** — механизм последовательного получения строк результата запроса.

**OPEN** — открытие курсора.

**FETCH** — получение строки или набора строк из курсора.

**CLOSE** — закрытие курсора.

**DEALLOCATE** — освобождение курсора в T-SQL.

**EXCEPTION** — раздел обработки исключений в PL/pgSQL и PL/SQL.

**TRY / CATCH** — механизм обработки ошибок T-SQL.

**SQLSTATE** — стандартизированный пятисимвольный код класса и вида SQL-ошибки.

**RAISE** — конструкция PL/pgSQL для выдачи сообщений и ошибок.

**SIGNAL / RESIGNAL** — конструкции MySQL для формирования и повторной передачи условий ошибок.

**Set-based Processing** — обработка набора строк одной SQL-операцией.

**Row-by-row Processing** — последовательная обработка строк.

**Транзакционная логика** — управление взаимосвязанными изменениями с учётом фиксации, отката и изоляции.

**Толстая база (Thick Database)** — архитектурный подход, при котором существенная часть прикладной логики размещается непосредственно в СУБД.

## Основная часть

### Тема 1. Ограничения декларативного SQL

SQL предназначен для работы с наборами данных.

Обычный запрос описывает результат, который необходимо получить.

Например:

```sql
SELECT
    customer_id,
    SUM(total_amount) AS total_amount
FROM orders
WHERE status = 'completed'
GROUP BY customer_id;
```

Запрос определяет:

- таблицу;
- условия отбора;
- группировку;
- вычисляемый агрегат.

Разработчик не описывает, в каком порядке читать страницы таблицы, каким способом выполнять группировку и какие индексы использовать.

Эти решения принимает оптимизатор СУБД.

#### Множественная обработка

Предположим, необходимо увеличить цены всех товаров определённой категории на 10%.

Декларативное решение:

```sql
UPDATE products
SET price = price * 1.10
WHERE category_id = 5;
```

Одна SQL-команда описывает изменение множества строк.

При этом СУБД самостоятельно определяет способ поиска и обновления подходящих записей.

Нет необходимости писать цикл, который отдельно получает и обновляет каждый товар.

#### Когда требуется алгоритмическая логика

Рассмотрим более сложную операцию:

1. Получить остаток товара.
2. Проверить допустимость списания.
3. Изменить количество.
4. Создать запись о движении товара.
5. Вернуть результат операции.
6. При ошибке обеспечить корректную отмену изменений.

Такую операцию можно реализовать в приложении, выполняющем SQL-запросы внутри транзакции.

В некоторых случаях удобнее разместить её в хранимой процедуре или функции СУБД.

Процедурный язык позволяет явно описать последовательность действий.

Однако нельзя утверждать, что сложные бизнес-правила вообще невозможно реализовать декларативным SQL.

Современный SQL предоставляет:

- `CASE`;
- CTE;
- оконные функции;
- `INSERT ... SELECT`;
- `UPDATE ... FROM`;
- `MERGE`;
- ограничения целостности;
- подзапросы;
- рекурсивные запросы.

Многие задачи, которые на первый взгляд требуют циклов, можно решить одной множественной операцией.

**Поэтому процедурный подход следует выбирать тогда, когда алгоритмическая последовательность действительно необходима, а не просто потому, что она привычнее разработчику.**

### Тема 2. Назначение процедурного программирования в SQL

Процедурный SQL дополняет декларативные запросы возможностью управлять последовательностью выполнения.

Он позволяет:

- объявлять переменные;
- сохранять промежуточные результаты;
- выполнять условные переходы;
- организовывать циклы;
- работать с курсорами;
- перехватывать ошибки;
- выполнять несколько взаимосвязанных SQL-команд;
- возвращать результаты вычислений.

#### Преимущества

**Выполнение рядом с данными.**

Если логика находится в СУБД, не требуется передавать каждое промежуточное значение приложению.

Это может сокращать сетевые обращения.

**Централизация правил.**

Если несколько приложений используют одну базу данных, часть общих операций можно реализовать централизованно.

**Транзакционная согласованность.**

Несколько связанных изменений можно выполнять в общем транзакционном контексте.

**Повторное использование.**

Хранимые функции и процедуры позволяют вызывать одну реализацию из разных SQL-клиентов.

**Контроль доступа.**

При корректном проектировании процедура может предоставлять ограниченный интерфейс выполнения операций без выдачи приложению широких прав на таблицы.

Но модель безопасности зависит от СУБД и режима исполнения объекта.

#### Недостатки

Процедурный код:

- часто привязан к конкретному диалекту;
- требует отдельных подходов к тестированию;
- может усложнять миграции;
- иногда скрывает бизнес-логику от разработчиков приложения;
- может создавать длительные транзакции;
- не всегда эффективен при массовой построчной обработке.

Нельзя считать, что выполнение логики внутри СУБД автоматически быстрее аналогичной логики в приложении.

Например, один правильно написанный `UPDATE` обычно предпочтительнее процедуры, которая выполняет отдельный `UPDATE` для каждой из миллиона строк.

### Тема 3. Процедурные диалекты четырёх СУБД

Реляционные СУБД предоставляют похожие концепции, но различные языки.

| Возможность | PostgreSQL | SQL Server | MySQL/InnoDB | Oracle |
|---|---|---|---|---|
| Основной процедурный язык | PL/pgSQL | T-SQL | Stored Program Language MySQL | PL/SQL |
| Анонимный блок | DO | Пакет T-SQL | Нет прямого аналога DO; блоки в сохранённых программах | Анонимный PL/SQL-блок |
| Локальные переменные | DECLARE | DECLARE @variable | DECLARE в BEGIN...END | DECLARE |
| Условный оператор | IF / ELSIF | IF / ELSE | IF / ELSEIF | IF / ELSIF |
| Циклы | LOOP, WHILE, FOR, FOREACH | WHILE | LOOP, WHILE, REPEAT | LOOP, WHILE, FOR |
| Обработка ошибок | EXCEPTION | TRY / CATCH | DECLARE HANDLER | EXCEPTION |
| Курсоры | Да | Да | Да | Да |
| Хранимые процедуры | Да | Да | Да | Да |

#### PostgreSQL

PL/pgSQL применяется в:

- функциях;
- процедурах;
- триггерных функциях;
- анонимных блоках `DO`.

Для однократной демонстрации удобно использовать:

```sql
DO $$
BEGIN
    RAISE NOTICE 'Hello from PL/pgSQL';
END;
$$;
```

`RAISE NOTICE` выводит диагностическое сообщение.

Это не табличный результат SQL-запроса.

#### SQL Server

T-SQL допускает выполнение процедурных инструкций непосредственно в SQL-пакете:

```sql
DECLARE @a INT = 7;
DECLARE @b INT = 5;
DECLARE @result INT;

SET @result = @a + @b;

IF @result > 10
BEGIN
    PRINT CONCAT('Result: ', @result);
END
ELSE
BEGIN
    PRINT 'Result is not greater than 10';
END;
```

Переменные обозначаются префиксом `@`.

`BEGIN ... END` группирует несколько инструкций.

Важно: `BEGIN` в такой конструкции не означает начало транзакции.

Для транзакции используется `BEGIN TRANSACTION`.

#### MySQL

В MySQL процедурные блоки используются внутри сохранённых программ, например процедур.

```sql
DELIMITER //

CREATE PROCEDURE demo_variables()
BEGIN
    DECLARE a INT DEFAULT 7;
    DECLARE b INT DEFAULT 5;
    DECLARE result_value INT;

    SET result_value = a + b;

    SELECT result_value AS result;
END//

DELIMITER ;
```

Вызов:

```sql
CALL demo_variables();
```

`DELIMITER` — команда клиента MySQL, а не SQL-оператор сервера.

Она изменяет символ, по которому клиент определяет конец отправляемой инструкции.

В приложениях, драйверах и некоторых SQL-клиентах способ отправки определения процедуры может отличаться.

#### Oracle

Oracle использует PL/SQL.

```sql
DECLARE
    a NUMBER := 7;
    b NUMBER := 5;
    result_value NUMBER;
BEGIN
    result_value := a + b;
    DBMS_OUTPUT.PUT_LINE(
        'Result: ' || result_value
    );
END;
/
```

Символ `/` применяется некоторыми клиентами Oracle для отправки завершённого PL/SQL-блока на выполнение.

Он не является частью синтаксиса самого блока.

Для просмотра `DBMS_OUTPUT` в клиенте может потребоваться включить соответствующий вывод.

#### Почему нельзя механически переносить код

Несмотря на сходство концепций, различаются:

- синтаксис;
- правила областей видимости;
- поведение курсоров;
- обработка ошибок;
- транзакционные ограничения;
- типы данных;
- получение результатов SQL-запросов;
- возвращение значений вызывающему приложению.

Поэтому перенос процедурного кода между СУБД требует анализа поведения, а не простой замены ключевых слов.

### Тема 4. Структура процедурного блока PL/pgSQL

В PostgreSQL общий вид блока:

```sql
DO $$
DECLARE
    -- объявления
BEGIN
    -- инструкции
EXCEPTION
    -- обработчики ошибок
END;
$$;
```

Раздел `DECLARE` необязателен.

Раздел `EXCEPTION` также необязателен.

Исполняемая часть `BEGIN ... END` обязательна.

#### Простейший блок

```sql
DO $$
BEGIN
    RAISE NOTICE 'Процедурный блок выполнен';
END;
$$;
```

#### Блок с переменными

```sql
DO $$
DECLARE
    a INTEGER := 10;
    b INTEGER := 20;
    result_value INTEGER;
BEGIN
    result_value := a + b;

    RAISE NOTICE 'Результат = %', result_value;
END;
$$;
```

Результат в сообщениях клиента:

```text
NOTICE: Результат = 30
```

#### Вложенные блоки

PL/pgSQL позволяет создавать вложенные блоки.

```sql
DO $$
DECLARE
    value_num INTEGER := 10;
BEGIN
    RAISE NOTICE 'Внешний блок: %', value_num;

    DECLARE
        inner_value INTEGER := 20;
    BEGIN
        RAISE NOTICE 'Внутренний блок: %', inner_value;
    END;
END;
$$;
```

Переменная внутреннего блока недоступна за его пределами.

При совпадении имён внутреннее объявление может скрывать внешнее.

Для сложного кода важно выбирать понятные имена и не злоупотреблять вложенными областями видимости.

#### BEGIN не всегда означает транзакцию

В PostgreSQL необходимо различать:

```sql
BEGIN;
```

как SQL-команду открытия транзакции и:

```sql
BEGIN
    -- инструкции PL/pgSQL
END;
```

как границы исполняемого блока.

Процедурный блок сам по себе не создаёт отдельную независимую транзакцию.

Это два различных использования одного ключевого слова.

### Тема 5. Переменные и присваивание значений

Переменные используются для хранения промежуточных результатов.

#### Объявление

```sql
DO $$
DECLARE
    counter INTEGER := 0;
    customer_name TEXT;
    total_amount NUMERIC(12, 2) := 1000.00;
    is_active BOOLEAN := true;
BEGIN
    RAISE NOTICE 'counter = %', counter;
END;
$$;
```

Переменная без начального значения обычно получает `NULL`.

#### Присваивание

В PL/pgSQL используется оператор:

```sql
:=
```

Например:

```sql
DO $$
DECLARE
    counter INTEGER := 10;
BEGIN
    counter := counter + 1;

    RAISE NOTICE 'counter = %', counter;
END;
$$;
```

Также допускается присваивание через `=` в поддерживаемом контексте PL/pgSQL, но `:=` обычно делает различие между присваиванием и SQL-сравнением более наглядным.

#### Типы, связанные с таблицей

В PL/pgSQL можно объявлять переменные через `%TYPE`.

Предположим, существует таблица:

```sql
CREATE TABLE demo_numbers (
    id INTEGER PRIMARY KEY,
    val TEXT NOT NULL
);
```

Объявление:

```sql
DO $$
DECLARE
    current_id demo_numbers.id%TYPE;
BEGIN
    current_id := 1;

    RAISE NOTICE 'id = %', current_id;
END;
$$;
```

Тип переменной связан с типом указанного столбца.

Это удобно, когда необходимо уменьшить дублирование определений типов.

Существует также `%ROWTYPE` для переменной составного типа строки таблицы или представления.

#### RECORD

Тип `record` позволяет хранить результат запроса с динамически определяемой структурой.

```sql
DO $$
DECLARE
    rec RECORD;
BEGIN
    SELECT id, val
    INTO rec
    FROM demo_numbers
    WHERE id = 1;

    RAISE NOTICE 'id = %, val = %', rec.id, rec.val;
END;
$$;
```

Структура `rec` определяется полученной строкой.

Однако обращаться к полям записи можно только после того, как её структура определена соответствующим присваиванием.

#### SELECT INTO в PL/pgSQL

Внутри PL/pgSQL:

```sql
SELECT val
INTO customer_name
FROM demo_numbers
WHERE id = 1;
```

означает присваивание результата запроса переменной.

Это отличается от обычной SQL-команды PostgreSQL:

```sql
SELECT ...
INTO new_table
FROM ...;
```

которая создаёт таблицу.

В T-SQL `SELECT ... INTO` также используется для создания таблицы, а присваивание переменной из запроса записывается иначе:

```sql
SELECT @variable = column_name
FROM table_name;
```

Поэтому перенос синтаксиса требует внимания.

#### SELECT INTO STRICT

В PL/pgSQL обычный `SELECT INTO` без `STRICT` получает первую возвращённую строку.

Если строк нет, целевые переменные получают `NULL`.

Если запрос вернул несколько строк, остальные не используются.

Без `ORDER BY` нельзя рассчитывать, какая из нескольких строк окажется первой.

Для строгой проверки можно использовать:

```sql
DO $$
DECLARE
    current_value TEXT;
BEGIN
    SELECT val
    INTO STRICT current_value
    FROM demo_numbers
    WHERE id = 1;

    RAISE NOTICE 'value = %', current_value;
END;
$$;
```

`STRICT` требует ровно одну строку.

Если строк нет, возникнет `NO_DATA_FOUND`.

Если строк несколько — `TOO_MANY_ROWS`.

#### FOUND

PL/pgSQL предоставляет специальную переменную `FOUND`.

```sql
DO $$
DECLARE
    current_value TEXT;
BEGIN
    SELECT val
    INTO current_value
    FROM demo_numbers
    WHERE id = 999;

    IF NOT FOUND THEN
        RAISE NOTICE 'Строка не найдена';
    END IF;
END;
$$;
```

`FOUND` изменяется после определённых SQL-операций и процедурных конструкций.

Нужно проверять его сразу после операции, результат которой интересует, поскольку последующие действия могут перезаписать значение.

#### GET DIAGNOSTICS

Для получения количества затронутых строк можно использовать:

```sql
DO $$
DECLARE
    affected_rows BIGINT;
BEGIN
    UPDATE demo_numbers
    SET val = upper(val)
    WHERE id <= 2;

    GET DIAGNOSTICS affected_rows = ROW_COUNT;

    RAISE NOTICE 'Обновлено строк: %', affected_rows;
END;
$$;
```

`ROW_COUNT` относится к последней соответствующей SQL-команде.

Для надёжной бизнес-логики это часто важнее, чем проверка только факта отсутствия SQL-ошибки.

### Тема 6. Условные конструкции IF и CASE

Условные конструкции позволяют выбирать ветку выполнения.

#### IF

Пример:

```sql
DO $$
DECLARE
    order_amount NUMERIC(12, 2) := 2500;
BEGIN
    IF order_amount >= 2000 THEN
        RAISE NOTICE 'Доставка бесплатная';
    ELSE
        RAISE NOTICE 'Доставка платная';
    END IF;
END;
$$;
```

#### ELSIF

Для нескольких условий:

```sql
DO $$
DECLARE
    order_amount NUMERIC(12, 2) := 1500;
BEGIN
    IF order_amount >= 5000 THEN
        RAISE NOTICE 'Скидка 15%%';

    ELSIF order_amount >= 2000 THEN
        RAISE NOTICE 'Скидка 10%%';

    ELSIF order_amount >= 1000 THEN
        RAISE NOTICE 'Скидка 5%%';

    ELSE
        RAISE NOTICE 'Без скидки';
    END IF;
END;
$$;
```

В PL/pgSQL используется `ELSIF`, хотя также поддерживается вариант `ELSEIF`.

В Oracle PL/SQL используется `ELSIF`.

В MySQL для составного `IF` используется `ELSEIF`.

В SQL Server применяется `IF ... ELSE`, при необходимости со вложенными условиями.

#### CASE как SQL-выражение

В обычном SQL `CASE` возвращает значение.

```sql
SELECT
    id,
    val,
    CASE
        WHEN id = 1 THEN 'Первый'
        WHEN id = 2 THEN 'Второй'
        ELSE 'Другой'
    END AS description
FROM demo_numbers;
```

Это декларативное выражение, а не процедурный оператор управления выполнением блока.

#### CASE как оператор PL/pgSQL

PL/pgSQL также предоставляет оператор `CASE`.

```sql
DO $$
DECLARE
    current_id INTEGER := 2;
BEGIN
    CASE
        WHEN current_id = 1 THEN
            RAISE NOTICE 'Первый';

        WHEN current_id = 2 THEN
            RAISE NOTICE 'Второй';

        ELSE
            RAISE NOTICE 'Другой';
    END CASE;
END;
$$;
```

Здесь `CASE` выбирает последовательность операторов.

Это не то же самое, что SQL-выражение `CASE ... END`, возвращающее значение.

У процедурного `CASE` в PL/pgSQL также есть особенность: если не предусмотрен `ELSE` и ни одно условие не подошло, может возникнуть ошибка `CASE_NOT_FOUND`.

#### NULL в условиях

Необходимо помнить о трёхзначной логике SQL.

Условие:

```sql
value_num = NULL
```

не является правильным способом проверки на `NULL`.

Следует использовать:

```sql
value_num IS NULL
```

В PL/pgSQL ветка `IF` выполняется только при значении условия `true`.

Если условие возвращает `false` или `NULL`, ветка `THEN` не выполняется.

### Тема 7. Циклы в процедурном SQL

Циклы предназначены для повторного выполнения инструкций.

В PostgreSQL доступны:

- `LOOP`;
- `WHILE`;
- `FOR`;
- `FOREACH`.

Наличие циклов не означает, что обработку каждой строки таблицы следует организовывать через итерации.

Для операций над наборами данных обычно сначала рассматривают обычные SQL-команды.

#### LOOP

Пример:

```sql
DO $$
DECLARE
    counter INTEGER := 0;
BEGIN
    LOOP
        counter := counter + 1;

        RAISE NOTICE 'counter = %', counter;

        EXIT WHEN counter >= 5;
    END LOOP;
END;
$$;
```

`LOOP` не содержит автоматического условия завершения.

Если `EXIT` недостижим, цикл может выполняться бесконечно.

Поэтому при проектировании алгоритма нужно убедиться, что условие выхода обязательно наступит либо предусмотрена возможность прерывания.

#### EXIT

`EXIT` завершает цикл.

```sql
EXIT;
```

С условием:

```sql
EXIT WHEN counter >= 5;
```

Если условие истинно, цикл завершается.

#### CONTINUE

`CONTINUE` пропускает оставшуюся часть текущей итерации и переходит к следующей.

```sql
DO $$
DECLARE
    counter INTEGER := 0;
BEGIN
    LOOP
        counter := counter + 1;

        EXIT WHEN counter > 7;

        CONTINUE WHEN counter % 2 = 0;

        RAISE NOTICE 'Нечётное число: %', counter;
    END LOOP;
END;
$$;
```

Выводятся:

```text
1
3
5
7
```

Здесь условие выхода проверяется до `CONTINUE`.

Это важно: если пропуск итерации располагается перед необходимой проверкой завершения, цикл может оказаться бесконечным.

#### WHILE

Цикл выполняется, пока условие истинно.

```sql
DO $$
DECLARE
    counter INTEGER := 1;
BEGIN
    WHILE counter <= 5 LOOP
        RAISE NOTICE 'counter = %', counter;

        counter := counter + 1;
    END LOOP;
END;
$$;
```

`WHILE` удобен, когда число повторений заранее неизвестно, но существует проверяемое условие продолжения.

#### FOR по числовому диапазону

```sql
DO $$
BEGIN
    FOR i IN 1..5 LOOP
        RAISE NOTICE 'i = %', i;
    END LOOP;
END;
$$;
```

Переменная цикла объявляется неявно и действует в пределах цикла.

Шаг по умолчанию равен 1.

Можно указать шаг:

```sql
DO $$
BEGIN
    FOR i IN 1..10 BY 2 LOOP
        RAISE NOTICE 'i = %', i;
    END LOOP;
END;
$$;
```

Вывод:

```text
1
3
5
7
9
```

Для обратного направления:

```sql
DO $$
BEGIN
    FOR i IN REVERSE 1..5 LOOP
        RAISE NOTICE 'i = %', i;
    END LOOP;
END;
$$;
```

Результат:

```text
5
4
3
2
1
```

#### FOR по результату запроса

```sql
DO $$
DECLARE
    rec RECORD;
BEGIN
    FOR rec IN
        SELECT id, val
        FROM demo_numbers
        ORDER BY id
    LOOP
        RAISE NOTICE 'id = %, val = %',
            rec.id,
            rec.val;
    END LOOP;
END;
$$;
```

На каждой итерации `rec` содержит очередную строку результата.

Здесь явный курсор не требуется: PL/pgSQL самостоятельно обеспечивает обход набора строк.

Но такая обработка остаётся построчной на уровне процедурной логики.

#### FOREACH по массиву

В PostgreSQL массивы можно обрабатывать через `FOREACH`.

```sql
DO $$
DECLARE
    numbers INTEGER[] := ARRAY[10, 20, 30];
    current_number INTEGER;
BEGIN
    FOREACH current_number IN ARRAY numbers LOOP
        RAISE NOTICE 'number = %', current_number;
    END LOOP;
END;
$$;
```

`FOREACH` здесь предназначен именно для массива PostgreSQL.

Он не является универсальным SQL-оператором, одинаково работающим в четырёх СУБД.

Для обработки JSON-массивов используются другие средства, например `jsonb_array_elements` и SQL/JSON-функции.

#### Управление вложенными циклами

В PL/pgSQL можно использовать метки:

```sql
DO $$
BEGIN
    <<outer_loop>>
    FOR i IN 1..3 LOOP
        FOR j IN 1..3 LOOP
            EXIT outer_loop WHEN i = 2 AND j = 2;

            RAISE NOTICE 'i = %, j = %', i, j;
        END LOOP;
    END LOOP;
END;
$$;
```

Метка позволяет указать цикл, который необходимо завершить.

Однако слишком много вложенных циклов и переходов снижает читаемость программы.

### Тема 8. Курсоры и последовательная обработка строк

Курсор предоставляет управляемый доступ к строкам результата запроса.

Типичный жизненный цикл:

1. Объявить курсор.
2. Открыть курсор.
3. Получать строки через `FETCH`.
4. Обработать строки.
5. Закрыть курсор.

#### Пример PostgreSQL

```sql
DO $$
DECLARE
    cursor_demo CURSOR FOR
        SELECT id, val
        FROM demo_numbers
        ORDER BY id;

    rec RECORD;
BEGIN
    OPEN cursor_demo;

    LOOP
        FETCH cursor_demo INTO rec;

        EXIT WHEN NOT FOUND;

        RAISE NOTICE 'id = %, val = %',
            rec.id,
            rec.val;
    END LOOP;

    CLOSE cursor_demo;
END;
$$;
```

`FOUND` после `FETCH` сообщает, удалось ли получить строку.

Если строк больше нет, `FOUND = false`.

#### Зачем нужен курсор, если есть FOR

PL/pgSQL поддерживает:

```sql
FOR rec IN SELECT ... LOOP
```

Во многих простых сценариях это удобнее явного курсора.

Явный курсор полезен, если требуется управлять:

- моментом открытия;
- отдельными операциями получения строк;
- позицией чтения;
- передачей курсора вызывающему коду;
- особенностями продолжительности жизни курсора.

Но нельзя считать, что явный курсор всегда эффективнее неявного перебора.

#### Курсоры и транзакции

В PostgreSQL обычные курсоры связаны с транзакционным контекстом.

Некоторые курсоры могут объявляться с `WITH HOLD`, чтобы оставаться доступными после успешного `COMMIT`.

Но такие курсоры имеют отдельные ограничения и могут потребовать материализации результата.

Следовательно, курсор не всегда означает постоянное обращение к исходной таблице при каждом FETCH.

Поведение зависит от типа курсора, плана запроса и транзакционного режима.

#### SQL Server

Пример T-SQL:

```sql
DECLARE @id INT;
DECLARE @val NVARCHAR(100);

DECLARE cursor_demo CURSOR LOCAL FAST_FORWARD FOR
    SELECT id, val
    FROM dbo.demo_numbers
    ORDER BY id;

OPEN cursor_demo;

FETCH NEXT FROM cursor_demo INTO @id, @val;

WHILE @@FETCH_STATUS = 0
BEGIN
    PRINT CONCAT('id = ', @id, ', val = ', @val);

    FETCH NEXT FROM cursor_demo INTO @id, @val;
END;

CLOSE cursor_demo;
DEALLOCATE cursor_demo;
```

В SQL Server `DEALLOCATE` освобождает ссылку на курсор.

`CLOSE` и `DEALLOCATE` решают разные задачи.

#### MySQL

В MySQL курсоры используются внутри сохранённых программ.

Для завершения чтения обычно применяют обработчик `NOT FOUND`.

Упрощённая схема:

```sql
DECLARE done BOOLEAN DEFAULT FALSE;

DECLARE cursor_demo CURSOR FOR
    SELECT id, val
    FROM demo_numbers;

DECLARE CONTINUE HANDLER FOR NOT FOUND
    SET done = TRUE;
```

Далее курсор открывается и обрабатывается через `FETCH`.

В MySQL порядок объявлений переменных, условий, курсоров и обработчиков имеет значение.

Например, объявления обработчиков размещаются после объявлений курсоров.

#### Oracle

Oracle поддерживает явные и неявные курсоры.

Для последовательного обхода результата часто используется:

```sql
BEGIN
    FOR rec IN (
        SELECT id, val
        FROM demo_numbers
        ORDER BY id
    ) LOOP
        DBMS_OUTPUT.PUT_LINE(
            rec.id || ': ' || rec.val
        );
    END LOOP;
END;
/
```

В этом случае управление открытием, получением строк и закрытием курсора выполняется автоматически.

#### Когда курсоры оправданы

Курсор может быть полезен, если:

- для каждой строки требуется отдельная алгоритмическая операция;
- обработка следующей строки зависит от предыдущего результата;
- требуется контролируемое чтение потока строк;
- используются специальные возможности курсора.

Но если задача сводится к одинаковому изменению множества строк, обычно предпочтительнее один SQL-запрос.

### Тема 9. Множественная обработка против построчной

Рассмотрим таблицу:

```sql
CREATE TABLE product_prices (
    product_id INTEGER PRIMARY KEY,
    price NUMERIC(12, 2) NOT NULL,
    category_id INTEGER NOT NULL
);
```

Необходимо увеличить цены категории 5 на 10%.

#### Построчное решение

Можно написать цикл:

```sql
DO $$
DECLARE
    rec RECORD;
BEGIN
    FOR rec IN
        SELECT product_id
        FROM product_prices
        WHERE category_id = 5
    LOOP
        UPDATE product_prices
        SET price = price * 1.10
        WHERE product_id = rec.product_id;
    END LOOP;
END;
$$;
```

Это технически возможно.

Но количество UPDATE соответствует количеству обработанных строк.

#### Множественное решение

```sql
UPDATE product_prices
SET price = price * 1.10
WHERE category_id = 5;
```

Второй вариант короче и обычно эффективнее.

СУБД может оптимизировать поиск строк и их изменение как одну операцию.

При этом не следует утверждать, что построчная обработка всегда медленнее при любых условиях.

Если каждая итерация содержит действительно независимое и сложное действие, сравнение может быть другим.

Но для обычных массовых изменений SQL множественный подход обычно является первым вариантом, который следует рассмотреть.

#### Почему построчная обработка часто дороже

Дополнительные расходы могут включать:

- многократное выполнение SQL-операторов;
- повторные обращения к индексам;
- переключение между процедурным исполнителем и SQL-исполнителем;
- повторную проверку условий;
- увеличенный объём процедурных операций.

Для оценки необходимо измерять фактическое время, а не полагаться только на общие утверждения.

В PostgreSQL можно использовать:

```sql
EXPLAIN (ANALYZE, BUFFERS)
UPDATE product_prices
SET price = price * 1.10
WHERE category_id = 5;
```

Важно: `EXPLAIN ANALYZE` действительно выполняет UPDATE.

Если нужно исследовать команду без сохранения изменений, её можно выполнить внутри явной транзакции и затем откатить, учитывая возможные нетранзакционные побочные эффекты.

### Тема 10. Обработка исключений

Процедурный код должен учитывать ошибки.

Например:

- нарушение уникальности;
- отсутствие ожидаемой строки;
- деление на ноль;
- неверное преобразование типа;
- конфликт транзакций;
- проблемы с правами доступа.

#### EXCEPTION в PL/pgSQL

```sql
DO $$
DECLARE
    result_value NUMERIC;
BEGIN
    result_value := 10 / 0;

    RAISE NOTICE 'Result = %', result_value;

EXCEPTION
    WHEN division_by_zero THEN
        RAISE NOTICE 'Ошибка: деление на ноль';
END;
$$;
```

В этом случае ошибка перехватывается обработчиком.

#### Обработка конкретных исключений

```sql
DO $$
BEGIN
    INSERT INTO demo_numbers (id, val)
    VALUES (1, 'duplicate');

EXCEPTION
    WHEN unique_violation THEN
        RAISE NOTICE 'Запись с таким ключом уже существует';
END;
$$;
```

Пример предполагает наличие первичного ключа или другого подходящего уникального ограничения на `id`.

#### WHEN OTHERS

Для обработки большинства ошибок можно использовать:

```sql
EXCEPTION
    WHEN OTHERS THEN
        RAISE NOTICE 'Произошла ошибка';
```

Однако бездумное подавление ошибок опасно.

Приложение может получить впечатление, что операция завершилась успешно, хотя часть ожидаемой работы не выполнена.

В PostgreSQL `WHEN OTHERS` не перехватывает некоторые специальные условия, включая `QUERY_CANCELED` и `ASSERT_FAILURE`, если они не указаны явно.

Поэтому не следует описывать его как абсолютный обработчик всех возможных ошибок.

#### Повторная передача ошибки

Если ошибку необходимо зарегистрировать и передать вызывающему коду, можно использовать:

```sql
DO $$
BEGIN
    PERFORM 10 / 0;

EXCEPTION
    WHEN division_by_zero THEN
        RAISE NOTICE 'Зафиксирована ошибка деления на ноль';
        RAISE;
END;
$$;
```

`RAISE;` без аргументов внутри обработчика повторно передаёт текущую ошибку.

#### SQLSTATE

Для точной идентификации ошибок могут использоваться SQLSTATE-коды.

Например:

```text
23505 — unique_violation
23503 — foreign_key_violation
40001 — serialization_failure
40P01 — deadlock_detected
```

Не каждую ошибку следует обрабатывать одинаково.

Нарушение уникальности обычно требует другого решения, чем временный конфликт сериализации.

#### GET STACKED DIAGNOSTICS

В PostgreSQL можно получать подробности об исключении.

```sql
DO $$
DECLARE
    error_message TEXT;
    error_state TEXT;
BEGIN
    PERFORM 10 / 0;

EXCEPTION
    WHEN OTHERS THEN
        GET STACKED DIAGNOSTICS
            error_message = MESSAGE_TEXT,
            error_state = RETURNED_SQLSTATE;

        RAISE NOTICE 'SQLSTATE: %, сообщение: %',
            error_state,
            error_message;
END;
$$;
```

Диагностические данные помогают формировать понятные журналы ошибок.

При этом не следует раскрывать конечным пользователям чувствительную внутреннюю информацию СУБД.

### Тема 11. Исключения и транзакционное поведение

Обработка исключений тесно связана с транзакциями.

Но разные СУБД используют разные правила.

#### PostgreSQL: откат изменений внутри блока EXCEPTION

В PL/pgSQL блок с разделом `EXCEPTION` использует механизм под-транзакции.

Если внутри блока возникает ошибка и она перехватывается, изменения данных, выполненные внутри этого блока до ошибки, откатываются.

При этом локальные переменные сохраняют значения, которые они получили до ошибки.

Пример:

```sql
DO $$
BEGIN
    INSERT INTO demo_numbers (id, val)
    VALUES (10, 'ten');

    BEGIN
        INSERT INTO demo_numbers (id, val)
        VALUES (20, 'twenty');

        RAISE EXCEPTION 'Тестовая ошибка';

    EXCEPTION
        WHEN OTHERS THEN
            RAISE NOTICE 'Внутренний блок отменён';
    END;

    RAISE NOTICE 'Внешний блок продолжается';
END;
$$;
```

После успешного завершения внешнего блока строка с `id = 10` сохраняется.

Строка с `id = 20` не сохраняется, поскольку её вставка была выполнена внутри блока, завершившегося исключением.

Это поведение важно для корректного проектирования частичного восстановления.

#### COMMIT и ROLLBACK в функциях PostgreSQL

Обычная PL/pgSQL-функция не может самостоятельно завершать транзакцию через `COMMIT` или `ROLLBACK`.

Например, следующий замысел некорректен:

```sql
CREATE FUNCTION invalid_function()
RETURNS void
LANGUAGE plpgsql
AS $$
BEGIN
    COMMIT;
END;
$$;
```

Создание определения может быть допустимо, но выполнение приведёт к ошибке транзакционного управления.

Для функций PostgreSQL транзакцией управляет вызывающий контекст.

#### Процедуры PostgreSQL

Начиная с PostgreSQL 11 поддерживаются процедуры с вызовом через `CALL`.

В определённых условиях процедура может выполнять `COMMIT` и `ROLLBACK`.

Но это не безусловная возможность.

Транзакционное управление ограничено:

- контекстом вызова;
- наличием внешнего явного транзакционного блока;
- цепочкой вызовов процедур;
- блоками с обработчиками исключений;
- отдельными атрибутами определения процедуры.

Например, если `CALL` выполняется внутри явно открытой транзакции, процедура не может произвольно завершить эту внешнюю транзакцию.

Также нельзя завершить транзакцию внутри блока с обработчиком `EXCEPTION`.

#### DO и транзакции

Анонимный блок `DO` в PostgreSQL при допустимом контексте вызова также может выполнять команды транзакционного управления.

Но если `DO` находится внутри явного транзакционного блока, такие команды не разрешены.

Поэтому нельзя делать вывод, что каждый процедурный блок PostgreSQL автоматически имеет право выполнять `COMMIT`.

#### SQL Server

В T-SQL ошибки обычно обрабатываются через:

```sql
BEGIN TRY
    BEGIN TRANSACTION;

    -- операции

    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    IF XACT_STATE() <> 0
        ROLLBACK TRANSACTION;

    THROW;
END CATCH;
```

`XACT_STATE()` позволяет определить состояние транзакции.

Это важно, поскольку после некоторых ошибок транзакция может находиться в состоянии, когда подтверждать изменения нельзя.

Поведение также зависит от настроек, включая `XACT_ABORT`.

#### MySQL

MySQL поддерживает обработчики:

```sql
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
    ROLLBACK;
    RESIGNAL;
END;
```

Обычно подобная конструкция размещается внутри сохранённой процедуры после корректных объявлений.

Но вызов `ROLLBACK` требует понимания транзакционного контекста.

Кроме того, некоторые ошибки InnoDB отменяют только оператор, а некоторые — всю транзакцию.

#### Oracle

Oracle использует раздел `EXCEPTION`.

```sql
BEGIN
    -- операции
EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;
        RAISE;
END;
/
```

Однако безусловный `ROLLBACK` внутри любого обработчика может отменить изменения, выполненные вызывающим кодом до входа в блок.

Поэтому границы владения транзакцией должны быть определены явно.

В Oracle также существуют автономные транзакции, но это специализированный механизм, который нельзя считать общим аналогом обычной обработки исключений в PostgreSQL.

### Тема 12. Практика: процедурные конструкции PostgreSQL

Подготовим таблицу для самостоятельного выполнения примеров.

```sql
DROP TABLE IF EXISTS demo_numbers;

CREATE TABLE demo_numbers (
    id INTEGER PRIMARY KEY,
    val TEXT NOT NULL
);

INSERT INTO demo_numbers (id, val)
VALUES
    (1, 'one'),
    (2, 'two'),
    (3, 'three');
```

#### Пример 1. Переменные

```sql
DO $$
DECLARE
    a INTEGER := 10;
    b INTEGER := 20;
    result_value INTEGER;
BEGIN
    result_value := a + b;

    RAISE NOTICE 'result = %', result_value;
END;
$$;
```

#### Пример 2. Получение значения из запроса

```sql
DO $$
DECLARE
    current_value TEXT;
BEGIN
    SELECT val
    INTO STRICT current_value
    FROM demo_numbers
    WHERE id = 2;

    RAISE NOTICE 'value = %', current_value;
END;
$$;
```

#### Пример 3. CASE

```sql
DO $$
DECLARE
    current_id INTEGER := 2;
BEGIN
    CASE current_id
        WHEN 1 THEN
            RAISE NOTICE 'one';

        WHEN 2 THEN
            RAISE NOTICE 'two';

        ELSE
            RAISE NOTICE 'other';
    END CASE;
END;
$$;
```

#### Пример 4. LOOP, CONTINUE и EXIT

```sql
DO $$
DECLARE
    i INTEGER := 0;
BEGIN
    LOOP
        i := i + 1;

        EXIT WHEN i > 7;

        CONTINUE WHEN i % 2 = 0;

        RAISE NOTICE 'i = %', i;
    END LOOP;
END;
$$;
```

#### Пример 5. WHILE

```sql
DO $$
DECLARE
    i INTEGER := 1;
BEGIN
    WHILE i <= 5 LOOP
        RAISE NOTICE 'i = %', i;

        i := i + 1;
    END LOOP;
END;
$$;
```

#### Пример 6. FOR по диапазону

```sql
DO $$
BEGIN
    FOR i IN 1..5 LOOP
        RAISE NOTICE 'i = %', i;
    END LOOP;
END;
$$;
```

#### Пример 7. FOR по строкам таблицы

```sql
DO $$
DECLARE
    rec RECORD;
BEGIN
    FOR rec IN
        SELECT id, val
        FROM demo_numbers
        ORDER BY id
    LOOP
        RAISE NOTICE 'id = %, val = %',
            rec.id,
            rec.val;
    END LOOP;
END;
$$;
```

#### Пример 8. FOREACH

```sql
DO $$
DECLARE
    numbers INTEGER[] := ARRAY[10, 20, 30];
    current_number INTEGER;
BEGIN
    FOREACH current_number IN ARRAY numbers LOOP
        RAISE NOTICE 'number = %', current_number;
    END LOOP;
END;
$$;
```

#### Пример 9. Явный курсор

```sql
DO $$
DECLARE
    cursor_demo CURSOR FOR
        SELECT id, val
        FROM demo_numbers
        ORDER BY id;

    rec RECORD;
BEGIN
    OPEN cursor_demo;

    LOOP
        FETCH cursor_demo INTO rec;

        EXIT WHEN NOT FOUND;

        RAISE NOTICE 'id = %, val = %',
            rec.id,
            rec.val;
    END LOOP;

    CLOSE cursor_demo;
END;
$$;
```

#### Пример 10. Обработка исключения

```sql
DO $$
BEGIN
    INSERT INTO demo_numbers (id, val)
    VALUES (1, 'duplicate');

EXCEPTION
    WHEN unique_violation THEN
        RAISE NOTICE 'Значение id уже существует';
END;
$$;
```

#### Пример 11. Изменение набора данных без цикла

```sql
UPDATE demo_numbers
SET val = upper(val)
WHERE id IN (1, 2);
```

Проверка результата:

```sql
SELECT *
FROM demo_numbers
ORDER BY id;
```

Последний пример демонстрирует, что простую массовую операцию не нужно усложнять процедурным обходом строк.

### Тема 13. Архитектурные границы процедурного кода

Размещение логики в базе данных — архитектурное решение.

Оно влияет на:

- производительность;
- сопровождение;
- переносимость;
- безопасность;
- тестирование;
- управление версиями;
- ответственность между приложением и СУБД.

#### Когда логика в БД оправданна

Процедурный код полезен, если необходимо:

- выполнить несколько тесно связанных SQL-операций;
- минимизировать сетевые обращения;
- обеспечить единый транзакционный контекст;
- централизовать правило, используемое несколькими приложениями;
- реализовать административную операцию;
- выполнить контролируемую миграцию данных;
- обработать специфические ошибки СУБД.

#### Когда лучше использовать приложение

Прикладной слой обычно удобнее для логики, связанной с:

- пользовательскими интерфейсами;
- внешними HTTP API;
- сложными интеграциями;
- распределёнными бизнес-процессами;
- обработкой файлов;
- логикой, требующей многочисленных внешних зависимостей;
- алгоритмами, не связанными непосредственно с работой с данными.

Это не жёсткое правило.

Выбор зависит от архитектуры системы, доступных инструментов и требований.

#### Проблема «толстой базы»

Под «толстой базой» обычно понимают архитектуру, в которой значительная часть бизнес-логики выполняется внутри СУБД.

У такого подхода есть преимущества:

- централизованное выполнение;
- близость к данным;
- уменьшение числа сетевых обращений;
- единая точка реализации некоторых правил.

Но есть и недостатки:

- высокая зависимость от конкретного SQL-диалекта;
- сложность интеграции с обычными инструментами разработки;
- ограниченная горизонтальная масштабируемость вычислений на стороне БД;
- сложность наблюдаемости и отладки;
- риск перегрузить сервер базы дополнительными вычислениями.

Нельзя считать «толстую базу» безусловно плохой архитектурой.

Но её использование должно быть осознанным.

#### Хранение процедурного кода в Git

Исходный код процедур, функций и других объектов базы данных следует хранить в системе контроля версий.

Обычно в репозитории находятся:

- миграции схемы;
- определения процедур;
- определения функций;
- триггерные функции;
- SQL-скрипты;
- тестовые данные и проверки;
- вспомогательные административные команды.

Например:

```text
database/
  migrations/
    V001__create_tables.sql
    V002__add_indexes.sql
    V003__create_procedures.sql
  routines/
    calculate_delivery_fee.sql
    reserve_inventory.sql
  tests/
    test_inventory.sql
```

Сама структура каталогов не является стандартом.

Для доставки изменений могут использоваться:

- Flyway;
- Liquibase;
- Alembic для соответствующих проектов;
- SQL-миграции;
- CI/CD;
- специализированные инструменты управления схемой.

Важно, чтобы изменение базы данных было воспроизводимым и согласованным с версией приложения.

#### Тестирование

Процедурный код требует проверки не только штатного результата, но и ошибок.

Например, для процедуры списания товара необходимо проверить:

1. Достаточный остаток.
2. Недостаточный остаток.
3. Отсутствующий товар.
4. Нулевое количество.
5. Отрицательное количество.
6. Повторный вызов.
7. Параллельные операции.
8. Ошибку внутри транзакции.
9. Корректность отката.
10. Ограничения прав доступа.

Особенно важно тестировать конкурентное выполнение, поскольку корректность обычного одиночного вызова не гарантирует корректность при одновременной работе нескольких клиентов.

## Итоговые выводы

1. **Процедурное программирование дополняет декларативный SQL.** Оно позволяет описывать алгоритмы, состоящие из нескольких действий, условий, циклов и обработки ошибок.

2. **Для массовых операций над данными предпочтительно сначала рассматривать обычный SQL.** Множественные операции часто эффективнее построчной обработки через циклы и курсоры.

3. **Четыре СУБД курса используют различные процедурные диалекты.** PostgreSQL предоставляет PL/pgSQL, SQL Server — T-SQL, MySQL — собственный язык сохранённых программ, Oracle — PL/SQL.

4. **Процедурный блок организует переменные и исполняемую логику.** Его синтаксис не следует смешивать с SQL-командами управления транзакциями.

5. **Переменные позволяют хранить промежуточные результаты.** При получении значений из запросов важно учитывать отсутствие строк, множественные результаты и соответствие типов.

6. **IF и CASE позволяют реализовывать ветвления.** При этом SQL-выражение CASE и процедурный оператор CASE решают разные задачи.

7. **LOOP, WHILE, FOR и FOREACH предоставляют различные способы повторения действий.** Условия завершения циклов должны быть корректными и проверяемыми.

8. **Курсоры обеспечивают последовательное получение строк.** Они полезны в определённых алгоритмах, но не должны автоматически заменять множественные SQL-операции.

9. **Обработка исключений должна сохранять корректность данных.** Перехват ошибки не означает, что операцию можно считать успешно выполненной.

10. **Транзакционное управление зависит от процедурного объекта и СУБД.** В PostgreSQL обычные функции не могут выполнять COMMIT и ROLLBACK, а процедуры и DO-блоки имеют специальные ограничения.

11. **Процедурный код не гарантирует высокую производительность сам по себе.** Необходимо учитывать число SQL-операций, объём данных, блокировки и фактические планы выполнения.

12. **Логику базы данных необходимо сопровождать как обычный программный код.** Она должна храниться в Git, проходить тестирование и доставляться через контролируемые миграции.

13. **Архитектурные границы определяются характером задачи.** Логика, тесно связанная с данными и транзакциями, может быть оправданна внутри СУБД, а внешние интеграции и сложные прикладные процессы часто лучше реализовывать на уровне приложения.

Главный результат занятия — понимание того, как использовать процедурные возможности SQL для решения задач, которые требуют алгоритмической логики, не теряя преимуществ декларативной обработки данных.
