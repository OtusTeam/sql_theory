
# Оптимизация вставки и обновления данных в SQL

## Превью / аннотация / краткое содержание

Занятие посвящено оптимизации операций изменения данных в реляционных СУБД.

Если при чтении основная задача заключается в эффективном поиске и обработке строк, то при вставке, обновлении и удалении СУБД должна изменять физические структуры хранения, поддерживать индексы, проверять ограничения целостности, обеспечивать транзакционность и журналировать изменения.

Поэтому оптимизация DML не сводится к уменьшению времени выполнения одной SQL-команды. Необходимо учитывать пропускную способность, стоимость транзакций, объём журналирования, блокировки, восстановимость и влияние массовых операций на других пользователей.

На занятии рассматриваются:

- особенности нагрузки INSERT, UPDATE и DELETE;
- отличие оптимизации чтения от оптимизации записи;
- транзакционные накладные расходы;
- построчная и пакетная вставка;
- многострочный INSERT и batch insert;
- массовая загрузка через PostgreSQL COPY;
- влияние индексов, ограничений и триггеров;
- генерация идентификаторов и её стоимость;
- WAL и журналы транзакций;
- минимальное журналирование и UNLOGGED-таблицы;
- оптимизация UPDATE и устранение ненужных изменений;
- пакетные обновления;
- блокировки и конкурентный доступ;
- загрузка через staging-таблицы;
- секционирование как механизм загрузки и обслуживания;
- особенности SQL Server, MySQL/InnoDB и Oracle;
- методика измерения эффективности DML.

Основные практические примеры приведены для PostgreSQL. Дополнительно рассматриваются соответствующие механизмы трёх других СУБД курса.

## Основные понятия

**DML (Data Manipulation Language)** — операции изменения данных, включая INSERT, UPDATE и DELETE.

**INSERT** — команда вставки строк в таблицу.

**UPDATE** — команда изменения существующих строк.

**DELETE** — команда удаления строк.

**Транзакция (Transaction)** — логическая единица работы, изменения которой подтверждаются или отменяются согласованно.

**COMMIT** — подтверждение транзакции.

**ROLLBACK** — откат изменений транзакции.

**Autocommit** — режим автоматического подтверждения отдельной SQL-команды при отсутствии явной транзакции.

**Batch Processing** — обработка данных пакетами.

**Batch Insert** — пакетная вставка нескольких строк или групп строк.

**Multi-row INSERT** — одна SQL-команда INSERT с несколькими наборами значений.

**Bulk Load** — специализированная массовая загрузка данных.

**COPY** — команда PostgreSQL для массового импорта и экспорта строк.

**psql \copy** — клиентская команда psql, использующая механизм COPY для передачи данных из файла на стороне клиента.

**BULK INSERT** — команда SQL Server для массовой загрузки данных.

**bcp** — утилита SQL Server для массового импорта и экспорта данных.

**LOAD DATA** — средство MySQL для массовой загрузки данных из файлов.

**SQL*Loader** — инструмент Oracle для массовой загрузки данных.

**External Table** — механизм обращения к внешним данным как к табличному источнику в поддерживающих его СУБД.

**Direct-Path Insert** — механизм Oracle для специализированной высокопроизводительной вставки данных.

**WAL (Write-Ahead Logging)** — механизм журналирования PostgreSQL, позволяющий восстанавливать состояние базы после сбоя.

**Transaction Log** — журнал транзакций SQL Server.

**Redo Log** — журнал восстановления изменений, используемый в InnoDB и Oracle.

**Undo** — информация, позволяющая обеспечивать откат и согласованное чтение в соответствующих СУБД.

**Durability** — свойство транзакций, обеспечивающее сохранность подтверждённых изменений согласно гарантиям конфигурации.

**Минимальное журналирование (Minimal Logging)** — режим выполнения определённых операций с уменьшенным объёмом записи в журнал.

**UNLOGGED TABLE** — таблица PostgreSQL, изменения данных которой не журналируются обычным образом через WAL.

**TEMPORARY TABLE** — временная таблица с ограниченной областью видимости и сроком жизни.

**synchronous_commit** — параметр PostgreSQL, определяющий ожидание синхронной фиксации WAL при завершении транзакции.

**Индекс (Index)** — структура доступа, ускоряющая определённые запросы, но требующая сопровождения при изменениях.

**PRIMARY KEY** — ограничение первичного ключа.

**FOREIGN KEY** — ограничение ссылочной целостности.

**UNIQUE** — ограничение уникальности.

**CHECK** — ограничение допустимых значений.

**Триггер (Trigger)** — автоматически выполняемый программный объект, связанный с определённым событием изменения данных.

**IDENTITY** — механизм автоматической генерации значений столбца.

**SERIAL** — исторически используемая в PostgreSQL форма объявления столбца с последовательностью.

**SEQUENCE** — независимый объект для генерации числовых значений.

**AUTO_INCREMENT** — механизм генерации числовых идентификаторов в MySQL.

**NEWSEQUENTIALID** — функция SQL Server для генерации определённого вида последовательных GUID.

**UUID** — 128-битный идентификатор.

**UUIDv7** — вариант UUID с временной составляющей, полезной, в частности, для приблизительной упорядоченности идентификаторов.

**MVCC** — многоверсионное управление конкурентным доступом.

**HOT Update** — оптимизация PostgreSQL, позволяющая при определённых условиях обновить строку без добавления новых записей в обычные индексы.

**Dead Tuple** — версия строки PostgreSQL, ставшая ненужной для допустимых снимков данных и доступная для очистки.

**VACUUM** — механизм обслуживания PostgreSQL, в том числе очистки мёртвых версий строк.

**Batch Update** — обновление данных ограниченными пакетами.

**Staging Table** — промежуточная таблица для приёма, проверки и преобразования данных.

**Upsert** — операция вставки либо обновления при обнаружении конфликта.

**ON CONFLICT** — механизм PostgreSQL для обработки конфликтов вставки.

**MERGE** — SQL-команда согласования данных источника и целевой таблицы с выполнением поддерживаемых действий.

**SKIP LOCKED** — механизм пропуска строк, заблокированных другими транзакциями.

**Секционирование (Partitioning)** — разделение логической таблицы на физические секции.

**ATTACH PARTITION** — присоединение существующей таблицы в качестве секции PostgreSQL.

**Partition Switching** — механизм SQL Server для переключения секций.

**EXCHANGE PARTITION** — механизм Oracle для обмена секции с таблицей.

**OLTP** — транзакционная нагрузка с частыми операциями над сравнительно небольшими наборами строк.

**OLAP** — аналитическая нагрузка с обработкой больших наборов данных.

**Baseline** — зафиксированный исходный результат измерений.

## Основная часть

### Тема 1. DML-операции как особый вид нагрузки

Операции чтения и изменения данных имеют разные характеристики.

Обычный SELECT получает строки из таблиц и индексов.

INSERT, UPDATE и DELETE дополнительно изменяют физическое состояние базы.

Например:

```sql
INSERT INTO orders (
    customer_id,
    status,
    total_amount
)
VALUES (
    1001,
    'created',
    1500
);
```

В зависимости от структуры таблицы PostgreSQL может выполнять:

1. Формирование новой строки.
2. Получение значения последовательности.
3. Проверку NOT NULL и CHECK.
4. Проверку уникальности.
5. Проверку внешних ключей.
6. Вызов триггеров.
7. Размещение строки в heap.
8. Добавление записей в индексы.
9. Формирование WAL.
10. Подтверждение транзакции.

Это не означает, что все перечисленные механизмы обязательно используются при каждой вставке.

Например, если у таблицы нет внешних ключей или триггеров, соответствующая работа отсутствует.

Но каждая дополнительная структура и проверка потенциально увеличивает стоимость изменения данных.

#### Отличие чтения и записи

При чтении индекс может существенно сократить количество обрабатываемых строк.

При записи индекс становится дополнительной структурой, которую необходимо поддерживать.

При этом индекс также может ускорить поиск строк для UPDATE или DELETE.

Поэтому влияние индекса на DML двойственное:

- ускоряет поиск целевых строк;
- увеличивает стоимость сопровождения изменённых данных.

Например:

```sql
UPDATE orders
SET status = 'completed'
WHERE order_id = 1001;
```

Индекс по `order_id` может сделать поиск строки очень дешёвым.

Но если на таблице существует множество индексов, изменение может потребовать дополнительных операций обслуживания.

#### Почему нельзя оценивать только время одной команды

Пусть два варианта загрузки вставляют миллион строк.

Первый завершает загрузку за 30 секунд, но почти полностью блокирует работу приложения.

Второй завершает её за 45 секунд, сохраняя приемлемое время ответа пользовательских запросов.

Для продуктивной OLTP-системы второй вариант может оказаться предпочтительнее.

Поэтому важны:

- скорость загрузки;
- пропускная способность;
- количество коммитов;
- продолжительность блокировок;
- объём журнала;
- время восстановления;
- влияние на параллельные запросы.

### Тема 2. Транзакции и пакетная организация операций

Каждая операция изменения данных выполняется в транзакционном контексте.

Транзакция обеспечивает атомарность изменений.

В PostgreSQL:

```sql
BEGIN;

INSERT INTO orders (
    customer_id,
    status,
    total_amount
)
VALUES (
    1001,
    'created',
    1500
);

INSERT INTO orders (
    customer_id,
    status,
    total_amount
)
VALUES (
    1002,
    'created',
    2000
);

COMMIT;
```

Обе вставки входят в одну транзакцию.

Если она успешно подтверждена, обе строки становятся зафиксированными.

Если выполняется ROLLBACK, изменения обеих команд отменяются.

#### Почему частые COMMIT могут быть дорогими

Предположим, приложение вставляет 100 000 строк.

В первом варианте оно выполняет:

```text
INSERT
COMMIT
INSERT
COMMIT
...
```

Во втором:

```text
BEGIN
INSERT
INSERT
INSERT
...
COMMIT
```

Во втором случае уменьшается число отдельных транзакционных фиксаций.

Это может сокращать:

- сетевые обмены;
- ожидания подтверждения WAL;
- накладные расходы клиента;
- повторные операции транзакционного управления.

Однако PostgreSQL может использовать механизмы групповой фиксации WAL, поэтому стоимость одного COMMIT не следует считать постоянной и полностью независимой от других транзакций.

#### Почему одна огромная транзакция не всегда лучше

Очень большая транзакция может:

- длительно удерживать блокировки;
- увеличивать объём WAL;
- затруднять обслуживание версий строк;
- создавать дополнительную нагрузку на репликацию;
- требовать длительного отката;
- усложнять восстановление загрузки после ошибки.

Поэтому пакетная обработка часто является компромиссом.

Например:

```text
Пакет 1 → COMMIT
Пакет 2 → COMMIT
Пакет 3 → COMMIT
```

Но это уже несколько независимых транзакций.

Если третий пакет завершится ошибкой, первые два останутся подтверждёнными.

**Разбиение на пакеты меняет атомарность всей бизнес-операции.**

Если требуется принцип «всё или ничего» для всей загрузки, можно отправлять данные несколькими пакетами, но подтверждать их одной транзакцией.

Таким образом, необходимо различать:

- размер сетевого пакета;
- количество строк в SQL-команде;
- границу транзакции.

Они не обязаны совпадать.

### Тема 3. Построчная и многострочная вставка

Рассмотрим таблицу:

```sql
CREATE TABLE import_products (
    product_id BIGINT PRIMARY KEY,
    product_name TEXT NOT NULL,
    price NUMERIC(12, 2) NOT NULL
);
```

#### Построчная вставка

```sql
INSERT INTO import_products
VALUES (1, 'Product 1', 100);

INSERT INTO import_products
VALUES (2, 'Product 2', 200);

INSERT INTO import_products
VALUES (3, 'Product 3', 300);
```

Если приложение отправляет каждую команду отдельно, возникают дополнительные сетевые и серверные расходы.

Но построчная вставка не обязательно означает отдельный COMMIT для каждой строки.

Приложение может выполнять множество отдельных INSERT внутри одной транзакции.

Это быстрее, чем подтверждать каждую строку отдельно, но всё ещё может уступать специализированной пакетной передаче.

#### Многострочный INSERT

```sql
INSERT INTO import_products (
    product_id,
    product_name,
    price
)
VALUES
    (4, 'Product 4', 400),
    (5, 'Product 5', 500),
    (6, 'Product 6', 600);
```

Одна команда вставляет три строки.

Такой способ уменьшает накладные расходы на отправку и разбор большого количества отдельных SQL-команд.

#### INSERT ... SELECT

Если данные уже находятся в базе, можно использовать множественную вставку:

```sql
INSERT INTO import_products (
    product_id,
    product_name,
    price
)
SELECT
    n,
    'Product ' || n::text,
    (n % 1000 + 100)::numeric
FROM generate_series(1000, 10000) AS n;
```

Этот вариант позволяет сформировать набор данных непосредственно на стороне СУБД.

Но нельзя считать INSERT ... SELECT универсально быстрее COPY.

Они предназначены для разных сценариев.

#### Размер многострочного INSERT

Чрезмерно большой SQL-текст может увеличивать:

- стоимость передачи;
- стоимость разбора;
- потребление памяти;
- сложность диагностики;
- размер единичной операции.

Поэтому при больших объёмах обычно используют пакетные методы приложения или специализированные bulk-load механизмы.

### Тема 4. Batch Insert

Batch Insert — общий подход к передаче нескольких строк или операций за один логический пакет.

Он может реализовываться через:

- многострочный INSERT;
- prepared statements;
- пакетные возможности драйвера;
- ORM bulk operations;
- COPY;
- специализированные средства загрузки.

Например, приложение может сформировать пакеты по 1000 строк.

Но универсального оптимального размера пакета не существует.

Он зависит от:

- размера строки;
- числа индексов;
- наличия триггеров;
- задержки сети;
- производительности WAL;
- количества конкурентных операций;
- требований к восстановлению после ошибки.

#### Выбор размера пакета

Для практического сравнения можно исследовать несколько вариантов:

```text
100 строк
1000 строк
5000 строк
10000 строк
```

Эти значения являются вариантами эксперимента, а не рекомендуемыми универсальными настройками.

Следует измерять:

- строк в секунду;
- полное время;
- время отдельных пакетов;
- объём WAL;
- задержку конкурирующих запросов;
- использование CPU и I/O.

#### Обработка ошибок

Если пакет содержит одну некорректную строку, поведение зависит от:

- SQL-команды;
- драйвера;
- СУБД;
- используемого режима импорта;
- транзакционных границ.

Поэтому необходимо заранее определить:

- отменять весь пакет;
- продолжать загрузку допустимых строк;
- сохранять некорректные строки отдельно;
- повторять пакет;
- пропускать уже обработанные записи.

Без такой политики повторная загрузка может создавать дубли.

### Тема 5. Массовая загрузка через COPY в PostgreSQL

Для массовой загрузки PostgreSQL предоставляет команду COPY.

Она позволяет передавать данные в специализированном формате без необходимости формировать отдельный SQL INSERT для каждой строки.

#### COPY FROM

```sql
COPY import_products (
    product_id,
    product_name,
    price
)
FROM '/var/lib/postgresql/import/products.csv'
WITH (
    FORMAT csv,
    HEADER true
);
```

Здесь файл читается серверным процессом PostgreSQL.

Путь относится к файловой системе сервера, а не SQL-клиента.

Для такой операции необходимы соответствующие права доступа.

#### \copy в psql

Если CSV находится на компьютере пользователя, при работе через psql можно использовать:

```text
\copy import_products (product_id, product_name, price)
FROM './products.csv'
WITH (FORMAT csv, HEADER true)
```

`\copy` — команда psql.

Она организует передачу данных между клиентским файлом и PostgreSQL через COPY.

Поэтому файл читается на стороне клиента.

Но это не отдельный SQL-оператор сервера.

#### COPY FROM STDIN

Драйверы PostgreSQL могут отправлять данные как поток.

Пример серверной команды:

```sql
COPY import_products (
    product_id,
    product_name,
    price
)
FROM STDIN
WITH (FORMAT csv);
```

Далее клиент использует протокол COPY для передачи данных.

Такой механизм подходит для загрузки данных, которые уже находятся в памяти приложения или поступают из другого источника.

#### Почему COPY часто быстрее

По сравнению с тысячами отдельных INSERT COPY сокращает:

- повторную передачу SQL-текста;
- количество сетевых запросов;
- накладные расходы на разбор SQL-команд;
- стоимость организации отдельных операций вставки.

Но COPY продолжает соблюдать применимые правила СУБД.

Она не отключает автоматически:

- индексы;
- CHECK;
- NOT NULL;
- внешние ключи;
- триггеры INSERT;
- транзакционное журналирование обычных таблиц.

#### COPY и триггеры

Если у целевой таблицы есть INSERT-триггер, при загрузке через COPY соответствующая логика выполняется.

Поэтому COPY в таблицу с тяжёлым построчным триггером может оказаться значительно медленнее COPY в аналогичную таблицу без такого триггера.

#### Обработка ошибок импорта

В современных версиях PostgreSQL для определённых ошибок преобразования входных данных COPY FROM поддерживает управляемые способы пропуска некорректных строк.

Но это не означает, что любые ошибки ограничений, триггеров или уникальности можно просто игнорировать тем же параметром.

Для сложных проверок и контроля отклонённых строк часто удобнее staging-таблица.

### Тема 6. Индексы как фактор стоимости записи

Индексы ускоряют чтение, но требуют сопровождения при изменении данных.

Создадим таблицу:

```sql
CREATE TABLE products_with_indexes (
    product_id BIGINT PRIMARY KEY,
    category_id INTEGER NOT NULL,
    product_name TEXT NOT NULL,
    price NUMERIC(12, 2) NOT NULL
);
```

Добавим индексы:

```sql
CREATE INDEX idx_products_category
ON products_with_indexes (category_id);
```

```sql
CREATE INDEX idx_products_price
ON products_with_indexes (price);
```

```sql
CREATE INDEX idx_products_name
ON products_with_indexes (product_name);
```

При INSERT необходимо добавить соответствующие индексные записи.

#### Чем больше индексов, тем больше потенциальная стоимость

Каждый индекс может требовать:

- поиска места вставки;
- изменения индексных страниц;
- журналирования;
- разделения страниц;
- обслуживания после UPDATE и DELETE.

Но нельзя утверждать, что стоимость каждого индекса одинакова.

Она зависит от:

- типа индекса;
- размера ключа;
- распределения значений;
- физического состояния структуры;
- локальности вставок;
- количества записей.

#### Загружать данные до создания индексов

При первичной загрузке пустой таблицы иногда выгоднее:

1. Создать таблицу.
2. Загрузить данные.
3. Создать вторичные индексы.
4. Собрать статистику.

Это позволяет СУБД построить индекс по готовому набору строк.

Но данный способ подходит не для всех сценариев.

В продуктивной таблице удаление индексов может ухудшить чтение, нарушить выполнение критичных запросов и потребовать длительного восстановления индексов.

Кроме того, нельзя бездумно удалять индексы, обеспечивающие PRIMARY KEY или UNIQUE.

Для контролируемой первичной загрузки подход полезен, но для обычной OLTP-таблицы требуется отдельное обоснование.

### Тема 7. Ограничения целостности и триггеры

Ограничения целостности повышают стоимость записи, но защищают корректность данных.

К ним относятся:

- PRIMARY KEY;
- UNIQUE;
- FOREIGN KEY;
- CHECK;
- NOT NULL.

Например:

```sql
CREATE TABLE order_items (
    order_id BIGINT NOT NULL REFERENCES orders(order_id),
    product_id BIGINT NOT NULL REFERENCES products(product_id),
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, product_id)
);
```

Каждая вставка должна удовлетворять соответствующим ограничениям.

#### Почему нельзя отключать ограничения без проверки

Предположим, внешние ключи временно отключены.

В таблицу могут попасть строки, ссылающиеся на несуществующие объекты.

После загрузки такие данные не становятся корректными автоматически.

Поэтому безопаснее загрузить их в staging-таблицу, проверить и только затем перенести в основную модель.

#### Триггеры

Триггер может выполнять дополнительные операции при каждой вставке.

Например:

- записывать аудит;
- изменять служебные поля;
- создавать запись outbox;
- обновлять связанную таблицу.

Если одна вставка приводит к нескольким дополнительным INSERT и UPDATE, общая стоимость возрастает.

Но отключение триггера может нарушить бизнес-логику.

Перед оптимизацией необходимо определить его назначение.

#### Массовые операции и строковые триггеры

В PostgreSQL `FOR EACH ROW`-триггер выполняется отдельно для каждой затронутой строки.

Если вставляется миллион строк, триггерная функция может вызываться миллион раз.

Для определённых задач можно рассмотреть statement-level триггер и transition tables.

Но их применение зависит от события и требований к логике.

При проектировании массовой загрузки следует предпочитать множественные операции, когда они способны корректно заменить построчную обработку.

### Тема 8. Генерация идентификаторов

При INSERT часто требуется сформировать уникальный идентификатор.

#### PostgreSQL IDENTITY

```sql
CREATE TABLE events_identity (
    event_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type TEXT NOT NULL
);
```

Значение генерируется через связанный механизм последовательности.

#### SERIAL

```sql
CREATE TABLE events_serial (
    event_id BIGSERIAL PRIMARY KEY,
    event_type TEXT NOT NULL
);
```

`BIGSERIAL` является специальной формой объявления, а не самостоятельным фундаментальным числовым типом PostgreSQL.

#### Последовательности

```sql
CREATE SEQUENCE event_seq;
```

```sql
SELECT nextval('event_seq');
```

Последовательности не гарантируют отсутствие пропусков.

#### Стоимость генерации

Генерация числового идентификатора обычно не является главным ограничением INSERT.

Но при очень интенсивной записи могут иметь значение:

- синхронизация;
- кеширование последовательности;
- распределение ключей;
- поведение индексов.

Для последовательности PostgreSQL можно настроить CACHE.

Однако увеличение CACHE может увеличивать число потенциально пропущенных значений при завершении сеансов или сбоях.

#### UUID

UUID позволяет генерировать идентификаторы без общего числового счётчика.

Но физическое поведение индексов зависит от структуры UUID.

Случайные UUIDv4 могут создавать менее локализованные вставки в B-tree.

UUIDv7 использует временную составляющую и обычно обеспечивает более благоприятную приблизительную упорядоченность значений.

Но UUIDv7 не гарантирует строгий порядок подтверждения транзакций или непрерывную последовательность.

#### SQL Server NEWSEQUENTIALID

В SQL Server можно использовать:

```sql
NEWSEQUENTIALID()
```

для значений GUID в поддерживаемом контексте DEFAULT.

Это помогает уменьшить некоторые проблемы случайного распределения ключей в clustered index.

Но последовательные GUID не следует рассматривать как универсальный механизм безопасности или сокрытия информации.

### Тема 9. WAL и стоимость журналирования

PostgreSQL использует WAL — Write-Ahead Logging.

Журнал предзаписи позволяет восстановить согласованное состояние базы после аварийного завершения.

Основной принцип:

> Необходимая информация о модификациях должна быть надлежащим образом записана в журнал до того, как соответствующие изменения страниц данных считаются устойчиво сохранёнными.

WAL необходим для:

- восстановления после сбоя;
- репликации;
- обеспечения транзакционных гарантий;
- восстановления по журналам в поддерживаемых конфигурациях.

#### Почему WAL может ограничивать INSERT

При массовой загрузке изменяются:

- страницы таблицы;
- страницы индексов;
- служебные структуры.

Изменения требуют журналирования.

Если подсистема хранения WAL перегружена, она может стать ограничивающим ресурсом.

#### Объём WAL

Для диагностики PostgreSQL предоставляет:

```sql
EXPLAIN (
    ANALYZE,
    BUFFERS,
    WAL
)
INSERT INTO some_table (...)
SELECT ...;
```

Показатель WAL доступен в поддерживаемых версиях PostgreSQL.

Пример выполняет INSERT, а не только показывает предполагаемый план.

Для безопасного эксперимента следует использовать отдельную таблицу и контролируемую транзакцию.

#### synchronous_commit

В PostgreSQL параметр:

```sql
SHOW synchronous_commit;
```

определяет поведение ожидания синхронной фиксации журнала при COMMIT.

При:

```sql
SET LOCAL synchronous_commit = off;
```

транзакция может сообщить об успешной фиксации до гарантированного сохранения соответствующего WAL на устойчивом носителе.

Если сервер аварийно завершится, часть недавно подтверждённых изменений может быть потеряна.

Но:

**synchronous_commit = off не означает отключения WAL.**

Изменения по-прежнему журналируются.

Меняется ожидание подтверждения устойчивой записи.

Такой режим нельзя механически применять к критичным операциям ради ускорения.

### Тема 10. Минимальное и отключённое журналирование

Некоторые операции и типы хранения позволяют уменьшить объём журналирования.

Однако возможности четырёх СУБД отличаются.

#### PostgreSQL UNLOGGED

Пример:

```sql
CREATE UNLOGGED TABLE staging_events (
    event_id BIGINT,
    event_type TEXT,
    created_at TIMESTAMPTZ
);
```

Данные такой таблицы не журналируются в WAL обычным способом.

Это может ускорять определённые операции записи.

Но имеются ограничения.

После аварийного завершения PostgreSQL данные UNLOGGED-таблиц автоматически очищаются при восстановлении.

Содержимое таких таблиц не передаётся на физические standby-реплики обычным способом потоковой репликации.

При этом UNLOGGED не означает отсутствия любого WAL в базе.

Метаданные и другие журналируемые операции продолжают использовать соответствующие механизмы PostgreSQL.

#### Когда UNLOGGED подходит

- временный staging;
- пересоздаваемые промежуточные результаты;
- некоторые аналитические расчёты;
- данные, которые можно полностью восстановить из внешнего источника.

#### Когда не подходит

- основные заказы;
- финансовые операции;
- единственные копии пользовательских данных;
- критичные журналы;
- данные, которые должны участвовать в обычной физической репликации.

#### TEMPORARY

Временные таблицы PostgreSQL также имеют особые свойства хранения и журналирования.

Они доступны в рамках соответствующей сессии.

Но TEMPORARY и UNLOGGED — разные механизмы.

UNLOGGED-таблица не становится автоматически временной и может быть доступна разным сессиям при наличии прав.

### Тема 11. Минимальное логирование в SQL Server

В SQL Server существуют recovery models:

- FULL;
- SIMPLE;
- BULK_LOGGED.

Для определённых массовых операций возможно минимальное логирование.

Но оно зависит от дополнительных условий.

Например:

- recovery model;
- структуры таблицы;
- наличия индексов;
- пустоты или заполненности таблицы;
- использования TABLOCK;
- репликации;
- вида bulk-операции.

При минимальном логировании в журнале всё равно фиксируются необходимые сведения о выделении пространства и других действиях.

Поэтому минимальное логирование не означает полного отсутствия transaction log.

#### BULK INSERT

Пример:

```sql
BULK INSERT dbo.import_products
FROM 'C:\data\products.csv'
WITH (
    FORMAT = 'CSV',
    FIRSTROW = 2,
    TABLOCK
);
```

Путь должен быть доступен в соответствующем контексте SQL Server.

Но сам по себе TABLOCK не гарантирует минимальное логирование.

Необходимо соблюдать остальные требования.

#### Recovery Model

Изменение recovery model — эксплуатационное решение.

Например, переход с FULL на BULK_LOGGED влияет на возможности точечного восстановления для журналов, содержащих определённые массовые операции.

Это требует понимания стратегии резервного копирования.

Поэтому нельзя рекомендовать переключение recovery model как обычный универсальный приём ускорения INSERT.

### Тема 12. Массовая загрузка в MySQL/InnoDB и Oracle

#### MySQL/InnoDB

MySQL поддерживает многострочный INSERT:

```sql
INSERT INTO products (
    product_id,
    product_name,
    price
)
VALUES
    (1, 'Product 1', 100),
    (2, 'Product 2', 200),
    (3, 'Product 3', 300);
```

Для загрузки файла используется `LOAD DATA`.

Например:

```sql
LOAD DATA LOCAL INFILE 'products.csv'
INTO TABLE products
FIELDS TERMINATED BY ','
ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 LINES
(product_id, product_name, price);
```

Доступность `LOCAL` зависит от настроек клиента и сервера.

При загрузке необходимо учитывать формат файла, кодировку и правила преобразования данных.

#### Особенности InnoDB

InnoDB использует:

- clustered index;
- secondary indexes;
- redo log;
- undo;
- транзакции;
- механизм блокировок.

При bulk load могут иметь значение:

- отключение autocommit с последующим контролируемым COMMIT;
- многострочная вставка;
- порядок первичного ключа;
- размер пакетов;
- внешние ключи и уникальные ограничения.

#### foreign_key_checks

MySQL позволяет временно изменить:

```sql
SET foreign_key_checks = 0;
```

Однако это опасно для произвольной загрузки.

После возврата:

```sql
SET foreign_key_checks = 1;
```

строки, вставленные при отключённых проверках, не проверяются автоматически задним числом.

Поэтому восстановление настройки не гарантирует целостность уже загруженных данных.

Для учебного и обычного прикладного импорта предпочтительнее сохранить проверки либо выполнять самостоятельную полную валидацию перед переносом данных.

#### Oracle

Oracle предоставляет:

- SQL*Loader;
- external tables;
- direct-path insert;
- INSERT ... SELECT;
- различные bulk-механизмы PL/SQL.

Например:

```sql
INSERT /*+ APPEND */ INTO target_table (
    id,
    value
)
SELECT
    id,
    value
FROM source_table;
```

Подсказка `APPEND` может использоваться для direct-path insert при выполнении соответствующих условий.

Но наличие подсказки не означает, что Oracle обязательно применит её в любой ситуации.

Также direct-path операции имеют ограничения по конкурентному доступу, индексам, триггерам и последующим операциям внутри транзакции.

Поэтому этот механизм требует отдельного изучения.

### Тема 13. UPDATE и физическое изменение строк

UPDATE изменяет значения существующих строк.

Например:

```sql
UPDATE products
SET price = price * 1.10
WHERE category_id = 5;
```

В PostgreSQL UPDATE создаёт новую версию строки в рамках MVCC.

Старая версия сохраняется, пока она необходима для видимости соответствующих транзакций.

#### Почему UPDATE может быть дорогим

Операция может включать:

- поиск подходящих строк;
- блокировку изменяемых строк;
- создание новых версий;
- проверку ограничений;
- выполнение триггеров;
- обслуживание индексов;
- запись WAL;
- последующую очистку устаревших версий.

Особенно дорого может обходиться массовое обновление индексируемых столбцов.

#### HOT Update

PostgreSQL поддерживает Heap-Only Tuple Update.

Если изменяемые столбцы не используются индексами и новая версия помещается на подходящей heap-странице, обновление может быть HOT.

Это позволяет избежать создания новых индексных записей.

Однако отсутствие изменения индексируемых столбцов не гарантирует HOT: важны также физические условия размещения версии строки.

#### Избыточные индексы

Каждый дополнительный индекс может ухудшать стоимость обновлений.

Поэтому таблица с интенсивной DML-нагрузкой не обязательно должна иметь максимум возможных индексов.

Индексирование необходимо согласовывать с профилем чтения и записи.

### Тема 14. Не обновлять неизменившиеся значения

Рассмотрим:

```sql
UPDATE products
SET status = 'active';
```

Даже если часть строк уже имеет `status = 'active'`, PostgreSQL может создать новые версии этих строк.

Это вызывает ненужную запись.

Лучше ограничить обновление:

```sql
UPDATE products
SET status = 'active'
WHERE status IS DISTINCT FROM 'active';
```

`IS DISTINCT FROM` корректно учитывает NULL.

Например:

- NULL отличается от `'active'`;
- `'inactive'` отличается от `'active'`;
- `'active'` не отличается от `'active'`.

#### Многостолбцовое обновление

```sql
UPDATE products
SET
    status = 'active',
    price = 1000
WHERE
    status IS DISTINCT FROM 'active'
    OR price IS DISTINCT FROM 1000;
```

Такой подход исключает строки, где оба значения уже соответствуют требуемым.

Но нельзя утверждать, что он всегда ускоряет запрос.

Сама проверка условий имеет стоимость.

Если обновлению подлежит почти вся таблица, выигрыш может быть небольшим.

Результат нужно измерять.

### Тема 15. Пакетное обновление данных

Массовый UPDATE способен затрагивать сотни тысяч или миллионы строк.

Если операция выполняется одной длительной транзакцией, это может увеличивать:

- время удержания блокировок;
- объём WAL;
- нагрузку на репликацию;
- количество версий строк;
- время отката.

Поэтому иногда полезна пакетная обработка.

#### PostgreSQL и LIMIT

PostgreSQL не поддерживает обычный синтаксис:

```sql
UPDATE products
SET ...
LIMIT 1000;
```

Для ограничения пакета можно использовать CTE.

Например:

```sql
WITH batch AS (
    SELECT product_id
    FROM products
    WHERE status = 'pending'
    ORDER BY product_id
    LIMIT 1000
)
UPDATE products AS p
SET status = 'processed'
FROM batch AS b
WHERE p.product_id = b.product_id;
```

Команда изменяет ограниченный набор строк.

Но если несколько воркеров выполняют такой запрос одновременно, необходимо учитывать конкурентные операции.

#### SKIP LOCKED

Для конкурентной обработки очереди можно использовать:

```sql
WITH batch AS (
    SELECT product_id
    FROM products
    WHERE status = 'pending'
    ORDER BY product_id
    LIMIT 1000
    FOR UPDATE SKIP LOCKED
)
UPDATE products AS p
SET status = 'processed'
FROM batch AS b
WHERE p.product_id = b.product_id
RETURNING p.product_id;
```

Здесь:

- выбирается ограниченная партия;
- строки блокируются;
- уже заблокированные строки пропускаются;
- выбранные строки изменяются;
- возвращаются идентификаторы обработанных строк.

Такой механизм полезен для фоновых воркеров.

Но SKIP LOCKED не гарантирует строгую справедливость.

Некоторые строки могут неоднократно пропускаться при конкуренции.

Также фактическая последовательность обработки не обязана совпадать с глобальным порядком идентификаторов.

#### Транзакционные границы

Если каждую партию подтверждать отдельно, операция становится частично фиксируемой.

При ошибке после нескольких партий предыдущие изменения остаются в базе.

Поэтому необходимы:

- контроль прогресса;
- возможность безопасного повтора;
- идемпотентная логика;
- понятное состояние обработки.

Если требуется атомарность всего обновления, разбивать его на независимо подтверждаемые транзакции нельзя без изменения бизнес-требований.

### Тема 16. UPDATE FROM и множественное изменение

Когда новые значения находятся в другой таблице, можно использовать UPDATE FROM.

Предположим:

```sql
CREATE TABLE product_price_updates (
    product_id BIGINT PRIMARY KEY,
    new_price NUMERIC(12, 2) NOT NULL
);
```

Обновление:

```sql
UPDATE products AS p
SET price = u.new_price
FROM product_price_updates AS u
WHERE p.product_id = u.product_id
  AND p.price IS DISTINCT FROM u.new_price;
```

Преимущества:

- одна SQL-команда;
- множественная обработка;
- отсутствует необходимость выполнять UPDATE отдельно для каждого товара;
- не изменяются строки, где цена уже соответствует требуемой.

#### Важность уникальности источника

Если одному целевому объекту соответствуют несколько строк источника с разными значениями, результат может быть неоднозначным.

Поэтому источник должен обеспечивать корректную кардинальность.

В приведённом примере `PRIMARY KEY (product_id)` гарантирует не более одной строки на товар.

Для импорта из внешнего файла дубли необходимо проверять отдельно.

### Тема 17. UPSERT и повторная загрузка данных

При загрузке часто требуется:

- вставить новую строку;
- обновить существующую;
- избежать дублирования.

PostgreSQL поддерживает:

```sql
INSERT ... ON CONFLICT
```

Пример:

```sql
INSERT INTO products (
    product_id,
    product_name,
    price
)
VALUES (
    1001,
    'Product 1001',
    1500
)
ON CONFLICT (product_id)
DO UPDATE
SET
    product_name = EXCLUDED.product_name,
    price = EXCLUDED.price;
```

#### Избегание ненужного UPDATE

Можно добавить условие:

```sql
INSERT INTO products (
    product_id,
    product_name,
    price
)
VALUES (
    1001,
    'Product 1001',
    1500
)
ON CONFLICT (product_id)
DO UPDATE
SET
    product_name = EXCLUDED.product_name,
    price = EXCLUDED.price
WHERE
    (products.product_name, products.price)
    IS DISTINCT FROM
    (EXCLUDED.product_name, EXCLUDED.price);
```

Это позволяет не выполнять физическое обновление, если данные не изменились.

#### UPSERT и идемпотентность

Upsert может быть частью идемпотентной загрузки.

Но сам по себе ON CONFLICT не гарантирует полную идемпотентность всей бизнес-операции.

Например, триггер может создавать новые события при каждом вызове.

Или приложение может выполнять дополнительные действия вне базы.

Поэтому необходимо определять идемпотентность на уровне полной операции.

### Тема 18. Блокировки и конкурентная DML-нагрузка

При изменении данных СУБД должна синхронизировать конфликтующие операции.

Например, два клиента одновременно обновляют один заказ.

PostgreSQL использует блокировки строк и MVCC для обеспечения допустимого порядка изменений.

#### Длительная транзакция

Предположим:

```sql
BEGIN;

UPDATE orders
SET status = 'completed'
WHERE created_at < TIMESTAMP '2026-01-01';
```

Если обновляется много строк, транзакция может длительно удерживать блокировки.

Другие операции, пытающиеся изменить те же строки, будут ожидать.

Обычный SELECT в PostgreSQL при MVCC часто может продолжать чтение согласованной версии данных без ожидания блокировки строки.

Поэтому неверно утверждать, что любой большой UPDATE полностью блокирует все чтения таблицы.

Но конфликты с DDL, блокирующими SELECT и другими операциями возможны.

#### Deadlock

Если две транзакции захватывают ресурсы в разном порядке, может возникнуть взаимная блокировка.

Для уменьшения риска полезны:

- короткие транзакции;
- единый порядок обработки строк;
- подходящие индексы;
- минимизация объёма изменений;
- корректная обработка ошибок повторного выполнения.

#### Пакетная обработка и OLTP

Пакетные UPDATE часто позволяют уменьшить продолжительность отдельных транзакций.

Но чрезмерное количество маленьких пакетов увеличивает накладные расходы на COMMIT и повторные запросы.

Поэтому размер пакета выбирается измерением.

### Тема 19. Staging-таблицы

Staging — промежуточный слой загрузки.

Он отделяет приём внешних данных от изменения основной бизнес-модели.

Общая схема:

```text
Файл / внешний источник
        ↓
Staging table
        ↓
Проверка и очистка
        ↓
Преобразование
        ↓
Целевая таблица
```

#### Почему staging полезен

Внешние данные могут содержать:

- дубли;
- неверные типы;
- отсутствующие идентификаторы;
- отрицательные значения;
- пустые обязательные поля;
- ошибки кодировки;
- несогласованные справочники.

Если сразу загружать их в основную таблицу, ошибки могут прерывать весь импорт.

Staging позволяет отдельно принять исходные данные и затем проверить их.

#### Создание staging

```sql
CREATE TABLE product_import_stage (
    product_id_text TEXT,
    product_name TEXT,
    price_text TEXT
);
```

Здесь значения первоначально сохраняются как текст.

Это позволяет принять строки, которые пока не прошли проверку числовых типов.

#### Загрузка

```sql
COPY product_import_stage (
    product_id_text,
    product_name,
    price_text
)
FROM '/var/lib/postgresql/import/products.csv'
WITH (
    FORMAT csv,
    HEADER true
);
```

Путь относится к серверной файловой системе.

#### Проверка

Например, выявим строки с пустыми обязательными значениями:

```sql
SELECT *
FROM product_import_stage
WHERE NULLIF(btrim(product_id_text), '') IS NULL
   OR NULLIF(btrim(product_name), '') IS NULL
   OR NULLIF(btrim(price_text), '') IS NULL;
```

#### Проверка числового формата

Можно предварительно проверить:

```sql
SELECT *
FROM product_import_stage
WHERE btrim(product_id_text) !~ '^[0-9]+$'
   OR btrim(price_text) !~ '^[0-9]+([.][0-9]+)?$';
```

Но регулярное выражение проверяет лишь допустимую текстовую форму.

Оно не гарантирует, что значение помещается в целевой числовой тип.

Поэтому после предварительной проверки необходимы контролируемые преобразования.

#### Перенос

После очистки:

```sql
INSERT INTO products (
    product_id,
    product_name,
    price
)
SELECT
    btrim(product_id_text)::BIGINT,
    btrim(product_name),
    btrim(price_text)::NUMERIC(12, 2)
FROM product_import_stage;
```

В рабочем сценарии перед переносом необходимо исключить некорректные и конфликтующие строки.

Staging не отменяет проверку ограничений целевой таблицы.

### Тема 20. UNLOGGED staging и сохранность данных

Для пересоздаваемого промежуточного слоя можно использовать:

```sql
CREATE UNLOGGED TABLE product_import_stage_fast (
    product_id_text TEXT,
    product_name TEXT,
    price_text TEXT
);
```

Такой подход может уменьшить объём обычного WAL для данных staging-таблицы.

Но необходимо учитывать:

- очистку после аварийного завершения;
- отсутствие обычной физической репликации содержимого;
- необходимость повторной загрузки после потери данных;
- отдельный жизненный цикл импорта.

Если staging содержит единственную копию внешних данных, UNLOGGED может быть недопустимым решением.

Если исходный файл надёжно хранится отдельно и импорт можно повторить, такой компромисс иногда оправдан.

### Тема 21. Секционирование при массовой загрузке

Секционирование позволяет разделять большую таблицу на физические части.

Например, события могут храниться по месяцам.

```sql
CREATE TABLE shipment_events (
    event_id BIGINT NOT NULL,
    event_time TIMESTAMP NOT NULL,
    event_type TEXT NOT NULL
)
PARTITION BY RANGE (event_time);
```

Секция:

```sql
CREATE TABLE shipment_events_2026_03
PARTITION OF shipment_events
FOR VALUES FROM ('2026-03-01')
             TO ('2026-04-01');
```

#### Загрузка подготовленной секции

Можно заранее создать отдельную таблицу:

```sql
CREATE TABLE shipment_events_2026_04 (
    LIKE shipment_events
    INCLUDING DEFAULTS
    INCLUDING CONSTRAINTS
);
```

Добавить проверку диапазона:

```sql
ALTER TABLE shipment_events_2026_04
ADD CONSTRAINT shipment_events_2026_04_chk
CHECK (
    event_time >= TIMESTAMP '2026-04-01'
    AND event_time < TIMESTAMP '2026-05-01'
);
```

Затем загрузить и проверить данные.

После этого:

```sql
ALTER TABLE shipment_events
ATTACH PARTITION shipment_events_2026_04
FOR VALUES FROM ('2026-04-01')
             TO ('2026-05-01');
```

#### Преимущества

- загрузка в отдельную таблицу;
- предварительная проверка;
- независимое построение индексов;
- возможность архивирования секциями;
- снижение стоимости удаления старых данных.

#### Ограничения

ATTACH PARTITION требует блокировок.

Если подходящего проверенного CHECK нет, PostgreSQL может сканировать присоединяемую таблицу.

Если существует DEFAULT-секция, возможны дополнительные проверки её данных.

Поэтому операция не является абсолютно неблокирующей.

Также секционирование не гарантирует ускорения всех INSERT.

Маршрутизация по секциям имеет собственную стоимость.

Положительный эффект зависит от ключа секционирования, числа секций и характера нагрузки.

### Тема 22. Практика: подготовка среды для измерений

Создадим отдельную учебную схему.

```sql
CREATE SCHEMA IF NOT EXISTS dml_demo;
```

Таблица для загрузки:

```sql
CREATE TABLE dml_demo.events (
    event_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    event_type TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
);
```

Создадим вторую таблицу для сравнения:

```sql
CREATE TABLE dml_demo.events_unlogged (
    LIKE dml_demo.events
    INCLUDING ALL
);
```

Преобразуем её в UNLOGGED:

```sql
ALTER TABLE dml_demo.events_unlogged
SET UNLOGGED;
```

Этот эксперимент следует выполнять только в отдельной учебной базе.

#### Очистка перед тестом

```sql
TRUNCATE TABLE
    dml_demo.events,
    dml_demo.events_unlogged;
```

TRUNCATE использует специальные блокировки и не эквивалентен массовому DELETE по всем эксплуатационным свойствам.

Поэтому в продуктивной таблице такую команду нельзя запускать без анализа последствий.

### Тема 23. Практика: массовая вставка через INSERT SELECT

Выполним:

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL)
INSERT INTO dml_demo.events (
    event_id,
    customer_id,
    event_type,
    created_at
)
SELECT
    n,
    (n % 10000) + 1,
    CASE
        WHEN n % 5 = 0 THEN 'updated'
        ELSE 'created'
    END,
    TIMESTAMPTZ '2026-01-01 00:00:00+00'
        + n * INTERVAL '1 second'
FROM generate_series(1, 100000) AS n;
```

Команда вставит 100 000 строк.

#### Что измерять

- Execution Time;
- количество обработанных строк;
- BUFFERS;
- WAL records;
- WAL bytes;
- время фиксации транзакции при отдельном измерении.

`EXPLAIN ANALYZE` действительно выполнит INSERT.

Для повторения эксперимента необходимо очистить таблицу либо использовать другие идентификаторы.

### Тема 24. Практика: сравнение обычной и UNLOGGED-таблицы

Повторим аналогичную вставку:

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL)
INSERT INTO dml_demo.events_unlogged (
    event_id,
    customer_id,
    event_type,
    created_at
)
SELECT
    n,
    (n % 10000) + 1,
    CASE
        WHEN n % 5 = 0 THEN 'updated'
        ELSE 'created'
    END,
    TIMESTAMPTZ '2026-01-01 00:00:00+00'
        + n * INTERVAL '1 second'
FROM generate_series(1, 100000) AS n;
```

Сравните:

- Execution Time;
- WAL bytes;
- буферные обращения;
- повторяемость результатов.

Следует помнить, что измерения могут зависеть от кеша и состояния сервера.

Нельзя утверждать, что UNLOGGED обязательно ускорит любую вставку во столько-то раз.

#### Важный вывод

Даже если UNLOGGED быстрее, необходимо отдельно оценить снижение гарантий восстановимости.

Эксперимент демонстрирует компромисс, а не универсальную рекомендацию.

### Тема 25. Практика: влияние индексов

Создадим дополнительный индекс:

```sql
CREATE INDEX idx_dml_events_customer
ON dml_demo.events (customer_id);
```

Очистим таблицу:

```sql
TRUNCATE TABLE dml_demo.events;
```

Повторим массовую вставку.

После этого создадим ещё один индекс:

```sql
CREATE INDEX idx_dml_events_type
ON dml_demo.events (event_type);
```

Снова очистим таблицу и повторим вставку.

#### Сравнение

| Конфигурация | Execution Time | WAL bytes |
|---|---|---|
| Только PRIMARY KEY | Измерить | Измерить |
| PRIMARY KEY + customer_id | Измерить | Измерить |
| PRIMARY KEY + customer_id + event_type | Измерить | Измерить |

Следует учитывать, что создание индексов между опытами изменяет кеш и состояние файлов.

Для более надёжного результата полезно повторить тесты и менять порядок вариантов.

### Тема 26. Практика: обновление без реального изменения значения

Создадим таблицу:

```sql
CREATE TABLE dml_demo.products (
    product_id BIGINT PRIMARY KEY,
    status TEXT NOT NULL,
    price NUMERIC(12, 2) NOT NULL
);
```

Заполним:

```sql
INSERT INTO dml_demo.products (
    product_id,
    status,
    price
)
SELECT
    n,
    CASE
        WHEN n % 2 = 0 THEN 'active'
        ELSE 'inactive'
    END,
    (n % 1000 + 100)::numeric
FROM generate_series(1, 200000) AS n;
```

Соберём статистику:

```sql
ANALYZE dml_demo.products;
```

#### Обновление всех строк

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL)
UPDATE dml_demo.products
SET status = 'active';
```

Команда может создавать новые версии даже для строк, которые уже имели статус `active`.

Для корректного повторяемого сравнения состояния данных между экспериментами должны быть одинаковыми.

#### Обновление только необходимых строк

На вновь подготовленной исходной таблице:

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL)
UPDATE dml_demo.products
SET status = 'active'
WHERE status IS DISTINCT FROM 'active';
```

Этот вариант изменяет только строки с другим статусом.

Сравните:

- число изменённых строк;
- Execution Time;
- WAL bytes;
- обращения к буферам;
- статистику обновлений.

Необходимо понимать, что второй запрос изменяет меньше строк, поэтому это сравнение демонстрирует пользу исключения ненужных изменений, а не превосходство одного синтаксиса при идентичном объёме обновления.

### Тема 27. Практика: пакетный UPDATE

Вернём части строк исходный статус:

```sql
UPDATE dml_demo.products
SET status = 'inactive'
WHERE product_id % 2 = 1;
```

Теперь обработаем одну партию:

```sql
WITH batch AS (
    SELECT product_id
    FROM dml_demo.products
    WHERE status = 'inactive'
    ORDER BY product_id
    LIMIT 1000
    FOR UPDATE SKIP LOCKED
)
UPDATE dml_demo.products AS p
SET status = 'active'
FROM batch AS b
WHERE p.product_id = b.product_id
RETURNING p.product_id;
```

Запрос обработает не более 1000 строк.

Для обработки всех строк приложение или внешний скрипт может повторять такие операции до отсутствия подходящих записей.

Если каждый пакет подтверждается отдельно, необходимо предусмотреть возможность безопасного повторного запуска после сбоя.

#### Что измерять

- время пакета;
- число затронутых строк;
- время COMMIT;
- блокировки;
- объём WAL;
- влияние на конкурентные операции.

Размер пакета следует подбирать экспериментально.

### Тема 28. Методика оптимизации DML

Оптимизацию вставки и обновления следует проводить последовательно.

#### Шаг 1. Определить нагрузку

Необходимо знать:

- количество строк;
- средний размер строки;
- частоту изменений;
- число индексов;
- наличие ограничений;
- наличие триггеров;
- количество параллельных операций.

#### Шаг 2. Измерить исходное состояние

Зафиксировать:

- время;
- rows/sec;
- WAL;
- CPU;
- I/O;
- ожидания;
- блокировки;
- задержки конкурирующих запросов.

#### Шаг 3. Определить причину

Например:

- слишком много отдельных COMMIT;
- большое количество SQL-команд;
- тяжёлые триггеры;
- избыточные индексы;
- высокая стоимость WAL;
- слишком много обновляемых строк;
- долгие транзакции.

#### Шаг 4. Выбрать изменение

Возможные решения:

- объединить отдельные INSERT в пакеты;
- использовать многострочный INSERT;
- использовать COPY;
- загрузить данные через staging;
- исключить ненужные UPDATE;
- изменить индексную стратегию;
- применять контролируемые пакетные UPDATE;
- использовать секции как единицу загрузки.

#### Шаг 5. Проверить корректность

Важно проверить:

- количество строк;
- отсутствие неожиданных дублей;
- ограничения целостности;
- корректность обновлённых значений;
- поведение при повторном запуске;
- восстановление после ошибки.

#### Шаг 6. Повторно измерить

Сравнить исходные и новые показатели в сопоставимых условиях.

#### Шаг 7. Оценить системный эффект

Даже если операция стала быстрее, нужно понять:

- не ухудшилось ли чтение;
- не увеличились ли блокировки;
- сохранились ли гарантии durability;
- не усложнилось ли восстановление;
- не появились ли дополнительные эксплуатационные риски.

## Итоговые выводы

1. **Операции INSERT, UPDATE и DELETE создают дополнительную физическую нагрузку на СУБД.** Помимо изменения строк они могут требовать сопровождения индексов, ограничений, триггеров и журналов.

2. **Оптимизация записи отличается от оптимизации чтения.** Индекс может ускорять поиск, но одновременно увеличивать стоимость вставки и обновления.

3. **Пакетная обработка часто позволяет уменьшить накладные расходы.** Но размер пакета и транзакционная граница должны выбираться отдельно.

4. **Одна большая транзакция не всегда оптимальна.** Она обеспечивает общую атомарность, но может увеличивать время удержания ресурсов и стоимость отката.

5. **Многострочный INSERT и COPY уменьшают стоимость передачи и обработки большого количества строк.** COPY особенно полезна при массовой загрузке из файлов и потоковых источников.

6. **COPY не обходит автоматически ограничения и триггеры.** Её преимущество связано с организацией массового ввода, а не отказом от правил целостности.

7. **Индексы необходимо проектировать с учётом профиля записи.** Избыточное индексирование способно существенно увеличивать стоимость DML.

8. **Триггеры и ограничения обеспечивают важные правила корректности.** Их отключение ради скорости допустимо только в контролируемых сценариях с последующей проверкой данных.

9. **Генерация идентификаторов имеет физическую стоимость, но обычно не является главным ограничителем INSERT.** Тип ключа и характер его распределения также влияют на индексные структуры.

10. **WAL обеспечивает восстановимость и транзакционные гарантии PostgreSQL.** Снижение объёма журналирования или ослабление ожидания фиксации меняет эксплуатационные риски.

11. **UNLOGGED-таблицы подходят для пересоздаваемых данных.** Они не обеспечивают обычных гарантий аварийного восстановления и физической репликации содержимого.

12. **Минимальное логирование в SQL Server зависит от конкретных условий.** Recovery model, структура таблицы и способ массовой загрузки должны рассматриваться совместно.

13. **UPDATE в PostgreSQL создаёт новые версии строк.** Поэтому ненужное обновление уже совпадающих значений способно увеличивать WAL и расходы на VACUUM.

14. **Пакетное обновление помогает управлять нагрузкой, но меняет атомарность при независимой фиксации пакетов.** Для надёжного повторного запуска нужны контроль прогресса и идемпотентность.

15. **Staging позволяет отделить быстрый приём данных от проверки и преобразования.** Это особенно полезно для внешних источников с неоднородным качеством данных.

16. **Секционирование помогает управлять массовой загрузкой и жизненным циклом больших таблиц.** Но не гарантирует ускорения любой вставки и имеет собственные накладные расходы.

17. **Эффективность DML следует оценивать не только временем одной операции.** Необходимо учитывать пропускную способность, WAL, блокировки, конкурентную нагрузку, восстановимость и целостность.

Главный результат занятия — понимание того, что оптимизация записи является балансом между скоростью изменения данных, транзакционными гарантиями, стоимостью сопровождения структур и устойчивостью системы.
