# Основная часть

## Тема 1. Встроенные функции и SQL-диалекты

SQL содержит большое количество операций и функций для обработки значений.

Например:

```text
строка
    ↓
UPPER
    ↓
строка в верхнем регистре
```

или:

```text
число
    ↓
ROUND
    ↓
округлённое число
```

или:

```text
дата и время
    ↓
извлечение месяца
    ↓
номер месяца
```

Но важно понимать:

> SQL стандартизирован не полностью на уровне конкретных имён и возможностей функций.

Одни функции совпадают между СУБД, другие имеют разные названия, синтаксис или семантику.

Например, задача:

> получить текущий момент времени

может быть решена через разные функции и выражения.

Поэтому полезно сначала понимать **операцию**, а затем искать её реализацию в выбранном SQL-диалекте.

---

# Тема 2. Функция работает с определённым типом данных

Рассмотрим:

```sql
UPPER('coffee')
```

Функция получает текст и возвращает текст.

Но выражение:

```sql
UPPER(100)
```

не является естественной строковой операцией.

СУБД может:

- выполнить неявное преобразование;
- потребовать явное преобразование;
- вернуть ошибку.

Поведение зависит от платформы.

Поэтому при чтении SQL полезно спрашивать:

```text
какого типа аргумент?
какого типа результат?
```

Это особенно важно в сложных выражениях.

---

# Тема 3. NULL внутри выражений

`NULL` означает отсутствие известного значения.

Например:

```text
delivered_at = NULL
```

может означать:

> доставка ещё не завершена.

`NULL` не равен:

```text
0
''
FALSE
```

---

## NULL и обычные операции

Рассмотрим:

```sql
price + NULL
```

Во многих обычных выражениях результат тоже будет:

```text
NULL
```

Логика:

> если один из необходимых операндов неизвестен, результат вычисления также неизвестен.

Но функции могут обрабатывать `NULL` по-разному.

Поэтому нельзя использовать универсальное правило:

```text
любая функция с NULL обязательно возвращает NULL
```

Например, `COALESCE` специально предназначен для обработки `NULL`.

---

# Тема 4. Строковые функции

Строковые функции позволяют:

- менять регистр;
- удалять лишние символы;
- извлекать часть строки;
- заменять текст;
- объединять строки;
- измерять длину.

---

## UPPER и LOWER

Пример:

```sql
SELECT UPPER('coffee');
```

Результат:

```text
COFFEE
```

И:

```sql
SELECT LOWER('COFFEE');
```

Результат:

```text
coffee
```

Это полезно, например, при нормализации внешних данных.

Если источник передаёт статусы:

```text
active
ACTIVE
Active
```

можно привести их к единому представлению:

```text
ACTIVE
```

---

# Тема 5. TRIM

`TRIM` удаляет крайние пробелы или другие поддерживаемые символы.

Например:

```sql
TRIM('   coffee   ')
```

даёт:

```text
coffee
```

При загрузке внешних данных это одна из наиболее часто используемых операций.

Например:

```text
" ACTIVE "
    ↓
TRIM
    ↓
"ACTIVE"
```

---

## Не удаляйте пробелы без понимания задачи

Разница:

```text
"New York"
```

и:

```text
"NewYork"
```

семантически важна.

Поэтому `TRIM` обычно используется для очистки **крайних** пробелов, а не для удаления всех пробелов внутри строки.

---

# Тема 6. SUBSTRING

`SUBSTRING` позволяет извлечь часть строки.

Концептуально:

```text
ABCDE
 ↓
BCD
```

Пример стандартоподобного синтаксиса:

```sql
SUBSTRING(code FROM 2 FOR 3)
```

Но конкретный синтаксис отличается между СУБД.

Например, SQL Server обычно использует форму:

```sql
SUBSTRING(code, 2, 3)
```

Поэтому при переносе SQL между платформами необходимо проверять синтаксис.

---

# Тема 7. LEFT и RIGHT

Во многих СУБД существуют функции для получения начала или конца строки.

Например:

```text
ABCDEF
```

первые три символа:

```text
ABC
```

или последние два:

```text
EF
```

Поддержка и точный синтаксис отличаются между платформами.

Например, PostgreSQL, SQL Server и MySQL имеют `LEFT()` и `RIGHT()`.

В Oracle те же задачи часто выражают через `SUBSTR`.

---

# Тема 8. REPLACE

`REPLACE` заменяет часть строки.

Например:

```sql
REPLACE('12,50', ',', '.')
```

может вернуть:

```text
12.50
```

Такая операция полезна при нормализации внешних значений.

Но её нужно использовать только при понятном формате данных.

Если строка:

```text
1,234.50
```

использует запятую как разделитель тысяч, простая замена:

```text
, → .
```

испортит значение.

---

# Тема 9. TRANSLATE и REPLACE — не одно и то же

В СУБД можно встретить функции:

```text
REPLACE
TRANSLATE
```

Они решают разные задачи.

`REPLACE` обычно заменяет одну подстроку другой.

`TRANSLATE` работает ближе к посимвольному сопоставлению.

Конкретный синтаксис и возможности зависят от платформы.

Поэтому:

```text
REPLACE != TRANSLATE
```

---

# Тема 10. Длина строки

Даже простая задача:

> посчитать длину строки

имеет платформенные нюансы.

Можно встретить:

```text
PostgreSQL → LENGTH / CHAR_LENGTH
SQL Server → LEN
MySQL      → CHAR_LENGTH / LENGTH
Oracle     → LENGTH
```

Особенно важно различать:

```text
количество символов
```

и:

```text
количество байтов
```

Например, в MySQL:

```text
CHAR_LENGTH
```

считает символы, а:

```text
LENGTH
```

— байты.

Для Unicode-строк это может дать разные результаты.

---

# Тема 11. Конкатенация строк

Конкатенация объединяет несколько строк.

Например:

```text
'Анна' + ' ' + 'Иванова'
```

должна дать:

```text
Анна Иванова
```

Но синтаксис различается.

---

## PostgreSQL и Oracle

Обычно используется оператор:

```sql
||
```

Например:

```sql
first_name || ' ' || last_name
```

---

## SQL Server

Традиционно используется:

```sql
+
```

Например:

```sql
first_name + ' ' + last_name
```

Также существует функция:

```sql
CONCAT(...)
```

---

## MySQL

Обычно используется:

```sql
CONCAT(...)
```

Например:

```sql
CONCAT(first_name, ' ', last_name)
```

Оператор `||` в стандартной конфигурации MySQL не следует считать переносимым оператором конкатенации.

---

# Тема 12. Конкатенация и NULL

Это место особенно опасно для переносимости.

Например:

```text
first_name = 'Анна'
middle_name = NULL
```

Результат объединения зависит:

- от выбранной функции;
- от оператора;
- от СУБД;
- иногда от настроек.

Поэтому нельзя переносить правило:

> NULL при конкатенации всегда превращается в пустую строку

между платформами.

Если бизнес-логика требует конкретного поведения, его лучше выразить явно.

Например:

```sql
COALESCE(middle_name, '')
```

при условии, что `NULL` действительно следует интерпретировать как пустой текст.

---

# Тема 13. Числовые функции

SQL предоставляет множество математических функций.

Часто используются:

```text
ABS
ROUND
FLOOR
CEIL / CEILING
POWER
SQRT
```

---

## ABS

Модуль числа:

```sql
ABS(-10)
```

Результат:

```text
10
```

---

## POWER

Возведение в степень:

```sql
POWER(2, 3)
```

Результат:

```text
8
```

---

## SQRT

Квадратный корень:

```sql
SQRT(25)
```

Результат:

```text
5
```

Конкретные допустимые аргументы и тип результата зависят от СУБД.

---

# Тема 14. ROUND

`ROUND` используется для округления.

Например:

```sql
ROUND(123.456, 2)
```

концептуально даёт значение с двумя знаками после десятичного разделителя.

Но правила округления, допустимые типы и поведение для отрицательного количества знаков могут различаться между платформами.

Поэтому для финансовых расчётов важно:

- понимать используемый числовой тип;
- понимать правила округления;
- не смешивать `FLOAT` и точные денежные значения без необходимости.

---

# Тема 15. FLOOR и CEIL

`FLOOR` возвращает ближайшее целое в сторону меньшего значения.

Например:

```text
FLOOR(5.8) → 5
```

Но для отрицательного числа:

```text
FLOOR(-5.2) → -6
```

Потому что:

```text
-6 < -5.2
```

---

`CEIL` / `CEILING` выполняет противоположную операцию:

```text
CEIL(5.2) → 6
```

Названия поддерживаемых функций различаются между СУБД.

---

# Тема 16. Деление и типы операндов

Операция:

```sql
5 / 2
```

не обязана давать одинаковый результат во всех SQL-диалектах и при всех типах данных.

Результат зависит от типов операндов.

Поэтому если нужен дробный результат, лучше явно обеспечить подходящий тип.

Концептуально:

```sql
CAST(5 AS DECIMAL(10,2)) / 2
```

Так намерение становится очевиднее.

Не следует рассчитывать на то, что одна и та же запись с целыми литералами ведёт себя одинаково во всех СУБД.

# Тема 17. Работа с датой и временем

Типичные задачи:

```text
получить текущую дату
получить текущий момент
добавить несколько дней
вычесть даты
получить год
получить месяц
найти начало месяца
сгруппировать данные по дню
```

Общая бизнес-задача одинакова, но функции разных СУБД заметно отличаются.

# Тема 18. Текущая дата и время

Можно встретить стандартные выражения:

```text
CURRENT_DATE
CURRENT_TIMESTAMP
```

Но платформы имеют и собственные функции.

Например:

```text
PostgreSQL
    CURRENT_DATE
    CURRENT_TIMESTAMP
    now()

SQL Server
    GETDATE()
    SYSDATETIME()
    SYSDATETIMEOFFSET()

MySQL
    CURRENT_DATE
    CURRENT_TIMESTAMP
    NOW()

Oracle
    CURRENT_DATE
    CURRENT_TIMESTAMP
    SYSTIMESTAMP
```

Эти функции не всегда имеют абсолютно одинаковую семантику.

Особенно важно понимать:

```text
часовой пояс
точность
локальное время сессии
время сервера
```

# Тема 19. Извлечение части даты

Типичная задача:

> получить год из даты.

Можно встретить стандартоподобную конструкцию:

```sql
EXTRACT(YEAR FROM created_at)
```

Она поддерживается несколькими СУБД.

Но платформы также предоставляют свои функции.

Например, SQL Server широко использует:

```sql
DATEPART(year, created_at)
```

или:

```sql
YEAR(created_at)
```

---

# Тема 20. Начало периода

В аналитике часто необходимо преобразовать:

```text
2026-09-17 13:45
```

в:

```text
2026-09-01 00:00
```

то есть получить начало месяца.

В PostgreSQL используется:

```sql
date_trunc('month', created_at)
```

В SQL Server современных версий существует:

```sql
DATETRUNC(month, created_at)
```

В Oracle часто используется:

```sql
TRUNC(created_at, 'MM')
```

В MySQL задача выражается другими функциями работы с датами.

Это хороший пример того, что функция по смыслу одинакова, но SQL-код платформозависим.

---

# Тема 21. Добавление и вычитание времени

Например:

> добавить семь дней.

В PostgreSQL естественно использовать:

```sql
created_at + INTERVAL '7 days'
```

SQL Server использует:

```sql
DATEADD(day, 7, created_at)
```

MySQL:

```sql
DATE_ADD(created_at, INTERVAL 7 DAY)
```

Oracle предоставляет собственную модель арифметики дат и interval-типы.

Поэтому работу с датами почти всегда необходимо проверять для конкретной СУБД.

---

# Тема 22. Разница между датами

Задача:

> сколько времени прошло между двумя моментами?

не имеет одного универсального решения.

Можно считать:

```text
дни
часы
минуты
календарные месяцы
полные годы
```

Это разные метрики.

Например:

```text
31 января → 28 февраля
```

может быть:

```text
28 дней
```

но одновременно:

```text
один календарный месяц
```

в определённой бизнес-логике.

Поэтому сначала необходимо определить, **что именно означает разница**, а затем выбирать функцию.

# Тема 23. Форматирование даты — это вывод, а не сама дата

Представим дату:

```text
2026-10-09
```

Для пользователя её можно показать:

```text
09.10.2026
```

или:

```text
October 9, 2026
```

Но это не означает, что значение внутри базы должно храниться строкой:

```text
'09.10.2026'
```

Правильнее хранить типизированное значение даты, а форматировать его на этапе представления.

---

## Почему это важно

Если даты хранятся строками:

```text
01.12.2026
10.01.2026
20.11.2026
```

обычная строковая сортировка может не соответствовать хронологическому порядку.

Тип `DATE` понимает календарную семантику значения.

# Тема 24. Агрегатные функции

Агрегатная функция получает набор строк и возвращает сводный результат.

Основные агрегаты:

```text
COUNT
SUM
AVG
MIN
MAX
```

Например:

```sql
SELECT COUNT(*)
FROM orders;
```

возвращает количество строк.

---

# Тема 25. COUNT(*) и COUNT(column)

Это разные выражения.

---

## COUNT(*)

```sql
COUNT(*)
```

считает строки.

Строка учитывается независимо от наличия `NULL` в отдельных столбцах.

---

## COUNT(column)

```sql
COUNT(delivered_at)
```

считает только строки, где:

```text
delivered_at IS NOT NULL
```

---

## Пример

Есть данные:

| order_id | delivered_at |
|---:|---|
| 1 | 2026-10-01 |
| 2 | NULL |
| 3 | 2026-10-02 |

Тогда:

```text
COUNT(*)            = 3
COUNT(delivered_at) = 2
```

Это очень важное различие.

---

# Тема 26. SUM и AVG

`SUM` суммирует значения.

Например:

```sql
SELECT SUM(total_amount)
FROM orders;
```

---

`AVG` вычисляет среднее.

```sql
SELECT AVG(total_amount)
FROM orders;
```

Большинство обычных агрегатных функций игнорирует `NULL`.

То есть:

```text
10
20
NULL
```

для `AVG` обычно означает среднее:

```text
(10 + 20) / 2
```

а не:

```text
(10 + 20 + 0) / 3
```

Это принципиально разные бизнес-смыслы.

---

# Тема 27. MIN и MAX

`MIN` и `MAX` находят минимальное и максимальное значение.

Например:

```sql
SELECT
    MIN(total_amount),
    MAX(total_amount)
FROM orders;
```

Эти функции применимы не только к числам.

В зависимости от типа и СУБД они могут работать с:

- датами;
- строками;
- другими сравнимыми типами.

Но смысл сравнения определяется типом, collation и платформой.

---

# Тема 28. GROUP BY

`GROUP BY` разбивает строки на группы.

Например:

```sql
SELECT
    store_id,
    COUNT(*) AS order_count
FROM orders
GROUP BY store_id;
```

Получаем:

```text
одна строка результата
на один store_id
```

---

## Без GROUP BY

```sql
SELECT COUNT(*)
FROM orders;
```

даёт один итог для всей таблицы.

---

## С GROUP BY

```sql
SELECT
    store_id,
    COUNT(*)
FROM orders
GROUP BY store_id;
```

даёт отдельный итог для каждого магазина.

---

# Тема 29. Что можно выводить при GROUP BY

В обычном агрегатном запросе выражение в `SELECT` должно:

- либо участвовать в группировке;
- либо быть вычислено агрегатной функцией;
- либо быть допустимо по правилам функциональной зависимости конкретной СУБД.

Например:

```sql
SELECT
    store_id,
    COUNT(*)
FROM orders
GROUP BY store_id;
```

корректно.

А запрос:

```sql
SELECT
    store_id,
    created_at,
    COUNT(*)
FROM orders
GROUP BY store_id;
```

в строгой модели проблематичен:

> какое из множества `created_at` внутри группы следует вернуть?

MySQL исторически имел более разрешительное поведение в некоторых режимах, однако на курсе используется `ONLY_FULL_GROUP_BY`.

Поэтому лучше писать SQL с однозначной семантикой.

---

# Тема 30. WHERE и HAVING

`WHERE` фильтрует строки **до группировки**.

Например:

```sql
SELECT
    store_id,
    COUNT(*) AS order_count
FROM orders
WHERE current_status = 'DELIVERED'
GROUP BY store_id;
```

Сначала выбираются доставленные заказы.

После этого они группируются.

---

`HAVING` фильтрует **группы после агрегирования**.

Например:

```sql
SELECT
    store_id,
    COUNT(*) AS order_count
FROM orders
WHERE current_status = 'DELIVERED'
GROUP BY store_id
HAVING COUNT(*) >= 100;
```

Получаем только магазины, у которых не меньше ста доставленных заказов.

---

## Логическая последовательность

```text
FROM
 ↓
WHERE
 ↓
GROUP BY
 ↓
HAVING
 ↓
SELECT
 ↓
ORDER BY
```

Это логическая модель обработки.

Физический план выполнения оптимизатор может построить иначе.

---

# Тема 31. COUNT(DISTINCT ...)

Для подсчёта уникальных значений используется:

```sql
COUNT(DISTINCT customer_id)
```

Например:

```sql
SELECT
    store_id,
    COUNT(DISTINCT customer_id) AS customer_count
FROM orders
GROUP BY store_id;
```

Так мы считаем:

```text
количество разных клиентов
```

а не:

```text
количество заказов
```

---

# Тема 32. DISTINCT — не способ исправлять неправильный JOIN

Представим, что после соединения:

```sql
JOIN
```

мы ожидали 100 строк, а получили 1000.

Самое простое:

```sql
SELECT DISTINCT ...
```

Но это может скрыть ошибку модели соединения.

Сначала необходимо понять:

- какая кардинальность связи;
- почему строки размножились;
- соответствует ли это бизнес-смыслу.

`DISTINCT` следует применять, когда уникальность результата действительно является частью задачи.

---

# Тема 33. Строковая агрегация

Иногда нужно получить:

```text
одна группа
→ список текстовых значений
```

Например:

| order_id | products |
|---:|---|
| 100 | Coffee, Milk, Bread |

Эту задачу разные СУБД решают разными функциями.

---

## PostgreSQL

Используется:

```text
STRING_AGG
```

Например:

```sql
STRING_AGG(product_name, ', ')
```

---

## SQL Server

Также используется:

```text
STRING_AGG
```

Для управления порядком используется синтаксис `WITHIN GROUP`.

---

## MySQL

Используется:

```text
GROUP_CONCAT
```

Например концептуально:

```sql
GROUP_CONCAT(product_name ORDER BY product_name SEPARATOR ', ')
```

---

## Oracle

Используется:

```text
LISTAGG
```

Например:

```sql
LISTAGG(product_name, ', ')
    WITHIN GROUP (ORDER BY product_name)
```

---

# Тема 34. Порядок при строковой агрегации

Если итог должен быть воспроизводимым:

```text
Bread, Coffee, Milk
```

а не произвольным:

```text
Milk, Bread, Coffee
```

порядок необходимо задавать явно.

Например:

```text
ORDER BY product_name
```

в синтаксисе соответствующей функции.

Без явного порядка нельзя считать последовательность элементов гарантированной.

---

# Тема 35. NULL в строковой агрегации

Большинство строковых агрегаторов пропускает `NULL`-значения.

Но конкретные:

- правила;
- максимальный размер результата;
- обработка переполнения;
- синтаксис сортировки;

зависят от СУБД.

Например, Oracle `LISTAGG` имеет собственные возможности контроля переполнения результата, а MySQL `GROUP_CONCAT` зависит от соответствующих ограничений конфигурации.

Поэтому строковая агрегация — явно платформозависимая область.

---

# Тема 36. Расширенные группировки

Иногда одного:

```sql
GROUP BY store_id, category_id
```

недостаточно.

Нужно одновременно получить:

```text
по магазину и категории
итог по магазину
общий итог
```

Для этого существуют расширенные формы группировки.

---

# Тема 37. ROLLUP

`ROLLUP` создаёт иерархические уровни итогов.

Представим группировку:

```text
year
month
```

Обычный `GROUP BY` даёт:

```text
2026 / 01
2026 / 02
2026 / 03
```

`ROLLUP` может дополнительно дать:

```text
итог за 2026
общий итог
```

---

## Концептуально

```sql
GROUP BY ROLLUP (year, month)
```

формирует группы:

```text
(year, month)
(year)
()
```

Порядок выражений имеет значение.

---

# Тема 38. CUBE

`CUBE` формирует все комбинации заданных измерений.

Для:

```text
store
category
```

можно получить:

```text
store + category
store
category
общий итог
```

Концептуально:

```sql
GROUP BY CUBE (store_id, category_id)
```

Число комбинаций быстро растёт с увеличением количества измерений.

Поэтому `CUBE` необходимо использовать осознанно.

---

# Тема 39. ROLLUP и CUBE отличаются между платформами

PostgreSQL, SQL Server и Oracle поддерживают развитые возможности:

```text
ROLLUP
CUBE
GROUPING SETS
```

MySQL поддерживает `ROLLUP`, в том числе современную форму:

```sql
GROUP BY ROLLUP (...)
```

и традиционную:

```sql
GROUP BY ... WITH ROLLUP
```

Но нельзя считать весь набор `CUBE / GROUPING SETS` одинаково доступным во всех четырёх СУБД.

Поэтому расширенные группировки следует проверять для выбранного диалекта.

---

# Тема 40. NULL в строках итогов

При `ROLLUP` или `CUBE` появляются строки, где группировочное значение выглядит как:

```text
NULL
```

Но возникает проблема.

`NULL` может означать:

```text
реальное NULL из исходных данных
```

или:

```text
строка итога по этому измерению
```

Для различения используется функция семейства:

```text
GROUPING(...)
```

Например концептуально:

```text
GROUPING(store_id) = 1
```

может означать, что `NULL` появился из-за уровня агрегирования.

Это надёжнее, чем пытаться определить итог только через:

```sql
store_id IS NULL
```

---

# Тема 41. Оконные функции

Обычный `GROUP BY` уменьшает детализацию.

Например:

```sql
SELECT
    store_id,
    AVG(total_amount)
FROM orders
GROUP BY store_id;
```

вернёт:

```text
одна строка на магазин
```

Исходные заказы исчезнут из результата.

---

Оконная функция позволяет сохранить каждую строку:

```text
заказ
+
среднее по его магазину
```

Например:

```sql
SELECT
    order_id,
    store_id,
    total_amount,
    AVG(total_amount) OVER (
        PARTITION BY store_id
    ) AS store_avg
FROM orders;
```

Результат:

| order_id | store_id | total_amount | store_avg |
|---:|---:|---:|---:|
| 1 | 10 | 1000 | 1500 |
| 2 | 10 | 2000 | 1500 |
| 3 | 20 | 500 | 500 |

Строки не схлопнулись.

---

# Тема 42. OVER

Ключевой элемент оконной функции:

```sql
OVER (...)
```

Например:

```sql
AVG(total_amount) OVER (...)
```

означает:

> посчитать `AVG`, но не как обычную агрегатную функцию, схлопывающую строки, а как оконную.

Окно определяет набор строк, относительно которого выполняется расчёт для текущей строки.

---

# Тема 43. PARTITION BY

`PARTITION BY` разделяет результат на независимые окна.

Например:

```sql
AVG(total_amount) OVER (
    PARTITION BY store_id
)
```

означает:

```text
для каждого заказа
посчитать среднее
только среди заказов того же магазина
```

Без:

```sql
PARTITION BY
```

окном может быть весь набор строк результата.

---

# Тема 44. ORDER BY внутри окна

Оконное:

```sql
ORDER BY
```

задаёт порядок строк **внутри вычисления функции**.

Например:

```sql
ROW_NUMBER() OVER (
    PARTITION BY store_id
    ORDER BY created_at
)
```

Это не то же самое, что финальный:

```sql
ORDER BY
```

запроса.

Запрос может выглядеть так:

```sql
SELECT
    ...,
    ROW_NUMBER() OVER (
        PARTITION BY store_id
        ORDER BY created_at
    ) AS rn
FROM orders
ORDER BY order_id;
```

Внутренний `ORDER BY` определяет номера.

Внешний `ORDER BY` определяет порядок строк в итоговом результате.

---

# Тема 45. ROW_NUMBER

`ROW_NUMBER` нумерует строки:

```text
1
2
3
4
...
```

Например:

```sql
ROW_NUMBER() OVER (
    PARTITION BY customer_id
    ORDER BY created_at
)
```

даёт порядковый номер заказа каждого клиента.

---

## Детерминированность

Если:

```text
created_at
```

одинаков у нескольких строк, их взаимный порядок может быть не определён.

Если нужен стабильный результат, следует добавить уникальный tie-breaker.

Например:

```sql
ORDER BY
    created_at,
    order_id
```

Теперь порядок однозначнее.

---

# Тема 46. RANK

`RANK` присваивает одинаковый ранг строкам с одинаковым значением сортировки.

Например:

```text
100 → 1
90  → 2
90  → 2
80  → 4
```

Обратите внимание:

```text
ранг 3 пропущен
```

---

# Тема 47. DENSE_RANK

`DENSE_RANK` также присваивает одинаковый ранг равным значениям, но не оставляет пропусков.

```text
100 → 1
90  → 2
90  → 2
80  → 3
```

---

# Тема 48. ROW_NUMBER, RANK и DENSE_RANK

Сравним:

| Значение | ROW_NUMBER | RANK | DENSE_RANK |
|---:|---:|---:|---:|
| 100 | 1 | 1 | 1 |
| 90 | 2 | 2 | 2 |
| 90 | 3 | 2 | 2 |
| 80 | 4 | 4 | 3 |

Используем:

```text
ROW_NUMBER
```

когда каждой строке нужен собственный номер.

Используем:

```text
RANK
```

когда одинаковые значения должны иметь одинаковый ранг, а пропуски соответствуют числу предыдущих строк.

Используем:

```text
DENSE_RANK
```

когда одинаковые значения имеют один ранг, но шкала должна оставаться плотной.

---

# Тема 49. LAG

`LAG` позволяет получить значение **предыдущей строки** относительно оконного порядка.

Например:

```sql
LAG(total_amount) OVER (
    PARTITION BY customer_id
    ORDER BY created_at
)
```

Для каждого заказа получаем сумму предыдущего заказа клиента.

---

## Сравнение с предыдущим значением

```sql
SELECT
    order_id,
    total_amount,
    LAG(total_amount) OVER (
        ORDER BY created_at
    ) AS previous_amount
FROM orders;
```

Теперь можно вычислить изменение:

```text
текущая сумма - предыдущая сумма
```

без self join.

---

# Тема 50. LEAD

`LEAD` работает в другую сторону.

Он получает значение следующей строки.

Например:

```sql
LEAD(created_at) OVER (
    PARTITION BY customer_id
    ORDER BY created_at
)
```

позволяет для каждого заказа получить дату следующего заказа клиента.

---

# Тема 51. LAG и LEAD зависят от порядка

Без понятного:

```sql
ORDER BY
```

понятие:

```text
предыдущая строка
следующая строка
```

не имеет бизнес-смысла.

Поэтому перед использованием `LAG` или `LEAD` нужно определить:

> относительно какого порядка строки считаются соседними?

Например:

```text
по времени
по версии
по номеру операции
```

---

# Тема 52. Агрегаты как оконные функции

Многие обычные агрегаты можно использовать с `OVER`.

Например:

```sql
SUM(total_amount) OVER (...)
```

или:

```sql
AVG(total_amount) OVER (...)
```

или:

```sql
MAX(total_amount) OVER (...)
```

Разница:

```text
SUM(...) без OVER
→ обычный агрегат

SUM(...) OVER (...)
→ оконный агрегат
```

---

# Тема 53. Накопительный итог

Представим заказы:

| created_at | amount |
|---|---:|
| 01.01 | 100 |
| 02.01 | 50 |
| 03.01 | 200 |

Накопительный итог:

| created_at | amount | running_total |
|---|---:|---:|
| 01.01 | 100 | 100 |
| 02.01 | 50 | 150 |
| 03.01 | 200 | 350 |

Можно рассчитать оконным `SUM`.

---

## Лучше явно задавать frame

Например:

```sql
SUM(total_amount) OVER (
    ORDER BY created_at, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING
             AND CURRENT ROW
)
```

Логика:

```text
от первой строки окна
до текущей строки
```

---

# Тема 54. Что такое window frame

`PARTITION BY` определяет раздел данных.

`ORDER BY` задаёт порядок.

А **frame** определяет конкретную часть упорядоченного раздела, которая участвует в расчёте для текущей строки.

Например:

```text
все строки от начала до текущей
```

или:

```text
текущая строка + три предыдущие
```

или:

```text
все строки раздела
```

---

# Тема 55. ROWS и RANGE — не одно и то же

Очень частая ошибка:

```sql
SUM(amount) OVER (
    ORDER BY created_at
)
```

и ожидание, что это всегда означает:

```text
суммировать строки одну за другой
```

Поведение default frame зависит от SQL-диалекта и оконной конструкции.

Особенно важно понятие **peer rows** — строк с одинаковым значением сортировки.

Поэтому для классического накопительного итога безопаснее явно написать:

```sql
ROWS BETWEEN UNBOUNDED PRECEDING
         AND CURRENT ROW
```

если именно построчное накопление является требуемой логикой.

---

# Тема 56. Пример с одинаковой датой

Есть данные:

| order_id | created_at | amount |
|---:|---|---:|
| 1 | 10:00 | 100 |
| 2 | 10:00 | 200 |
| 3 | 11:00 | 50 |

Если окно определяется только:

```sql
ORDER BY created_at
```

первые две строки являются peers по значению сортировки.

В зависимости от frame это может влиять на результат накопительного расчёта.

Если нужна последовательная обработка каждой строки, добавляем:

```sql
ORDER BY created_at, order_id
```

и явно используем:

```sql
ROWS
```

---

# Тема 57. Скользящее окно

Оконные функции позволяют считать не только накопление с начала.

Например:

> среднее по текущей и двум предыдущим строкам.

Концептуально:

```sql
AVG(amount) OVER (
    ORDER BY created_at, order_id
    ROWS BETWEEN 2 PRECEDING
             AND CURRENT ROW
)
```

Для каждой строки окно содержит максимум три наблюдения.

Это используется для:

- moving average;
- сглаживания;
- анализа временных рядов;
- локальной динамики.

---

# Тема 58. GROUP BY и оконные функции можно комбинировать

Сначала можно получить агрегат:

```text
продажи за день
```

а затем оконной функцией:

```text
накопительные продажи по дням
```

Например концептуально:

```sql
SELECT
    sale_date,
    daily_amount,
    SUM(daily_amount) OVER (
        ORDER BY sale_date
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND CURRENT ROW
    ) AS running_amount
FROM (...);
```

Это важный аналитический паттерн:

```text
сначала изменить гранулярность
↓
затем применить оконную аналитику
```

---

# Тема 59. Оконная функция не заменяет GROUP BY

Иногда кажется:

> если существуют оконные функции, GROUP BY больше не нужен.

Это неверно.

`GROUP BY` отвечает на задачу:

```text
получить одну строку на группу
```

Оконная функция:

```text
сохранить строки,
но добавить расчёт относительно других строк
```

Это разные инструменты.

---

# Тема 60. Когда вычисляются оконные функции

Логически оконные функции вычисляются после:

```text
FROM / JOIN
WHERE
GROUP BY
HAVING
```

и перед финальной сортировкой результата.

Поэтому нельзя во всех СУБД просто написать:

```sql
WHERE ROW_NUMBER() OVER (...) = 1
```

в том же уровне запроса.

Классический способ:

```sql
SELECT *
FROM (
    SELECT
        ...,
        ROW_NUMBER() OVER (...) AS rn
    FROM ...
) AS q
WHERE rn = 1;
```

Некоторые современные СУБД предоставляют дополнительные конструкции для фильтрации результатов оконных функций, но их поддержка платформозависима.

---

# Тема 61. Типичный паттерн: последняя строка в группе

Задача:

> получить последний заказ каждого клиента.

Можно присвоить номер:

```sql
ROW_NUMBER() OVER (
    PARTITION BY customer_id
    ORDER BY created_at DESC, order_id DESC
)
```

После этого оставить:

```text
rn = 1
```

Получаем одну последнюю строку на клиента.

Этот подход полезен для:

- последнего статуса;
- последнего события;
- текущей версии записи;
- наиболее свежего измерения.

---

# Тема 62. Типичный паттерн: Top-N внутри каждой группы

Задача:

> получить три самых дорогих заказа каждого клиента.

Используем ранжирование внутри:

```text
PARTITION BY customer_id
```

Например:

```sql
ROW_NUMBER() OVER (
    PARTITION BY customer_id
    ORDER BY total_amount DESC, order_id
)
```

и затем:

```text
rn <= 3
```

# Тема 65. Платформенные различия оконных функций

Все четыре СУБД курса поддерживают современные оконные функции, включая основные механизмы:

```text
OVER
PARTITION BY
ORDER BY
ROW_NUMBER
RANK
DENSE_RANK
LAG
LEAD
```

Но существуют различия:

- в доступных функциях;
- в оконных frame;
- в работе с `NULL`;
- в дополнительных опциях;
- в возможности фильтровать аналитический результат специальным синтаксисом.

Поэтому переносить сложную оконную аналитику между СУБД необходимо с проверкой документации.

# Тема 66. Производительность функций

Нельзя считать:

```text
функция = медленно
```

или:

```text
встроенная функция = всегда быстро
```

Влияние зависит от места использования.

Например:

```sql
SELECT UPPER(name)
FROM products;
```

просто вычисляет представление результата.

Но:

```sql
WHERE UPPER(name) = 'COFFEE'
```

может повлиять на возможность использования обычного индекса по `name`.

---

## Возможные решения

В зависимости от СУБД можно рассмотреть:

- подходящий collation;
- индекс по выражению;
- вычисляемый столбец;
- функциональный индекс;
- специальный тип индекса;
- изменение модели запроса.

Но решение следует принимать после анализа фактической проблемы.

# Тема 67. Производительность агрегатов

Запрос:

```sql
SELECT
    store_id,
    COUNT(*)
FROM orders
GROUP BY store_id;
```

должен обработать необходимый объём входных данных.

Если таблица содержит:

```text
10 000 строк
```

это одна нагрузка.

Если:

```text
1 000 000 000 строк
```

— совершенно другая.

Производительность зависит от:

- объёма данных;
- селективности фильтра;
- индексов;
- порядка доступа;
- доступной памяти;
- статистики;
- выбранного алгоритма агрегирования;
- степени параллелизма;
- конкретной СУБД.

Само наличие `GROUP BY` не означает, что запрос «плохой».

# Тема 68. Производительность оконных функций

Оконная функция часто требует:

```text
разделить данные
+
упорядочить их
```

Особенно выражение:

```sql
OVER (
    PARTITION BY ...
    ORDER BY ...
)
```

может требовать сортировки большого набора данных.

Но нельзя сделать универсальный вывод:

```text
оконные функции медленные
```

Во многих задачах они позволяют намного эффективнее выразить вычисление, которое иначе потребовало бы:

- self join;
- коррелированного подзапроса;
- нескольких проходов по данным.

Оценивать необходимо конкретный план.

---

# Тема 69. Частые ошибки

## 1. Считать функцию одинаковой во всех СУБД

Например:

```text
STRING_AGG
```

не является универсальным названием функции строковой агрегации.

---

## 2. Полагаться на неявное преобразование типов

Например:

```text
строка + число
```

может иметь разное поведение между платформами.

---

## 3. Считать NULL нулём

`AVG` обычно игнорирует `NULL`, а не превращает его в `0`.

---

## 4. Путать COUNT(*) и COUNT(column)

Один считает строки, другой — ненулевые значения выражения.

---

## 5. Использовать DISTINCT для маскировки размножения строк

Сначала нужно понять причину.

---

## 6. Путать WHERE и HAVING

```text
WHERE → строки до группировки
HAVING → группы после агрегирования
```

---

## 7. Полагаться на порядок внутри STRING_AGG / LISTAGG / GROUP_CONCAT без явной сортировки

Порядок должен быть частью выраженной логики.

---

## 8. Путать NULL исходных данных с NULL от ROLLUP

Для этого существует `GROUPING`.

---

## 9. Использовать ROW_NUMBER без полного порядка

При равных значениях сортировки нумерация может быть недетерминированной.

---

## 10. Путать RANK и DENSE_RANK

`RANK` оставляет пропуски после ties.

`DENSE_RANK` — нет.

---

## 11. Использовать LAG без бизнес-порядка

«Предыдущая строка» существует только относительно определённого `ORDER BY`.

---

## 12. Делать накопительный итог без понимания window frame

Для классического построчного итога лучше явно задать:

```sql
ROWS BETWEEN UNBOUNDED PRECEDING
         AND CURRENT ROW
```

---

## 13. Путать ORDER BY окна и ORDER BY результата

Это два разных назначения.

---

## 14. Форматировать дату слишком рано

Для вычислений и группировки лучше сохранять тип даты, а строковое представление формировать на этапе вывода.

---

# Практический пример

Представим таблицу:

```text
orders
```

с данными:

| order_id | customer_id | store_id | created_at | total_amount |
|---:|---:|---:|---|---:|
| 1 | 10 | 100 | 2026-10-01 10:00 | 1000 |
| 2 | 10 | 100 | 2026-10-03 12:00 | 2000 |
| 3 | 20 | 100 | 2026-10-03 13:00 | 500 |
| 4 | 20 | 200 | 2026-10-04 09:00 | 1500 |

---

## Задача 1. Количество заказов по магазину

```sql
SELECT
    store_id,
    COUNT(*) AS order_count
FROM orders
GROUP BY store_id;
```

---

## Задача 2. Средний чек по магазину

```sql
SELECT
    store_id,
    AVG(total_amount) AS avg_amount
FROM orders
GROUP BY store_id;
```

---

## Задача 3. Оставить только магазины с несколькими заказами

```sql
SELECT
    store_id,
    COUNT(*) AS order_count
FROM orders
GROUP BY store_id
HAVING COUNT(*) >= 2;
```

---

## Задача 4. Пронумеровать заказы клиента

```sql
SELECT
    order_id,
    customer_id,
    created_at,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY created_at, order_id
    ) AS order_number
FROM orders;
```

---

## Задача 5. Сравнить заказ с предыдущим

```sql
SELECT
    order_id,
    customer_id,
    total_amount,
    LAG(total_amount) OVER (
        PARTITION BY customer_id
        ORDER BY created_at, order_id
    ) AS previous_amount
FROM orders;
```

---

## Задача 6. Накопительная сумма заказов клиента

```sql
SELECT
    order_id,
    customer_id,
    total_amount,
    SUM(total_amount) OVER (
        PARTITION BY customer_id
        ORDER BY created_at, order_id
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND CURRENT ROW
    ) AS running_amount
FROM orders;
```

# Итоговые выводы

- Встроенные функции работают с конкретными типами данных и могут различаться между SQL-диалектами.
- `NULL` означает отсутствие известного значения и требует отдельного понимания при вычислениях и агрегировании.
- `UPPER`, `LOWER`, `TRIM`, `SUBSTRING` и `REPLACE` являются базовыми инструментами очистки и обработки текста.
- Конкатенация и её взаимодействие с `NULL` платформозависимы.
- Числовые функции позволяют округлять, сравнивать и преобразовывать значения, но итог зависит и от типа операндов.
- Дата и время особенно платформозависимы: одинаковая операция может выражаться через совершенно разные функции.
- Форматирование даты следует отделять от хранения и вычислений с датой.
- `COUNT(*)` считает строки, а `COUNT(expression)` — ненулевые значения выражения.
- `SUM`, `AVG`, `MIN` и `MAX` обычно не учитывают `NULL` как обычное значение.
- `GROUP BY` уменьшает детализацию до одной строки на группу.
- `WHERE` фильтрует строки до группировки, `HAVING` — уже сформированные группы.
- Строковая агрегация реализуется как `STRING_AGG`, `GROUP_CONCAT` или `LISTAGG` в зависимости от платформы.
- `ROLLUP` создаёт иерархические итоги, а `CUBE` — комбинации итогов по нескольким измерениям.
- Возможности `ROLLUP`, `CUBE` и `GROUPING SETS` различаются между СУБД.
- Оконные функции сохраняют детализацию строк и добавляют расчёт относительно связанного набора строк.
- `PARTITION BY` определяет раздел окна, `ORDER BY` — порядок внутри него, а window frame — конкретный набор строк для расчёта.
- `ROW_NUMBER`, `RANK` и `DENSE_RANK` имеют разную семантику при совпадениях.
- `LAG` и `LEAD` позволяют обращаться к предыдущей и следующей строке без self join.
- Для накопительных расчётов важно явно понимать и при необходимости задавать window frame.
- Производительность функции определяется не её названием, а типами данных, объёмом входных данных, условиями запроса, индексами и выбранным планом выполнения.
